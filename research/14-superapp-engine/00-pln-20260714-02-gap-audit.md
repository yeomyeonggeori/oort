`mock 검증`은 `구현됨`보다 낮은 상태다. 한 surface가 여러 상태를 가지면, 사용자에게 약속할 수 있는 가장 낮은 end-to-end 상태를 대표 판정으로 쓴다.

## 2. 한 줄 결론

momo에는 Work 카드·run ledger·일반 승인/resume·감사·비용 원장의 골격이 있지만, 슈퍼앱 엔진의 신뢰 루프인 **capability grant → immutable Context Packet → provider/source retrieval → approval-gated execution → source/cost/audit result**는 아직 연결되지 않았다. 현재 critical path는 Work UI 확장이 아니라 **승인된 보안 ADR → Capability/Context/Memory runtime foundation → inbound MCP/plugin executor → Google Workspace read sync**다.

## 4. Work v0와 실제 Codex Work/runtime 차이

### 4.1 현재 momo 경로

1. 사람이 Work brief와 sandbox를 제출한다.
2. server가 `agent_run`과 outbox `agent_job`을 만든다.
3. codex-workbench adapter가 host의 기존 Codex 로그인 상태를 사용해 `codex exec --json`을 실행한다.
4. `read-only`는 바로 완료한다.
5. `workspace-write`는 먼저 read-only planning turn을 수행하고, adapter가 **momo 자체 approval_request**를 합성한다.
6. 승인 시 보존한 Codex session ID로 `codex exec ... resume`를 workspace-write sandbox에서 실행한다.

이 설계는 “momo가 upstream Codex/OpenAI credential을 갖지 않는다”는 경계를 지키고 coarse human gate를 제공한다. 다만 승인 단위는 Codex의 실제 command/file/permission 요청이 아니라 momo가 만든 단계 전환이다.

### 4.2 공식 Codex product-integration surface와의 차이

2026-07-14 공식 Codex manual과 local `codex-cli 0.144.1` schema를 대조했다.

| 항목 | 현재 `codex exec` adapter | 실제 product integration에 필요한 상태 |
|---|---|---|
| transport | non-interactive JSONL subprocess | local `codex app-server` stdio JSON-RPC sidecar가 deep integration에 적합하다. |
| lifecycle | session ID + 별도 `resume` process | `thread/start`/`thread/resume`, `turn/start`, `turn/steer`, `turn/interrupt`, streamed item/turn events를 보존한다. |
| approval | read-only plan 뒤 coarse momo approval 합성 | `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`를 momo approval ledger에 1:1 연결한다. |
| identity | adapter session ID 중심 | Codex `threadId`/`turnId`/`itemId`와 momo run/message/approval ID의 immutable mapping이 필요하다. |
| tool/user input | final/partial text 중심 | elicitation, tool input, dynamic tool call, artifact/file change를 typed event로 처리해야 한다. |
| sandbox semantics | 한 번의 단계 승격 | sandbox와 approval policy를 별개로 보존하고 native request마다 최소 권한으로 판단해야 한다. |
| credentials | host login을 child가 직접 사용 | 그대로 유지한다. app-server는 동일 host에 stdio로 띄우고 auth directory/token을 momo server로 보내지 않는다. |

공식 근거: [Codex App Server](https://learn.chatgpt.com/docs/app-server.md), [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode), [Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security.md). App-server approval method 이름은 local CLI가 생성한 0.144.1 JSON schema로 추가 확인했다.

### 4.3 방향 제안

- `codex exec` adapter를 즉시 제거하지 않는다. read-only batch/fallback로 유지할 수 있다.
- interactive Work의 목표 transport는 **user-owned host의 local app-server stdio sidecar**로 제안한다. experimental WebSocket remote exposure는 v0 out of scope다.
- 이 변경은 실행/승인/credential 경계이므로 Accepted ADR 없이 구현하지 않는다.
- momo에는 upstream Codex/OpenAI OAuth token/API key를 저장·proxy·log하는 필드나 secret reference를 만들지 않는다.

## 5. Context, memory, capability의 실제 경계

현재 mention projection, AgentWorker context assembly, macOS local copilot packet은 서로 다른 목적의 partial implementation이다. 이를 하나의 완성된 Context Broker로 계산하면 안 된다.

제안하는 authoritative flow는 다음과 같다.

1. Capability Registry/Cache가 설치·grant·provider scope·schema hash·policy version을 해석한다.
2. Context Broker가 요청자의 membership과 channel/thread/source visibility를 재검증한다.
3. Memory Plane이 retrieval-time permission을 통과한 typed refs만 반환한다.
4. Context Broker가 immutable Context Packet과 projection hash를 저장한다.
5. executor는 packet의 typed `tool_grants`와 현재 capability/policy version을 다시 비교한다.
6. 외부 write는 proposed action hash를 approval에 고정하고 승인 뒤 동일 payload만 실행한다.
7. 결과는 source refs, tool result, cost, policy evidence, audit IDs와 함께 timeline에 남는다.

Capability Cache에는 source body나 context summary를 저장하지 않는다. Memory Plane에는 provider credential을 저장하지 않는다. Context Packet에는 bearer/token/refresh token을 절대 넣지 않는다.

## 6. Security boundary audit

### 6.1 절대 불변식

- momo server/DB/worker는 upstream Codex/OpenAI OAuth access token, refresh token, API key를 보관·proxy·log하지 않는다.
- Codex auth는 user-owned execution host의 Codex runtime에만 존재한다.
- `MOMO_AGENT_TOKEN`은 momo control-plane bearer이며 provider credential이 아니다.
- Hermes-facing bearer는 `HERMES_API_KEY` 등 별도 runtime secret boundary다. Context Packet, message props, audit payload, plugin manifest에 넣지 않는다.
- Google Workspace token policy는 아직 research spec이다. token custody, encryption/KMS, revoke/delete, DWD/service account 경계는 Accepted ADR 뒤에만 구현한다.
- 외부 write 승인에는 workspace/channel/member, plugin/tool, resource scope, normalized input hash, capability version, policy version, expiry, idempotency key가 묶여야 한다.

### 6.2 주요 위협과 gate

| 위협 | 필수 방어 |
|---|---|
| prompt/source가 권한을 확대 | retrieval과 execution 때 각각 membership/provider scope를 재검증하고 untrusted source label을 보존한다. |
| stale capability로 write | capability/policy version mismatch 시 fail closed; grant revoke가 cache와 pending approval을 invalidate한다. |
| approval 뒤 payload swap | canonical JSON/hash를 approval과 job에 저장하고 executor 직전에 비교한다. |
| webhook replay/forgery | versioned signature, key ID, timestamp window, nonce/delivery ID uniqueness, body hash, constant-time verify, rate limit을 적용한다. |
| cross-tenant leak | 모든 신규 tenant table에 `workspace_id`, FORCE RLS, tx별 `SET LOCAL app.workspace_id`, BYPASSRLS 최소화가 필요하다. |
| secret leak | secret value를 DB 일반 컬럼, manifest, packet, message, logs, test fixture에 넣지 않고 lifecycle audit에는 secret ref/key ID만 남긴다. |
| 비용 폭주 | execution 전 reserve, stream 중 ceiling, completion reconcile, retry idempotency, provider별 pricing version을 server가 소유한다. |

## 7. 성능·runtime 감사 기준

초기 목표치는 Accepted ADR/issue에서 확정하되, 최소 gate는 다음을 권고한다.

- Context Packet: 200-message fixture에서 assembly p95 250ms 이하(외부 provider fetch 제외), deterministic hash 재현 100%.
- Capability Cache: warm lookup p95 25ms 이하, grant revoke/invalidation propagation 5초 이내.
- Memory retrieval: 10k workspace fixture에서 permission-filtered top-k p95 500ms 이하; forbidden ref 반환 0건.
- Inbound MCP: read tool p95 750ms 이하(로컬 DB), 100 concurrent call에서 cross-tenant/error leakage 0건; bounded request/result size.
- Webhook: signature verify+enqueue p95 200ms 이하, duplicate delivery exactly-once effect, rotation overlap과 replay window fixture 통과.
- GWS sync: cursor resume/idempotent replay, 429/5xx exponential backoff, bounded concurrency, source tombstone/revoke가 citation visibility에 반영.
- Codex Work: sidecar crash/restart, approval timeout/reject, duplicate native request, reconnect/resume, server retry에서 run/approval/result가 중복되지 않아야 한다.

수치는 첫 구현 PR에서 같은 hardware profile과 fixture 크기를 evidence로 기록하고, 달성 불가능하면 숫자를 숨기지 말고 ADR 또는 issue 계획 이탈로 환류한다.
