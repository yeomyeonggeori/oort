## [Unreleased]

### Added
- Phone: swipe-to-reply and the thread reply box get the same emoticon preview and one-press send as the chat composer. With a reply header up (swipe a message to reply), a picked emoticon or GIF no longer goes into the text as `:name:`: it waits above the composer as a picture with a small ✕ and no explanatory text, standing together with the reply header, and one press of send posts the large-emoticon message and then the text message, both as replies to the same thread, under two different `client_msg_id`s. The second does not leave before the first is confirmed; if the first fails the second stays as a failed row without a request and a resend from either row starts with the first, and if only the second fails the picture is not sent again. Cancelling the reply keeps the preview and the next send goes to the chat itself. The thread reply box works the same way; its failed rows stay in the thread with their resend buttons (the box itself is emptied once you press send, as in the chat composer). Small emoji still go into the text at the caret (#5490, the phone pair of #5487).
- Web, desktop and phone: the first section of the Emoticons tab now shows what you use most and most recently, stills and GIFs together (up to 12, two rows of six on the web), instead of only the last-used stills. The order weighs how many times you sent a picture against how long ago you last did: the score is the count times 0.5 to the power of (days since the last use / 7), so one use yesterday stays above ten uses a month ago, while ten uses three days ago stay above one use yesterday; ties go to the one used last. The small team emoji are left out, a GIF stands still exactly as it does in the grid (it is still found in the GIF tab's own sets, not twice in this tab's), and the section is now headed "Frequent & recent" (the same name on its button in the strip under the grid, and for the screen reader), while the GIF tab's "Recent" stays as it was, in name and order (GIFs only, last used first). The section is worked out once when the window opens and does not move while it is open, even after a send succeeds, and changes only the next time you open it; a picture hidden or deleted meanwhile drops out without reshuffling the rest. Searching and keyword matching are unchanged, and the usage history stays on the device with no server change (#5503).
- Phone: the reaction picker (the "+" in the message actions) has the same three tabs as the web, Emoticons, Emoji and GIF, built from the same grid and set strip as the emoticon window instead of the old "Emoji + Our team" layout. It still opens on Emoji; picking an emoticon or a GIF adds it as one reaction (no big picture is sent), and the search field filters all three tabs.
- Web, desktop and phone: a GIF used as a reaction keeps moving. Reaction chips are the one exception to the "stops after four plays" rule (a GIF inside a message still stops after four plays and replays when pressed): the chip plays on without a pause, shows the still first frame when Reduce Motion is on, and stands still while scrolled out of view. Nothing changes on the server — the picture is drawn from the same bytes with only the repeat count switched to "forever".
- Web, desktop and phone: Settings has an "Emoticon suggestions" switch that turns the typing suggestion row off for good on this device (on by default). On web and desktop it is the last row of Appearance › Conversation display, on the phone it sits in the View card under Link previews. While it is off no suggestion row stands above the composer however well the typed word matches, and turning it on again brings the row back about 0.3 seconds later without restarting the app. The choice is kept on the device only, per workspace and member (nothing goes to the server, other members see no change), a saved value that cannot be read counts as on, and the ✕ on a suggested word still mutes only that word in that conversation until the app restarts.
- Web, desktop and phone: a photo or GIF you attach now carries its width and height, so a picture you have never seen before takes its final frame from the first moment instead of a placeholder that grows when it arrives (about 80 pt on a slow connection, the last bit of the chat-entry shake). The sending app measures the picture the way receiving apps do and declares the size before the message goes out; the server only checks the range and the file type and never opens the picture. Photos sent before this update, and photos from an app that has not updated yet, behave as before, and older apps simply ignore the new field. This is a server API and database change (ADR-0151 amendment 9, migration 178).

### Changed
- Phone: the emoticon suggestion row also stands in the thread reply box and with a swipe-reply header up — v0.1.44 showed it only in the chat composer. The same conditions apply there: only while the keyboard is up, no preview is chosen and the window is closed (#5490).

### Fixed
- Phone: the emoticon suggestion row now spans the whole width of the composer card, edge to edge with it, instead of a card only as wide as its pictures, so the message it covers no longer pokes out beside or above it as a half-cut bubble; the row grows 4 pt upward only, so the pictures stay where they were, and the ✕ now sits at the right end of the row. The buttons in the strip at the bottom of the emoticon window (recent, favorites, each set, Other and +) can now be pressed over a full 44 pt width instead of 40 pt: the extra 2 pt on each side is touch area that stops at the gap to the next button, and the drawn button stays 40 pt wide (#5492).
- Phone, web and desktop: registering, editing, hiding or deleting one emoticon no longer blanks every emoticon on screen (#5491, ADR-0218 addendum 9). The server now sends a small detail notice (what changed and which emoticon) ahead of the usual change notice, in the same transaction. A hide or delete takes down only that picture at once; a registration or an edit leaves every picture as it is and only reads the list again, so there are no empty frames and no pictures downloaded again (the phone used to delete every picture file and fetch them all again on each notice, and the web cleared every picture it held). If the detail does not arrive, or the app talks to an older server, nothing is left to chance: every picture is taken down as before, so a hidden one never stays on screen. On the phone that fallback now stops drawing at once but keeps the picture files and deletes only the ones the new list drops (all of them if the list cannot be read). Apps that are already installed ignore the detail and behave exactly as before.

## [0.1.44] - 2026-11-07

GitHub Release: <https://github.com/yeomyeonggeori/oort/releases/tag/v0.1.44>. Tag target: `main=7fb34e996`. Multi-arch (linux/amd64 + linux/arm64), digest pins in `releases/latest.json`; SLSA v1 provenance verified for the app and postgres lists. **No database migration** (the schema stays at 174; the migration runner reports `applied=0 skipped=174 total=174`), no change to the role SQL under `infra/rust/sql`, no new environment variable, no new route and no change to the API contract: this release is an image swap. Two server behaviours change. **The re-encoding of a newly registered emoticon writes the same picture in fewer bytes**: a still tries several lossless PNG settings and keeps the smallest, and a GIF gets a cropped frame box and a chosen global palette (the new `motion` module of `momo-expressions`; the direct dependencies `gif` and `color_quant` are the versions `image` already pulled in, so there is no new crate and no new licence); limits, wire and database are unchanged, pictures already stored are not rewritten, and an input that used to be refused for exceeding the size limit can now fit and register when its smallest lossless form is within the limit. The re-encoding is heavier than before (a still is written up to eight times and a GIF is scanned twice, all inside the decoder child process's existing 10-second limit), and it had not run under the Linux isolation limits of a team instance before this release. **The helper's "Hand it to …" buttons also offer the team Hermes**: the agent pinned to the operator's own link is a candidate when it is an active member of the channel, is not paused, has no connector owner and its call scope is open to the person who asked. Nothing else on the server changes: the Hermes service, the push relay, Centrifugo, the role SQL, the environment variables an upgrade needs and the OpenAPI document are the same as in v0.1.43, and nothing is known to need a lockstep rollout (an older app against this server, and this release's apps against an older server, were not tested on a device).

The Emoji tab joins the standard characters and the team's small emoji (one row under the search field, found by the same search). The Emoticons and GIF tabs are a six-column grid of pictures only (names and codes stay in the tooltip and the accessible name), in the order Recent, Favorites, sets (two or more pictures sharing a name prefix `<prefix>_`) and Other, with a strip under the grid (a clock, a star, the first picture of each set and a "+") that jumps to a section. "Add" moved to the "+" at the end of the strip, and Report and Delete moved to the menu of a picture, opened by right-click, long-press, or Shift+F10 and the Menu key on a focused picture (the desktop app's engine sends no context-menu event for those keys, so the grid opens the menu itself and focus returns to the picture when it closes). The menu also holds "Add to favorites" and "Remove from favorites" (a local list per device, workspace and person; no server contract). The arrow keys move over the grid, Enter picks and Esc closes; the strip marks the current section with a fill that an edge-to-edge picture can no longer cover (#5453, #5471, #5486).
- Web and desktop: an emoticon or GIF waits in a preview above the composer and goes out together with the text. Picking one no longer puts `:name:` into the text: the picture waits above the composer in a small card (a 56 px picture with a small ✕ beside it, no explanatory text; Esc dismisses the link card, then the emoticon, then the quote), and one press of send posts the large-emoticon message and then the text message, in that order, under two different `client_msg_id`s. The second does not leave before the first is confirmed; if the first fails the second stays as a failed row without a request, and a resend from either row starts with the first under the same ids. The thread reply box works the same way and sends both replies to the same thread, and the hint sentence that used to stand under a `:name:`-only text is gone from both boxes; reactions keep the old behaviour (`:name:` goes into the text) (#5453, #5471, #5487, PR #5496).
- Phone: the emoticon window takes the keyboard's place — the smiley button in the composer lowers the keyboard and opens the window in the same spot, at the last keyboard height (remembered on the device) and with no separate sheet. While it stands the button is drawn pressed (its accessibility name changes to "Show keyboard"); pressing it again or tapping the text box brings the keyboard back, and tapping the chat list closes the window only. The window has the same three tabs as the web (the last tab is remembered until the app is closed), a picture grid for Emoticons and GIF with a strip at the bottom (Recent, Favorites, sets and a "+" for Add), a long press on a picture that adds or removes a favorite (kept on the device; the accessibility action and the announcement say so), and a preview above the composer (the picture and a small ✕ that announces "Preview removed"); one send posts the large emoticon message and then the text message, and small emoji go into the text at the caret. A thread reply box has no preview: a picked emoticon goes into the text as `:name:` (#5452, PR #5481).
- Web and desktop: emoticon suggestions while you type — about 0.3 seconds after you stop typing, when the last word (or a short whole text) equals the name, display name or a tag of a large emoticon or GIF, one to five pictures (a GIF stands still) appear in a thin row floating above the whole composer (above the agent activity rail, link cards and the preview, so it never covers them), with no text but a small ✕ at the end. A press puts the picture in the preview and never sends it by itself, Enter still sends the message, Esc closes the row, the up arrow moves into it only when the caret is on the first visual line (in a long wrapped paragraph it still moves through the text), and the ✕ turns off suggestions for that word in this conversation (kept in memory only); no row appears while a preview is already chosen. The matching runs on the device only (`normalizeKeyword` and `suggestExpressions` in the core, #5474), so what you type never leaves it (#5454, #5474, #5476, PR #5480, #5489, PR #5498).
- Phone: emoticon suggestions while you type, the same row as on the web — one to five pictures (a GIF stands still) and a small ✕ in a thin row floating above the composer, about 0.3 seconds after you stop typing, only in the chat composer (not in a thread reply box) and only while the keyboard is up, no preview is chosen and the window is closed. A press puts the picture in the preview and never sends it, and the ✕ ("Turn off suggestions for this word" for the screen reader) turns the word off in this conversation (#5454, #5478, PR #5483).

### Changed
- Server: the re-encoding of a newly registered emoticon writes the same picture in fewer bytes. Stills try lossless PNG settings (on average 18% smaller at large and 26% at small over 32 stills, identical pixels), and GIFs get a cropped frame box and a chosen global palette (on average 4% at large, 8% at small and 35% for the thumbnail over 8 GIFs). Limits, wire and database are unchanged, pictures already stored are not rewritten, and a picture that was over the byte limit before can now register when the smaller form fits (#5455, #5467).
- Server: the helper's "Hand it to …" buttons also list the team Hermes. `delegation_candidates_in_tx` adds the agent pinned to the operator's own link (`agent_provider_pin.kind = 'operator_env'`) when all four hold: it has no connector owner, its call scope is open to the requester, it is not paused and it is an active member of the channel. Before, only agents with a live hosted connection were listed, so the team Hermes never appeared; no migration (ADR-0201 addendum v4, #5373, #5449).
- Web, desktop and phone: the emoticon window opens on the Emoticons tab first — the composer's and the thread reply box's picker started on Emoji on the web, and the phone window now takes its first tab from the same core constant (`DEFAULT_EXPRESSION_PICKER_TAB`); the reaction picker on web and desktop keeps opening on Emoji, and the status picker has no tabs (#5482, PR #5484).

## [0.1.43] - 2026-11-06

GitHub Release: <https://github.com/yeomyeonggeori/oort/releases/tag/v0.1.43>. Tag target: `main=a28331ea4`. Multi-arch (linux/amd64 + linux/arm64), digest pins in `releases/latest.json`; SLSA v1 provenance verified for the app and postgres lists. One database migration (174; the schema goes from 173 to 174): 174 adds the tenant table `member_activity` (one row per member and workspace with `seen_at`, a composite foreign key to `member` with cascade, row-level security enabled and forced with the standard `ws_isolation` policy; `SELECT, INSERT, UPDATE` to `momo_app` and `SELECT` to `momo_notifier`, each when the role exists). It only creates a table: no existing table is altered or rewritten, no row is scanned and no data changes; its foreign keys take `SHARE ROW EXCLUSIVE` on `workspace` and `member` until the file commits (the same shape as 164 and 173 of v0.1.42; the lock modes of 174 were measured on PostgreSQL 18.6 in an isolated container at schema 173: the two foreign keys take `SHARE ROW EXCLUSIVE` on `workspace` and `member`, and the file ran in about 5 ms on an empty database), so writes to those two tables wait for that moment. No rollback SQL ships with 174, and whether the previous image runs on schema 174 has not been tested (the table is new and no older code reads it). **`bootstrap_runtime_roles.sql` changes** by one grant (`momo_notifier` `SELECT` on `member_activity`, skipped until the table exists; the migration carries the same grant). **Deploy order: the migration (the API's pre-deploy), then the notifier, then the API, then the apps.** A notifier that starts before 174 cannot read the activity table, so it sends every phone push at once and logs a warning, because the phone-push delay fails open. There is no change to the push relay (no new push reason or category), to the Centrifugo configuration or to the environment variables an upgrade needs, and nothing is known to need a lockstep rollout: the new route and the error codes are additive, and the desktop and web app of this release stops sending its new signal to a server that answers 404 or 405 (an older app against this server was not tested). **One default changes with the image**: `MOMO_REFRESH_REUSE_SWEEP_ALL_SESSIONS` is now on unless it is exactly `false`, so a refresh token that comes back after its grace period ends the whole login for password sign-ins on the web and the desktop as it already did for a phone linked by QR; an operator who sees unexpected mass sign-outs on web and desktop sets it to `false` and restarts (the phone is always ended, and a typo leaves it on). **The Hermes lock gate takes a sixth config** (the default config with a team model fragment, Codex as the primary and Claude Sonnet 5.5 as the fallback) and the model id `claude-sonnet-5-5`, and refuses the old `claude-sonnet-5` config; **Railway refuses a variable over 32,768 characters, so `HERMES_LOCKGATE_B64` is now given in parts `_2` to `_5` and `HERMES_LOGIN_RELAY_B64` in parts `_2` and `_3`** (the start command joins them and checks the same sha256). An existing Hermes service keeps the gate it was started with; to take the new gate, config and start command, follow `docs/RELEASING.md` (the Hermes step) and `infra/railway/README.md`: check the names in the volume's `.env` first, then change `HERMES_LOCKGATE_B64` with its parts, `HERMES_CONFIG_B64` and the start command's checksums together.

- Server: the file store's 502 and 503 answers carry a code in `error.code` — `drive_not_configured` (503), `drive_access_denied` (502) and `drive_upstream_failed` (502, with `Retry-After: 5`); statuses, sentences and the 400, 404 and 413 answers are unchanged, so the codes are additive; the OpenAPI lists (`ErrorResponse.error.code` and the 502 and 503 answers of three attachment operations) and the generated type are updated in step; a maintenance or restart signal cannot come from the API itself (it takes no new connection after the stop signal, and the 502 during a replacement is made by the edge), so only its shape (`503 server_restarting` with `Retry-After`) is reserved for a follow-up at the edge (ADR-0151 addendum 7, #5223, #5368; no migration).

### Changed
- Server: an agent called in a channel or in a DM with more than two people answers under the message that called it — its final answer, approval card, tool lines and notice lines go to a new thread on the calling message, and only a 1:1 DM keeps the conversation itself. One function, `momo_agent::answer_place_root`, decides the place: a 1:1 DM → the conversation; inside a thread → that thread's root; anything else → the calling message as the root; a deleted calling message or root, and work runs → the conversation. A room is 1:1 only when it is `kind='dm'`, its `dm_key` does not start with `group:` or `admitted:` and it has at most two active participants (an unknown head count is not 1:1).
