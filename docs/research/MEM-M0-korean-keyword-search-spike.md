- 날짜 2026-09-29 · 트랙 엔진 · 계획 `claudedocs/memory-research/plan.md` §4.4·§8.4 (Q5) · #500(메시지 검색)에도 전달
- 제품 코드 변경 없음. 벤치·픽스처는 `server-rust/bench/kr-keyword-search/`(워크스페이스 밖 독립 크레이트, 자체 `Cargo.lock`이라 서버 `Cargo.lock`·GHCR 고지 번들 불변).

## 방법

- **코퍼스** 900건(시드 고정 합성 팀 대화 풍 문장, 실제 대화 미사용). 개념 50개 = 낱말 짝 (A, B). 개념마다 정답 문서 8건(A·B 함께 포함), 한쪽만 담은 방해 문서, 잡음 200건. 정답 라벨은 생성 시 확정하고 생성기가 라벨 누수(다른 문서가 A·B를 함께 담음)를 검사한다.
- **질의 50쌍**(종류별 10): `josa` 조사 변형(질의 「승인을 일정이」, 문서엔 온갖 조사), `two_syllable` 두 음절 낱말(배포·결재…), `spacing` 붙여쓰기/띄어쓰기(팀기억/팀 기억), `english` 영문 혼용(PR·QA·API + 리뷰 등), `typo` 1자 오타.
- **규모 측정**: 900건 + 잡음 100,000건 = 100,900건 표. 정답 라벨은 그대로 유효(잡음은 개념 짝을 동시에 담지 않음). 「small」=900건만(`id like 'd%'`), 「scale」=100,900건 전체.
- **지표**: recall@10 = 상위 10 안의 정답 수 / min(10, 정답 수), MRR = 상위 10 기준. 순위는 tsvector 후보 모두 `to_tsquery` OR + `ts_rank_cd`(내장에는 IDF/BM25가 없다), trgm은 질의 낱말별 `word_similarity` 합.
- 측정기 자체 점검: 정답을 그대로 낸 오라클은 1.0, 빈 결과는 0.0이어야 스크립트가 진행한다. `ILIKE` 전체 구절(현행 방식)은 0에 가까워야 정상인 대조군.

- 질의 지연은 워크스페이스 필터 없이 10만 건 전체에서 잰 값이다. 실제 기억 항목은 워크스페이스(RLS)·청중 술어로 이미 좁혀지므로 trgm 지연은 여기서 크게 줄어야 한다 — **워크스페이스 범위 지연은 M2 구현 때 재측정 필요(미검증)**. 2음절 낱말은 trigram 3개뿐이라 선택도가 낮다.
- 쓰기는 모두 10⁻⁵초/건 규모라 요약 잡·추출 잡의 빈도(사람당 하루 수십 건)에선 무시된다.

## 후보 2 lindera 라이선스·크기 (탈락 기준 확인)

- `lindera 6.2.0` MIT, `lindera-ko-dic 6.2.0` MIT, 사전 `mecab-ko-dic-2.1.1-20180720` **Apache-2.0**(크레이트 `NOTICE.txt`에 전문). 전이 의존 149개 전부 permissive(MIT/Apache/Unicode-3.0/ISC/BSD/Zlib/CDLA-Permissive-2.0 등, 카피레프트 없음) → **라이선스로는 탈락 아님**. 채택 시 NOTICE에 lindera·mecab-ko-dic 귀속 + GHCR 고지 번들 재생성(새 크레이트 149개).
- **크기**: `embed-ko-dic`로 넣으면 릴리스 바이너리 87 MB(사전 약 86 MB가 그대로 얹힘, 사전 파일 합계 dict.words 39.5 + matrix 20.6 + trie 10.9 + vals 8.2 + idx 6.4 MB). 파일로 두고 `load_dictionary(path)`를 써도 이미지가 같은 만큼 는다. 프로세스 시작 시 로딩 약 50 ms, RSS 약 47 MB.
- **빌드 위험**: `build.rs`가 사전 tarball(약 50 MB)을 `https://Lindera.dev/…`에서 내려받는다(md5 고정). Docker/CI 빌드가 외부 네트워크에 의존하므로 채택 시 사전 벤더링(레포 밖 캐시 또는 아티팩트) 필요.
- 대조: bigram·trgm은 의존·바이너리 증가가 0이다(trgm은 이미 `001_init.sql`의 `pg_trgm`).

## 권장 (planner 결재용, Q5)

1. **M2 기본안 = `pg_trgm` 단독(후보 3)**: 새 의존·바이너리 증가 0, recall 0.835(scale)로 기준 통과, 오타에 유일하게 강함(0.69), 쓰기 비용 낮음. 항목 본문에 `gin (body gin_trgm_ops)`를 두고 질의를 공백 낱말로 쪼개 `낱말 <% body`(OR)를 워크스페이스·청중 술어와 같은 쿼리에 넣는다. 조건: 워크스페이스 범위 지연 재측정, 임계값(0.3~0.5) 튜닝, 조사 접미 약함(josa 0.59)은 질의측 조사 제거 휴리스틱 또는 M3 융합으로 보완.
2. **상향안 = lindera 추가 + RRF(후보 2+3, 0.83)**: 조사·띄어쓰기를 0.86~0.99로 끌어올려 균형이 좋지만 바이너리 +86 MB와 빌드 시 사전 다운로드를 산다. M2에서 부족이 실측되면 M3(벡터 RRF와 같은 시점)에 추가하는 것을 권한다 — 벡터가 들어오면 어차피 융합 구조다.
3. **자체 bigram(후보 1)은 비권장**: 인덱스 2배, 조사 붙은 bigram 잡음으로 josa 0.25, 이득이 trgm에 흡수된다. 현행 `simple` 공백 토큰(0.203)과 `ILIKE` 구절(0.02)은 한국어 기억 검색에 부적합하다.
4. **#500(메시지 검색)**: 현행 `ILIKE '%구절%'`은 구절 그대로 있을 때만 맞는다. 낱말 OR + `word_similarity` 순위(후보 3)가 같은 `message_body_trgm_idx`로 개선 여지가 있으나, 메시지 검색은 부분문자열 기대(사용자가 친 그대로)가 있으니 UX 결정 후 별도 이슈로.

## 한계 (결과 해석 시)

- 합성 코퍼스: 개념 낱말이 2음절 명사 위주, 문장 구조가 단순해 **trgm에 유리하고 형태소 분석의 강점(긴 문장·용언 활용·복합 명사 분해)은 덜 드러난다.** 절대 수치보다 후보 간 상대 비교와 종류별 강약으로 읽을 것. 「띄어쓰기」는 복합어의 뒤 낱말이 공유돼 쉬운 편이다.
- 오타 질의 recall이 전 후보에서 낮은 것은 정상(오타 낱말은 1자만 다르므로 trgm만 일부 잡음). 정답 문서 수가 개념마다 8건으로 균일하다.
- 순위 함수는 내장 `ts_rank_cd`(IDF 없음). `pg_textsearch` BM25는 `external.md` §2.2대로 이번엔 검증하지 않았다(한국어 토크나이저·이미지 동봉 미검증).
- 지연은 단일 세션 순차 측정(psql `\timing`, 질의 50개×5회), 로컬 부하 영향 있음. runtime-unverified: 실제 Railway PG.
- **재사용**: 평가 세트(#3160)는 `server-rust/bench/kr-keyword-search/fixtures/queries.json`(50쌍, 정답 문서 id 포함)과 `corpus.jsonl`(900건)을 그대로 쓸 수 있다.
