## 이 문서의 목적

oort의 최종 결정권자(성재)가 **메신저 시스템을 원리부터 이해한 상태로 ADR을 판단**할 수 있게 만드는 책이다. ux-bible이 "Slack은 왜 그렇게 느껴지는가"를 다룬다면, 이 바이블은 "메신저는 왜 그렇게 지어지는가"를 다룬다.

- 모든 장은 **문제 → 업계의 해법 스펙트럼 → oort의 선택과 이유 → 열린 결정** 순서로 쓴다.
- oort 코드를 인용할 때는 `file:line`을 달아 언제든 실물과 대조할 수 있게 한다.
- 각 장 머리에 `최종 대조: YYYY-MM-DD @ <commit>`을 표기한다. 아키텍처 정본(불변식·시스템 지도)이 바뀌는 merge가 있으면 momo-main 통합 세션이 해당 장의 대조일을 갱신하거나 "정본과 어긋남" 마크를 남긴다.

## 이 바이블을 읽는 법

- **결정을 앞두고**: 06장의 결정 큐 매핑에서 해당 ADR을 찾고, 연결된 장의 해법 스펙트럼을 먼저 읽는다.
- **처음부터**: 01 → 02만 읽어도 oort 코드리뷰와 ADR 문서의 언어(outbox, seq, RLS, fanout, backfill)가 전부 해석된다.
- **비교하며**: 03~05는 같은 문제 번호(P로 시작하는 문제 지도 번호)를 교차 인용한다. "Slack은 M4를 이렇게, Discord는 저렇게" 식으로 읽는다.

## 문제 번호 규약

01장이 정의하는 문제 지도 번호 `M1~M11`(Messenger problem)을 전 장이 공유한다. ux-bible의 P1~P15(원칙)와 다른 축이다 — P는 "어떻게 느껴져야 하는가", M은 "무엇을 풀어야 하는가".
