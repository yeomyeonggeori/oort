# ADR-0180: 기기 연결 — 1회용 QR 링크 토큰으로 폰 세션 발급

- 상태: **Accepted** (2026-09-02 성재 결재 — "2~5까지는 승인". 기안 Fable 같은 날 2026-09-02 모바일 발제 "QR만 찍으면 연동, iOS 전용" + 편성 D-10)
- 발제: `docs/planning/2026-09-02-launch-program-plan.md` §6 M0 / 브리프 §3 UX-R2
- 관련: ADR-0162(hosted pairing — 15분 1회용 pairing 값 선례) · ADR-0166(첫 소유자 claim token — 1회용·TTL·소비 시 무효 선례) · ADR-0004(자격 비유입) · ADR-0167(same-origin·`--public-origin`) · ADR-0120(푸시 — `devices` 라우트는 푸시 등록용, 본 ADR 비접촉) · `docs/onboarding-deeplink.md`(`oort://join` 정본) · buzz `desktop/src-tauri/src/commands/pairing.rs`(NIP-AB: QR→SAS→릴레이 신원 전송)

## 맥락

폰 클라(RN, iOS)는 서버 주소·초대 코드·이메일·비밀번호를 손으로 치거나 `oort://join` 딥링크 프리필로만 붙는다. 이미 데스크톱에 로그인한 사용자가 폰을 붙이는 데 다시 자격을 입력해야 하고, 셀프호스트 주소(Funnel/Railway 도메인)는 폰에서 치기 가장 나쁜 문자열이다. buzz는 데스크톱 QR → 폰 스캔 → 양쪽 6자리 SAS 대조 → 릴레이로 신원(nsec)을 전송한다. 우리는 서버 계정 모델이므로 "신원 전송"이 아니라 **"이미 인증된 세션이 새 기기 세션을 발급"**하면 된다 — 더 짧고, 서버가 감사·해제를 가진다.

현행 자산: `POST /v1/auth/login|refresh|logout`(access+refresh, `momo-auth` token_store가 세션 토큰을 기록·회수), `POST /v1/join`(공개·초대 코드), `POST /v1/claim`(1회용 토큰 소비 선례), 폰 키체인 세션 저장(`secureSession.ts`), 딥링크 소비 `oort://`·`momo://` 이중 등록.

## 결정

- **D1 토큰.** 인증된 사람 멤버가 `POST /v1/auth/device-link` 로 **링크 토큰**을 발급한다: 발급자 세션·멤버·워크스페이스에 귀속, **TTL 120s**, **1회 소비**, 원문은 응답에만 실리고 저장은 해시. 토큰은 자격이 아니라 **교환권**이다 — 그 자체로는 어떤 API도 호출할 수 없다.
- **D2 QR 페이로드 = 딥링크.** `oort://link?server=<percent-encoded base>&token=<base64url>` — `onboarding-deeplink.md`의 `join` 문법(파라미터 2개·순서 무관·미지 파라미터 무시·`momo://` 흡수)을 그대로 따른다. 폰 카메라 앱으로 찍어도 앱이 열린다(QR 전용 스캐너가 유일한 문이 아님).
- **D3 소비.** 폰이 `POST /v1/auth/device-link/redeem {token, device:{name, platform}}` (공개 — `/v1/join`과 같은 사유로 인증 미들웨어 밖, per-IP 레이트리밋) → 서버는 토큰 검증·소비 후 **그 멤버의 새 세션**(access+refresh, `realtime_web_socket_url`)을 `LoginResponse` 동형으로 발급하고, 발급자 화면에 "연결됨: <기기명>"을 수렴시킨다(폴링 GET `…/device-link/{id}` — outbox 이벤트 없음 v1, 리마인더·사이드바 무-outbox 전례).
- **D4 SAS는 모드별.** 서버가 `MOMO_CENTRIFUGO_WS_URL=same-origin`+`--public-origin`으로 **공개 오리진 모드**임을 알 때만 양쪽에 4자리 SAS(토큰 해시 파생)를 표시하고 발급자가 "일치" 확인 후에야 세션이 활성화된다(중간자 QR 바꿔치기 방어). 루프백/LAN 모드는 SAS 생략(TTL 120s·1회 소비·TLS가 경계). 모드 판별은 서버 config에 이미 있는 값만 쓴다 — 새 env 없음.
- **D5 감사·해제.** 소비 시 `audit_event(kind='device.linked')` + 세션 토큰에 기기 라벨. 설정 › 기기 목록에서 즉시 회수(`revoke_member_session_tokens` 재사용). 발급 토큰은 TTL 만료·소비·발급자 로그아웃 중 먼저 오는 것으로 무효.
- **D6 경계.** `require_human`(에이전트 세션은 링크 토큰 발급 불가 — 에이전트 자격은 ADR-0173 경로). 토큰 원문은 로그·감사·진단 번들에 비유입(ADR-0004 규율 동형). 푸시 `devices` 라우트와 무관 — 푸시 등록은 세션 발급 뒤 현행 경로.
- **D7 표면.** 웹/데스크톱: 설정 › 기기 "폰 연결" 카드(QR·120s 카운트다운·재생성·SAS(모드별)·연결됨 수렴) + 온보딩 S5 "폰에서도 쓰기" 진입점(UX-R2). 폰: ConnectScreen "QR로 연결"(expo-camera) → redeem → 키체인 저장 → SAS(모드별) → 워크스페이스 착지. Maestro 플로 1본.

## 기각 대안

- **buzz식 신원 전송(refresh 토큰 자체를 QR에)**: QR이 자격이 된다 — 사진·화면 공유로 유출 시 즉시 세션 탈취. 기각.
- **초대 코드 재사용(`oort://join`)**: 새 계정 생성 문법이라 "같은 사람의 두 번째 기기"를 표현하지 못하고 멤버가 둘이 된다. 기각.
- **SAS 상시 필수**: 로컬 루프백에서까지 4자리 대조를 시키면 "QR만 찍으면"이 깨진다. 공개 오리진 모드에 한정(D4).
- **outbox 이벤트로 즉시 수렴**: v1 폴링(≤2s)으로 충분, 실시간 배선은 후속.

## 영향·게이트

- 서버: 라우트 2(발급·소비) + 상태 GET 1, 테이블 `device_link_token`(해시·member·session·expires·consumed_at·sas) 마이그레이션 1본, RLS 동일. `schema_v0.sql` 무접촉.
- red proof: ①만료 토큰 소비 401 ②2회 소비 409 ③에이전트 발급 403 ④발급자 로그아웃 후 소비 401 ⑤공개 오리진 모드에서 SAS 미확인 시 세션 비활성 ⑥루프백 모드 SAS 생략 ⑦토큰 원문 로그 0건(grep 게이트).
- 클라: 웹 카드 design-review, 폰 Maestro 1본 + 시뮬레이터 카메라 목. 딥링크 정본 문서에 `link` 절 추가.
- 티켓: M0s(engine) → M0w(uxui) → M0m(mobile). Railway E2E(SH-5a)의 마지막 수용 칸.
- 재사용(2026-09-28): 이 ADR의 교환권 모양(TTL 120s·1회 소비·해시 저장·원문은 응답에만)을 ADR-0195 D-7(패스키 앱 로그인 교환권)이 PKCE 결속을 더해 그대로 쓴다.

조사에서 나온 구조적 사실: Steam·Telegram·Discord·WhatsApp·RFC 8628·GitHub는 모두 **새 기기가 코드나 QR을 띄우고 로그인된 기기가 입력·스캔해서 승인**한다. ADR-0180은 반대다(**로그인된 기기가 띄우고 새 기기가 입력**). 폰에는 카메라가 있고 데스크탑에는 없기 때문이다. 이 방향 차이가 아래 C5·C6과 기각 대안 A를 낳는다.

### 결정

**C1. 코드는 같은 교환권의 다른 손잡이다.** 별도 토큰이 아니다. 같은 `device_link_token` 행에 코드용 열을 더한다. TTL 120초·1회 소비·발급자 세션 결속·멤버당 1개(G4)가 코드에도 그대로 걸린다. 코드로 소비하든 토큰으로 소비하든 **한 행이 한 번만** 소비된다. 새 발급(재생성)은 이전 행과 그 코드를 함께 지운다.

**C2. 모양 [권장].** 8자, 알파벳 27자 `23456789BCDFGHJKMNPQRSTVWXZ`(숫자 2~9 + 자음 19자 — RFC 8628의 base-20 `BCDFGHJKLMNPQRSTVWXZ`에서 `L`만 뺀 것. 모음·`0`·`1`·`I`·`L`·`O`가 없다). 27^8 = 282,429,536,481 ≈ 2^38.0이다(RFC 예시의 20^8 ≈ 2^34.5보다 3.5비트 많다).
- 표시는 `BCDF-GHJK`(하이픈은 표시용). 입력은 공백·하이픈을 지우고 대문자로 바꾼 뒤 길이 8·알파벳을 검사한다. 어긋나면 코드 경로의 같은 401이다(C4).
- 생성은 편향 없이 뽑는다: 난수 바이트가 243(=27×9) 미만일 때만 `바이트 % 27`을 쓰고 나머지는 버린다(모듈로 편향 방지).
- 비슷해 보이는 글자(`2/Z`·`5/S`·`8/B`·`6/G`)는 남는다. 화면은 고정폭 대문자로 크게 보이고, 오타는 어차피 존재하지 않는 코드라 실패 예산(C6)에서 세어진다. 정규화로 서로 맞춰 주지 않는다(엔트로피를 깎는다).

**C3. 저장은 키 있는 MAC이다 [권장].** `code_mac = HMAC-SHA256(서버 비밀에서 파생한 키, 정규화한 8자)`. Rust에서 계산해 SQL에는 bytea로 넘기고 평문 코드도 `sha256(code)`도 저장하지 않는다. 이유: 2^38은 GPU 한 장이면 몇 분 안에 sha256을 오프라인에서 뒤집을 수 있는 크기라 [추정], 살아 있는 120초 동안 DB를 읽을 수 있는 쪽이 코드를 복원하게 된다. 키 파생은 `jwt_secret`에서 용도 문자열(`oort/device-link-code/v1`)로 한다(HKDF-SHA256 권장, 구현이 확정). `jwt_secret`을 바꾸면 살아 있는 코드가 모두 죽는다(120초라 수용).
- 소비 시 `code_mac`를 **NULL로 지운다**(소비된 행은 기기 목록 행으로 오래 남는다). 코드에 걸린 UNIQUE는 `code_mac IS NOT NULL`인 행에만 건다.
- 발급은 UNIQUE 충돌 시 새 코드로 최대 5번 다시 뽑는다. Postgres는 위반이 트랜잭션을 중단시키므로 `INSERT … ON CONFLICT DO NOTHING`을 돌리거나 savepoint를 쓴다. 조회는 새 EXECUTE 전용 definer 함수로 한다 — 086의 `device_link_workspace_id`와 같은 모양(`STABLE STRICT SECURITY DEFINER`, `search_path = pg_catalog`, uuid 하나만 돌려줌, `momo_app`에만 EXECUTE).

**C4. 소비 라우트 [권장].** `POST /v1/auth/device-link/redeem`의 본문에 `token` **또는** `code`를 받는다(둘 다·둘 다 없음은 400). 코드 요청은 정규화 → MAC → definer 조회 → 기존 소비 트랜잭션이다.
- 새 공개 엔드포인트는 만들지 않는다. 기존 `redeem`을 확장하고, 새 라우트 `deny`는 발급자 세션이 부르는 인증된 라우트다.
- **코드 요청의 실패는 전부 같은 401이다**: 형식 오류·없음·만료·이미 소비됨·발급자 세션 폐기. 본문도 같다. 토큰 경로의 409는 그대로 둔다(G7: 코드에서는 「맞았다」를 알려 주면 안 된다).
- 확인이 걸린 소비의 응답에 **`sas` 숫자를 동봉**한다. 폰이 토큰 없이도 숫자를 보이려면 서버가 줘야 한다(G3). E-2가 #2010의 서버 절반(응답에 `sas`)을 흡수한다. 폰의 파생 은퇴는 #2010의 정리 계획대로 진행하고 QR 경로 폰도 서버 값을 보이게 한다(C5의 한계 문장이 파생에 기대지 않는다). 단 은퇴는 **서버가 `sas`를 내는 버전이 퍼진 뒤(또는 한 릴리스 동안 폴백을 유지)**에 한다: 구서버의 redeem 응답에는 `sas`가 없어서 폴백이 사라지면 숫자가 안 보인다.

**C5. 코드 소비에는 발급자 확인이 항상 걸린다 — 모드와 무관하다 [권장].**
- 토큰 소비는 D4 그대로다(공개 오리진 모드에서만 SAS). **코드 소비는 루프백·LAN에서도** 새 세션을 `pending`으로 만들고 발급자가 확인해야 풀린다. 이유: 코드는 38비트짜리 입력이고(C6의 수치), 화면에 떠 있어서 어깨너머·화면 공유로 읽힌다. 읽은 사람이 120초 안에 자기 폰에 치면 발급자가 확인하지 않는 한 연결되지 않는다.
- 이를 위해 SAS 4자리는 **항상 계산해 보관**하고(「토큰 소비에 확인이 필요한가」는 새 열로 옮긴다. 기존 행은 `sas IS NOT NULL`을 이관한다), 코드 소비 행은 `redeemed_via = code`를 가진다.
- **확인 마감**: 확인이 걸린 **모든** 소비(코드, 그리고 공개 오리진 모드의 토큰 SAS)가 `confirm_by = 소비 + 120초`를 가진다. G8의 빈틈(마감 없음)을 닫는 것이고, 토큰 경로의 사용자 경험은 그대로다(폰의 SAS 대기 화면이 이미 120초다).
- **상태 기계.** 불가능한 전이는 이름 붙은 오류로 답한다.

| 현재 상태 | 동작 | 결과 |
|---|---|---|
| 발급됨(미소비) | redeem(`token`·`code`) | 새 세션. 확인이 필요하면 토큰이 `pending`이고 `confirm_by`가 선다 |
| 발급됨(미소비) | confirm·deny | 409 `device_link_not_redeemed` |
| 대기 | confirm, `confirm_by` 안 | 200, 세션 활성. 이미 확인됐으면 200(멱등) |
| 대기 | deny | 200, 대기 세션 토큰 폐기, 행에 `denied_at`. 이미 거절됐으면 200(멱등) |
| 대기 | `confirm_by` 지남 | 대기 세션 토큰 폐기(발급·소비·상태 조회 때 게으르게). confirm·deny는 410 `device_link_expired` |
| 거절됨 | confirm | 409 `device_link_denied` |
| 확인됨 | deny | 409 `device_link_already_confirmed`. 이미 연결된 기기는 `DELETE /v1/auth/devices/{id}`(D5)로 끊는다 |
| 확인이 필요 없는 소비(토큰·LAN·루프백) | confirm·deny | 409(현행 `NotRequired`) |

- **폰이 상태를 가르는 계약.** 대기·거절·마감으로 폐기된 세션 모두 지금은 같은 401이라 폰이 구별하지 못한다(G12). 401 본문의 `error.code`를 `device_link_pending`·`device_link_denied`·`device_link_expired`로 정하고, 폰의 `probeDeviceLinkAccess`가 이 값을 읽어 「거절됐어요」·「시간이 지났어요」를 보인다. **코드가 없는 401은 지금처럼 pending으로 읽는다**(코드를 모르는 구서버 호환 — 셀프호스트가 앱보다 늦게 올릴 수 있다). 폐기 사유는 `token`의 새 열 `revoked_reason`(NULL 허용)에 남긴다. 인증 미들웨어가 읽는 표가 `token`이라(`token_store.rs:115-149`) 핫패스에 조인을 더하지 않는다. `TokenState::Revoked`가 사유를 싣게 하는 것이 E-2의 핫패스 변경이다.
- 발급자 화면(C9)은 **숫자와 서버 호스트의 대조를 시킨다**: 「내 폰에 보이는 숫자와 서버 이름이 이 화면과 같은가요?」 RFC 8628 §5.4의 취지(사용자에게 기기 소유를 확인시킨다)를 따른 것이다. RFC는 새 기기가 코드를 띄우는 구조라 문자 그대로는 아니다. 사람이 **자기 폰**을 본다. 남이 읽어서 친 코드는 발급자 자신의 폰에 숫자가 없거나(아직 안 쳤다·이미 소비돼 실패했다) 다르다.
  - **한계(정직하게)**: 이 숫자는 서버가 알려 주는 값이다. 사용자가 **잘못된 서버 주소를 직접 쳐서** 그 중간자 서버가 진짜 서버의 숫자를 폰에 중계하면 숫자는 맞아 버린다. 그때 막는 것은 호스트 대조(카드의 호스트와 폰이 보이는 호스트)와 사람의 판단뿐이다. 대조 없이 [허용]을 누르는 사용자는 막지 못한다(위험 절).
  - **QR 경로와의 차이는 숫자의 출처가 아니다.** 토큰을 본 중계자는 폰이 파생하는 숫자와 같은 숫자를 계산할 수 있어서 파생 여부는 중계를 막지 못한다. 실제 차이는 QR이 **서버 주소를 페이로드에 싣고 사람이 주소를 치지 않는다**는 점이다. 코드 경로는 사람이 주소를 쳐서 잘못된 주소를 칠 수 있다. 두 경로 모두 중계를 막는 것은 호스트 대조다.
- **거절**: `POST /v1/auth/device-link/{id}/deny`(발급자 세션)를 새로 둔다(위 표). 지금은 거절 수단이 없다 — 발급자가 할 수 있는 일은 확인뿐이다.
- `status` 응답에 `needsConfirmation`·`via`·`sas`·`codeClosed`를 가산한다(카드가 발급 응답의 `sas`로 판단하던 것을 서버 사실로 바꾼다, G8. `codeClosed`는 C6의 예산이 닫힌 동안 참이다).

**C6. 시도 제한 — IP가 아닌 축이 본체다 [권장].**
- **IP 키 예산만으로는 모자란다.** IP는 첫 `X-Forwarded-For` 홉을 그대로 믿으므로(G5) 직접 노출된 서버나 값을 덧붙이는 프록시에서는 무한히 우회된다. IP 키 예산은 보조로만 둔다.
- 본체는 **인스턴스 전역 실패 예산** `RATE_LIMIT_DEVICE_CODE_FAILURES`(기본 **5** / **고정 60초 창** — 공용 `RATE_LIMIT_WINDOW_SECONDS`를 따르지 않는다. 운영자가 그 값을 줄이면 같은 5가 더 많은 시도를 허용해 아래 산식이 조용히 깨진다)다. **예약-환급** 방식이다:
  - 핸들러가 본문을 읽어 `code`가 있으면, 그 요청은 DB를 만지기 전에 예산 한 칸을 **먼저 선점**한다. 선점이 안 되면(예산 소진) **맞는 코드여도** 429 + `Retry-After`다. 성공·실패를 가를 수 있으면 예산이 있어도 추측이 가능해지므로, 닫힌 동안은 모든 답이 같다.
  - 코드가 맞아 소비되면 그 칸을 **돌려준다**. 실패(401)는 돌려주지 않는다.
  - 선점이 원자적이라 병렬로 쏜 오답이 예산을 넘지 못한다. 잠금이 DB 호출을 감싸지 않으므로 DB가 느려도 요청이 줄을 서지 않는다. (기존 `per_ip_refused`는 확인(`exhausted`)과 기록(`check`) 사이에 핸들러가 끼어 있어 병렬 요청이 모두 확인을 통과한 뒤 기록된다. `rate_limit.rs:515-541`. 그 모양을 그대로 쓰지 않는 이유다. 선점은 `check_at`, 환급은 제한기에 이미 있는 `forget_at`(`rate_limit.rs:267-281`: 단일 사용 슬롯을 먼저 잡고 일이 안 되면 돌려준다 — `audit_denial_once`가 같은 모양으로 쓴다)으로 한다.)
  - **게이트는 핸들러 안에 있다(미들웨어가 아니다).** 본문의 `token`/`code`를 읽은 뒤에야 알 수 있기 때문이다. `token` 요청은 이 예산을 읽지도 쓰지도 않는다. 라우트 단위로 걸면 코드 예산 소진이 QR·링크까지 막는다.
- 보조: IP당 `RATE_LIMIT_DEVICE_CODE_PER_IP`(기본 **3** 실패 / 60초, 같은 예약-환급). `X-Forwarded-For`가 없는 프록시 뒤에서는 `client_ip`가 연결 peer로 떨어져(`rate_limit.rs:324-332`) 이 IP 예산이 사실상 두 번째 전역 예산이 된다. 두 값 모두 0이나 파싱 불가는 **끄는 값이 아니라** 기본값으로 되돌린다(추측 가능한 공개 표면의 노브는 끄기를 두지 않는다). 규모가 큰 팀은 값을 올릴 수 있다(최소 1).
- **닫히는 비용.** 인터넷의 누구나 분당 오답 5건으로 코드 경로를 닫아 둘 수 있다(비용 0). 닫히는 것은 코드 경로뿐이고 QR·링크 붙여넣기는 열려 있다. 그러나 이 비용의 피해자는 카메라가 없고 범용 클립보드도 없는 사람(코드가 필요한 바로 그 사람)이다. 그래서 닫힌 상태는 **눈에 보인다**: 폰은 429에서 「잠시 뒤에 다시 해 주세요」와 함께 「링크 붙여넣기」·「주소로 로그인」을 안내하고, 발급자 카드는 `codeClosed`로 「코드 연결이 잠시 닫혀 있어요(맞지 않는 코드가 많아서)」를 보인다(운영자 신호).
- 카운터는 프로세스 메모리다(`SlidingWindowRateLimiter`). 서버가 여러 대면 예산이 대수만큼 늘어난다(단일 인스턴스 셀프호스트가 기준이다).
- 수치 [V 산술 / 추정 N]: 한 120초 구간에서 공격자가 쓸 수 있는 실패는 ≤ 10회(5/60초 × 2)이고, 맞는 코드가 하나라도 걸릴 확률은 ≈ 10·N / 27^8이다. N은 동시에 살아 있는 코드 수(멤버당 1개, 카드를 연 멤버 수).

| 동시 카드 N | 확률 | 2^- | RFC 8628 §5.1 기준(2^-32) |
|---|---|---|---|
| 4(소규모 팀) | 1.4e-10 | 32.7 | 만족 |
| 6 | 2.1e-10 | 32.1 | 만족 |
| 16 [추정] 상한 | 5.7e-10 | 30.7 | 근접. **발급자 확인(C5)이 두 번째 문이다** |

참고로 현행 IP 게이트만 쓰면 IP당 120초에 60회이고 IP 수는 제한이 없다. 같은 표의 5회와 격차가 크다.

**C7. 서버 주소는 폰이 알아야 한다 — 「입력 0칸」이 아니라 「카메라 0개」다 [권장].** 코드는 서버를 가리키지 못한다. 폰 「코드로 연결」 화면은 **주소 칸 + 코드 칸**이다. 주소는 저장된 값이 있으면 채우고(G9) `normalizeServerUrl`로 검증한다. 데스크탑·웹 카드는 코드 옆에 **서버 호스트**(예: `team.example.com`)를 같이 보인다. 호스트를 틀리게 친 폰은 연결되지 않고 읽은 코드를 잃는 것이 없다(120초·확인 필요, C5). 단 중계 서버로 치는 경우는 C5의 한계다.

**C8. 링크 붙여넣기 [권장].**
- 받는 형태는 딥링크 파서가 이미 받는 `oort://link?server=…&token=…`과 `momo://`뿐이다(G11). 그 밖의 문자열은 「oort 연결 링크가 아니에요」를 보이고 **네트워크 호출 0건**이다. 폰의 붙여넣기 칸은 ADR-0215 U-7의 claim 링크 칸과 한 칸이라, 한 판별 함수(코어)가 연결 링크·claim 링크·그 밖(invalid) 셋으로 가르고 claim 링크는 ADR-0215 D8의 길(호스트 칩 확인)로 보낸다. 이 절의 「링크」는 연결 링크다. 붙여넣은 내용은 오류 문구·로그·분석에 싣지 않는다.
- **클립보드는 사용자의 한 번의 동작 뒤에만 읽는다.** iOS 16+는 `ClipboardPasteButton`(시스템 붙여넣기 버튼, 권한 요청 없음)을 쓰고, 지원하지 않는 환경은 사용자가 입력 칸에 직접 붙여넣는다. 화면이 열릴 때·앱이 앞으로 올 때 `getStringAsync`를 부르지 않는다(iOS 16+에서는 프롬프트가 뜨고 거부하면 빈 문자열이다). 빈 문자열은 「링크 없음」이다.
- **붙여넣은 링크는 호스트를 한 줄로 보이고 사용자가 「연결」을 누른 뒤에만 redeem한다.** 클립보드 심기(남의 서버 링크를 복사해 두는 것) 방어다.
- **비대칭을 알고 둔다.** 딥링크·QR은 지금 그대로 즉시 redeem한다. `oort://link?server=<공격자>&…`를 열게 하는 웹 페이지·메시지는 클립보드 심기보다 쉬운 공격이다. 이 증보는 그 문제를 알면서 붙여넣기만 닫는다(새로 만드는 표면이라 규율을 처음부터 건다). 딥링크·QR에도 같은 호스트 확인을 거는 것은 **별도 이슈 U-9**다(기존 동작의 변경이라 따로 결재한다).
- 데스크탑 「복사」는 지금처럼 딥링크 전체를 복사한다(G2). 그 120초 동안 클립보드에는 살아 있는 교환권이 있다. 같은 Apple 계정의 다른 기기로 범용 클립보드가 옮겨 줄 수 있다 [추정]. 방어는 1회 소비·120초·확인이다. 데스크탑은 만료 시점에 클립보드가 우리가 쓴 값 그대로일 때만 비운다(best-effort, `runtime-unverified`).

**C9. 표면 [권장].**
- 웹·데스크탑 카드: QR 아래에 「코드 `BCDF-GHJK` · `team.example.com`」, 「코드 복사」(하이픈 없는 8자)·「링크 복사」(기존 「복사」의 새 이름). 카운트다운·재생성은 그대로이고 재생성하면 코드도 바뀐다. 코드로 소비되면 카드가 「연결 요청: <기기 이름> · 확인 숫자 NNNN」과 [허용]·[거부]로 바뀐다(모드 무관). 이름 옆에 「이름은 연결하는 쪽이 정한 값이에요」 한 줄을 둔다(이름은 인증 정보가 아니다). `codeClosed`일 때는 코드 대신 닫힘 안내를 보인다(C6).
- 폰 M0: 보조 링크 행에 「코드로 연결」을 더한다. 링크가 세 개를 넘지 않게 「링크 붙여넣기」는 코드 화면 안의 두 번째 행으로 둔다. 카메라 거부 화면(M1 거부)은 「주소로 로그인」 앞에 「코드로 연결」을 안내한다. 코드 화면은 주소·코드·붙여넣기, 제출 뒤에는 기존 SAS 대기 화면(M2)을 그대로 쓰되 서버가 준 `sas`와 **호스트**를 함께 보인다. 429는 C6의 안내를 보인다.

**C10. 감사·관측.** `device.linked`의 `via`는 토큰 소비가 `"qr"`(기존 값 유지, 붙여넣은 링크 포함), 코드 소비가 `"code"`다. 거절은 `device.link.denied`. 실패한 코드 시도는 감사 행을 쓰지 않는다(그 시점에는 워크스페이스를 모른다). 대신 버스트마다 WARN 한 줄만 낸다(`gate_per_ip`의 `should_log` 모양, 코드·IP 외 값 없음). 코드 원문은 로그·감사·진단 번들에 들어가지 않는다. 증명은 **서버 시험**이다(ADR-0166의 `claim_conformance_pg` 모양, 수용 기준 11).

### 기각 대안

| 대안 | 기각 이유 |
|---|---|
| A. 폰이 코드를 띄우고 로그인된 데스크탑이 입력·승인(RFC 8628·WhatsApp 모양) | **보안 모양은 A가 더 낫다.** 저엔트로피 코드를 사람이 **인증된 세션에** 치고(그 행위가 곧 §5.4의 기기 소유 확인이다), 폰이 쥔 256비트 `device_code`가 있어야 세션을 받는다. 중계 피싱(위험 절)도 통하지 않는다. 그러나 이 증보로 정하지 않는다: ① 이슈 Goal 1(a)·owner 기대(「QR 옆에 코드, 폰에서 입력」)와 방향이 반대다 ② **새 공개 엔드포인트 둘**(시작·폴링)과 **테넌트 밖 대기 테이블**(폰은 워크스페이스를 모르는 채 요청을 만든다. ADR-0195 D-6 `webauthn_challenge` 선례)이 필요해 증보가 아니라 새 기능이다 ③ 폰이 서버 주소를 먼저 알아야 하는 점은 같다 ④ 이 증보의 코드 경로는 링크 붙여넣기(토큰)가 못 덮는 경우(범용 클립보드가 없는 환경)의 보조다. **다시 볼 조건**: 코드 경로가 주된 길이 되거나 중계 피싱 사례가 보이면 A로 옮긴다(이 증보를 대체하는 별도 ADR). 이 방향 차이는 owner 확인을 권장한다. 같은 모양은 「새 데스크탑·웹을 로그인된 폰이 승인」(Steam·Telegram·Discord 모양)에도 맞다 |
| B. 6자리 숫자(전화 OTP 모양) | 2^20이라 같은 예산으로 2^-32에 못 닿는다. NIST의 6자리는 시도 제한을 전제한 최소치다 |
| C. 코드를 sha256으로 저장 | 2^38을 오프라인에서 뒤집는다(C3) |
| D. IP당 예산만 | `X-Forwarded-For` 우회(G5) |
| E. 루프백·LAN에서는 코드도 확인 생략(D4 그대로) | 화면 공유·어깨너머로 읽힌 코드를 막을 문이 없다(C5) |
| F. 코드에 서버 주소를 접두로 넣기 | 주소는 임의 길이라 짧은 코드가 되지 않는다. mDNS 발견(`_momo._tcp`)은 LAN에서만 되고 Railway·터널에서는 안 된다 |
| G. 코드를 별도 토큰 행으로(토큰과 독립) | 같은 멤버에 live 교환권이 둘이 되어 「한 행 한 번」이 깨진다(C1) |
| H. 전역 임계 구역(잠금)으로 예산 확인·검증·기록을 묶기 | 잠금이 DB 호출(`pool.acquire().await`, 타임아웃 없음)을 감싸 DB가 느릴 때 코드 요청이 전부 줄을 선다. 예약-환급이 같은 보장을 잠금 없이 준다(C6) |

### DB 계약 (새 migration만)

- 번호: main·track/uxui는 149, track/engine은 151이 마지막이다 [V, 2026-10-26]. 실제 번호는 구현 시점의 다음 번호다. `schema_v0.sql`은 건드리지 않는다.
- `device_link_token`의 새 열: `code_mac bytea NULL`(`code_mac IS NOT NULL`인 행에 부분 UNIQUE), `redeemed_via text`, `confirm_by timestamptz`, `denied_at timestamptz`, 토큰 소비의 확인 필요 여부 열(SAS를 항상 채우는 대신 옮긴다. 기존 행은 `sas IS NOT NULL`을 이관), `token`의 새 열 `revoked_reason`(거절·마감 구분, NULL 허용, C5).
- **새 EXECUTE 전용 definer 함수** `momo_join_private.device_link_workspace_id_by_code(bytea)`(086의 `device_link_workspace_id`와 같은 모양). RLS FORCE·`ws_isolation`은 기존 그대로다. 새 테넌트 테이블은 없다.

### 수용 기준 (red proof)

각 항목은 조건 하나만 거짓인 입력으로 쓰고 조건을 지우면 빨개지는 사보타주를 둔다. 사보타주는 구현 PR이 해당 줄을 실제로 바꿔 그 시험이 빨개지는지 손으로 확인하고 PR 본문에 적는 변이다. 규칙 셋: ① 그 줄 하나만 바꿨을 때 **지정한 시험은 반드시 빨개지고**, 같은 기능을 공유해서 함께 빨개지는 다른 시험은 PR 본문에 적는다. ② 방어층이 겹쳐 있으면 결과를 단정하고 두 층을 함께 지우거나 층마다 오류 코드를 구별한다. ③ 동시성 시험은 반복 횟수(예: 100회)나 결정적 간섭을 쓴다. 새 보안 문장을 `claims.yaml`·SECURITY.md에 올릴 때는 저장소 안 음성 대조(ADR-0214 D4)가 구현 이슈의 몫이다. 서버 PG 시험은 `infra/security-pack/selection.txt`에 올려 PR CI 레인으로 편입한다(현재 목록에 `device_link_conformance_pg`가 없다). `runtime-unverified` — 시험은 구현 이슈가 쓴다.

1. **1회(C1·C3).**
   - 1a 코드로 소비한 뒤 같은 행의 **토큰** 소비는 409다(상태까지 단정한다. 반대 방향은 소비된 코드가 조회되지 않는 1b가 덮는다). 사보타주: 소비됨 검사를 뺀다(뒤의 `consumed_at IS NULL` 가드가 401로 거절해 409 단정이 빨개진다).
   - 1b 소비된 행의 `code_mac`는 NULL이다. 사보타주: NULL 처리를 뺀다.
2. **다른 멤버 행(C3).**
   - 2a 멤버 A·B가 같은 워크스페이스에 동시에 live 링크를 갖고 A의 코드로 소비하면 A의 세션만 생기고 B의 행은 소비되지 않는다. 사보타주: 소비 UPDATE에서 `id` 조건을 지운다(그 워크스페이스의 live 링크가 모두 소비된다. `code_mac`는 전역 유일이라 조회 쪽 조건을 지워서는 이 행이 빨개지지 않는다).
   - 2b 코드 생성기를 주입(결정적 난수 이음새)해 같은 코드를 강제로 만든다: 발급이 새 코드로 다시 뽑는다. 사보타주: 충돌 처리(`ON CONFLICT` 재시도)를 지우면 발급이 오류로 끝나 빨개진다.
   - 2c 스키마 시험: 부분 UNIQUE가 있다. 사보타주: UNIQUE를 지운다.
3. **예산(C6).** 한 행은 조건 하나씩이다.
   - 3a 서로 다른 `X-Forwarded-For`로 오답 5건 → 6번째는 **맞는 코드여도** 429 + `Retry-After`. 사보타주: 버킷 키에 IP를 붙인다.
   - 3b 예산이 소진된 상태에서 `token` redeem은 200이다. 사보타주: 게이트를 라우트 단위(미들웨어)로 옮긴다.
   - 3c 실패 4 → 성공 1 → 실패 1: 마지막 실패는 429가 아니라 401이다. **실패 4건은 서로 다른 `X-Forwarded-For`로 보내 IP 보조 예산(3)이 먼저 닫히지 않게 한다.** 사보타주: 환급(`forget_at`)을 지운다(성공이 칸을 계속 써서 마지막이 429가 된다).
   - 3d 서로 다른 `X-Forwarded-For`로 동시 50개의 오답 → 정확히 5건이 401이고 나머지 45건은 429다(IP 보조 예산이 먼저 닫히지 않게 IP를 나눈다). 사보타주: 선점을 「확인 후 기록」으로 바꾼다.
   - 3e 노브 `0`·파싱 불가는 기본값(5·3)으로 되돌아간다. 사보타주: 0을 「끔」으로 해석한다.
   - 3f IP 보조 예산: 같은 IP에서 오답 3건 → 4번째는 429(전역 예산이 남아 있어도). 사보타주: IP 예산을 지운다.
   - 3g 닫힌 동안(소진 중) 오답과 정답의 429 응답 본문이 바이트 단위로 같다. 사보타주: 정답에만 다른 본문을 낸다.
4. **같은 오류(C4).** 형식 오류·없음·만료·소비됨·발급자 로그아웃인 코드 요청의 응답 본문이 바이트 단위로 같은 401이다(다섯 원인은 서로 다른 `X-Forwarded-For`로 보내 IP 보조 예산이 먼저 닫히지 않게 한다). 사보타주: 만료를 410으로 둔다. 「소비됨」은 소비 때 `code_mac`를 지워서 코드 경로가 `AlreadyUsed`(409)에 닿지 못하므로 1b와 짝으로 본다. 토큰 경로의 409는 그대로다(회귀 시험).
5. **상태 기계(C5).** 표의 전이마다 한 행이다.
   - 5a LAN 모드로 발급한 링크를 코드로 소비하면 세션이 확인 전까지 401 `device_link_pending`이고, 토큰으로 소비하면 즉시 유효하다. 사보타주: pending을 모드로만 정한다.
   - 5b `confirm_by` 안의 confirm은 200이고 두 번째도 200(멱등)이다. 사보타주: 두 번째 confirm을 409로 낸다.
   - 5c deny → 200·대기 토큰 폐기·감사 `device.link.denied` 1행이고 폰의 다음 요청이 401 **`device_link_denied`**다. 사보타주: deny의 폐기가 pending과 같은 코드를 내게 한다.
   - 5d 거절 뒤 confirm → 409 `device_link_denied`. 사보타주: confirm이 거절 표식을 보지 않게 한다.
   - 5e 확인 뒤 deny → 409 `device_link_already_confirmed`(활성 세션이 끊기지 않는다). 사보타주: deny가 활성 세션도 폐기하게 한다.
   - 5f `confirm_by` 뒤의 confirm·deny → 410 `device_link_expired`, 대기 토큰은 폐기되고 폰의 401 코드는 `device_link_expired`다. 사보타주: 코드 경로에서 `confirm_by`를 세우지 않는다(토큰 경로의 마감은 5g가 따로 겨냥한다).
   - **5g 토큰 SAS 경로의 마감**: 공개 오리진 모드에서 **토큰**으로 소비 → `confirm_by` 뒤 confirm 410·대기 토큰 폐기. 사보타주: 토큰 경로에서 `confirm_by`를 세우지 않는다(코드 경로에만 마감을 거는 구현이 빨개진다).
   - 5h 미소비 링크의 confirm·deny → 409 `device_link_not_redeemed`. 사보타주: 미소비를 `NotFound`로 낸다.
   - 5i 확인이 필요 없는 소비(토큰·LAN)의 confirm·deny → 409(`NotRequired`). 사보타주: 이 행에서 deny가 토큰을 폐기하게 한다.
   - 5j 대기 중 두 번째 deny → 200(멱등)이고 감사 행은 1개다. 사보타주: 두 번째 deny를 409로 낸다. 5k 거절 뒤 deny → 200(멱등). 사보타주: 같다.
6. **저장(C3).** 어떤 열에도 평문 코드나 `sha256(code)`와 같은 값이 없다(시험이 `digest(code,'sha256')`를 검색해 0건을 단정한다). `jwt_secret`을 바꾸면 같은 코드가 조회되지 않는다. 사보타주: sha256으로 바꾼다.
7. **코드 생성(C2).** 알파벳 27자, 금지 문자(모음·`0`·`1`·`I`·`L`·`O`) 0, 추출 상수 243. 분포: 270만 글자 표본에서 27자 각각의 빈도가 기대값(10만)의 ±2% 안이다(편향 `% 27`은 +5.5%/−5.1%라 걸린다. ±2%는 표준편차의 6배라 플레이크가 아니다). 사보타주: `% 256 % 27`로 바꾼다.
8. **폰의 숫자 출처(C4·C5).** 코드 redeem 응답에 `sas`가 있고 폰은 토큰 없이 그 숫자를 보인다. **QR 경로의 폰도 서버가 준 `sas`를 보이고 파생 함수(`deviceLinkSasDigits`)를 부르지 않는다**(소스 시험으로 호출 0건). 이 소스 시험은 **파생을 은퇴시키는 #2010 정리 PR에서만 켠다**(서버가 `sas`를 내는 버전이 퍼진 뒤 또는 한 릴리스 폴백 유지). 사보타주: 응답에서 `sas`를 빼거나 파생 폴백을 되살린다.
9. **붙여넣기(C8).**
   - 9a 연결 링크도 claim 링크도 아닌 붙여넣기는 네트워크 호출 0건이고 내용이 어디에도 나타나지 않는다. 사보타주: 오류 문구에 내용을 넣는다.
   - 9b 화면 포커스·앱 포그라운드에서 클립보드 읽기 0건(spy). 사보타주: 포커스에서 읽게 한다.
   - 9c 붙여넣은 링크는 호스트 확인 뒤에만 redeem한다. 사보타주: 확인을 건너뛰게 한다.
   - 9d `getStringAsync`가 빈 문자열이면 「링크 없음」이다(네트워크 호출 0건). 사보타주: 빈 문자열을 redeem에 넘긴다.
10. **카드·안내(C6·C9).** 한 행에 하나씩이다.
    - 10a 카드에 코드·호스트가 보인다. 사보타주: 호스트를 지운다.
    - 10b 코드 소비 시 숫자와 [허용]·[거부]가 보인다. 사보타주: 버튼을 지운다.
    - 10c 이름 옆 「이름은 연결하는 쪽이 정한 값이에요」 문구가 있다. 사보타주: 문구를 지운다.
    - 10d `codeClosed`일 때 카드가 닫힘 안내를 보인다. 사보타주: 안내를 지운다.
    - 10e 폰은 429에서 「링크 붙여넣기」·「주소로 로그인」을 안내한다. 사보타주: 안내를 지운다.
11. **감사·로그(C10, 서버 시험).** `device.linked`의 `via`는 코드 소비에서 `code`, 토큰 소비에서 `qr`이다. 코드 원문의 비유입은 `claim_conformance_pg.rs:274-357`의 모양(`tracing_subscriber`로 로그를 가로챔)으로 발급 → 소비 → 실패 전 경로를 돌리고, 코드(하이픈 있는 표시형·없는 8자)가 로그와 `audit_log.detail`에 0건임을 단정한다(그 파일은 `audit_log`를 읽지 않으므로 이 검색은 새로 쓴다). 일부러 로그에 코드를 찍는 변이에서 빨개지는 음성 대조를 둔다. 웹의 `deviceLinkSecrets.gate.test.ts` 모양은 캡처 파일 이름 위생에만 쓴다.

### 구현 슬라이스

- **E-2 (engine·security)** 짧은 코드: migration(위 DB 계약)·MAC 키 파생·발급과 소비 확장·예약-환급 예산(`check_at`·`forget_at`)·상태 기계·deny 라우트·`status` 가산 필드·401 코드(인증 미들웨어 핫패스와 `TokenState`의 폐기 사유 변경 포함)·#2010의 서버 절반 흡수. 서버 PG 시험(`device_link_conformance_pg`)을 `selection.txt`에 올린다. **독립 보안 검수 Blocker 0·High 0**이 머지 조건이다.
- **U-3 (uxui)** 웹·데스크탑 「폰 연결」 카드: 코드·호스트 표시, 코드 소비 시 [허용]·[거부]와 숫자, `codeClosed` 안내(C9).
- **U-5 (uxui·phone)** 폰 「코드로 연결」·「링크 붙여넣기」·카메라 거부 화면 안내·호스트 확인·429 안내(C7~C9). 붙여넣기 칸은 ADR-0215 U-7의 claim 링크 칸과 **한 칸으로 합치고** 한 판별 함수(코어)가 두 종류를 가른다.
- **U-9 (uxui·phone)** QR·딥링크로 연결할 때도 서버 호스트 확인 한 줄(C8의 비대칭).
- **#2010 (OPEN, engine)** E-2가 서버 절반을 흡수한다. 폰의 파생 은퇴(정리)와 **수용 8의 소스 시험**은 #2010의 정리 PR이 가진다(서버가 `sas`를 내는 버전이 퍼진 뒤 또는 한 릴리스 폴백 유지). QR 경로 안전 근거는 파생이 아니다(C5).
- 문서: 딥링크 정본(`docs/onboarding-deeplink.md`)에는 코드 절을 구현이 더한다.

### 위험과 미검증

- `runtime-unverified`: `ClipboardPasteButton`의 기기 동작, 맥 클립보드 비우기, 전체 시험(수용 기준).
- **N은 추정이다**(C6 표). 동시에 카드를 여는 멤버가 16명을 넘는 팀이면 확률이 2^-30.7보다 나빠진다. 그 팀은 예산 값을 낮출 수 있다(최소 1).
- 전역 예산이 닫히는 비용은 모두에게 간다(코드 경로만, C6). 닫힘은 눈에 보이게 했다.
- 짧은 코드는 화면에서 읽힌다. 마지막 방어는 사람의 숫자·호스트 대조(C5)이고 대조를 건너뛰는 사용자는 막지 못한다.
- **중계 피싱.** 사용자가 잘못된 서버 주소를 쳐서 중간자 서버가 코드를 진짜 서버로 중계하면 서버가 주는 숫자도 중계된다(C5 한계). 코드 경로는 QR 경로보다 이 공격에 약하다(QR은 주소가 페이로드에 있다). 완화는 카드·폰의 호스트 표시와 확인 화면뿐이고, 더 강한 길은 코드가 토큰을 대신하는 한 없다. 기각 대안 A의 방향(로그인된 데스크탑이 입력)이 이 공격에 강하다.
- **딥링크·QR의 즉시 redeem**은 이 증보가 고치지 않는다(U-9).
- **401 코드 계약은 인증 미들웨어(핫패스)와 `TokenState`·`token` 표를 건드린다**(C5). 구서버·구앱 조합에서는 코드가 없는 401을 pending으로 읽어 지금처럼 동작한다.
- **롤링 배포 겹침(영향 작음).** 구버전 인스턴스는 `sas IS NOT NULL`로 확인 필요를 판단한다(`device_link.rs:230`). 새 인스턴스가 SAS를 채워 발급한 LAN 링크를 구버전 인스턴스가 토큰으로 소비하면 pending 세션이 생긴다. 120초 링크가 배포 순간에 걸칠 때만 생기는 일이라 받아들인다. E-2는 expand/contract(새 열을 먼저 더하고 「항상 채움」은 구버전이 사라진 릴리스)로 줄일 수 있다.

### 후속

1. 「새 데스크탑·웹을 로그인된 폰이 승인」(Steam 모양)이 필요해지면 기각 대안 A의 방향으로 별도 ADR을 쓴다.
2. 전역 예산이 실제로 닫히는 빈도를 본 뒤 기본값 5를 다시 본다.
