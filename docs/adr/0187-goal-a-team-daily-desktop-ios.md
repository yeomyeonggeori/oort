## 1. 맥락

기안자가 2026-09-23에 재진단 리뷰에서 잰 사실이다.

- **목표 정의가 흔들렸다.** 1차 목표 문장이 8/3, 8/10, 9/2, 9/7, 9/8, 9/22에 각각 다시 쓰였다.
- **작업이 앱보다 절차에 쏠렸다.** 최근 30일 main 커밋이 닿은 영역은 아래와 같다. 09-22 하루에 작업 PR 12개를 올리는 데 승격·sync PR이 33개 들었다.

  | 영역 | 커밋 수 |
  |---|---|
  | 웹 | 492 |
  | docs | 396 |
  | STATUS.md | 366 |
  | 서버 | 79 |
  | iOS | 28 |
  | 데스크탑 | 1 |

- **팀이 쓸 수 있는 실물이 없다.**
  - 지속 인스턴스가 없다. NCP는 철수했고 `app.oor7.com`은 해석되지 않으며, Railway 부팅은 드라이브 권한에서 실패했다.
  - `release-desktop.yml`은 한 번도 돌지 않았고, DMG는 v0.1.1(08-22) 하나뿐이다.
  - iOS 앱은 웹의 약 1/3 규모다(31k줄 대 92k줄). 원격 작업 화면은 읽기 전용이고 기본으로 숨겨져 있다(#2166).
  - 데스크탑에서 에이전트 세션을 돌리는 프로그램이 없다(Swift daemon은 #2165로 삭제).

기안자는 같은 날 리뷰에서 두 읽기를 냈고, 성재는 A를 골랐다.
- **A:** 팀이 매일 쓰는 데스크탑과 iOS를 먼저 완성하고 외부 출시를 뒤로 미룬다.
- **B:** 지금의 셀프호스팅 설치 순서를 유지한다.

## 2. 결정

### D1. 목표 A — 내부 팀이 Buzz급으로 쓰는 데스크탑 앱과 iOS 앱
- **성재:**
  - 「목표는 내부에서 buzz급으로 사용할 수 있도록 데스크탑 앱과 iOS 앱을 제공하는 것이야.」 (리뷰 요청 발화)
  - 「목표를 A로 확정하자.」 (결정 발화)
- **A안에 적혀 있던 것**(성재가 A를 고르며 함께 확정):
  - 외부 출시는 목표 A 뒤다. 연기 목록은 D6에 있다.
  - 내부 테스트의 정의가 바뀐다. 성재와 한 명이 도는 스모크 대신, 팀 전원이 정한 기간 동안 oort를 주 메신저로 쓰고 불편을 전부 티켓으로 만든다.
  - 셀프호스팅 기둥은 목표 A 동안 「팀 인스턴스 하나가 업그레이드와 백업을 견디며 돈다」로 줄어든다. 이미 만든 설치 자산은 외부 출시 때 다시 쓴다.
- **기안자 도출:**
  - 첫 이정표는 데스크탑과 iOS가 둘 다 M7-I PASS로 팀에 배포되는 것이다.
  - 내부 테스트 기간은 §4 확정점이다.

### D2. 팀 인스턴스는 Railway가 기본, Tailscale은 보조
- **성재:**
  > 「팀 인스턴스는 레이웨이로 할 것 같고 테이스케일은 같이 활용할 수 있는 범위가 있으면 활용해도 괜찮을 것 같아. 즉 레이웨이를 통한 배포를 일단 디폴트로 생각하면 될 것 같고 테이스케일은 원격과 관련된 부분, 만약에 필요하다면 우리 iOS 앱이 그때까지 마감이 잘 안 된다면 그렇게 하면 될 것 같고 사실 이제 원격 관련해하고 테이스케일 안 쓰고 iOS 앱을 쓰는 걸 목표로 하면 좋을 것 같아.」
- **정리:**
  - 팀 인스턴스는 Railway 배포가 기본이다.
  - Tailscale은 같이 쓸 수 있는 범위에서 활용한다. 특히 iOS 앱이 준비되기 전의 원격 경로다.
  - 목표는 Tailscale 없이 iOS 앱으로 원격 작업을 하는 것이다.
- **기안자 도출:** Railway 배포는 ADR-0184 경로를 따른다(#2205). D4를 만족하려면 이 인스턴스에 notifier와 push relay가 함께 떠야 한다.

### D3. iOS 목표 — Buzz 모바일 수준 + Codex·Claude iOS 앱 같은 원격 작업
- **성재:**
  > 「버즈급 iOS의 범위는 너이 추천을 해주면 좋을 것 같아. 근데 최소한 버즈도 모바일 앱이 있거든. 그 정도 수준의 원격 작업 그리고 알림 시스템 그리고 데스크탑에서 사용자들이 했던 걸 트래킹하고 온전히 독까지 요청할 수 있는 마치 코덱스나 클라우드에 iOS 앱 같은 느낌이 내가 iOS 앱의 목표로 설정하면 좋을 것 같아.」
- **기안자 도출(확인 대기):**
  - **목표를 네 기둥으로 정리한다.**
    1. 대화. D1 발화의 「buzz급으로 사용」에서 왔다.
    2. 알림
    3. 데스크탑에서 한 작업의 추적
    4. 폰에서 작업을 끝까지 요청하기
  - **세부 범위는 기안자 권고안으로 내고 성재가 확정한다**(목표 A 계획 문서).
  - 원격 작업은 Tailscale 없이 하는 것이 목표다(D2 원문). 그래서 데스크탑 쪽에 실행 주체가 목표 A 안에 있어야 한다.
    - 그 구조와 보안 경계는 별도 ADR(ADR-0188)에서 정한다.
    - ADR-0183이 「출시 후」로 미룬 #1256·#1927의 순서 변경도 그 ADR에서 정한다.
    - ADR-0100에 따라 그 ADR이 Accepted가 된 뒤에만 구현을 머지한다.

### D4. 실기기 푸시는 필수
- **성재:** 「실기기 푸시 보류는 왜 들어가 있는지 모르겠는데 실기기 푸시까지 돼야 될 것 같고 왜냐하면 iOS 앱까지 배포를 목표로 하고 있으니까」
- **보류의 성격(기록 확인):** 09-08 보류는 기술적 차단이 아니었다. 성재의 09-08 결재 4번 「실기기 APNs는 데스크톱 셀프호스팅 완료 뒤」라는 순서 결정이었다. JOURNAL 09-08과 `2026-09-08-remaining-work-map.md`에 기록돼 있다. 이 결정으로 그 보류를 해제한다.
- **기안자 도출:** 실기기 푸시는 M7-I 항목(I-4)이다. 기준은 앱이 종료된 상태에서 1회 받는 것이다.

### D5. 배포는 TestFlight internal에서 App Store로, M7은 두 등급
- **성재:**
  > 「테스트플라이트 내부 배포도 좋고 아니면 아예 실제 배포로 해서 그걸 사용하는 방향도 괜찮을 것 같아. M7 게이트를 내부 배포와 스토어 두 등급으로 나누는 것도 괜찮은데 내부 배포뿐만 아니라 아예 스토어 배포 목표로 설정해도 괜찮을 것 같고 필요하다면 두 등급으로 나누는 게 좋을 것 같아.」
- **정리:**
  - App Store 배포도 목표에 들어간다.
  - TestFlight internal도 좋고, 실제 배포로 바로 가서 쓰는 방향도 열려 있다.
  - M7은 두 등급으로 나눈다. 게이트 정본은 `docs/cicd/03-store-readiness-gate.md`다.
- **기안자 도출:**
  - 순서는 M7-I 팀 배포 → M7-S다. 스토어 직행을 허용할지는 §4에서 정한다.
  - 등급별 적용 대상과 항목을 나눈다.
    - M7-I: TestFlight internal, 직접 전달 공증 DMG.
    - M7-S: App Store, external TestFlight, 공개 공증 배포.
  - 배포 건마다 owner 승인을 받는다.
  - 데스크탑 next 채널은 팀 채널이다(§5 2차 결재). 게시는 M7-I 규칙을 따른다.

### D6. 목표 A 동안 미루는 것
성재가 고른 A안에 들어 있던 연기 목록이다. 아래 항목은 목표 A가 끝날 때까지 새로 착수하지 않는다. 이미 main에 있는 자산은 유지한다.
- 그록봇 VM 발행 이미지 재실측(E2E-A)
- Railway 밖의 플랫폼 경로 확장. A안은 Fly·AWS·Cloudflare를 적었고, GCP는 기안자 보충이다.
- 외부 셀프호스터 모집(A안). 하네스 복붙 설치의 외부 재현은 기안자 보충이다.
- AX-5 #2511, AX-8 #2514

미루지 않는 것도 적는다.
- Railway 실배포 #2205는 팀 인스턴스(D2)가 된다.
- AX-6 #2512 초대 E2E는 팀 인스턴스 위에서 돌려 인스턴스 검증을 겸한다.
- AX-7 #2513 폰 승인·결과 카드는 폰 승인 버튼 #1084와 한 파도로 처리한다.
- App Store 제출 항목(#20–#22·#30·#31)은 목표에 남는다(D5). 순서는 M7-I 팀 배포가 안정된 뒤다. 이 순서는 A안 원문이고, 스토어 직행 여부는 §4에 열려 있다.
- #1281 next 채널 재발행은 M7-I PASS 뒤 첫 팀 게시로 한다(next = 팀 채널, §5 2차 결재).

### D7. 실행 체계 — Grok 은퇴, Opus 5.5 서브에이전트, 병렬 상한 없음
- **성재:**
  > 「그로그를 은퇴시키고 아예 현재 단계 기준에서는 오프스 5.5를 워커로 사용하거나 아니면 워커의 개념보다는 오프스 5.5를 서브 에이전트 형태로 활용해서 병렬 작업 처리를 할 수 있는 형태로 하면 좋을 것 같고 병렬의 상하는 따로 두지 않을게. 그래서 너가 그거를 적절하게 판단해서 작업을 해주면 좋을 것 같아」
- **정리:** 정본은 `docs/planning/PIPELINE.md`와 `worker-adapters.md`다.
- **기안자 도출(성재가 판단을 맡긴 범위):** 고정 상한 대신 판단 기준을 둔다.
  - 호스트 load가 코어 수를 넘으면 새 무거운 작업을 미룬다.
  - 결과가 흔들리는 작업은 호스트 전체에서 하나씩 돌린다. 병합 트리 게이트, Docker 스택 게이트, iOS 빌드·시뮬레이터, 캡처 측정이 여기에 속한다.
- planner 레인의 기본 모델은 이 결정에 들어 있지 않다. PIPELINE에 성재 확인 대기로 적는다.

### D8. 절차 — 묶음 승격, STATUS 규칙 폐지, 증거는 PR 본문
- **성재(위임):** 「묶음 성격과 스테이터스 MD 규칙 폐지는 너가 확인하고 괜찮을 것 같으면 진행해도 좋을 것 같아.」
- **기안자가 확인한 사실:**
  - **STATUS.md를 강제하는 게이트·스크립트가 없다.**
    - `pr-ci.yml`에서는 레인 관심 경로 주석에만 나온다.
    - 나머지 언급은 폐지된 부트스트랩 데이터(`scripts/github*`)뿐이다.
    - 규칙은 AGENTS, PR·이슈 템플릿, 일부 문서에만 있다.
  - **묶음 승격을 막는 위상 검사가 없다.** `check_track_alignment.sh --remote`는 트랙이 main보다 앞서는 것을 허용하고, main이 두 트랙의 조상이기만 요구한다.
- **그래서 아래와 같이 정한다.**
  - **track→main 상시 위임은 PR 단위에서 묶음 단위로 바꾼다.** 하루 한 번, 또는 다른 트랙이 그 변경을 소비해야 할 때 한 번에 승격하고 양 트랙을 sync한다(TRACKS §3).
  - **검증 증거의 정본은 PR 본문이다.**
    - `STATUS.md`는 2026-09-23에 동결한 역사 기록이다.
    - 릴리스 요약은 `CHANGELOG.md`와 GitHub Release에 둔다. 묶음 승격 때 통합자가 `[Unreleased]`로 옮긴다.
    - 현재 위치는 CURRENT_STATE, 짧은 이력은 JOURNAL에 둔다(ADR-0100 증보).

## 4. 확정점
**2026-09-23 2차 결재로 정해진 것(§5):**
- **「독」의 해석.** 기안자 읽기(「폰에서 데스크탑 작업 세션을 따라가고 작업을 끝까지 요청 — 시작·지시·승인·중단」)를 결재 질문에 적었고, 성재는 이의 없이 답했다.
- **iOS 세부 범위와 순서.** 「원격 작업까지 팀 배포 전에」. M7-I 팀 배포는 ADR-0188 R1까지 기다린다(M7 I-8).
- **원격 작업 구조.** ADR-0188 Accepted.
- **데스크탑 배포 채널.** 「next를 팀 채널로 인정」. 공개 URL이지만 광고하지 않으며, 게시는 M7-I 규칙을 따른다.

**아직 열려 있는 것:**
- **내부 테스트 기간.** 기안자 기본값은 2주다.
- **M7-I 승인 단위.** 기본은 배포 건마다 owner 승인이다. 이를 계열이나 기간 단위로 완화할지 정해야 한다.
- **스토어 직행 허용 여부.** M7-I 팀 배포를 거치지 않고 M7-S로 바로 갈 수 있는지 정해야 한다.
  - 기안자 권고: M7-I 먼저. 팀 사용 기간이 S-1 크래시-free의 분모가 되기 때문이다.

## 증보 2026-09-26 — 허들 P0·P1과 로컬 워크벤치 M1을 목표 A에 넣는다
- **성재:** 「전부 권장대로 가자」(허들 2.0 Q2 「목표 A에 허들을 넣을까」, 작업 공간 2.0 Q1 「로컬 워크벤치 M1을 목표 A 안에서 R1과 병렬로」의 권장안). 기록은 ADR-0122 증보 2026-09-26과 ADR-0190~0192(#2754).
- **허들 P0·P1이 목표 A 범위다.** P0는 #2757·#2758·#2759·#2761, P1은 #2760·#2762~#2768이다. 녹음·전사·요약(P2, #2770·#2771)과 CallKit(#2769)은 목표 A 밖이다. `infra/railway/railway.json`의 「huddle deferred」 문구는 #2759에서 바뀐다. 기안자 확인: `docs/cicd/03-store-readiness-gate.md`에 허들 항목이 없으므로, 이 편입이 M7-I 팀 배포의 진입 조건을 바꾸지는 않는다. iOS 허들의 마이크 사용 문구와 팀 내부 고지는 **M7-I 범위**다. 허들로 생기는 스토어 등급 항목(App Privacy 신고, `PrivacyInfo.xcprivacy`, 개인정보처리방침 갱신)은 **M7-S 항목**으로 두고, 이 증보가 목표 A의 첫 이정표(M7-I 팀 배포) 안으로 당기지 않는다.
- **로컬 워크벤치 M1이 목표 A 범위다**(ADR-0190). R1과 병렬인 데스크탑 UXUI 줄이고 서버 변경이 없다: #2772~#2777, #2789. 에이전트 칸(M2)은 ADR-0188 R1과, 계정·쿼터(M3)는 R2와 같은 줄로 간다. 원격 호스트 세팅(M4), 팀 샌드박스(M5), 커넥터 C2~C4는 목표 A 밖이다(ADR-0192 D7).
