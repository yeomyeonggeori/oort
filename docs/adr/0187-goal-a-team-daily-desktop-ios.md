## 1. 맥락

기안자가 2026-09-23에 재진단 리뷰에서 잰 사실이다.

- **목표 정의가 흔들렸다.** 1차 목표 문장이 8/3, 8/10, 9/2, 9/7, 9/8, 9/22에 각각 다시 쓰였다.
- **작업이 앱보다 절차에 쏠렸다.** 최근 30일 main 커밋이 닿은 영역은 아래와 같다. 09-22 하루에 작업 PR 12개를 올리는 데 승격·sync PR이 33개 들었다.

  | 영역 | 커밋 수 |
  |---|---|
  | 웹 | 492 |
  | docs | 396 |
  | STATUS.md | 366 |
  | 서버 | 79 |
  | iOS | 28 |
  | 데스크탑 | 1 |

- **팀이 쓸 수 있는 실물이 없다.**
  - 지속 인스턴스가 없다. NCP는 철수했고 `app.oor7.com`은 해석되지 않으며, Railway 부팅은 드라이브 권한에서 실패했다.
  - `release-desktop.yml`은 한 번도 돌지 않았고, DMG는 v0.1.1(08-22) 하나뿐이다.
  - iOS 앱은 웹의 약 1/3 규모다(31k줄 대 92k줄). 원격 작업 화면은 읽기 전용이고 기본으로 숨겨져 있다(#2166).
  - 데스크탑에서 에이전트 세션을 돌리는 host 프로그램이 없다(Swift daemon은 #2165로 삭제).

기안자는 같은 날 리뷰에서 두 읽기를 냈고, 성재는 A를 골랐다.
- **A:** 팀이 매일 쓰는 데스크탑과 iOS를 먼저 완성하고 외부 출시를 뒤로 미룬다.
- **B:** 지금의 셀프호스팅 설치 순서를 유지한다.

## 2. 결정

### D1. 목표 A — 내부 팀이 Buzz급으로 쓰는 데스크탑 앱과 iOS 앱
- 성재: 「목표는 내부에서 buzz급으로 사용할 수 있도록 데스크탑 앱과 iOS 앱을 제공하는 것이야.」 이어서 「목표를 A로 확정하자.」
- **첫 이정표:** 데스크탑과 iOS가 둘 다 **M7-I PASS**(D5)로 팀에 배포된다.
- **내부 테스트의 정의가 바뀐다.** 성재와 한 명이 도는 스모크에서 「팀 전원이 정한 기간 동안 oort를 주 메신저로 쓰고, 불편을 전부 티켓으로 만든다」로 바꾼다. 기간은 열린 확정점이다(§4).
- **셀프호스팅 기둥이 줄어든다.** 목표 A 동안은 「팀 인스턴스 하나가 업그레이드와 백업을 견디며 돈다」가 그 기둥의 범위다. 이미 만든 설치 자산은 외부 출시 때 다시 쓴다.
- 외부 출시는 목표 A 뒤다. 외부 출시란 외부 셀프호스터 3, 그록봇 VM 설치(E2E-A), 하네스 복붙 설치, 추가 플랫폼 경로를 말한다.

### D2. 팀 인스턴스는 Railway가 기본, Tailscale은 보조
성재 원문:
> 「팀 인스턴스는 레이웨이로 할 것 같고 테이스케일은 같이 활용할 수 있는 범위가 있으면 활용해도 괜찮을 것 같아. 즉 레이웨이를 통한 배포를 일단 디폴트로 생각하면 될 것 같고 테이스케일은 원격과 관련된 부분, 만약에 필요하다면 우리 iOS 앱이 그때까지 마감이 잘 안 된다면 그렇게 하면 될 것 같고 사실 이제 원격 관련해하고 테이스케일 안 쓰고 iOS 앱을 쓰는 걸 목표로 하면 좋을 것 같아.」

- 팀의 지속 인스턴스는 ADR-0184 경로의 Railway 배포다(#2205).
- D4를 만족하려면 이 인스턴스에 notifier와 push relay가 함께 떠야 한다.
- Tailscale은 iOS 원격 작업이 준비되지 않았을 때만 쓰는 임시 원격 경로다. 목표는 Tailscale 없이 iOS 앱으로 원격 작업을 하는 것이다.

### D3. iOS 목표 — Buzz 모바일 수준 + Codex·Claude iOS 앱 같은 원격 작업
성재 원문:
> 「버즈급 iOS의 범위는 너이 추천을 해주면 좋을 것 같아. 근데 최소한 버즈도 모바일 앱이 있거든. 그 정도 수준의 원격 작업 그리고 알림 시스템 그리고 데스크탑에서 사용자들이 했던 걸 트래킹하고 온전히 독까지 요청할 수 있는 마치 코덱스나 클라우드에 iOS 앱 같은 느낌이 내가 iOS 앱의 목표로 설정하면 좋을 것 같아.」

- **목표의 네 기둥:**
  1. Buzz 모바일 수준의 대화
  2. 알림
  3. 데스크탑에서 한 작업의 추적
  4. 폰에서 작업을 끝까지 요청하기
- **세부 범위**는 기안자가 권고안을 내고 성재가 확정한다(목표 A 계획 문서).
- **원격 작업**은 폰이 데스크탑 쪽 명령 실행을 일으키는 보안 경계다.
  - 구조는 별도 ADR(ADR-0188)로 정하고, 그 ADR이 Accepted가 된 뒤에만 머지한다(ADR-0100).
  - 데스크탑에서 세션을 돌리는 쪽을 **목표 A 안에서** 만든다. ADR-0183이 「출시 후」로 미룬 #1256·#1927의 순서를 이 결정이 바꾼다.

### D4. 실기기 푸시는 필수
- 성재: 「실기기 푸시 보류는 왜 들어가 있는지 모르겠는데 실기기 푸시까지 돼야 될 것 같고 왜냐하면 iOS 앱까지 배포를 목표로 하고 있으니까」
- 09-08 결재 2번의 보류는 기술적 차단이 아니었다. 「데스크톱 셀프호스팅 완료 뒤 테스트」라는 순서 결정이었고, 이 결정으로 해제한다.
- 앱이 종료된 상태의 실기기 푸시 1회 수신은 M7-I 항목(I-4)이다.

### D5. 배포는 TestFlight internal에서 App Store로, M7은 두 등급
성재 원문:
> 「테스트플라이트 내부 배포도 좋고 아니면 아예 실제 배포로 해서 그걸 사용하는 방향도 괜찮을 것 같아. M7 게이트를 내부 배포와 스토어 두 등급으로 나누는 것도 괜찮은데 내부 배포뿐만 아니라 아예 스토어 배포 목표로 설정해도 괜찮을 것 같고 필요하다면 두 등급으로 나누는 게 좋을 것 같아.」

- **M7-I(내부):** 팀 대상 공증 DMG, 업데이터 매니페스트, TestFlight internal.
- **M7-S(스토어):** App Store, external TestFlight, 공개 공증 DMG. M7-I PASS가 전제다.
- 게이트 정본은 `docs/cicd/03-store-readiness-gate.md`이고, Tauri·RN 기준으로 다시 썼다. 은퇴한 Swift 체크리스트는 git 히스토리에 있다.
- App Store 배포도 목표에 들어간다. 순서는 M7-I 팀 배포 → M7-S다.

### D6. 목표 A 동안 미루는 것
성재가 고른 A안에 들어 있던 연기 목록이다. 아래 항목은 목표 A가 끝날 때까지 새로 착수하지 않는다. 이미 main에 있는 자산은 유지한다.
- 그록봇 VM 발행 이미지 재실측(E2E-A)
- Railway 밖의 플랫폼 경로 확장(Fly·AWS·GCP·Cloudflare)
- 외부 셀프호스터 모집과 하네스 복붙 설치의 외부 재현
- AX-5 #2511, AX-8 #2514

미루지 않는 것도 적는다.
- Railway 실배포 #2205는 팀 인스턴스(D2)가 된다.
- AX-6 #2512 초대 E2E는 팀 인스턴스 위에서 돌려 인스턴스 검증을 겸한다.
- AX-7 #2513 폰 승인·결과 카드는 폰 승인 버튼 #1084와 한 파도로 처리한다.
- App Store 제출 항목(#20–#22·#30·#31)은 목표에 남는다(D5). 순서만 M7-I 팀 배포가 안정된 뒤다.

### D7. 실행 체계 — Grok 은퇴, Opus 5.5 서브에이전트, 병렬 상한 없음
- 성재 원문:
  > 「그로그를 은퇴시키고 아예 현재 단계 기준에서는 오프스 5.5를 워커로 사용하거나 아니면 워커의 개념보다는 오프스 5.5를 서브 에이전트 형태로 활용해서 병렬 작업 처리를 할 수 있는 형태로 하면 좋을 것 같고 병렬의 상하는 따로 두지 않을게. 그래서 너가 그거를 적절하게 판단해서 작업을 해주면 좋을 것 같아」
- 정본은 `docs/planning/PIPELINE.md`와 `worker-adapters.md`다.
- 고정 상한 대신 판단 기준을 둔다.
  - 호스트 load가 코어 수를 넘으면 새 무거운 작업을 미룬다.
  - 결과가 흔들리는 작업은 호스트 전체에서 하나씩 돌린다. 병합 트리 게이트, Docker 스택 게이트, iOS 빌드·시뮬레이터, 캡처 측정이 여기에 속한다.

### D8. 절차 — 묶음 승격, STATUS 규칙 폐지, 증거는 PR 본문
성재: 「묶음 성격과 스테이터스 MD 규칙 폐지는 너가 확인하고 괜찮을 것 같으면 진행해도 좋을 것 같아.」 기안자가 확인한 사실은 아래와 같다.

- **STATUS.md를 강제하는 게이트·스크립트가 없다.**
  - `pr-ci.yml`에서는 레인 관심 경로 주석에만 나온다.
  - 나머지 언급은 폐지된 부트스트랩 데이터(`scripts/github*`)뿐이다.
  - 규칙은 AGENTS, PR·이슈 템플릿, 일부 문서에만 있다.
- **묶음 승격을 막는 위상 검사가 없다.** `check_track_alignment.sh --remote`는 트랙이 main보다 앞서는 것을 허용하고, main이 두 트랙의 조상이기만 요구한다.

그래서 아래와 같이 정한다.
- **track→main 상시 위임은 PR 단위에서 묶음 단위로 바꾼다.** 하루 한 번, 또는 다른 트랙이 그 변경을 소비해야 할 때 한 번에 승격하고 양 트랙을 sync한다(TRACKS §3).
- **검증 증거의 정본은 PR 본문이다.**
  - `STATUS.md`는 2026-09-23에 동결한 역사 기록이다.
  - 릴리스 요약은 `CHANGELOG.md`와 GitHub Release에 둔다.
  - 현재 위치는 CURRENT_STATE, 짧은 이력은 JOURNAL에 둔다(ADR-0100 증보).

## 3. 기안자 판단 — 위임 범위 안에서 정한 것
성재가 이의를 내면 정정한다.
- **M7-I 기록 단위는 마이너 계열의 첫 빌드다.** 같은 계열의 다음 빌드는 PR 본문에 I-1·I-5 증거를 적는다. 빌드마다 30분 스모크와 owner 승인을 요구하면 TestFlight internal 반복이 막히기 때문이다.
- **옛 G-H(Enterprise Trust)는 M7-S에서 뺀다.** 위협 모델, SBOM·라이선스 스캔, 시크릿 스캔, VDP, 보안 백서가 이 항목이다(MOMO-140). 앱 심사와 무관한 항목이라 외부·엔터프라이즈 출시 단계에서 다시 태운다. 사라진 것이 아니라 연기다.

## 4. 열린 확정점
목표 A 계획 문서에서 권고안과 함께 묻는다.
- **「독」의 해석.** 기안자는 「폰에서 데스크탑 작업 세션을 따라가고 작업을 끝까지 요청(시작·지시·승인·중단)할 수 있다」로 읽었다.
- **iOS 세부 범위와 순서.**
- **내부 테스트 기간.**
- **원격 작업 구조(ADR-0188).**
