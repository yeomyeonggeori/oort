## 맥락

### 실측 (2026-10-16, 운영 oort-team) [V]
- **푸시가 한 번도 나가지 않았다.** `push_dispatch_log`가 0행이었다. 후보(`outbox.kind='push_candidate'`) 15건은 전부 `done`이었다. 판정(`momo-push` `judge_targets`)이 대상을 0명으로 냈고, 억제된 대상은 SQL에서 걸러져 로그에 남지 않는다.
- **원인은 「방해 금지」였다.**
  - 성재의 `member.presence_status='dnd'`(10-01 15:18 KST), `notification_rule.dnd=true`, `dnd_until=NULL`이었다.
  - 방해 금지를 고르면 서버가 같은 tx에서 일시 중지를 켠다(ADR-0124 증보 2 「묶어」, `presence.rs:517-528`). 그런데 어느 클라이언트도 기한을 보내지 않아(`selfStatus.ts:77-97`), 일시 중지가 끝나지 않았다.
  - 판정은 DND를 승인 요청보다 위에 둔다. 그래서 15일 동안 모든 알림이 0건이었다.
- **사용자는 알 수 없었다.**
  - 폰 방해 금지 설명은 「알림은 「알림 일시 중지」가 멈춥니다」(`model.ts:112-113`)였다. 증보 2가 요구한 「알림도 함께 멈춰요」와 반대다.
  - 방해 금지를 고른 뒤 일시 중지 스위치는 다시 읽지 않아 꺼짐으로 남는다.
  - 일시 중지 표시는 폰 프로필 시트와 웹 설정 › 알림 밖에 없다.
- **피해**
  - 10-13 승인 카드가 1시간 뒤 만료됐다(#3738).
  - 10-16 03:07 승인 카드가 04:07 시간 초과됐다.
  - 둘 다 폰 알림 0건이었다.
- **첫 왕복.** 19:17 성재가 일시 중지를 끄자 19:34:09 첫 푸시(승인 요청)가 나갔고 APNs 200을 받았다. 19:35:23 승인했고 그록봇 run은 `succeeded`였다. 성재는 본문을 눌러 앱의 카드에서 승인했다. 도착 강조가 승인 뒤에도 남는 문제는 #3921이다.
- **잠금 화면 승인은 동작하지 않는다.**
  - 앱이 종료돼 있으면 Face ID를 통과해도 요청이 나가지 않는다. expo는 응답을 받자마자 iOS에 완료를 알린다(`NotificationCenterManager.swift:111-124`). JS 리스너는 세션 갱신 뒤에야 붙고, 콜드 런치의 마지막 응답은 본문 탭만 받는다(`tapArrival.ts:82`, 시험 `pushTap.test.tsx:1146`이 이 동작을 고정한다).
  - 앱이 정지 상태이면 백그라운드 실행 시간을 잡지 않는다. `decideApproval`은 401에 갱신하지 않는 raw fetch를 쓴다(`api.ts:1133-1147`).
  - 결과는 `console.log`로만 남고, 결정된 승인의 알림은 버튼이 산 채로 남는다.

### 성재 요청 (원문, 2026-10-16)
1. 「지금 모바일쪽 알림 관련해서 데스크탑에서 그록봇으로 테스팅하는 부분과 관련한 알림들이나 승인관련 알림같은게 안오고 있거든 모바일에서 말이야. 알림에서 눌러서 관련위치 이동 및 알림에서 승인 바로 때려버리는 그런 기능들도 설계해서 작업해줘.」
2. 「푸시알림이 토글형태로 되어야 하고, 일시 정지는 뭔가 시간설정이 있어야하는게 정상일거 같아. 일단 내쪽에서 일시정지 꺼뒀어. 모바일을 설치 후 첫 온보딩때 저런 알림같은것도 받을건지 사용자한테 받자」
3. 「알림받고 승인했는데도 저렇게 표시되는데 백그라운드로 저거 해소해줘」(→ #3921)

### 지금 있는 것 [V]
- **경로:** message INSERT 트리거 → notifier 판정 → Ed25519 서명 → push-relay(닫힌 어휘: reason 6종, category 4종) → APNs.
  - 페이로드는 id-only이고 `aps.alert`는 자리표시 「oort / 새 알림」이다.
  - NSE(Swift, `ios/NotificationService`)가 `push_fetch` 토큰(6시간, ADR-0188 §8.7)으로 본문을 받아 다시 쓴다.
- **어휘 일치:** 카테고리 4종과 이유 6종의 문자열은 서버·relay·JS·Swift에서 같다.
- **버튼:** 메시지·멘션에는 답장, 승인에는 승인·거절(인증 필수, 앱을 열지 않음), 작업에는 버튼이 없다(`categories.ts`).
- **탭 착지:** 종류별 착지는 #2569·#2584에 있다. `work_run_done`은 대화로 간다(페이로드에 run id가 없다).
- **결정 라우트:** `POST /v1/workspaces/{ws}/approvals/{id}/decision`. 같은 키로 같은 판정을 다시 보내면 200 재생, 다른 판정이면 409, 이미 결정된 것은 409에 저장된 상태를 실어 보낸다. 서명은 요구하지 않는다(`approvals.rs:444-946`).
- **판정의 빈틈**
  - 승인 요청은 채널의 모든 사람에게 간다. 결정 권한이 없는 사람도 받는다.
  - 채널에서 에이전트의 대화 응답, 승인 만료 줄, 멈춤 줄은 아무에게도 가지 않는다(멘션 기록이 Skip 경로, ADR-0199 맥락).
  - APNs 410은 토큰을 무효화하지 않는다(ADR-0120 D4 미구현).

## 결정

### D1. 「푸시 알림」은 이 폰의 스위치다
- **켬**은 OS 허용과 이 기기의 서버 등록이다. 끄면 기존 `DELETE /v1/workspaces/{ws}/devices/{id}`로 이 기기 토큰만 무효화한다(`revoke_device`는 토큰만 무효화한다).
  - 앱은 「사람이 껐다」를 기기에 기억한다. `PushProvider`가 다음 실행에 자동으로 다시 등록하지 않는다.
- OS가 거부한 상태에서 켜려 하면 iOS 설정을 연다. OS가 아직 묻지 않았다면 허용 창을 띄운다.
- 데스크탑 OS 알림과 다른 기기에는 영향이 없다.
- 서버 계약은 바뀌지 않는다.

### D2. 멈춤에는 항상 기한이 있다 (ADR-0124 증보 2를 화면에서 완성)
- 알림 일시 중지와 방해 금지 모두 기한을 고르고 나서 켜진다. 기한 목록은 30분 · 1시간 · 2시간 · 내일 오전 9시까지 · 다음 주 월요일 오전 9시까지 · 직접 고르기(날짜·시각)다.
- 「직접 끌 때까지」는 고를 수 없다. 서버 계약(`dndUntilMs`, `null`=기한 없음)은 그대로 둔다.
  - 이미 있는 기한 없는 행은 판정을 바꾸지 않는다. 화면에서 「기한 없음 · 기한 정하기」로 보인다.
- 방해 금지 설명은 「알림도 함께 멈춰요」로 고친다(증보 2의 요구).
- 방해 금지를 쓴 뒤 일시 중지 상태를 다시 읽는다.
- 일시 중지만 끄고 상태가 아직 방해 금지이면 「상태는 아직 방해 금지예요 · 풀기」를 한 줄로 보인다.
- 증보 1의 머리 「Proposed」 표기를 실제 상태(Accepted, 증보 2·3의 전제)에 맞춘다.
- 화면 작업은 #2899가 소유한다.

### D3. 멈춤이 보인다
- 일시 중지가 진행 중이면 폰 인박스 맨 위와 데스크탑 사이드바의 내 이름 아래에 한 줄을 둔다: 「알림 일시 중지 중 · 오후 9:30까지 · 다시 켜기」.
- 기한이 지나면 서버 재조회 값을 믿는다(클라이언트 타이머로 풀지 않는다).

### D4. 첫 실행 알림 단계 (ADR-0193 D8 증보)
- M3을 「어떤 알림을 받을까요?」로 넓힌다. 종류 미리 보기 세 장을 보인다.
  - 승인 요청 — [승인][거절] 버튼과 「잠금 화면에서 바로」
  - 작업 끝남
  - 나를 부른 멘션·답
- 작업 끝남은 스위치(기본 켬)이고 `push-kinds`에 쓴다. 승인 요청·멘션·DM은 「항상 와요」로 적는다.
- iOS 허용 창 앞의 버튼은 [계속] 하나다(Apple HIG, D8 유지). 거부하면 「프로필 › 알림에서 켤 수 있어요」.
- M3의 조건(iOS 권한 미결정일 때만)은 바꾸지 않는다. 기존 설치자에게는 뜨지 않는다. 성재의 「설치 후 첫 온보딩」과 같다.

### D5. 누르면 그 자리
- #2569의 종류별 착지를 유지한다.
- 도착 강조는 결정되면 바로, 보인 뒤에는 시간이 지나면 물러난다(#3921).
- 다른 워크스페이스 알림의 전환 제안, `work_run_done`의 run 상세 착지는 이 결정 밖이다(후속).

### D6. 잠금 화면 승인·거절 (ADR-0188 §8.7 증보, ADR-0137 보완)
- **처리 주체 = 네이티브.**
  - 앱 타깃의 Swift 처리기를 `NotificationCenterManager.shared.addDelegate`로 앱 시작 시 붙인다. iOS에서 승인·거절 액션은 이 처리기가 혼자 맡는다.
  - 처리기는 `didReceive` 안에서 동기로 `beginBackgroundTask`를 잡는다. expo가 곧바로 completion을 불러도 요청이 끝날 때까지 산다.
  - JS(`handlePushResponse`)는 iOS에서 승인·거절을 더 이상 보내지 않는다. 답장은 JS가 계속한다.
- **자격 = `push_action` 토큰.**
  - `push_fetch`(§8.7)와 같은 모양이고 허용 경로가 하나다: `POST /v1/workspaces/{ws}/approvals/{approval}/decision`.
    - `ws`는 토큰의 워크스페이스다. 그 외는 403이고, DB 조회 전에 판정한다.
    - 결정 라우트의 기존 검사(사람 여부·채널 멤버·역할·만료·멱등)는 그대로다. 토큰은 bearer를 바꿀 뿐 권한을 더하지 않는다.
  - 발급은 `POST /v1/auth/push-action-token`(사람 access bearer)이다. 행은 호출자 세션 계열의 `token(kind='session', label='push_action')`이다.
  - 수명은 6시간이고, 세션이 회전할 수 있는 동안만 산다(`push_fetch_session_live`와 같은 규칙). 계열당 살아 있는 토큰은 4개까지다.
  - 앱 전용 키체인 그룹(`app.momo.ios.devicekey`)에 둔다. NSE 공유 그룹에는 두지 않는다.
  - 로그아웃·기기 해제·세션 끝(재사용 소탕·비밀번호 변경·정지·제거)에서 함께 죽는다.
  - 감사 로그에 `via=push_action`을 남긴다.
- **기각한 대안**
  - 기기 키 서명: 엔클레이브 키는 생체 인증 창이 필요하고, 화면 없이 깨어난 앱에서는 띄울 수 없다.
  - 네이티브 refresh: refresh 재사용 탐지와 JS 갱신이 경주한다. 경주에 지면 로그아웃된다.
  - 승인 버튼이 앱을 연다: 「바로」가 아니다.
- **멱등:** `client_decision_id`는 알림 요청 식별자와 액션에서 결정적으로 만든다. 두 번 눌러도 200 재생이다.
- **결과 고지:** 원래 알림을 같은 스레드의 로컬 알림 한 줄로 바꾸고, 같은 승인의 다른 알림을 걷는다.
  - 성공: 「승인했어요 · {제목}」/「거절했어요 · {제목}」
  - 다른 곳에서 이미 결정됨: 「이미 승인된 요청이에요」(원장의 실제 방향)
  - 실패·토큰 없음·만료·403: 「승인하지 못했어요 — 눌러서 앱에서 마무리」. 누르면 카드로 간다.
- 앱 안 결정과 다른 기기의 결정도 그 승인의 알림을 걷는다(JS, 앱이 살아 있을 때).

### D7. 버튼을 보일 때와 숨길 때
- **카테고리를 둘로 나눈다.**
  - `momo.approval`은 잠금 화면에서 승인·거절한다.
  - `momo.approval.open`은 「열어서 결정」 하나이고 인증 뒤 카드를 연다.
- 서버는 `approval.action_type`으로 고른다. 아래는 open이다.
  - 한 번만 보이는 비밀을 내는 액션(초대·페어링 링크): 잠금 화면에서는 비밀을 보일 곳이 없다.
  - 작업 호스트 권한(ADR-0188 D-권한: 잠금 화면 허용 금지)
  - 호스트 선택이 필요한 실행 승인
  - 기본은 inline이고, open 목록은 서버 코드 한 곳에 둔다.
- 어휘 증보: relay `ALLOWED_CATEGORIES` +1, phone `PUSH_CATEGORY`, Swift 상수에 넣는다. **relay를 먼저 배포한다**(ADR-0120 A-6 순서). 구버전 앱은 모르는 카테고리를 버튼 없이 보인다(fail-safe).
- **NSE가 본문을 못 받으면 버튼을 뗀다.** 자리표시 「새 알림」으로 떨어지면 `categoryIdentifier`를 open(또는 버튼 없음)으로 바꾼다. 무엇인지 모르는 것을 잠금 화면에서 승인하게 두지 않는다.
- **받는 사람을 좁힌다.** `approval_request`는 그 승인을 결정할 수 있는 사람에게만 간다(결정 라우트와 같은 규칙: 채널 멤버 + 액션의 역할·소유자 조건). 그 밖의 사람은 채널에서 카드를 보고, 푸시는 받지 않는다.

### D8. 내가 부른 에이전트의 답·멈춤 (ADR-0120 증보)
- 에이전트가 쓴 메시지가 사람 X의 요청에 답하면 X에게 푸시한다.
  - 판정 기준은 `reply_to_id`의 작성자, 또는 run 요청자(trigger 메시지 작성자)다.
  - 대상 메시지는 최종 응답, 승인 만료 결과, 멈춤 줄이다. 생산자는 trigger를 `reply_to_id` 또는 props로 남긴다.
- 와이어 reason은 기존 `mention`이다(어휘 변경 없음, NSE가 본문을 그린다).
  - 판정에는 「보고 있으면 보내지 않는다」를 적용한다. X의 `read_state`가 그 채널에서 30초 안에 움직였으면 보내지 않는다(부록 A-8과 같은 창).
  - 사람 멘션·DM에는 이 창을 적용하지 않는다(현행 그대로).
- `work_run_done`(type=work)은 그대로 둔다. 같은 메시지에는 이유가 하나만 붙는다. 우선순위는 approval_request > work_run_done > mention > dm이다.

### D9. 죽은 토큰을 걷는다 (ADR-0120 D4 이행)
- APNs 410, 400 `BadDeviceToken`, `DeviceTokenNotForTopic`을 받으면 그 `push_token`을 무효화한다(`invalidated_at`).
- 환경 불일치(relay 400)는 감사 한 줄을 남기고 무효화하지 않는다. 운영자 설정 문제다.

### D10. 이 결정 밖 (연결만)
- 시험 알림·진단(「시험 알림 보내기」 + 막힌 이유)은 방향만 정하고, 계약은 후속에서 정한다.
- `push_fetch` 수명 6시간 때문에 생기는 자리표시 문제는 후속에서 정한다. D7의 버튼 떼기가 안전 쪽을 먼저 막는다.
- 승인 만료 10분 전 알림은 #3738, 앱이 앞에 있을 때의 배너는 #2592다.
- 규칙 PATCH 경합은 #3012, 통합 표시는 #3335, 다른 기기 즉시 반영은 #2851이다.

## 보안·경계 요약
- 새 자격 증명은 `push_action` 토큰 하나다.
  - 이 토큰으로 할 수 있는 일은 「내가 이미 결정할 수 있는 승인 요청에 승인·거절」뿐이다. 메시지 읽기·쓰기, 설정, 세션 연장은 할 수 없다.
  - 6시간 뒤 만료되고, 로그아웃·기기 해제·세션 끝에서 서버가 함께 죽인다.
  - 폰 안 앱 전용 키체인에만 있고 NSE는 읽지 못한다.
- 잠금 화면 버튼은 iOS 인증(Face ID·암호)을 거쳐야 눌린다. 분실 폰이 잠긴 채로 승인하지 못한다.
- 비밀을 내는 승인과 호스트 권한은 잠금 화면에서 결정하지 않는다(D7).
- 무엇인지 모르는 알림에는 버튼이 없다(D7).
- 받는 사람 좁히기(D7)로, 결정 권한이 없는 사람의 잠금 화면에는 승인 버튼이 생기지 않는다.
