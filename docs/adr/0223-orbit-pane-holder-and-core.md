## 배경

### 지금 있는 것 [V]
- 데스크탑 앱 프로세스가 PTY를 연다(ADR-0190 D1). `pty.rs`(2,538줄)가 PTY 열기, 하네스 허용목록, 계정 변수 빼기(`STRIPPED_ENV`), 폴더 검사, 출력 흐름 제어(`pty_ack`)를 맡는다. `pane_signal.rs`(576줄)는 훅 신호를 받는다. 0700 폴더의 Unix 소켓이고 같은 uid만 받으며, 칸마다 무작위 토큰이 있다. 그래서 다른 칸의 프로그램이 일부러 환경을 읽지 않는 한 칸 3의 프로그램이 칸 5의 상태를 바꾸지 못한다(같은 사용자 프로그램은 환경을 읽을 수 있다, D3).
- 앱이 끝나면 모든 칸이 끝난다(`lib.rs`의 `RunEvent::Exit` → `kill_all`). 웹뷰의 headless 미러가 스크롤백을 이 기기 localStorage에 둬서 다시 열면 전의 화면을 보이지만, 프로그램은 새로 뜬다.
- workd(A 레인)는 앱의 자식이라 앱과 함께 꺼진다(ADR-0188 D2). 앱과 workd는 0700 폴더의 Unix 소켓 하나로만 말한다. workd는 소켓 폴더를 bind 때 한 번 확인하고, 같은 uid와 상대의 코드 서명을 확인한다. 앱은 반대로 소켓 상대가 자기가 띄운 자식 pid인지 확인한다(`momo-workd`의 `control_socket.rs`, 데스크탑 `work_host.rs`).
- 칸 지기 통로는 메시지마다 보낸 쪽의 서명을 확인한다(D3). workd 제어 소켓도 같은 확인 방식(메시지마다 서명 확인)으로 옮긴다 — #5619.
- OSC 7501 상태 보고는 오늘 허용 출처가 됐고 읽는 곳은 전용 모듈 하나다(ADR-0190 증보 2026-11-09). 구현 #5579가 진행 중이다. 이것이 칸 코어 0단계다.

### herdr-core에서 확인한 것 (v0.1.19, 읽기만 했다)
- 앱이 꺼져도 칸을 붙드는 서버(hc)와 holder가 있다. 다시 붙으면 지금 화면·기록·상태를 준다. 상태는 OSC 7501 보고만 쓰고 화면 글자로 짐작하지 않는다. 이벤트 구독은 첫 스냅숏 + 하나씩 오르는 순번이고, 15초마다 심장 박동, 뒤처지면 놓침 + 새 스냅숏이다([API 문서](https://github.com/herdrdev/herdr-core/blob/v0.1.19/schema/README.md)).
- **모든 칸의 환경에 hc 소켓 주소를 넣는다**([`api/run.rs`](https://github.com/herdrdev/herdr-core/blob/v0.1.19/crates/herdr-core/src/api/run.rs#L218-L219)). 보안 문서는 「There is no separate API password or per-client permission check.」라고 적는다([security](https://github.com/herdrdev/herdr-core/blob/v0.1.19/docs/security.md)). 그래서 한 칸의 프로그램이 다른 칸의 화면을 읽고, 입력하고, 서버를 끌 수 있다. 지금 oort의 칸별 토큰보다 후퇴다.
- 빌드에 Zig 0.16과 Ghostty 서브모듈이 필요하고 `rust-version` 선언이 없다. 공개 뒤 15일에 10판이 나왔고 기본 동작이 자주 바뀐다. 라이선스는 Apache-2.0이다([저장소](https://github.com/herdrdev/herdr-core)).
- 원격 컴퓨터(`machine.*`)·파일(`file.*`)·화면 읽기(`read`)·입력(`send`·`keys`)·문서 저장(`doc.*`) 명령이 있다.

## 업계는 (ADR-0100 비교 참조)
- **herdr-core**: 보는 창과 PTY 주인을 나눠서 앱을 꺼도 칸이 산다. 대신 칸끼리 서로 믿는 구조다(위).
- **tmux**: 소켓은 기본으로 주인만 접근한다. 읽기 전용 손님의 경계는 `attach -r`이 아니라 서버의 접근 목록(`server-access -r`)이다([설명서](https://man.openbsd.org/tmux.1)).
- **OSC 7501**(Program Status Protocol 0.4): 프로그램이 터미널에 자기 상태를 알리는 공개 규격이다([kitty 문서](https://github.com/kovidgoyal/kitty/blob/master/docs/misc-protocol.rst)). Codex TUI와 Claude Code(2.1.295부터)가 낸다.
- oort가 다른 점: PTY 주인의 소켓을 칸에게 주지 않는다. 원격·화면 읽기·입력 명령을 두지 않는다. 같은 공개 규격을 쓰고 herdr-core에서는 생각만 빌린다.

## 선택지와 기각 사유

| 선택지 | 판단 |
|---|---|
| A. herdr-core를 crate로 의존 | 기각. workd는 PTY를 열 수 없고(ADR-0190 D1·ADR-0188 D6), 앱 안에서 돌리면 앱과 함께 죽어 결국 B가 된다. 판을 올릴 때마다 컴파일이 깨질 수 있고, 데스크탑 MSRV(1.89)를 올리고 CI·배포에 Zig를 더해야 한다 |
| B. 판을 고정한 hc 바이너리를 옆에 띄우기 | 기각. 모든 칸이 hc 소켓을 받아 칸끼리 화면을 읽고, 입력하고, 서버를 끌 수 있다. oort 쪽에서 막을 길이 없다. 기본 동작이 판마다 바뀌고, macOS에서 「Herdr Core」 이름으로 권한 창이 뜬다 |
| C. herdr-core를 포크하거나 옮겨 오기 | 기각. 65파일 870KB를 15일 10판 속도로 따라가야 해서 버전 따라가기를 포기하는 셈이다 |
| D. 지금 PTY에서 OSC 7501만 받기 | 이미 한다(0단계). 앱을 꺼도 칸이 사는 것은 얻지 못한다 |
| **E. 지금 데스크탑 코드를 우리 crate로 떼고 칸 지기를 둔다** | **채택.** 칸별 토큰 경계를 지키고 판 따라가기는 생각만 빌리는 일로 가벼워진다. 앱과 칸 지기는 XPC로 메시지마다 서명을 확인한다(D3). 품은 5~7주로 본다(hc 붙이기의 3~4.5주보다 길다) |

## 결정

### D1. 칸 코어 라이브러리 `momo-orbit`와 칸 지기 — 사람이 연 터미널 칸의 PTY 주인을 칸 지기로 바꾼다 (ADR-0190 D1 증보)
- 데스크탑 터미널 코드를 Rust crate `momo-orbit`(가칭)로 뗀다. 들어가는 것은 PTY 열기, 하네스 허용목록과 경로 찾기, 계정 변수 빼기(ADR-0191 D2), 폴더 검사, 화면 모델, 질의 자동 응답(D4), 상태 기계(OSC 7501 + 훅), 이벤트 순번(D5), 출력 흐름 제어, 프로토콜 타입이다. 처음에는 지금 `pty.rs`·`pane_signal.rs`의 동작을 그대로 옮긴다.
- 화면 모델은 permissive 후보(`alacritty_terminal` Apache-2.0, `vt100` MIT)를 시험으로 고르고 NOTICE에 귀속을 반영한다. 고르는 시험에 「되비추기 문자열이 입력으로 나오지 않는다」를 넣는다(D4).
- **칸 지기**는 crate를 감싼 작은 실행 파일이다. 이름은 `momo-` 접두로 구현이 정한다(가칭 `momo-orbit-holder`). 앱 번들 안 helper로 같은 팀이 Developer ID로 서명하고, 앱이 SMAppService로 등록하는 launchd 에이전트로 돈다(D3). 앱이 첫 칸을 열며 붙으면 launchd가 띄우고, 칸 지기는 앱보다 오래 산다.
- 칸 지기는 macOS에서만 쓴다. 다른 OS와, 칸 지기를 쓸 수 없는 빌드·설정(D3 끝)에서는 지금처럼 앱 안에서 같은 crate로 PTY를 연다(대체 모드).
- **사람이 연 터미널 칸(L 칸)의 PTY는 칸 지기가 연다.** 앱 안에서 PTY를 여는 것은 둘뿐이다. 하나는 ADR-0190 D3-f 로그인의 숨은 PTY다. 짧게 살고 앱과 함께 끝나야 해서 앱에 남는다. 다른 하나는 위의 대체 모드다. 앱이 스스로 돌리는 그 밖의 짧은 명령(D3-a 상태 확인·D3-c git 읽기·D3-e 앱 명령)도 지금처럼 앱에 남는다.
- **앱 쪽 단정은 앱에 그대로 남긴다.** ADR-0190 D1의 「서버 이벤트·딥링크·workd는 PTY를 열 수 없다」를 지키는 것은 칸 지기 통로가 아니라 앱 안의 단정이다. 서버 이벤트·딥링크·발견·트레이·Agent Port 처리기는 모두 앱 안에서 돌아서, 그 요청도 서명된 앱 연결로 나가기 때문이다.
  - 웹뷰의 PTY 명령 표만 칸 호스트 클라이언트에 닿는다. 딥링크·발견·서버 이벤트·Agent Port·트레이 처리기에서 그 이름이 나오면 소스 시험이 실패한다(지금 `shell_contract.rs`의 `nothing_but_the_command_table_reaches_the_pty`를 칸 호스트 클라이언트까지 넓힌다).
  - PTY 명령 capability(`capabilities/pty.json`)는 main 웹뷰의 번들 출처에만 준다.
  - CSP는 번들 스크립트만 허용한다.
  - D3-f 로그인의 숨은 PTY는 이 단정의 예외 한 줄로 적는다.
- **crate와 칸 지기에는 새 단정을 더한다.** 제어 통로 밖의 입구가 없다. 네트워크가 없다(D4). 상태 신호(OSC 7501)를 읽는 곳은 전용 모듈 하나다(ADR-0190 D4-b-7501). 화면 모델은 그리기·스냅숏·제목·닫힌 목록 질의 응답에만 쓰고, 그 결과로 상태를 짐작하거나 앱 밖으로 내보내지 않는다. 소스 시험의 예외는 화면 모델 crate 한 곳으로 이름을 적는다.
- 화면 모델과 스크롤백은 칸 지기의 메모리에 있고 이 기기 밖으로 나가지 않는다(ADR-0190 D2). 칸 지기가 붙드는 칸은 웹뷰가 스크롤백을 localStorage에 두지 않는다. 다시 붙을 때 칸 지기가 첫 화면을 주기 때문이다. 그래서 미결 1을 정하기 전까지 그 칸의 디스크 사본은 0개다. 대체 모드의 칸은 지금(ADR-0190 D1)대로다.
- workd(A 레인)는 이 ADR 밖이다. 앱을 끄면 workd는 지금처럼 꺼진다(ADR-0188 D2).
- 앱은 「칸 호스트」 경계 하나로만 칸 지기와 말한다. 그래서 칸 지기를 다른 구현으로 바꿔 끼울 수 있다(D6).
- 지키는 경계: PTY로 가는 입구는 서명된 앱의 웹뷰 명령 표 하나다. 화면 글자는 기기 밖으로 나가지 않는다.

### D2. 앱을 꺼도 칸이 산다 — 기본 켬, 「앱 밖에서 도는 중」 표시, 끌 때 한 번 묻기
- 설정 「앱을 꺼도 터미널 유지」는 **기본 켬**이다. 끄면 앱이 끝날 때 모든 칸이 끝난다(지금과 같다). 칸 지기를 쓸 수 없으면(D3 끝) 이 설정은 꺼져 있고 바꿀 수 없다.
- 앱을 끌 때 도는 칸이 있으면 **한 번 묻는다.** 고를 것은 계속 두기와 모두 끝내기이고 기본은 계속 두기다. 업데이트도 앱을 끄는 일이라 같이 묻는다. 보안 고침이 든 업데이트에서는 기본이 모두 끝내기다(「업데이트 넘김」). oort에서 로그아웃하거나 계정을 바꿀 때도 같이 묻고, 그때도 기본은 모두 끝내기다. 문구는 디자인 검수가 정한다.
- 칸 목록에 **「앱 밖에서 도는 중」**을 표시한다. 앱을 꺼도 계속 도는 칸이라는 뜻이다. 앱을 다시 켜면 칸 지기에 다시 붙고, 그동안 돈 칸이 이 표시와 함께 목록에 돌아온다.
- 칸마다 그 칸을 연 oort 계정을 적어 둔다. 다른 계정으로 로그인한 앱에는 그 칸을 붙이지 않는다. 앞사람이 로그인해 둔 하네스에 다음 사람이 붙는 길을 막는다.
- 앱이 꺼진 동안 공유 요약(S1)은 갱신되지 않는다. 칸 지기는 서버와 말하지 않는다. 공유 카드는 마지막 업데이트 시각만 말하고 「진행 중」을 이어 주장하지 않는다(ADR-0220 P1).
- 칸이 하나도 없고 앱이 붙어 있지 않으면 칸 지기는 스스로 끝난다. 칸이 하나라도 있으면 칸 지기는 macOS 로그아웃이나 컴퓨터를 끌 때까지 산다. 앱을 지워도 칸이 끝날 때까지 남는다. 그때 칸을 스스로 끝낼지는 미결 4다.
- 지키는 경계: 사람이 모르는 채 도는 프로세스가 되지 않는다(표시·묻기·설정 셋이 함께 간다).

### D3. 제어 통로는 앱과 칸 지기만 쓴다 — XPC로 메시지마다 서명을 확인하고, 칸에는 자기 칸 신호 토큰만 준다
- **제어 통로는 XPC다.** 칸 지기는 앱이 SMAppService로 등록하는 launchd 에이전트이고, 이름 붙은 Mach 서비스 하나로만 말한다. 양쪽이 상대의 코드 서명 요건을 연결에 건다(`xpc_connection_set_peer_code_signing_requirement`). 칸 지기는 oort 앱의 요건을 걸고, 앱은 칸 지기 helper의 요건을 건다. 두 요건 모두 정확한 identifier와 우리 팀 ID를 고정한다(아래 「요건을 통째로 적는다」). 그래서 workd와 다른 팀의 프로그램은 어느 쪽 요건도 채우지 못하고, 앱은 칸 지기인 척할 수 없다. 확인은 커널이 메시지마다 붙이는, 보낸 쪽의 audit token으로 한다.
- **XPC를 고른 이유**(보안 검수 H1이 권한 두 안 중 (가), 자세한 근거는 검수 보고(비공개)):
  - Unix 소켓에서 접속 때 한 번 본 상대 정보는, 그 뒤 상대가 바뀌어도 다시 확인되지 않는다(macOS의 일반 동작). 그래서 메시지마다 그 메시지를 보낸 쪽을 확인하는 XPC를 쓴다.
  - 소켓 파일이 없어서 소켓 자리를 가로채는 길도 없다. 같은 Mach 서비스 이름을 다른 프로그램이 먼저 잡아도 앱 쪽 요건에 걸리고, 판 번호만 든 빈 인사 말고는 아무것도 나가지 않는다.
  - 다른 안((나): Unix 소켓 + 키체인 비밀로 서로 확인하는 인사 + 프레임마다 토큰 다시 맞춰 보기)은 프로파일이 필요한 키체인 접근 그룹과, 우리가 만들고 지켜야 하는 인사 규격이 더 든다. 같은 확인을 커널과 XPC가 해 주는 쪽을 골랐다.
- **요건을 통째로 적는다.** 두 방향 요건은 각각 한 문자열이고, 팀 값은 자기 서명에서 읽는다(지금 workd의 `app_requirement`와 같은 방식).
  - 칸 지기가 거는 앱 요건: `anchor apple generic and identifier "app.momo.desktop" and certificate leaf[subject.OU] = "<팀 ID>" and certificate 1[field.1.2.840.113635.100.6.2.6] exists and certificate leaf[field.1.2.840.113635.100.6.1.13] exists`
  - 앱이 거는 칸 지기 요건: 같은 모양이고, identifier만 칸 지기 helper의 것이다.
  - 요건은 연결마다 한 번만 걸 수 있어서 한 문자열로 합친다. 듣는 쪽은 받은 연결마다 활성화 전에 건다. 팀만 거는 전용 API(`xpc_connection_set_peer_team_identity_requirement`)는 macOS 14.4부터라, 앱 최소 판(14.0)에서는 팀을 문자열에 직접 적는다.
  - Developer ID 두 칸 때문에 같은 팀의 개발 인증서로 서명한 빌드는 통과하지 못한다. 강화 런타임과 위험 권한 셋(`get-task-allow`·`disable-library-validation`·`allow-dyld-environment-variables`)은 요건 문자열로 적을 수 없어서, 메시지마다 `SecCodeCreateWithXPCMessage`로 얻은 상대 코드에서 본다([확인 필요] macOS 14.0에서 도는지는 궤도-2가 확인한다). 빌드 검사가 칸 지기 helper와 앱 본체의 강화 런타임을 함께 확인한다(지금 workd 검사와 같은 모양).
- 붙어 있는 앱 연결은 하나뿐이다. 새 연결이 붙으면 옛 연결에 「다른 곳에서 붙었어요」를 보내고 끊는다.
- 앱은 칸 지기를 확인하기 전에는 아무 내용도 보내지 않는다. 첫 메시지는 판 번호만 든 빈 인사이고, 요건을 통과한 답을 받은 뒤에 환경·계정·칸 열기·키 입력을 보낸다. 다시 붙을 때마다 같다. 확인에 실패한 칸 지기를 만나면 새 칸 지기를 조용히 띄우지 않고 「확인할 수 없는 터미널 지기가 있어요」를 보인다.
- **칸의 환경에는 제어 통로의 이름도 확인 값도 넣지 않는다.** 칸에는 그 칸의 신호 토큰·칸 ID·신호 소켓 주소만 준다(지금 `pane_signal.rs`). 신호 소켓은 제어 통로와 다른 Unix 소켓이고, 그 칸의 토큰이 맞는 닫힌 신호 한 줄만 받는다.
- **칸 신호 토큰이 가르는 범위.** 칸 토큰은 다른 칸의 프로그램이 일부러 읽지 않는 한 칸을 가른다. 같은 사용자 프로그램은 다른 프로세스의 환경을 읽어 상태 신호를 꾸밀 수 있다(macOS에서 같은 uid 프로세스의 환경은 읽힌다). 신호는 「에이전트 보고」로만 쓰이므로 이 위험을 받아들인다. 화면을 읽거나 입력하는 길은 제어 통로에만 있고, 토큰으로는 열리지 않는다.
- 앱 바이너리의 보조 모드(훅 클라이언트 `--oort-pane-hook`)는 신호 소켓에만 쓴다. 제어 통로의 서비스 이름은 코드 안의 상수이고 칸 환경에서 오지 않는다. 그래서 칸 프로그램이 환경을 바꿔도 보조 모드를 제어 통로로 보낼 수 없다. 다만 칸 지기가 거는 앱 요건은 실행 파일의 서명을 보므로 같은 실행 파일의 모든 모드가 그 요건을 채운다. 그래서 칸 지기 통로 클라이언트에 닿는 것은 메인 앱 모드의 칸 호스트 클라이언트뿐이다. 보조 모드와 그 밖의 인자 입구에서 그 이름이 나오면 소스 시험이 실패한다(D1의 앱 쪽 단정과 같은 시험). 빌드 검사는 번들 안의 다른 실행 파일이 앱 identifier를 갖지 않음을 본다.
- **신호 소켓 자리.** 환경 변수(`$TMPDIR`)가 아니라 uid로 정해지는 자리에 0700으로 둔다(`confstr(_CS_DARWIN_USER_TEMP_DIR)` 아래 또는 `~/Library/Application Support/` 아래). 경로는 `sun_path` 한도(104바이트) 안이다. 칸 지기는 사는 동안 잠금 파일에 `flock`을 쥔다. 몇 분마다 그 경로가 아직 자기 소켓(inode)인지 보고, 아니면 앱에 알려 칸 목록에 보이게 한다.
- **칸 지기를 쓸 수 없을 때.** 서명으로 상대를 확인할 수 없는 빌드(서명 없음·ad-hoc)와, 사용자가 로그인 항목에서 백그라운드 실행을 끈 경우에는 launchd 에이전트를 쓰지 않는다. 「앱을 꺼도 터미널 유지」는 꺼지고 바꿀 수 없으며, 칸은 대체 모드로 연다(D1). 개발 빌드에서 칸 지기를 시험할 때는 앱의 자식으로 띄우고 물려준 연결 하나로만 말한다. 앱은 자기 자식(pid)에만 붙고, 앱이 끝나면 칸 지기도 끝난다. 개발 빌드와 배포 빌드는 다른 서비스 이름과 다른 신호 소켓 폴더를 쓴다. 개발 모드는 컴파일 때만 고르고, 배포 빌드에는 그 코드가 없다. 실행 때 깃발·환경 변수·설정 파일로 개발 모드나 다른 칸 지기 경로를 고르지 못하고, 칸 지기 실행 파일은 번들 안 고정 자리다.
- 지키는 경계: 칸끼리 서로의 화면을 읽거나 입력하지 못한다. herdr-core가 모든 칸에 서버 소켓을 주는 것과 다른 점이 이것이다.

### D4. 원격 입력·에이전트 입력·바깥 통신은 없다
- 칸 지기가 PTY에 쓰는 것은 두 가지뿐이다. 확인된 앱 연결로 온 사람 입력, 그리고 닫힌 목록의 질의에 대한 자동 응답이다. 서버·폰·다른 컴퓨터·에이전트(Agent Port 도구, workd, 칸 안의 다른 프로그램)가 칸에 입력하는 길은 없다.
- **질의 자동 응답.** 터미널 질의에 답하는 바이트는 사람 키가 아니라서 규칙을 따로 둔다. 같은 뜻을 #5586이 ADR-0190 증보로 지금 레인에 적는다.
  - **닫힌 목록의 질의에만 고정 바이트로 답한다.** 목록은 DA1·DA2·DSR 상태(`CSI 5 n`)·커서 위치 보고(`CSI 6 n`)·OSC 7501 지원 질의(#5586)다. 커서 위치 보고만 화면 모델이 센 행·열 숫자 둘을 담는다. 목록에 더하려면 이 ADR을 고친다.
  - **프로그램 출력의 값을 응답에 섞지 않는다.** 프로그램이 정한 글자를 돌려주는 질의에는 답하지 않는다: 창 제목·아이콘 이름 보고, DECRQSS, OSC 4·10·11·12 색 질의, OSC 52 읽기. 프로그램이 클립보드에 쓰는 OSC 52도 따르지 않는다. 터미널이 프로그램이 정한 글자를 셸 입력으로 돌려주면 명령이 된다(xterm 제목 보고 CVE-2003-0063부터 이어져 온 부류).
  - **사람 입력으로 세지 않는다.** 자동 응답은 OSC 7501 `done`·`error` 표시를 내리는 「사람의 키」가 아니고, ADR-0222 R2의 시계에도 들지 않는다.
  - **원격·에이전트 입력이 아니다.** 칸 지기가 자기 화면 모델로 만든 답이고, 어떤 통로로도 바깥에서 들어오지 않는다.
  - 자동 응답은 사람 입력과 같은 줄 상한을 따르고, 줄이 차면 버린다. OSC 7501 지원 질의에는 하네스 칸에서만 답한다(#5586과 같다).
  - 답하는 곳은 하나다. 칸 지기의 칸에서는 웹뷰의 터미널 그리기(xterm.js)가 질의에 답하지 않고, 앱 연결로 오는 것은 사람 입력뿐이다. 앱 안 레인(대체 모드 포함)은 궤도-1 전까지 ADR-0190의 질의 응답 증보(#5586: 목록은 OSC 7501 하나, 답은 상수)를 따른다. 궤도-1이 그 증보를 고치는 증보(목록 넓히기, 커서 위치 보고 예외, xterm.js 답 끄기)를 함께 낸다.
- 화면 글자를 읽어 내보내는 명령은 없다(ADR-0190 D4-b 「긁지 않는다」).
- **칸 지기는 바깥과 통신하지 않는다.** 서버·다른 컴퓨터·업데이트 서버에 연결하지 않고 TCP를 열지 않는다. 원격 컴퓨터·파일 명령은 없다(ADR-0188 D6). 공유 요약은 지금처럼 앱이 올린다(ADR-0190 D4, ADR-0222 D9).
- 「바깥 통신 없음」의 소스 시험은 칸 지기 바이너리의 의존 그래프까지 본다. 허용 목록 밖의 crate를 거절하고, `std::net`(TCP·UDP)과 바깥으로 나가는 소켓 연결이 없는지 보고, 링크된 심볼을 검사한다. 신호용 Unix 소켓을 듣는 코드 한 곳과 XPC는 이름을 적어 예외로 둔다. 샌드박스는 칸 프로그램에도 물려지므로 칸 지기를 샌드박스로 묶어 막을 수 없다. 그래서 이 시험이 유일한 막이다.
- 지키는 경계: 원격 셸 금지. 화면 글자는 기기 밖으로 나가지 않는다. 에이전트는 터미널을 조작하지 않는다.

### D5. 이벤트에는 순번·심장 박동·놓침 스냅숏을 두고, 앱이 없어도 출력을 막지 않는다
- 앱이 붙으면 칸 지기는 먼저 스냅숏(칸 목록, 칸마다 상태·크기·제목·첫 화면)을 보내고, 이어서 순번이 하나씩 오르는 이벤트를 보낸다.
- 이벤트가 없어도 심장 박동을 보낸다(**[추정]** 15초). 앱은 박동이 끊기면 다시 붙는다. 칸 지기는 앱이 떨어져도 칸을 끝내지 않는다.
- 앱이 뒤처지거나 순번이 비면 칸 지기가 「놓침」과 새 스냅숏을 보낸다. 앱은 잃은 이벤트를 찾지 않고 스냅숏으로 다시 맞춘다.
- **흐름 제어와 상한.** 앱이 붙어 있지 않으면 칸 지기는 출력을 계속 읽어 화면 모델에만 넣고, 원문 바이트는 쌓지 않는다. 그래서 앱이 없어도 칸 프로그램이 멈추지 않는다. `pty_ack`은 붙어 있는 앱 연결의 되밀기로만 쓴다. 상한을 둔다: 칸당 스크롤백 **[추정]** 5,000줄(지금 headless 미러와 같다), 칸 지기당 칸 **[추정]** 32개, 스냅숏 **[추정]** 칸당 4 MiB, 한 메시지 **[추정]** 1 MiB. 넘으면 오래된 줄부터 버리고 그 칸에 「앞부분을 버렸어요」를 보인다.
- 칸 상태는 OSC 7501과 훅을 합친 한 상태 기계에서 나오고 「에이전트 보고」로 표시한다. 서버가 확인한 사실과 섞지 않는다(ADR-0220 P1, ADR-0190 증보 2026-11-09). ADR-0222 R2의 시계 둘은 이 이벤트의 시각으로 센다.
- 지키는 경계: 상태는 프로그램이 알린 값만 쓴다. 신호가 없으면 상태를 짐작하지 않는다(ADR-0222 D12). 출력이 많은 칸 하나가 칸 지기를 메모리 부족으로 죽여 모든 칸을 끝내지 않는다.

### D6. herdr-core는 쓰지 않는다 — 칸별 인증이 생기면 다시 본다 (ADR-0154 D5-⑵ 갱신)
- herdr-core를 crate·바이너리·포크 어느 모양으로도 쓰지 않는다. 코드는 가져오지 않는다(클린룸). 같은 공개 규격(OSC 7501)을 쓰고, 공개 문서에서 생각만 빌린다(다시 붙을 때의 첫 화면, 흐름 제어, 순번과 놓침, 터미널 질의에 대한 자동 응답과 사람 입력의 구분).
- herdr-core 새 판의 바뀐 기록은 승격 주기마다 한 번 훑는다. 칸별 인증(칸마다 다른 권한)이 들어오면 칸 지기 자리에 hc를 꽂는 시험을 다시 연다. 앱이 「칸 호스트」 경계 하나로만 말하므로(D1) 그때 바꿔 끼울 수 있다.
- ADR-0154 D5-⑵(「herdr = 워커 호스트 런타임 실험, 실행만, 버전 핀」)는 「oort 칸 코어(궤도)」로 갱신한다.

## 프로세스 계약 스케치

숫자는 **[추정]**이고 구현이 확정한다.

### 수명
- **시작**: 앱이 칸을 처음 열 때 칸 지기 에이전트를 SMAppService로 한 번 등록하고 XPC로 붙는다. 붙으면 launchd가 칸 지기를 띄운다. Mach 서비스 이름이 하나라 로그인한 사용자마다 칸 지기는 하나다. macOS는 등록 때 백그라운드 실행 알림을 보이고, 사용자는 로그인 항목에서 끌 수 있다. 끄면 대체 모드다(D3 끝).
- **붙기**: 앱은 시작할 때 XPC로 붙는다. 첫 메시지는 판 번호만 든 빈 인사다(D3). 서명 요건을 통과한 답을 받은 뒤 프로토콜 판과 양쪽의 「안전한 가장 낮은 판」을 맞추고(「업데이트 넘김」) 스냅숏을 받는다(D3·D5).
- **떼기**: 앱이 끝나면 연결이 닫힌다. 설정이 켬이고 사람이 계속 두기를 고르면 칸 지기는 칸을 붙든 채 남는다. 설정이 끔이거나 모두 끝내기를 고르면 앱이 끝나기 전에 모두 끝내기를 보내고, 칸 지기는 칸을 끝낸 뒤 스스로 끝난다.
- **끝**: 칸이 없고 앱이 붙어 있지 않으면 **[추정]** 60초 뒤 스스로 끝난다. 칸을 끝내는 순서는 지금 `kill_all`과 같다(프로세스 그룹에 SIGHUP, 짧게 기다린 뒤 남은 것에 SIGKILL). 칸 지기는 자기 번들이 디스크에서 사라지거나 자기 서명이 맞지 않게 되면 새 연결을 받지 않는다(업데이트로 번들이 같은 서명 요건을 채우는 새 판으로 바뀐 것은 여기에 들지 않는다, 「업데이트 넘김」). 그때 칸을 스스로 끝낼지는 미결 4다.

### 통로·칸 열기·칸별 토큰
- 제어 통로는 XPC 메시지다. 메시지마다 크기 상한이 있고 모르는 필드는 거절한다. TCP는 루프백도 없다.
- **칸 열기 요청은 하네스 종류·폴더·프로필 라벨만 싣는다.** argv와 환경은 칸 지기가 허용목록과 `STRIPPED_ENV`로 만든다(ADR-0190 D3-c의 「명령 번호만」과 같은 모양). 칸 환경의 바탕은 칸 지기가 물려받은 환경(launchd가 준 것)이 아니라, 앱이 칸 지기를 확인한 뒤 넘긴 환경이다. 서명된 칸 지기는 모르는 argv와 디버그·로그 환경 변수를 받지 않는다.
- 칸 지기의 로그(stderr·os_log)에는 화면 글자·입력 바이트·환경 값이 없다. 시험으로 확인한다.
- **칸에 물려주는 fd.** 칸 지기가 칸을 띄울 때 자식에게 남는 fd는 0·1·2(그 칸의 tty)뿐이다. 다른 칸의 PTY 마스터, 신호 소켓(듣는 것과 붙은 것), 잠금 파일은 CLOEXEC로 두고 띄울 때 한 번 더 닫는다. 칸 지기는 받은 연결을 다른 프로세스에 넘기지 않는다. 지금은 `portable-pty`가 자식 쪽에서 3번 이상의 fd를 닫아 지키는데, 화면 모델 crate의 다른 띄우기 길로 바꿔도 이 규칙은 같다.
- 칸을 열 때마다 무작위 토큰을 만든다. 칸 환경에는 그 칸의 토큰·칸 ID·신호 소켓 주소만 넣고, 계정 변수는 뺀다(ADR-0191 D2). 칸이 끝나면 토큰을 버리므로 끝난 칸의 늦은 신호는 아무 데도 가지 않는다.

### 이벤트
- 순번은 칸 지기 안에서 하나씩 오른다. 칸 지기가 새로 뜨면 세대 번호가 바뀌고, 앱은 세대가 다른 순번을 섞지 않는다.
- 이벤트 종류는 닫힌 목록이다: 생김 · 끝남(끝난 이유: 프로그램이 끝남·사람이 끝냄·칸 지기가 끝남) · 상태 · 제목 · 크기 · 앞부분 버림.
- 흐름 제어와 상한은 D5다.

### 업데이트 넘김
- 칸 지기는 앱 번들 안에 있고 스스로 갱신하지 않는다. 앱이 업데이트돼도 도는 칸 지기는 옛 판으로 남아 칸을 붙든다.
- 새 앱은 인사에서 판을 맞춘다. 새 앱은 지금 판과 직전 판(**[추정]** 한 판 뒤까지)의 칸 지기와 말한다.
- **안전한 가장 낮은 판.** 인사에 「안전한 가장 낮은 칸 지기 판」을 싣는다. 앱은 그보다 낮은 칸 지기에는 입력을 보내지 않고 최소 명령만 쓴다. 칸 목록에는 「보안 고침이 든 업데이트예요. 터미널을 다시 열어야 적용돼요」를 보인다. 보안 고침이 든 업데이트에서는 끌 때 묻는 창의 기본이 모두 끝내기다(D2). 칸 지기도 「안전한 가장 낮은 앱 판」을 갖고, 그보다 낮은 앱의 인사는 거절한다. 거절당한 앱은 「업데이트가 필요해요」를 보인다.
- 판이 달라도 바뀌지 않는 최소 명령을 둔다: 칸 목록 · 칸 끝내기 · 칸 지기 끝내기. 맞지 않는 판이면 앱은 칸을 「업데이트 전 터미널」로 보이고 최소 명령만 쓴다.
- 마지막 칸이 끝나면 옛 칸 지기도 끝나고, 다음 칸은 새 판 칸 지기로 뜬다.
- [확인 필요] 업데이트가 번들을 새 파일로 바꿔 끼우는지(같은 파일을 덮어쓰면 도는 칸 지기가 코드 서명 검사로 죽을 수 있다)와, 새 앱의 XPC 요건이 옛 판 칸 지기를 받아들이는지는 궤도-3이 공증 판 둘로 확인한다. 둘 중 하나라도 안 되면 업데이트 전에 「터미널이 끝나요」로 묻는다. 칸이 말없이 사라지는 일은 없게 한다.

### 결코 범위에 들지 않는 것
원격 컴퓨터와 원격 셸(`machine.*`) · 파일 읽기·쓰기 명령(`file.*`) · 화면 글자를 읽어 내보내는 명령(`read`) · 에이전트·서버·폰·다른 칸·보는 사람의 입력(`send`·`keys`·`wait`) · 프로그램이 정한 글자를 돌려주는 질의 응답과 OSC 52 · 문서 저장(`doc.*`) · TCP와 바깥 통신 · 스스로 갱신 · 칸끼리 서로 보기 · A 레인 세션(workd) · 칸 배치(탭과 분할은 웹이 그린다).

## 위협과 방어
- **칸끼리 조작**: 칸 환경에 제어 통로가 없고, 신호 소켓은 그 칸의 토큰이 맞는 닫힌 신호만 받는다(D3). 같은 사용자 프로그램이 환경을 읽어 다른 칸의 상태 신호를 꾸미는 것은 받아들인 위험이다. 바뀌는 것은 「에이전트 보고」뿐이다.
- **접속 뒤 바뀌는 상대**: 메시지마다 보낸 쪽의 서명을 확인한다(D3).
- **가짜 칸 지기**: 소켓 파일이 없다. 같은 서비스 이름을 먼저 잡은 프로그램은 앱 쪽 요건에 걸린다. 앱은 칸 지기를 확인하기 전에는 빈 인사 말고는 보내지 않고, 확인에 실패하면 새 칸 지기를 조용히 띄우지 않는다(D3).
- **개발 서명 빌드와 주입**: 요건을 Developer ID로 좁히고 상대의 강화 런타임과 위험 권한을 본다. 빌드 검사가 helper와 앱 본체를 함께 본다(D3).
- **칸 지기 환경 꾸미기**: 칸 환경의 바탕은 앱이 칸 지기를 확인한 뒤 넘긴 환경이고, 칸 지기는 모르는 argv·디버그 환경 변수를 받지 않는다(「통로·칸 열기·칸별 토큰」).
- **질의 답 되비추기**: 닫힌 목록에만 고정 바이트로 답하고 프로그램이 정한 글자를 돌려주지 않는다(D4).
- **fd 새기**: 칸에는 0·1·2만 남는다(「통로·칸 열기·칸별 토큰」).
- **메모리에서 화면 읽기**: 칸 지기는 강화 런타임으로 서명하고 `get-task-allow`를 주지 않는다. 빌드 검사가 확인한다(D3).
- **출력 폭주**: 상한을 두고 오래된 줄부터 버린다(D5).
- **옛 판 칸 지기**: 안전한 가장 낮은 판보다 낮으면 입력을 보내지 않는다(「업데이트 넘김」).
- **다른 계정이 남은 칸에 붙기**: 칸마다 연 계정을 적고 다른 계정의 앱에는 붙이지 않으며, 로그아웃·계정 바꾸기 때 묻는다(D2).
- **칸 지기 끄기(남는 위험)**: 같은 사용자의 프로그램이 OS 신호로 칸 지기를 끝내는 것은 막지 못한다. 그러면 칸이 끝나고, 앱은 칸이 끝났다는 사실만 보인다. 화면을 읽거나 입력하는 길은 아니다.
- **모르는 채 남는 프로세스**: 기본 켬이어도 끌 때 묻고, 칸 목록에 표시하고, 설정으로 끈다(D2). [확인 필요] launchd가 띄운 칸 지기와 그 칸들이 앱의 TCC 허락(마이크 등)을 물려받는지, 앱이 꺼진 뒤에도 그런지는 궤도-3이 확인한다.
- **범위 밖**: workd 제어 소켓도 같은 확인 방식(메시지마다 서명 확인)으로 옮긴다 — #5619.

## 결과
- (+) 앱을 껐다 켜거나 업데이트해도 Claude Code·Codex 세션과 화면이 그대로다.
- (+) 칸별 토큰 경계를 지키고, herdr-core의 가장 큰 위험(칸끼리 조작)을 들이지 않는다.
- (+) 제어 통로의 상대 확인을 메시지마다 커널 값으로 하고 소켓 파일이 없어서, 통로 상대를 속이는 부류가 구조로 닫힌다.
- (+) 상태 기계와 이벤트 순번이 crate 하나에 모여, 화면은 한 곳의 낱말을 쓴다.
- (−) 우리 코드라 품이 크다(5~7주에 XPC·launchd 등록이 더해진다). herdr-core의 새 기능은 생각만 빌려 다시 만들어야 한다.
- (−) 앱 밖에서 도는 프로세스가 하나 는다. 표시·묻기·설정을 함께 지켜야 하고, 사용자는 로그인 항목에서 칸 지기를 볼 수 있다.
- (−) 같은 사용자의 프로그램이 칸 지기를 OS 신호로 끄는 것과, 환경을 읽어 상태 신호를 꾸미는 것은 막지 못한다.
- (−) 업데이트 뒤 옛 판 칸 지기와 새 앱이 함께 도는 기간이 생겨서 프로토콜 판을 둘 맞춰야 한다.

## 미결
1. **칸 지기의 화면을 디스크에 둘지.** 지금 결정은 메모리뿐이라 칸 지기가 끝나면 화면도 끝난다. 칸 지기가 붙드는 칸은 웹뷰의 localStorage 사본도 두지 않으므로 디스크 사본은 0개다(D1). 디스크에 두려면 0700 폴더, 보존 기한, 비밀 경고가 함께 필요하다.
2. **컴퓨터를 다시 켠 뒤 칸 되살리기(셸로).** 이번에 정하지 않았다. 칸 코어 메모의 추천은 「되살려도 원래 명령은 다시 돌리지 않는다」다.
3. **끌 때 묻는 창에 「다시 묻지 않기」를 둘지.** 디자인 검수가 정한다.
4. **앱이 지워졌거나 오래 붙지 않을 때 칸을 스스로 끝낼지.** 보안 검수 1회차 L4는 번들이 사라지면 **[추정]** N분 뒤, 앱이 붙지 않은 채 **[추정]** 7일 뒤 칸을 끝내자고 권했다. 사람이 돌린 프로그램을 끝내는 일이라 이 ADR은 정하지 않았다. 정하기 전까지 칸 지기는 새 연결만 받지 않는다(「수명」).
