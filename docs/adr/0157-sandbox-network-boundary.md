# ADR-0157 — 샌드박스 네트워크 경계: 여러 팀에게 "안전한"을 팔기 위한 나머지 절반

- Status: **Accepted** (기안 2026-08-08 Fable · 성재 승인 2026-08-09)
- 관련: ADR-0156(D5 — CubeProxy/CubeEgress 유보) · ADR-0150(대화 유출 경계 — Proposed) · ADR-0144(샌드박스 자격증명=파일시스템 로컬) · `research/2026-08-08-cubesandbox-requirements-adapter-mapping.md`(CubeNet CIDR·CubeAPI 무인증 실측)

## Context

CubeSandbox 채택(ADR-0156)으로 **컴퓨트 격리**(팀별 전용 커널 microVM)는 섰다. 그러나 "여러 팀에 격리된 샌드박스를 제공하는 안전한 AI native sandbox"(2026-08-08 성재 발제)의 나머지 절반은 **네트워크 경계**다: VM 경계가 아무리 강해도 같은 호스트의 샌드박스들이 서로에게, 또는 momo 내부망(PG·API 내부 포트)에 네트워크로 닿으면 팀 격리는 광고문이 된다. 실측 근거: CubeNet 기본 CIDR `192.168.0.0/18`(전 샌드박스가 한 대역), CubeAPI 기본 무인증.

## Decision (Proposed 권고안)

1. **D1 — 샌드박스 → momo 내부망 기본 차단.** 샌드박스가 닿을 수 있는 momo 표면은 **공개 REST(HTTPS, app 도메인)뿐** — workd가 쓰는 것과 동일한 문(등록·컨트롤 폴링·메시지 API). PG·Centrifugo 내부 포트·CubeAPI·호스트 메타데이터(169.254.0.0/16)는 호스트 레벨에서 차단. 근거: 단일 쓰기경로 불변식의 네트워크 판 — 문이 하나면 감사도 하나다.
2. **D2 — 샌드박스 ↔ 샌드박스 기본 차단.** 팀 간은 물론 같은 팀 내에서도 기본 차단(세션 간 협업이 필요해지면 그때 명시 허용을 별건 결정 — 지금 수요 0). 격리의 네트워크 절반.
3. **D3 — 인터넷 egress는 v0 허용 + 정직한 명제.** 개발 세션은 패키지 설치·git·API 호출이 본질이라 egress 차단은 제품을 부순다. 대신 ADR-0150과의 관계를 명제로 고정: **"샌드박스에 주입된 컨텍스트는 유출 가능하다고 간주한다"** — 통제 지점은 egress 필터가 아니라 ①무엇을 주입하는가(컨텍스트 최소 주입 — 세션 스레드 요약만, 채널 전체 히스토리 금지) ②승인 게이트(도구 실행 전 사람 승인 — 기구축). 도메인 allowlist류 egress 필터는 유료 팀 수요가 실증되면 CubeEgress 유보 해제로 후속(v1).
4. **D4 — 구현 기제는 D4-② 실기동에서 실측 후 선택**: CubeNet 설정으로 충분한가 vs 호스트 nftables 선언인가 vs CubeEgress 부속 일부 해제인가. 어느 쪽이든 규칙은 **호스트에 선언적 파일로**(레포 관리·리뷰 가능) — 런타임 API로 심는 규칙 금지.
5. **D5 — CubeAPI 비노출 성문화**: CubeAPI는 루프백/내부 전용 + `AUTH_CALLBACK_URL`로 momo가 인증 주체(D4-① 발견). 공인 IP 바인딩 금지를 설치 런북의 검증 항목으로.

## Slack·업계 비교

E2B·Modal은 관리형이라 이 경계를 provider가 소유한다 — self-host의 대가로 우리가 소유하게 된 결정이다. Codex Cloud의 2-phase(시크릿 수명 분리)와 우리 D3의 "주입 최소화"는 같은 통찰: **egress를 막으려 하지 말고 들어가는 것을 줄여라.**

## Consequences

- D4-② 실기동 티켓에 네트워크 기제 실측 항목 추가(어느 층에서 D1/D2가 성립하는가).
- 설치 런북(전용 호스트)에 D5 검증 항목.
- ADR-0150(대화 유출 경계)이 Accepted 되면 D3의 주입 최소화 조항과 상호 참조.

## 증보 1 — D4 답: 기제 선택이 아니라 기대값 검증 (2026-08-09 실측)

D4는 세 후보(CubeNet 설정 / 호스트 nftables / CubeEgress 해제) 중 하나를 고르라 했으나 **실측 결과 어느 것도 아니다**: Cubelet 내장 eBPF `deny_out`이 **기본값으로 D1·D2·D3를 이미 만족**한다(모든 tap에 `10/8`·`127/8`·`169.254/16`·`172.16/12`·`192.168/16` 거부 — D2는 양성 대조로 검증: 호스트는 피어 리스너에 200, 이웃 샌드박스만 차단). 따라서 **D4를 "기제 선택"에서 "기대값 검증"으로 재정의**한다 — 설치 런북에 `cubevsmapdump` 기반 게이트를 두어 그 기본값이 우리가 믿는 그대로인지 배포마다 확인한다(기본값 신뢰가 아니라 계약화).

**추가 발견(ADR-0150 입력)**: 템플릿 빌드가 **CubeEgress MITM 루트 CA를 기본으로 rootfs에 굽는다** — `--with-cube-ca=false`로 꺼야 한다. 우리가 쓰지 않는 컴포넌트의 신뢰 앵커가 샌드박스에 심기는 것은 D3(주입 최소화) 정신과 충돌한다.

## 증보 2 (Accepted — 성재 승인 2026-08-17 "0156-4·0157-2 승인") — 부트스트랩 배달 포트와, CubeProxy가 무인증으로 여는 문 (2026-08-16, #1437)

> 기안 2026-08-16. ADR-0156 증보 4(초안)가 도입하는 게스트 내 수신 포트 `49983`의 경계 판정. 실측: momo-cube-host, CubeSandbox v0.6.0.

ADR-0156 증보 4는 momo 템플릿에 **게스트 안에서 듣는 포트**를 하나 신설한다(`:49983`, Cubelet이 create 중 부트스트랩 자격을 배달하는 곳). 새 리스너는 경계 진술을 요구한다 — 어깨를 으쓱하고 넘어갈 항목이 아니다.

**D1/D2는 이 포트에서도 성립한다(실측).** 이웃 샌드박스에서 측정: 피어의 `49983` · 피어의 노출 포트 · 호스트 CubeAPI(`10.0.1.7:3000`) · 호스트 CubeProxy(`10.0.1.7:80`·`:443`) 전부 `errno=111 REFUSED`. 호스트 공인 IP는 80/443이 **timeout**(firewalld), 8443만 CONNECTED(우리 display 프록시 — 49983으로 라우팅하지 않는다). 증보 1의 Cubelet eBPF `deny_out` 기본값이 여기서도 그대로 일한다.

**동시에, 새로 이름 붙여야 하는 문이 하나 있다.** CubeProxy는 `0.0.0.0:80`·`0.0.0.0:443`에서 듣고 **`/sandbox/<sandboxID>/<port>/`를 무인증으로 라우팅**하며, `request_host.lua`가 **envd 포트(49983)를 이름으로 예외 처리**한다 — 즉 CubeProxy에 닿을 수 있고 sandboxID를 아는 자는 임의 샌드박스의 제어 포트에 POST할 수 있다(호스트 로컬에서 실증: 200). 따라서:

1. **호스트의 80/443이 인터넷에 닫혀 있는 것은 위생이 아니라 보안 통제다.** INFRA-A 런북의 F1 firewalld 규칙(public 존 = 8443 + 운영자 IP의 22, 2줄)이 인터넷과 모든 샌드박스의 제어 포트 사이에 서 있는 유일한 것이다. 설치 런북의 검증 항목으로 승격한다(D5의 CubeAPI 비노출 검증과 같은 급).
2. **1회용 수신기가 2층이다.** `momo-bootstrap-init`은 첫 배달 후 소켓을 닫고 다시 열지 않는다(실측: 이후 POST는 TCP refused, pause/resume 후에도 동일). sandboxID가 substrate 밖에서 알려질 수 있는 시점에는 create가 이미 반환됐고 포트는 닫혀 있다.
3. **D5 확장**: "CubeAPI는 루프백/내부 전용"에 **CubeProxy도 같은 문장으로** 포함한다. CubeProxy를 외부에 노출하는 구성은 이 ADR 위반이며, 필요해지면 별건 결정이다.

**D3 재확인**: 배달되는 것은 여전히 최소다 — server URL·workspace id·display name·1회용 등록 토큰 4개뿐이고 provider 운영자 자격은 포함되지 않는다(ADR-0004, conformance가 단정). "주입된 것은 유출 가능하다고 간주한다"는 명제는 그대로이며, 토큰이 프로세스 환경이 아니라 0600 파일로 착지하는 것은 그 명제를 반증하려는 시도가 아니라 **읽기 표면을 좁히는** 조치다.

**미측정으로 남기는 것**: 게스트→호스트 UDP 헤어핀(런북 §8-B와 동일 사유 — ACG UDP 규칙 부재). 이 증보의 판정에는 영향이 없다.
