## 배경

### 지금 있는 것 [V]
- 「작업」 화면은 결과 중심 한 화면이고, 줄 하나는 맡긴 일 하나(run 또는 작업 세션)다(ADR-0202 D1·D3). run에는 요청한 사람 칸이 없어 감사 행 `agent.work.queued`나 트리거 메시지 작성자에서 거꾸로 읽는다(ADR-0202 맥락). 담당자와 진행을 따로 적는 개체가 없다.
- run 원장(`agent_run_event`, ADR-0200 D2)은 서버가 쓴다. 에이전트가 알린 활동·계획은 「에이전트 보고」로 최신 창을 굴리고, 생각 글은 저장하지 않는다(ADR-0200 증보 7-4·7-6).
- 승인 카드는 채널과 인박스에 있고 한 번 누르면 결정된다(ADR-0186, #3829). 질문에는 구조 통로가 없어서 에이전트가 사람을 멘션한 글이 대신한다(ADR-0220 P2 ②의 전환기 예외). 「작업」 화면은 승인 단추를 따로 갖지 않는다(ADR-0202 D1).
- 팀 보기에는 내가 멤버인 채널의 일만 보이고, 볼 수 없는 일은 숫자도 없다. 사람별 활동 타임라인과 「지금 누가 무엇을 하는지」 판은 없다(ADR-0202 D2·D5).
- 로컬 터미널은 공유를 켜야 S1(이름·저장소·브랜치·폴더 이름·하네스·상태·단계 표지·diff 숫자·PR URL·마지막 활동 시각)만 서버에 올리고, 화면 글자는 긁지 않는다(ADR-0190 D4-b). 오늘 OSC 7501 상태 보고가 허용 출처가 됐다(같은 ADR 증보 2026-11-09, 구현 #5579 진행 중). 팀원 터미널 화면 보기는 목표 A 뒤다(ADR-0190 D6).
- GitHub 앱은 읽기 권한 다섯 줄이라 배포·Actions·status 사건을 받지 않는다(ADR-0205 D6).
- 에이전트가 스스로 내 맥의 Claude Code·Codex를 여는 길은 설계로 막혀 있다(ADR-0188 §3, ADR-0198 D6). 사람이 `@별칭`이나 폰 「내 맥에 보내기」로 시키는 A 레인은 코드가 있지만 실기기 왕복을 확인한 기록이 없다(A 레인 코드 감사, M7-I I-8 #5327).

### 바라는 것
요구는 머리에 옮긴 owner 원문 그대로다. 내 일을 누가 가져갔는지, 팀의 일이 어떻게 나뉘고 어디까지 갔는지 알고 싶다. 남의 일은 읽기만으로 따라가고, 부품끼리는 느슨하게 잇는다. 개발자가 아닌 사람도 읽을 수 있는 말을 쓴다. 그리고 오케스트레이터가 누구인지, 하위 작업이 동시에·차례로 몇 개인지, 담당자가 누구인지, 얼마나 걸렸는지를 한눈에 본다.

## 결정

### D1. 이름과 경계 — 궤도·원장·별자리는 서로 직접 부르지 않는다
- 이름은 셋이다. **궤도**(Orbit)는 터미널 칸 코어다(ADR-0223). **원장**(Ledger)은 작업과 진행 기록이다(D2·D3). **별자리**(Constellation)는 오케스트레이터 뷰다. 작업 하나 안에서 누가 지휘하는지, 하위 작업이 동시에·차례로 몇 개인지, 담당자가 누구인지, 얼마나 걸렸는지를 한 화면에 그린다.
- 코드 이름은 지금 규칙대로 `momo-` 접두를 쓴다(예: `momo-orbit`).
- 셋은 서로의 저장소나 프로세스를 직접 읽지 않는다. 잇는 것은 원장의 기록과 ID(작업 ID·하위 작업 ID·터미널 세션 ID)뿐이다. 원장은 터미널 화면을 모르고, 궤도는 작업의 내용을 모른다. 궤도에서 원장으로 가는 것은 공유 요약의 작업 번호 한 칸과 상태 낱말뿐이다(D5). 그래서 칸 코어를 바꿔 끼워도 원장은 바뀌지 않는다.
- 별자리는 원장을 읽기만 한다. 서버가 아는 하위 작업(`agent_run`·`work_session`)과 그 원장 줄로 그리고, 오케스트레이터가 알린 계획·단계는 「에이전트 보고」로 그린다. 하위 작업을 오케스트레이터 아래에 묶는 근거는 지금 있는 `agent_run.parent_run_id`(깊이 4 이하, ADR-0132 D3)와 작업 ID다. 맡기기 자체를 서버 사실로 남기는 길은 이 ADR이 정하지 않는다(미결 1). 보이는 범위는 R3가 화면에 적는다.
- 지키는 경계: 한 부품의 고장이나 교체가 다른 부품의 데이터 계약을 바꾸지 않는다. 별자리는 원장의 가시성(D2)을 넓히지 않는다.

### D2. 「작업」은 oort 안의 가벼운 항목이다
- 작업은 워크스페이스마다 1부터 오르는 **작업 번호**(#142), 제목, **집 채널**을 갖는다. 보이는 범위는 집 채널의 활성 멤버다(ADR-0202 D2·ADR-0194 D5와 같은 가시성). 볼 수 없는 작업은 제목도 숫자도 나오지 않는다.
- 칸은 넷이다.
  - **담당자**: 책임지는 사람. **사람만** 된다. 앱 검사만이 아니라 DB가 막는다(데이터 계약). 비울 수 없고, 바꿀 때도 사람으로만 바꾼다. 작업은 지금 사람만 만들므로(데이터 계약, 미결 6) 만들 때의 기본값은 만드는 사람이다.
  - **진행**: 지금 그 일을 하는 사람이나 에이전트다. 비어 있으면 「대기 중」이다. 진행이 바뀌면 진행 기록에 행동 줄이 남는다(D3).
  - **요청한 사람**: 이 작업을 청한 멤버. 서버가 만들 때 적고 바꾸지 않는다. 사람이나 에이전트다.
  - **대신한 사람**: 진행이 누구의 요청으로 일하는지. 화면의 「○○ 님 요청으로」의 ○○이고 **사람만** 된다. 요청한 사람이 사람이면 같은 사람이다. 오케스트레이터 에이전트가 청했으면 그 오케스트레이터에게 일을 맡긴 사람이다. 서버가 요청의 출처(트리거 메시지·맡김 기록)에서 정하고, 에이전트가 고쳐 쓰지 못한다.
- **하위 작업**은 작업에 연결된 `agent_run`·`work_session`이다. 둘에 작업 ID 칸을 더하고, run에는 요청한 사람·대신한 사람을 정식 칸으로 둔다. 자식 run은 부모의 작업 ID를 물려받는다(서버가 만들 때 쓴다).
- **GitHub·Linear 이슈는 링크로 붙는다.** 바깥 이슈는 정본이 아니다. 링크의 상태는 누가 알렸는지(에이전트 보고 또는 GitHub 기준)와 함께 둔다(데이터 계약 「링크」). 바깥 이슈를 고치거나 닫는 쓰기는 없다.
- 작업의 상태 낱말(내 확인 필요·문제 있음·진행 중·대기 중·최근 완료)은 서버가 하위 작업·카드·링크에서 정해 내려 준다. 클라이언트는 짐작하지 않는다(ADR-0200 D1과 같은 방식). 상태 낱말은 출처가 `server`·`external`인 값으로만 정한다. 출처가 `agent`인 값 때문에 바뀌는 낱말(예: 에이전트가 알린 「합쳐짐」·「배포됨」)에는 「에이전트 보고」를 붙인다.
- 지키는 경계: 책임은 늘 사람에게 있다. 에이전트는 진행이 되어도 새 권한을 얻지 않는다(호출 권한과 채널 접근은 그대로다). 대신한 사람은 서버가 정하므로 에이전트가 남의 이름을 빌려 「○○ 님 요청으로」를 만들 수 없다.

### D3. 진행 기록 — 종류는 Linear와 맞추고, 줄마다 출처와 중간 과정 칸을 둔다 (ADR-0200 증보)
- 진행 기록의 종류는 Linear 에이전트 활동과 같다: **사람의 말**(`prompt`) · **생각**(`thought`) · **행동**(`action`) · **질문**(`elicitation`) · **답**(`response`) · **오류**(`error`). DB 값은 Linear 토큰을 그대로 쓰고, 화면 낱말은 i18n 사전이 맡는다(ADR-0200 7-1 관례). 바깥 연동이 번역 없이 된다.
- 줄마다 **출처** 칸을 둔다: `server`(서버가 확인한 사실) · `agent`(에이전트나 터미널 프로그램이 알린 값) · `human`(사람이 쓴 글) · `external`(GitHub이 서명해 보낸 사건). 화면은 낱말표대로 그린다. 서버가 확인한 값은 표시 없이 쓰고, 에이전트 보고에만 「에이전트 보고」, GitHub에서 온 값에만 「GitHub 기준」을 붙인다. 출처가 다른 두 값을 한 줄에서 한 사실처럼 섞지 않는다(ADR-0220 P1). 서버 사실을 표시 없이 그리는 이 규칙과 ADR-0220 P1 시험 줄(모든 문구에 출처 표지)의 관계는 미결 11이다.
- **출처를 모르는 값**(칸이 없거나 모르는 값)은 「에이전트 보고」로 그린다. 표시가 없으면 서버 사실로 읽히므로, 출처를 모를 때는 약한 쪽으로 그린다. 미결 11과 따로 지금 정한다. 시험: 출처 없는 값이 표시 없이 그려지면 실패한다.
- 줄마다 **중간 과정** 칸을 둔다. 중간 과정은 기본으로 접혀 「중간 과정 n개 펼치기」로 보인다. 남기는 기록(맡김·가져감·질문·결정·답·오류)은 늘 보인다. run 원장 줄을 지우는 규칙은 지금 그대로다(ADR-0200 D2·T3·7-6). 큰 줄기는 서버가 확인한 사실을 남기고 에이전트 보고는 최신 창을 굴리는 것이다. 새 작업 원장의 규칙은 데이터 계약에 적었다.
- 덧붙이기만 한다. 고칠 일이 있으면 새 줄을 쓰고 고친 줄을 가리킨다.
- 사람의 말은 사람만 만든다. 에이전트 bearer로 들어온 줄의 출처는 서버가 `agent`로 정하고, 요청이 출처를 고르지 못한다.
- 생각은 어휘에 있지만 ADR-0200 증보 7-4(생각 글은 저장하지 않는다)를 바꾸지 않는다. 생각 줄은 늘 중간 과정이다. 생각 줄에 글을 실을지는 미결 2다.
- 하위 작업의 run 원장(`agent_run_event`)은 그대로 두고 복사하지 않는다. run 원장의 종류마다 아래 대응을 서버 읽기 한 곳에 두고, 작업 화면과 내보내기는 두 원장을 시간순으로 합쳐 같은 모양으로 그린다. **[추정]** 대응표이고, 구현이 바꾸면 이 표를 고친다.

| run 원장 종류 (ADR-0200) | 진행 기록 종류 | 출처 | 중간 과정 |
|---|---|---|---|
| `queued`·`claimed`·`started`·`paused`·`resumed`·`cancelled` | 행동 | `server` | 아니요 |
| `stage`·`activity` | 행동 | `agent` | 예 |
| `tool_call`·`doorbell_rung` | 행동 | `server` | 예 |
| `approval_requested` | 질문 | `agent` | 아니요 |
| `approval_decided`(승인·거부) | 사람의 말 | `server` | 아니요 |
| `approval_decided`(만료·취소) | 행동 | `server` | 아니요 |
| `succeeded` | 답(결과 칸은 「에이전트 보고」, ADR-0202 D1) | `server` | 아니요 |
| `failed`·`timed_out` | 오류 | `server` | 아니요 |
| `plan` | 줄이 아니라 하위 작업의 계획 칸 | `agent` | — |

- 지키는 경계: 출처 칸이 빈 줄은 없다. 진행 기록은 그 작업을 볼 수 있는 사람만 읽는다. 「작업」 목록에는 남의 하위 작업 단계·행동을 흘리지 않는다(ADR-0202 D5 「세밀 추적 없음」 그대로). 에이전트가 쓴 글은 믿지 않는 일반 텍스트로 그린다(ADR-0200 7-3).

### D4. 승인과 질문은 한 카드 틀이다 (ADR-0186·ADR-0220 P2 ②·ADR-0202 D1 증보)
- **질문은 승인 카드와 같은 틀이다.** 받는 사람 한정, 선택지와 직접 쓰기(선택지를 강요하지 않는다), 기한, 결과(답함·거부·만료). 되돌릴 수 없는 일이면 카드 맨 위에 적는다(ADR-0220 P7). 이것이 ADR-0220 P2 ②(질문)의 구조 통로다. 전환기 예외(사람 멘션을 질문으로 인정)를 언제 끝낼지는 정하지 않는다(미결 9).
- 질문을 받고 답하는 것은 그 작업의 집 채널 활성 **사람** 멤버뿐이다(승인과 같다). 에이전트는 질문에 답하지 못한다. 그 안에서 누구에게 먼저 가는지만 미결 4다. 질문 알림은 P2 ②의 사유이고 받는 사람에게만 간다(ADR-0220 P3).
- **결정 행은 하나다.** 「작업」 화면과 폰 시트에서도 대화의 카드와 **같은 부품, 같은 결정 행**으로 결정한다. 어디서 누르든 같은 결정 라우트를 지나고 먼저 온 결정이 이긴다(#3829 한 번 누르기 그대로). ADR-0202 D1의 「승인 버튼을 따로 갖지 않는다」는 「대화 카드와 다른 부품을 갖지 않는다」로 읽는다.
- **결정할 사람에게만 단추가 보인다.** 다른 사람에게는 「○○ 님의 승인을 기다려요」(질문이면 「답을 기다려요」)만 보인다. 결정자는 서버가 확인하고, 화면에서 단추를 숨기는 것은 거들 뿐이다.
- 질문의 결과는 사람의 말 줄로 남고(D3), 고른 값은 에이전트에게 구조화된 값으로 돌아간다.
- **질문의 답은 승인을 대신하지 못한다.** 질문 카드에는 실행할 행동이 없다. DB가 막는다: 질문이면 `action_type = 'question'`이고 실행 payload가 없다(CHECK). 결정 라우트는 승인일 때만 실행기를 부른다. 질문의 결과(답함·고른 값·직접 쓴 글)는 어떤 승인 게이트도 채우지 않는다: 행동 레지스트리(ADR-0186), host 승인(ADR-0188 D3), 서명 승인(ADR-0210 D3) 모두. 시험: 같은 run에 질문의 답 「예」가 있어도 행동은 여전히 막혀 있다.
- 지키는 경계: **다른 사람 대신 승인은 계속 없다.** 관리자·담당자·요청한 사람도 남에게 온 카드를 대신 누르지 못한다(ADR-0202 D5, ADR-0188 D3). 결정자를 바꾸고 싶으면 대화로 청한다.

### D5. 터미널과 작업 번호 — 공유 요약에 작업 번호 하나만 더한다 (ADR-0190 D4-b 증보)
- ADR-0190 D4-b의 S1에 **작업 번호** 한 칸을 더한다. 다른 칸은 더하지 않는다. 작업 제목은 싣지 않는다.
- 출처는 주인이 터미널 메뉴에서 고른 작업뿐이다. 화면 글자나 명령 줄에서 번호를 뽑지 않는다(D4-b 「긁지 않는다」 그대로).
- 서버는 같은 워크스페이스의 작업이고 공유하는 사람이 그 작업의 집 채널 활성 멤버일 때만 받는다. 아니면 이유를 밝히지 않고 똑같이 거절한다. 작업 번호로 남의 작업이 있는지 떠보는 길을 막는다.
- 작업 상세의 「연결된 터미널」 줄은 그 터미널 공유를 볼 수 있는 사람(공유의 집 채널 멤버)에게만 보인다. 볼 수 없는 사람에게는 줄도 숫자도 없다.
- 거꾸로, 공유 요약에 실린 작업 번호는 그 작업도 볼 수 있는 사람에게만 내려 준다. 곧 공유의 집 채널 멤버이면서 작업의 집 채널 멤버여야 한다. 아니면 그 칸이 없다. 작업이 있다는 것과 워크스페이스의 작업 번호 순서가 새지 않게 한다.
- 공유를 끄면 작업 번호도 같은 트랜잭션에서 지운다(D4-b 해제 규칙 그대로).
- 지키는 경계: 화면 글자·스크롤백·경로는 여전히 기기 밖으로 나가지 않는다. 번호 하나로 연결될 뿐 터미널과 작업은 서로의 내용을 읽지 않는다(D1).

### D6. 팀 보기의 사람·에이전트별 묶음 — 개수와 상태만 (ADR-0202 D5 증보)
- 「작업」 팀 보기에서 사람·에이전트별 묶음을 허용한다. 보이는 것은 열린 상태(내 확인 필요·문제 있음·진행 중·대기 중)의 개수뿐이다. 사람 줄에는 「최근 완료」를 내지 않는다. 일정 기간의 처리 수를 나란히 놓으면 처리량 비교가 되기 때문이다. 에이전트 줄에는 낸다.
- 사람과 에이전트를 같은 목록에 가나다순으로 둔다. 걸린 시간·활동량·순위·막대 길이 비교는 없다. 마지막 활동 시각이나 처리 속도를 묶음 단위로 내지 않는다.
- 셈에 드는 것은 내가 볼 수 있는 작업뿐이다. 볼 수 없는 작업은 숫자에도 들지 않는다(「공유되지 않은 작업 n개」 금지, ADR-0194 D5).
- 기본 보기는 채널별이다. 사람·에이전트별은 사람이 고를 때만 보인다. 묶는 기준은 담당자다. 진행으로 묶으면 「지금 누가 무엇을 하는지」 판에 가까워지므로 쓰지 않는다. 기준을 바꾸려면 이 ADR을 증보한다(미결 12).
- 묶음에서 남의 작업 목록으로 내려가는 길은 없다. 사람으로 거르는 것은 「내 것」 하나뿐이다.
- 서버 응답은 기존 가시성 조회 위의 개수 집계다. 사람 ID로 묶은 시간 정보는 응답에 없다. ADR-0220 P4의 시험(「사람 ID로 묶어 내놓는 판이 없다」)은 이 묶음에서 「열린 상태의 개수 말고는 없다」로 읽는다.
- 지키는 경계: 팀 감시는 계속 없다. 「지금 누가 무엇을 하는지」 판과 사람별 활동 타임라인은 만들지 않는다(ADR-0202 D5). 이 묶음은 「누가 몇 개를 어떤 상태로 가졌나」까지다.

### D7. 진행 소식 — 에이전트가 초안을 쓰고 사람이 고쳐 게시한다 (ADR-0220 P2 ⑥ 증보)
- 진행 소식은 사람이 게시한다. 에이전트는 초안만 쓴다. 초안은 사람의 작성창을 미리 채우는 제안 카드로 오고(지금 `work.request.open`이 입력창을 채우는 방식과 같다), 사람이 고쳐 보내야 글이 된다. 에이전트가 바로 올리는 길은 없다.
- 초안을 청하는 것은 사람이다(직접 부르기, 또는 사람이 만든 예약, ADR-0220 O3). 초안은 청한 사람에게만 간다.
- 게시한 글은 쓴 사람의 메시지이고 출처는 `human`이다. **쓴 사람만 고친다.**
- 이것이 ADR-0220 P2 ⑥(정기 보고)의 통로다. 새 알림 사유는 없다. 게시된 글은 사람의 글이라 지금 알림 규칙을 따른다.
- 지키는 경계: 보고의 주인은 사람이다. 에이전트의 자유 발화가 알림 사유가 되지 않는다(ADR-0220 P2 금지).

### D8. 남의 터미널 화면 보기 — 지금은 열지 않고, 열 때의 기본값만 지금 정한다 (ADR-0190 D6 그대로)
- 지금은 열지 않는다. 따라보기는 「결과만」과 「진행 상황」 두 단계까지다. 진행 상황은 작업을 열었을 때 채널 멤버에게 보인다(ADR-0202 D5가 이미 허용한다).
- 열 때의 기본값은 아래와 같다. 바꾸려면 이 ADR을 고친다.
  1. **세션마다 주인 동의.** 보려는 사람이 청하면 주인에게 동의 카드가 가고, 주인은 그 세션에 한해 허락한다. 동의는 다음 세션으로 이어지지 않는다.
  2. **1시간.** 지나면 보기가 끝나고, 더 보려면 다시 청한다.
  3. **보는 사람 표시.** 주인의 터미널 머리에 지금 보는 사람이 보인다.
  4. **접근 기록.** 누가·어느 터미널을·언제·어떤 동의로 봤는지 남긴다(D10).
  5. **비밀 경고.** 화면의 비밀번호·토큰이 가려지지 않는다는 것을 동의 카드에 적는다.
  6. **oort가 발급한 보는 사람 등급으로 막는다.** ADR-0126 D1의 `observer` 등급(출력만, 입력·크기·끝내기 프레임은 발급 자체가 안 되고 호스트가 다시 검사)을 쓴다. 칸 코어가 그리는 「보기 전용」 표시는 거들 뿐 경계가 아니다.
  7. **주인이 언제든 끝낸다.** 주인이 끊으면 그 즉시 끊긴다.
  8. **청할 수 있는 사람**은 그 공유를 볼 수 있는 사람 멤버뿐이고, 한 사람이 청하는 횟수에 상한이 있다(**[추정]** 한 터미널에 하루 5번).
  9. **관리자도** 주인 동의 없이는 보지 못한다.
  10. **주인은** 자기 터미널의 접근 기록을 본다(D10).
- ADR-0126 D1의 세션 단위 `observation` 「기본 open」은 열 때 위의 1로 바뀐다. ADR-0126 머리에 지금 포인터를 달았다.
- D8을 여는 증보는 ADR-0223 D4도 함께 고친다. 칸 지기는 바깥과 말하지 않으므로, 보는 사람 쪽 프레임을 다시 검사하는 것은 앱(칸 호스트 클라이언트)이다. 칸 지기 통로에는 보는 사람의 입력 길이 없다.
- 보는 쪽에는 입력하는 길 자체가 없다. 화면이 지나는 길(직결·종단 암호화)은 열 때 정한다. 서버가 화면을 중계하거나 저장하는 안은 기각된 채다(ADR-0126 D1).
- 지키는 경계: 팀 감시 없음. 지금은 어떤 화면 글자도 기기 밖으로 나가지 않는다.

### D9. 다른 컴퓨터의 터미널 — 입력은 막고 이름·폴더·상태·업데이트 시각만 보인다 (ADR-0188 D6 그대로)
- 다른 컴퓨터(내 다른 맥, 클라우드 상자 등)의 터미널에는 입력하지 않는다. 입력은 그 컴퓨터 앞에 앉은 사람만 한다(ADR-0190 D2). 원격 입력과 원격 셸은 없다(ADR-0188 D6).
- 다른 컴퓨터에서 보이는 것은 이름·폴더·상태·업데이트 시각뿐이다. 이것은 서버에 있는 공유 요약(S1, ADR-0190 D4)을 컴퓨터별로 묶은 것이다. 컴퓨터끼리 직접 말하는 길은 없고, 칸 지기는 서버나 다른 컴퓨터와 말하지 않는다(ADR-0223 D4).
- 공유하지 않은 터미널은 다른 컴퓨터에서 보이지 않는다. 연결이 끊긴 컴퓨터는 마지막으로 받은 상태를 「n분 전 업데이트」와 함께 보인다. 타이머로 온라인을 짐작해 사실처럼 쓰지 않는다(ADR-0220 P1).
- 지키는 경계: 원격 입력 없음. 화면 글자는 기기 밖으로 나가지 않는다.

### D10. 관리자 기록 — 「누가 터미널 화면을 봤나」 (감사 범위)
- 기존 감사 기록에 행 종류 둘을 정해 둔다: 터미널 화면 보기 시작과 끝. 남기는 것은 누가(보는 사람)·어느 터미널(세션 ID)·언제(시작·끝 시각)·동의 번호뿐이다. 화면 내용·명령·경로는 남기지 않는다.
- 읽는 사람은 워크스페이스 관리자와, 자기 터미널의 행에 한해 그 터미널의 주인이다.
- D8이 열리기 전에는 이 행을 쓰는 곳이 없다. 이 ADR은 행 종류와 읽는 권한만 정하고, 쓰는 길은 D8을 여는 증보와 같은 PR에서 연다. 새 표는 만들지 않는다.
- 지키는 경계: 감사에는 내용이 아니라 사실만 남는다.

### D11. 「배포됨」 — v1은 에이전트 보고로만 (ADR-0205 D6 그대로)
- v1에서 「배포됨」은 「에이전트 보고」로만 보인다. GitHub 앱 v1 권한(읽기 다섯 줄)은 배포·Actions·status 사건을 받지 않는다. 받을 수 없는 값을 GitHub 기준처럼 그리지 않는다.
- GitHub에서 확인하는 길(권한을 넓히거나 다른 배포 신호를 받기)은 v1 뒤에 따로 정한다. 권한을 넓히면 설치한 모든 계정이 다시 승인해야 한다. ADR-0205 D6은 바꾸지 않는다.
- 지키는 경계: 출처 칸. 에이전트가 알린 「배포됨」을 서버나 GitHub이 확인한 값과 섞지 않는다.

### D12. 신호를 안 보내는 터미널의 낱말 — 디자인 검수에서 정한다
- 프로그램이 상태 신호(훅·OSC 7501)를 보내지 않는 터미널을 화면에서 무엇이라 부를지는 디자인 검수에서 정한다. 이 ADR은 낱말을 정하지 않는다.
- 정해진 것은 하나다. 신호가 없으면 상태를 짐작하지 않는다(화면 글자로 추측하지 않는다, ADR-0190 D4-b). 그 낱말은 「진행 중」·「완료」 같은 상태 낱말을 빌려 쓰지 않는다.

### D13. 에이전트가 스스로 내 맥의 Claude Code·Codex를 여는 길 — 미룬다
- 사람이 시키는 A 레인(내 맥의 `momo-workd`, ADR-0188)을 먼저 단단히 한다. 폰 세션 화면 문, 멈춤 알림, 턴 끝 요약 같은 빈틈은 따로 이슈로 다룬다(A 레인 코드 감사의 빈틈 표).
- ADR-0188 §3 불변식(결정자 = host 소유자, 에이전트 컨트롤은 member host에 `kill`만, 소유자 지시 판별)과 ADR-0198 D6(에이전트가 내 맥의 하네스를 빌려 쓰는 것은 정하지 않는다)을 그대로 둔다.
- 열려면 ADR-0188 §3 개정, ADR-0198 D6 결정, 약관 재검토가 먼저다. 미결 10으로 적는다.

## 구현 규칙 (결정 아님 — planner 추가, timon 설계 참고)

timon(ai-timon/timon, AGPL-3.0)은 설계 참고로만 쓴다. 생각만 빌리고, 구현은 timon 코드를 보지도 옮기지도 않는다. 구현 이슈에도 코드 링크를 붙이지 않는다.

### R1. 다시 시키기 — 같은 조건으로 계속 다시 시키지 않는다
- oort를 지난 하위 작업에 적용한다.
- 자동 다시 시키기는 간격을 늘리며 상한까지만 한다(**[추정]** 3번). 상한을 넘으면 그 하위 작업과 작업은 「문제 있음」이다.
- 오케스트레이터가 다시 시키려면 에이전트·하네스·모델 중 하나 이상을 바꿔야 한다. 오케스트레이터의 다시 시키기에도 상한이 있고(**[추정]** 모두 합쳐 6번), 넘으면 사람만 다시 시킨다. 사람이 다시 시키면 셈이 새로 시작한다.
- 기다리면 풀리는 사유(사용량 한도·연결 끊김)로 끝난 것은 셈에 넣지 않는다.
- 다시 시킬 때마다 진행 기록에 행동 줄(출처 `server`)을 남기고, 무엇이 바뀌었는지와 셈에 들었는지를 싣는다. 무엇이 바뀌었는지는 서버가 아는 값으로 판단한다. 모델처럼 에이전트 보고뿐인 값은 「에이전트 보고」로 보인다. 서버가 막게 될 때(ADR-0200 증보)는 서버가 아는 값(에이전트·하네스)만 「바꿈」으로 센다. 모델은 에이전트 보고라 세지 않는다.
- v1은 표시와 기록 규칙이다. 서버가 상한을 넘은 다시 시키기를 막으려면 ADR-0200 증보가 먼저다(「이슈 나누기」 표).

### R2. 시계 둘 — 「너무 오래 조용함」과 「턴 예산」
- 하위 작업과 터미널이 멈춘 것 같은지를 두 시계로 따로 센다. 「너무 오래 조용함」은 정한 시간 동안 새 진행 기록·출력·상태 신호가 없는 것이다. 「턴 예산」은 일하고 있어도 한 차례가 정한 시간을 넘는 것이다.
- **사람을 기다리는 시간(승인·질문 카드 대기)은 두 시계 어디에도 넣지 않는다.**
- 두 시계는 다른 낱말로 보이고, 「조용함」과 「오래 걸림」을 한 낱말로 섞지 않는다. 낱말과 숫자는 구현 이슈가 기존 기준(ADR-0200의 「조용해요 · 마지막 보고 n분 전」)에 맞춰 **[추정]**으로 정한다.
- 시계는 표시만 하고 아무것도 멈추지 않는다. 자동으로 멈추게 하려면 ADR-0190·0200 증보가 먼저다. 시계의 근거는 서버가 받은 시각(하위 작업)과 칸 지기가 받은 시각(터미널, ADR-0223 D5)이다. 칸 지기가 받은 시각은 이 기기의 값이라, 공유로 서버에 닿아 팀에게 보이면 「에이전트 보고」로 그린다.

### R3. 별자리가 보이는 범위를 화면에 적는다
- 오케스트레이터 뷰는 「oort를 거친 하위 작업만 보여요」를 적는다. 오케스트레이터가 oort 밖에서 부린 하위 에이전트(예: 하네스 안의 자체 하위 에이전트)는 보이지 않는다. oort는 바깥 런타임의 지시문을 쥐지 않으므로(ADR-0132 D4) 보이지 않는 것이 「없음」으로 읽히지 않게 한다(ADR-0220 P1).

## 데이터 계약 스케치 (migration이 아니다)

숫자는 **[추정]**이고 구현이 확정한다. migration 번호는 구현이 착수 때 정한다.

- **모든 새 테넌트 표**: `workspace_id NOT NULL`, RLS `ENABLE`+`FORCE`, `ws_isolation` 정책 대상, 트랜잭션마다 `SET LOCAL app.workspace_id`. 쓰기 경로에 BYPASSRLS가 없다. Rust는 sqlx 런타임 쿼리를 쓴다. `schema_v0.sql`은 건드리지 않고 `server/Migrations/` 새 migration으로만 더한다.
- **작업 `work_item`**: `id`, `workspace_id`, 작업 번호(워크스페이스마다 1부터, 같은 트랜잭션에서 워크스페이스 카운터 행을 잠그고 올린다, `(workspace_id, 번호)` 유일), 집 채널(필수, FK), 제목(1~200자, 제어·서식 문자 금지), 닫힘 상태(열림·완료·취소, 닫는 사람은 미결 7), 만든 이, 만든 시각.
  - 담당자 `assignee_member_id NOT NULL`: **BEFORE INSERT·UPDATE 트리거**가 같은 워크스페이스의 `member.kind='human'`인지 확인하고, 아니면 `check_violation`으로 거절한다(118 `cloud_box_owner_is_human`과 같은 방식이고, 여기는 UPDATE도 막는다).
  - 진행 `doer_member_id`: NULL 허용, 사람이나 에이전트, 같은 워크스페이스.
  - 요청한 사람 `requested_by_member_id NOT NULL`: 서버가 만들 때 쓰고, 바꾸는 UPDATE는 트리거가 거절한다. v1에서 요청한 사람은 작업을 만드는 사람(인증된 호출자)이고, 어느 경로든 요청 본문에서 받지 않는다. 다른 사람의 부탁으로 만드는 길은 미결 6과 함께 정한다.
  - 대신한 사람 `on_behalf_of_member_id NOT NULL`: 담당자와 같은 트리거로 사람만 받는다. 요청한 사람이 사람이면 같은 값이어야 한다(CHECK와 트리거).
  - **에이전트 bearer 경로의 요청 본문에는 요청한 사람·대신한 사람·행위자 칸이 없다.** 서버가 그 호출의 lease handle이 묶인 run(`bound_handle`, ADR-0186 D2)에서 run 사슬(`parent_run_id`)을 거슬러 올라가, 뿌리 run의 대신한 사람으로만 채운다. 뿌리 run의 대신한 사람은 서버가 트리거 메시지나 맡김 기록에서 쓴 사람이다. 뿌리에 사람이 없으면 거절한다.
  - **미결 6·7을 정하기 전까지**: 작업은 사람만 만든다(에이전트 bearer의 만들기 라우트는 없다). 닫기와 담당자 바꾸기는 담당자 본인과 관리자만 하고, 에이전트는 못 한다. 진행 칸에서 사람은 자기 자신만 넣고 뺀다. 에이전트는 그 작업에 묶인 run의 lease를 가진 동안 자기 자신만 넣는다.
- **하위 작업**: 새 표가 없다. `agent_run`·`work_session`에 NULL 허용 `work_item_id`(FK `(workspace_id, work_item_id)`)를 더하고, `agent_run`에 요청한 사람·대신한 사람 칸(옛 행은 NULL)을 더한다. 대신한 사람은 같은 사람 검사를 받는다. 자식 run의 작업 ID는 부모 것과 같아야 한다.
- **진행 기록 `work_item_event`**: PK `(workspace_id, work_item_id, seq)`(작업마다 오르는 순번), 하위 작업 ID(NULL 허용), 종류(`prompt`·`thought`·`action`·`elicitation`·`response`·`error`), 출처(`server`·`agent`·`human`·`external`), 중간 과정(bool), 행위자, 짧은 글(NULL 허용, ADR-0200 7-3의 문자 규칙 함수 하나를 길이만 바꿔 쓴다), 가리키는 대상(카드·링크·메시지 ID), 고친 줄 순번(NULL 허용), 서버 시각.
  - CHECK: `prompt`이면 출처가 `human`이나 `server`이고 행위자는 사람이다(트리거). `thought`이면 출처 `agent`, 중간 과정 참, 글 NULL이다(7-4가 바뀌기 전까지). `elicitation`·`response`·`error`는 중간 과정이 거짓이다. 출처가 `external`이면 링크 대상이 있다.
  - 출처는 쓰는 코드 경로가 정한다. 에이전트 bearer 경로는 `agent`만 쓰고, `server`·`external`은 서버 코드(전이 헬퍼·서명된 GitHub 수신)만 쓴다.
  - 행위자는 언제나 인증된 호출자이고 요청 본문에서 받지 않는다. 에이전트가 진행 기록을 쓰는 것은 그 작업의 진행이거나, 그 작업에 묶인 run의 lease를 가진 동안뿐이다.
  - 행은 고치지 않는다. 지우는 것은 출처 `agent`이면서 중간 과정인 줄의 최신 창 굴리기뿐이다(ADR-0200 7-6과 같은 한 함수, **[추정]** 작업당 200줄).
  - 실시간: INSERT와 같은 트랜잭션에서 outbox → relay → Centrifugo로 종류만 든 얇은 프레임을 보내고, 내용은 REST가 가시성을 다시 확인해 준다(ADR-0200 D2와 같다). 클라이언트 직접 publish는 없다.
- **결정(승인·질문 카드)**: 새 표 없이 기존 `approval`을 넓힌다. 종류(승인·질문), 선택지(**[추정]** 2~4개, 각 1~60자), 직접 쓰기 허용 여부, 결과 「답함」을 더한다. 질문 카드도 승인 카드처럼 하위 작업(run)에 묶인다(ADR-0186 §1.2의 모양 그대로). 질문이면 `action_type = 'question'`이고 실행 payload가 없다(CHECK, D4).
- **링크 `work_item_link`**: 작업 ID, 시스템(`github`·`linear`), 종류(`pr`·`branch`·`commit`·`issue`·`release`), URL(https, 호스트는 시스템별 허용 호스트 `github.com`·`linear.app`과 정확히 같아야 한다), 붙인 쪽(사람·에이전트)과 붙인 멤버, 확인한 사람(NULL 허용), 상태(닫힌 목록: 열림·리뷰 기다림·CI 통과·CI 미통과·합쳐짐·닫힘·배포됨), 상태 출처(`agent`·`external`), 상태 시각, 받은 사건 ID(`external`일 때 GitHub 전달 ID).
  - 상태 출처 `external`은 서명을 확인한 GitHub 수신 경로(ADR-0205 D4)만 쓴다. v1에서 「배포됨」은 `agent`로만 들어온다(D11).
  - 링크를 붙이는 것은 그 작업을 볼 수 있는 사람과, 그 작업의 진행인 에이전트다. 에이전트가 붙인 링크의 상태는 GitHub이 확인하기 전까지 `agent`다.
  - 에이전트가 붙인 링크는 상태가 GitHub 기준이어도 「에이전트가 붙인 링크」로 보이고, 사람이 확인하기 전까지 작업의 상태 낱말을 바꾸지 않는다. PR에 대한 사실은 GitHub이 확인해도, 「이 작업의 PR이다」는 에이전트가 알린 것이기 때문이다.
  - 「확인한 사람」은 사람만 된다(담당자와 같은 트리거). 확인하는 것은 그 작업을 볼 수 있는 사람 멤버이고, 에이전트 bearer에는 확인 길이 없다.
- **터미널 공유 요약**: `work_session_share`(ADR-0190 D4-b)에 NULL 허용 작업 ID 한 칸. 클라이언트는 작업 번호를 보내고, 서버가 가시성을 확인한 뒤 ID로 바꿔 둔다(D5). 작업이 지워지면 NULL이 된다.
- **감사**: 기존 감사 기록에 행 종류 둘(터미널 화면 보기 시작·끝)을 예약한다. 필드는 보는 사람·터미널 세션 ID·시각·동의 ID다. 새 표가 없고, 쓰는 곳은 D8을 열 때 생긴다(D10).
- 터미널 화면 보기의 동의 행(D8)은 열 때 정한다. 지금은 만들지 않는다.

## 불변식 대조
- Postgres가 원본이고 쓰기 길은 하나다. 진행 기록·링크·작업의 쓰기는 같은 트랜잭션의 outbox를 지나고, Centrifugo는 전송만 한다.
- 에이전트는 1급 멤버다. 진행 칸에 사람과 같은 자리로 든다. 담당자와 대신한 사람만 사람이다.
- 모든 새 표는 `workspace_id` + RLS FORCE + `SET LOCAL app.workspace_id`이고 BYPASSRLS가 없다.
- `schema_v0.sql`은 그대로이고 새 migration만 쓴다. sqlx 런타임 쿼리를 쓴다.
- 공개 API(작업·진행 기록·링크·질문 카드 라우트, S1 칸)와 DB 계약이 바뀌므로 이 Accepted가 구현 머지 조건이다(ADR-0100).

## 위협과 방어
- **에이전트가 담당자가 되는 길**: INSERT·UPDATE 트리거가 막는다. 앱 검사를 빼도 DB가 거절한다.
- **출처 꾸미기**: 출처는 요청이 고르지 않고 쓰는 경로가 정한다. 에이전트 bearer로 `server`·`external`·`human` 줄을 쓸 수 없다.
- **남의 이름 빌리기**: 대신한 사람은 서버가 요청의 출처에서 정하고, 에이전트 bearer의 요청 본문에는 그 칸이 없다. 뿌리 run에 사람이 없으면 거절한다. 에이전트가 「○○ 님 요청으로」를 고르지 못한다.
- **질문으로 행동 실행**: 질문 카드에는 실행할 행동이 없고(CHECK), 질문의 답은 어떤 승인 게이트도 채우지 않는다(D4).
- **남의 PR 붙이기**: 에이전트가 붙인 링크는 사람이 확인하기 전까지 작업 상태를 바꾸지 않고 「에이전트가 붙인 링크」로 보인다. URL 호스트는 허용 호스트와 정확히 같아야 한다.
- **작업 번호로 떠보기**: S1의 작업 번호와 작업 조회는 이유를 밝히지 않고 똑같이 거절한다(D5).
- **대신 승인**: 결정자는 서버가 확인한다. 단추 숨김은 거들 뿐이다(D4).
- **팀 감시로 번지기**: 묶음 응답에 시간·활동량이 없고, 사람 줄에는 열린 상태의 개수만 있다. 묶음에서 남의 목록으로 내려가는 길이 없다(D6). 시험이 응답 필드를 못 박는다.
- **화면 글자 유출**: S1에 번호 하나만 더한다(D5). 남의 터미널 화면 보기는 열지 않는다(D8).
- **질문 남발**: 받고 답하는 사람은 그 작업의 집 채널 활성 사람 멤버뿐이고(D4), 알림은 P2 ②의 받는 사람에게만 간다. 카드 수 상한은 구현이 정한다(**[추정]** 하위 작업당 열린 질문 3개).

## 결과
- (+) 「누가 내 일을 가져갔나」를 담당자·진행·요청한 사람 칸이 답한다. GitHub을 쓰지 않는 사람도 「내 것」을 갖는다.
- (+) 진행 기록이 Linear와 같은 종류라 바깥 연동이 번역 없이 되고, 출처 칸 덕에 서버 사실과 에이전트 보고가 섞이지 않는다.
- (+) 승인과 질문이 한 결정 행이라 대화·작업 화면·폰의 상태가 어긋나지 않는다.
- (+) 세 부품이 ID로만 이어져 칸 코어를 바꿔도 원장이 바뀌지 않는다.
- (−) 새 표 셋(작업·진행 기록·링크)과 run 칸 셋이 는다. 원장이 둘(작업·run)이라 읽을 때 둘을 합쳐 그려야 한다.
- (−) 남의 터미널 화면 보기, GitHub으로 확인하는 「배포됨」, 에이전트가 스스로 하네스를 여는 길은 v1에 없다.
- (−) 사람·에이전트별 묶음은 감시와 가깝다. 응답 필드를 시험으로 지켜야 한다.
- (−) v1 별자리는 oort를 지난 하위 작업만 보여서 오케스트레이터의 실제 계획과 다를 수 있다. R3가 그 사실을 화면에 적는다.

## 미결
1. **에이전트끼리 맡기기가 oort를 지나게 할지**(v4 결정 표 「계획 단계·하위 작업」, 결재 밖). 지나게 하면 단계와 하위 작업을 서버 사실로 그린다. 여기에 걸린 timon 조사의 두 항목은 ② 결과를 묶어 같은 오케스트레이터 세션으로 돌려주기와 ⑤ 맡길 수 있는 범위(사람이 정한 위임 허용 목록)다. owner가 정한다.
2. **생각 줄에 글을 실을지.** ADR-0200 증보 7-4(생각 글은 저장하지 않는다)와 부딪힌다. 정하기 전까지는 7-4를 따른다.
3. **계획 확인 카드**(timon ①). 오케스트레이터는 나눈 결과만 내고, 사람이 진행 방식과 모델을 서버 카탈로그에서 고른다. 그러면 계획과 모델이 서버 사실이 된다. ADR-0220 §3-5 ①(「계획은 알림이고 승인이 아니다」)을 읽는 법이 바뀌므로 owner가 정한다.
4. **질문이 가는 길**(timon ③). 받고 답하는 사람의 범위(집 채널 활성 사람 멤버)는 D4가 정했고, 이 미결은 사람 멤버 안의 순서와, 질문 카드의 결과에 「정하지 않음」(거절이 아님)을 더할지만 다룬다. 결과를 더하는 것은 ADR-0220 P7의 결과 셋(승인·거부·만료)에 하나를 더하는 증보라 owner가 정한다. timon 안의 「하위 작업의 질문은 맡긴 오케스트레이터에게 먼저 간다」는 D4(에이전트는 질문에 답하지 못한다)를 바꾸므로, 이 미결이 아니라 이 ADR의 증보가 필요하다.
5. **모델 이름의 출처**(v4 결정 표, 이 이슈 밖). 오케스트레이터 뷰가 그리는 모델 이름을 어디서 가져올지는 ADR-0220 증보가 필요해 정하지 않았다. 정하기 전까지 화면은 D3의 출처 규칙을 따른다. 남은 시간은 v4가 ADR 없는 화면 규칙으로 나눴으므로 디자인 검수에서 다룬다.
6. **작업이 생기는 길.** 정하기 전까지는 사람만 만든다(데이터 계약). 사람이 「작업 만들기」로만 만드는지, 맡긴 일(ADR-0202 D3)에서 저절로 생기는지, 에이전트가 만들 수 있는지. 에이전트가 만들 수 있다면 사람이 청하지 않은 작업의 대신한 사람을 누구로 둘지(ADR-0220 P3의 「소유자, 없으면 관리자」를 따를지)도 함께 정한다.
7. **작업을 닫고 담당자를 바꾸는 사람.** 정하기 전까지는 담당자 본인과 관리자만 한다(데이터 계약). 완료·취소와 담당자 바꾸기를 누가 하는지(담당자·진행한 사람·요청한 사람·관리자), 에이전트가 할 수 있는지, 담당자가 워크스페이스를 떠나면 어떻게 하는지.
8. **(닫음) ADR-0126 D1 포인터.** 보안 검수 1회차 L10에 따라 ADR-0126 머리에 포인터를 지금 달았다.
9. **질문의 전환기 예외를 끝낼 때.** 질문 카드가 선 뒤 사람 멘션을 질문으로 인정하는 예외(ADR-0220 P2 ②, O1)를 언제 끝낼지.
10. **에이전트가 스스로 내 맥의 하네스를 여는 길(D13).** ADR-0188 §3 개정, ADR-0198 D6 결정, 약관 재검토(T0b #3566) 뒤 owner가 정한다. 첫 모양 후보는 「에이전트 제안 카드 → 소유자의 기기 서명 승인 → 소유자 권한으로 시작」이다(ADR-0220 P8).
11. **출처 표시 낱말과 ADR-0220 P1.** 낱말표는 서버 사실을 표시 없이 그리고 「에이전트 보고」·「GitHub 기준」만 붙인다. ADR-0220 P1 시험 줄은 모든 문구에 출처 표지를 요구하고, 이미 착륙한 낱말(「oort 기록」, ADR-0200 T4)과도 다르다. 기본 모양을 서버 사실의 표지로 읽을지, ADR-0220 증보로 시험 줄을 고칠지 planner가 정한다(#5591 미결 13과 같은 물음). 출처를 모르는 값을 「에이전트 보고」로 그리는 것은 D3이 이미 정했다.

3. **사람·권한을 바꾸는 일**: 워크스페이스에 새 사람·새 에이전트를 들이기(초대, 외부 에이전트 데려오기), 역할, **대화가 쌓인 채널**에 사람이나 에이전트를 넣기, 에이전트의 접근 범위(승인 채널)와 호출 범위, 신원(에이전트의 이름·역할 라벨·이미지 아바타). ADR-0186 V7이 「위임 대상이 될 수 없는 등급」으로 못박은 접근 범위·신원이 여기다. 한 가지만 E3이 푼다: 에이전트가 방금 만든 새 채널에 넣기.
4. **돈이 드는 일**: 하루 한도 올리기, 단가가 더 높은 모델로 바꾸기, 유료 자원 만들기.
5. **남의 것을 쓰는 일**: 다른 사람의 맥에서 실행(ADR-0188 D3), 개인 연결 토큰(ADR-0211), 남이 담당자인 작업을 닫거나 고치기, 남이 소유한 에이전트에게 일을 맡기기(E4).
6. **확인 절차를 건너뛰는 일**: 자기가 낸 것을 자기가 승인하기, 검사·한도·고지를 끄기, 행동 권한 설정 자체를 바꾸기.

- 여섯은 닫힌 목록이다. 더하거나 빼려면 이 절을 증보한다.
- 새 행동을 레지스트리에 더할 때 등급을 정하지 않으면 사람 몫이다(기본값).
- 레지스트리의 행동 가운데 E3의 닫힌 목록에 없는 것은 여섯에 이름으로 들지 않아도 모두 사람 몫이다(지금의 승인 카드와 승인자 그대로). 여섯은 왜 사람 몫인지의 까닭이고, 행동 권한의 대상을 정하는 것은 E3의 목록이다.
- **사람 몫이라고 적은 것이 에이전트에게 새 길을 열지는 않는다.** 지금 에이전트에게 길이 없는 것은 여전히 없다: 다른 사람의 맥에서 실행(ADR-0188 §3, 이 문서 D13), 요청자가 없는 run의 개인 연결(ADR-0211 D5), 남이 담당자인 작업을 닫거나 고치기(미결 7). 결정자는 그 행동의 기존 규칙(승인 역할·host 소유자·토큰 주인)이 정한다. E2-6의 셋은 에이전트가 제안할 수도 없다(카드도 없다).
- 지키는 경계: 사람 몫의 행동은 행동 권한 설정에 「허용」 값이 없고, 그 값을 받는 서버 경로도 없다. 시험: 사람 몫 행동에 「허용」을 쓰려는 요청은 거절된다.

### E3. 행동 권한

- 설정 이름은 **「행동 권한」**, 값은 **「허용 · 물어보기 · 차단」**이다(owner 2026-11-12 「permission에 관한 부분」). 「맡기기」「알려만 줘」는 쓰지 않는다.
- **값의 뜻.** 「물어보기」는 지금의 승인 카드다. 「허용」은 아래 조건에서 카드를 건너뛴다. 「차단」은 에이전트의 그 종류 제안과 실행을 모두 닫는다. 사람이 자기 화면에서 하는 같은 일은 막지 않는다. 값을 낮추면(허용 → 물어보기 → 차단) 이미 떠 있는 카드와 진행 중인 실행은 결정·실행 때의 재증명에서 새 값으로 판정한다(ADR-0186 U-b-3 끄개와 같은 방식).
- **대상은 닫힌 목록이다.** 행동 권한의 대상은 아래 넷뿐이다. 더하려면 이 절을 증보하고, 구현 이슈는 줄일 수만 있다.
  1. `channel.create` — `kind=private`만. 공개 채널을 만드는 호출은 값과 상관없이 승인 카드다. `memberHandles`로 함께 넣는 대상은 4의 규칙을 따른다.
  2. `agent.profile.update`의 소개·상태 문구·프리셋 아바타. 이름·역할 라벨·이미지 아바타가 든 호출은 사람 몫이다(ADR-0186 V3-1·V3-6, V4-M 7번).
  3. `workspace.settings.update`의 `role_labels`. `welcome_prompt`는 다른 에이전트의 턴에 들어가는 글이라 대상이 아니다(ADR-0186 V7·V3-2c).
  4. 새 채널에 넣기(아래).
  - 관리자도 지금 대신 결정하지 못하는 행동(승인자가 본인·DM 상대·host 소유자·토큰 주인인 것)은 대상이 될 수 없다.
  - 「되돌릴 수 있다」는 사람이 oort 안의 행동 한 번으로 원래대로 돌릴 수 있고, 그 사이 oort 밖으로 나갔거나 다른 에이전트의 턴에 들어간 것이 없다는 뜻이다. 대상은 이 뜻에 맞는 것 가운데 위 넷이다.
- **「허용」의 뜻(planner 결정, owner 확인 대기 ㄱ).** 「허용」은 그 종류의 카드를 건너뛸 뿐이고 승인 규칙을 바꾸지 않는다. **그 run의 대신한 사람(D2)이 그 행동의 승인 역할을 스스로 가졌을 때**, 곧 지금 그 카드를 승인할 수 있는 사람일 때, 그 사람의 부탁을 승인으로 치고 카드 없이 실행한다. 결정자는 대신한 사람이고 실행은 그 사람의 권한이다(ADR-0186 D2 「실행은 결정자 권한」 그대로). 대신한 사람에게 승인 역할이 없으면 「허용」이어도 「물어보기」다(지금처럼 승인 역할을 가진 사람에게 카드가 간다).
  - 승인 역할은 행동마다 레지스트리가 정한 그대로다. `channel.create`·`channel.member.add`·`hosted.channels.grant`는 관리자, `agent.profile.update`는 대상 에이전트의 소유자나 관리자(`agent_editor`), `role_labels`는 `workspace_operator`다.
  - 그 밖의 조건은 「물어보기」와 같다. 「허용」은 카드가 만들어졌을 자리에서만 카드를 대신한다. 제안 카드를 만들 수 없는 때(문마다의 행동 목록에 없음, 팀 AI의 사전 점검·오염 규칙 — ADR-0201 증보 v3 B4)에는 「허용」 실행도 없다.
  - 서버는 실행할 때마다 **같은 트랜잭션에서 다시 본다**: ① 그 종류의 값이 지금 「허용」이다 ② 인자 검증·이름 해석·시야 규칙(ADR-0186 V1-a~d)을 그대로 지난다 ③ 그 run의 대신한 사람이 지금 활성 사람 멤버이고 게스트가 아니며 그 행동의 승인 역할을 지금 갖고 있다. 그 run은 그 사람이 앱(웹·데스크탑·폰)의 사람 세션에서 직접 쓴 글로 부른 run이다(E5) ④ 요청자가 게스트이거나 그 방에 게스트가 있으면(ADR-0219 D8) 지금처럼 아무것도 만들지 않는다 ⑤ 멈춤 조건(E6)에 걸리지 않는다. 값이 「물어보기」이거나 ③이 어긋나면 지금의 승인 카드로 가고, 값이 「차단」이면 닫힌다. ②·④·⑤가 어긋나면 지금의 거절 그대로다.
  - **대신한 사람이 없는 run**(먼저 제안, ADR-0186 v5)은 「허용」이어도 「물어보기」이고 v5의 목록·끄개·한도를 그대로 따른다(owner 확인 대기 ㄷ). 사람이 청하지 않아 서버가 「에이전트가 연 작업」으로 표시한 작업(E4)의 run도 같다. 그 작업의 담당자는 그 일을 부탁한 사람이 아니다.
  - **에이전트가 맡겨 생긴 하위 run**도 「허용」이어도 「물어보기」다. 물려받은 대신한 사람은 표시와 책임의 칸이고(E4), 그 사람이 그 행동을 직접 부탁한 것이 아니다. 묻는 쪽이 이긴다(E1).
  - 에이전트는 이 실행으로 관리자 권한이나 채널 owner 자리를 얻지 않는다. 만든 채널의 owner는 대신한 사람이고, 사람 owner가 없는 채널은 생기지 않는다. 감사에는 행위자(에이전트)·결정자(대신한 사람)·근거(행동 권한 설정 행)를 남긴다. 설정을 바꾼 관리자가 떠나거나 역할이 내려가도 값은 워크스페이스 설정으로 남고, 실행 판정은 대신한 사람의 지금 권한으로 한다.
  - **상한.** 에이전트 하나가 「허용」으로 실행하는 수는 종류마다 **[추정]** 시간당 6·하루 20이다(ADR-0186 U-d처럼 DB에서 센다). 넘으면 거절이 아니라 「물어보기」로 떨어진다.
  - 이 결정으로 닫히는 것은 둘이다. 관리자의 설정이 본인의 결정을 대신하는 길(결정자는 늘 승인 역할을 가진 채 직접 부탁한 사람이다)과, 승인 역할이 없는 멤버가 에이전트를 시켜 관리자 전용 일을 하는 길이다.
- **새 채널에 넣기(owner 2026-11-12).** 에이전트가 방금 만든 새 채널에 사람이나 에이전트를 넣는 것은 행동 권한의 대상이다(`channel.member.add`·`hosted.channels.grant`의 이 경우만).
  - 「새 채널」은 서버가 판정하고, **넷이 모두 참**이어야 한다. ① 서버가 그 채널을 만들 때 같은 트랜잭션에 적어 둔 기록(만든 에이전트·작업 ID·run 사슬)이 지금 호출과 같다. 채널 이름, 에이전트의 인자, 감사 조회로 판정하지 않는다 ② 만든 지 **[추정]** 10분이 지나지 않았다 ③ 넣는 시점에 그 채널에 메시지가 한 건도 없다. 만든 에이전트의 글, 스레드 답, 첨부만 있는 글, 삭제된 글, 웹훅·연동 글도 센다. 서버가 쓴 입장 줄만 뺀다. 그 채널을 집으로 하는 작업·터미널 공유도 없어야 한다 ④ 판정과 넣기는 채널을 잠근 한 트랜잭션이다.
  - 넣을 수 있는 것은 이 워크스페이스의 활성 멤버·에이전트뿐이다. **게스트는 넣을 수 없다**(ADR-0219 O5 (a)·D12). 한 채널에 「허용」으로 넣는 수는 합쳐 **[추정]** 10이다.
  - **만들면서 함께 넣기.** `channel.create`의 `memberHandles`로 채널을 만들면서 함께 넣는 사람·에이전트에도 같은 규칙을 건다. 게스트는 넣을 수 없고, 위 합쳐 **[추정]** 10에 들어가며, 아래의 바깥에서 도는 에이전트의 순서와 다른 에이전트의 승인 채널 조건도 그대로 걸린다. 조건에 안 맞는 대상이 섞인 호출은 그 호출 전체가 「물어보기」다(E1의 「한 호출에 층이 섞이면 높은 층」과 같은 줄).
  - **다른 에이전트를 넣을 때(planner 결정, owner 확인 대기 ㄴ).** 멤버십과 함께 **그 에이전트 connection의 승인 채널에 이 새 채널 하나를 올리는 것**까지 한다. 멤버십만으로는 바깥에서 도는 에이전트가 그 채널을 읽지 못해서(ADR-0186 V0·V8-2), owner가 바란 「에이전트가 그룹을 꾸린다」가 서지 않기 때문이다.
    - 조건은 위 「허용」과 같다. 대신한 사람이 `hosted.channels.grant`의 승인 역할(지금은 관리자, ADR-0162)을 가졌을 때만 「허용」으로 실행하고, 아니면 승인 역할을 가진 사람에게 카드가 간다. 그 카드를 결정할 때에도 「새 채널」 판정 넷을 다시 본다(ADR-0186 V1-d). 어긋나면 그 카드로는 실행되지 않는다.
    - 대상은 이미 이 워크스페이스의 멤버인 에이전트뿐이다. 새 에이전트를 데려오는 것(`agent.invite`)과 connection의 confirm은 사람 몫 그대로다. DM 승인·승인 scope와 V5가 쓰지 않는다고 적은 칸은 건드리지 않고, 승인 채널 합계 상한도 그대로다.
    - 이 한 가지에 한해 ADR-0186 V5(「대상 connection은 제안자 자신 하나」)·V11(그 시험)·V7(「`hosted.channels.grant`는 위임 대상이 될 수 없다」)을 바꾼다. ADR-0162(채널 승인 권한 주체는 관리자)는 바꾸지 않는다. 승인 역할을 가진 사람이 직접 부탁했거나 카드로 승인할 때만 실행되기 때문이다. **대화가 있는 채널로 남의 connection을 넓히는 길은 그대로 없다.** 만든 에이전트 자신의 connection에 새 채널을 올리는 것은 ADR-0186 V3 (3) 그대로다.
  - **바깥에서 도는 에이전트의 순서(owner 확인 대기 ㄹ).** 바깥에서 도는 에이전트는 사람보다 먼저, 또는 같은 트랜잭션에 넣는다. 사람이 이미 든 채널에 바깥 에이전트를 넣는 것은 글이 없어도 사람 몫이다. 여기서 사람은 채널 owner인 대신한 사람 말고 다른 사람이다(대신한 사람은 그 일을 부탁한 사람이다). 바깥에서 도는 에이전트가 든 채널의 입장 줄에는 「이 방의 글이 oort 밖으로 나가요」를 적는다.
  - 까닭: 채널에 누군가를 넣는 일이 사람 몫인 것은 그 채널에 쌓인 대화가 새로 들어온 쪽에 보이기 때문이다(바깥에서 도는 에이전트라면 oort 밖으로 나간다). 방금 만든 빈 채널에는 새어 나갈 과거가 없다.
  - 조건이 하나라도 안 맞으면(남이 만든 채널, 글이 있는 채널, 시간이 지난 채널, 게스트나 워크스페이스 멤버가 아닌 대상) 사람 몫이다(E2-3).
  - 넣은 사실과 위 입장 줄은 그 채널의 줄로 보이게 한다 — [확인 필요]. ADR-0186 V0(2026-10-11)은 채널 만들기·멤버 넣기 함수가 감사 행도 outbox도 쓰지 않는다고 적었다. 구현 이슈가 지금 그 줄이 있는지 확인하고, 없으면 이 길에서 서버가 쓴다. 넣어진 사람에게 가는 배지·푸시가 ADR-0220 P2의 사유 밖인지도 같은 자리에서 확인한다.
  - 배경: owner가 2026-10-11부터 바란 「에이전트 하나를 들이면 그 에이전트가 그룹을 꾸린다」(ADR-0186 증보 V3의 발의)를 카드 여러 장 없이 하려는 것이다.
- 처음 값: **새 워크스페이스는 모두 「물어보기」**다. 운영자가 올릴 수 있다(운영 설정이지 기본값이 아니다).
- 값을 바꾸는 것은 워크스페이스 관리자인 **사람**뿐이다. 에이전트는 이 설정을 제안할 수도 없다(E2-6). 바꾼 기록은 감사 행으로 남는다.
- 행동 권한을 바꾸는 라우트와 멈춤 조건을 거는·푸는 라우트(E6)는 **앱(웹·데스크탑·폰)의 사람 세션만** 받는다. 개발자·CLI 토큰 표(ADR-0216 D4)와 사람용 MCP 표에 넣지 않고, 시험이 그 거절을 확인한다.
- 「허용」으로 실행된 행동은 지금 승인 뒤와 같은 실행기를 지난다.
- 「전부 허용」은 없다. 종류 하나씩만 고른다.
- 설정 화면은 종류마다 지난 기간의 물음 수와 승인 수를 보이고(E8), 「허용」 옆에 「이 일을 승인할 수 있는 사람이 직접 시켰을 때만 카드 없이 실행돼요」를 적는다.

### E4. 에이전트 몫과 「에이전트 결정」 줄

- 에이전트 몫: 일을 나누고 순서를 정하기, 어느 에이전트에게 맡길지(맡김 허용 목록 안), 실패한 하위 작업을 다시 시키기(R1의 상한 안), 겹침을 피하는 방법 고르기(E7), 하위 에이전트의 물음에 답하기, 작업 만들기(미결 6을 닫는다 — 아래). 이 목록은 닫혀 있다(E1).
- 어느 모델을 쓸지는 사람이 정해 둔 범위 안에서만 에이전트가 고른다. 단가가 더 높은 모델로 바꾸는 것은 E2-4다. 다만 모델은 에이전트 보고(R1)라 서버가 가르지 못한다. 서버가 지키는 것은 한도이고, 모델 이름은 「에이전트 보고」로 보인다.
- 에이전트가 정한 것은 진행 기록에 **「에이전트 결정」** 줄로 남는다: 무엇을 정했는지, 정한 쪽, 근거가 된 것. 출처는 `agent`다(D3). 서버가 확인한 사실처럼 그리지 않는다.
- 에이전트 몫은 이 작업 안에서 끝나고 되돌릴 수 있는 일뿐이다. 사람은 기록을 보고 뒤집을 수 있다(다시 시키기·멈추기·작업 닫기).
- **질문의 길(D4를 바꾼다).** 하위 작업의 질문은 그 일을 맡긴 오케스트레이터가 먼저 받는다.
  - 질문을 받는 오케스트레이터는 서버가 부모 run에서 정한다. 하위 에이전트는 받는 쪽을 고르지 못하고, 그 부모 run의 lease를 가진 에이전트만 답한다. 부모 run이 없는 일(사람이 직접 맡긴 일)의 질문은 지금처럼 사람에게 간다.
  - 오케스트레이터의 답은 결정 라우트를 지나지 않는다. 승인·질문 카드의 결정 라우트는 계속 사람 principal만 받는다(ADR-0186 D2, 이 문서 D4). 하위 작업의 질문은 처음에는 카드(`approval` 행)가 아니라 진행 기록의 질문 줄(출처 `agent`)이고, 오케스트레이터의 답은 답 줄(출처 `agent`, 「에이전트 결정」)이다. 사람의 말 줄로 남지 않는다.
  - 오케스트레이터가 답할 수 없거나 E6의 묻는 때에 해당하면 사람에게 올린다. 사람에게 올릴 때에만 서버가 질문 카드를 만든다. 사람에게 가는 질문 카드의 틀·받는 사람 한정·결과는 D4 그대로다.
- **질문의 답은 승인을 대신하지 못한다(D4 그대로).** 에이전트가 답한 질문도 어떤 승인 게이트도 채우지 않는다.
- **작업 만들기(미결 6을 닫는다).** 에이전트도 작업을 만들 수 있다. 담당자는 그 일을 맡긴 사람(「대신한 사람」, D2)이고 DB가 사람만 받는 것은 그대로다.
  - 에이전트가 만든 작업의 집 채널은 그 run의 채널이고 에이전트가 고르지 못한다.
  - 사람이 청하지 않은 일에서 생긴 작업의 담당자는 ADR-0220 P3(「소유자, 없으면 관리자」)를 따른다. 서버는 그 작업을 「에이전트가 연 작업」으로 표시하고 「○○ 님 요청으로」를 그리지 않는다(데이터 계약의 「뿌리에 사람이 없으면 거절한다」를 이 경우에 한해 바꾼다). 그 담당자는 부탁한 사람이 아니므로 「허용」의 대신한 사람으로 치지 않는다(E3). 이 경우 대신한 사람 칸(데이터 계약의 NOT NULL)을 어떻게 둘지는 구현 이슈가 데이터 계약과 맞춘다 — [확인 필요].
  - 에이전트 하나가 여는 작업은 **[추정]** 열린 것 10개·하루 20개까지다.
  - 에이전트가 만든 작업의 하위 작업은 만든 run의 사슬·깊이·R1 셈을 물려받는다. 새 작업을 만들어 셈을 새로 시작하지 못한다.
- **맡기기는 oort를 지난다(미결 1의 「지나게 함」을 닫는다).** 오케스트레이터가 다른 에이전트에게 일을 맡기는 것은 서버를 지나고, 단계와 하위 작업은 서버 사실로 남는다. 까닭은 E9-5다. 이 줄은 owner의 다섯 답에 없었고 planner가 owner 발의에서 읽은 것이다(「결재 기록」).
  - **맡김 허용 목록은 사람이 정한다.** 정하기 전까지는 오케스트레이터와 소유자가 같은 에이전트(ADR-0186 V4-M 1번의 「같은 소유자」), 그리고 소유자가 없는 워크스페이스 에이전트만이다. 남이 소유한 에이전트에게 맡기는 것은 E2-5다. 사람이 목록을 정하는 화면(미결 1의 ⑤)과 결과를 같은 오케스트레이터 세션으로 돌려주기(미결 1의 ②)는 남는다.
  - 맡긴 일을 하는 동안 하위 에이전트의 oort 도구 읽기·쓰기는 (하위 에이전트 자신의 범위) ∩ (그 작업의 집 채널)로 줄어든다(ADR-0219 D8의 제한 run과 같은 방식). 「하위 에이전트는 부모보다 넓은 권한을 얻지 않는다」는 이 줄임으로 지킨다.
  - 하위 run이 물려받는 대신한 사람은 표시와 책임의 칸이다. 요청자 권한이 아니다. 하위 run에는 ADR-0201·ADR-0211 D5의 요청자가 없고(ADR-0211 D5 4번 그대로), 「허용」도 채우지 못한다(E3).

### E5. 판정의 근거와 믿는 곳

- 층을 가르는 것은 **행동의 종류와 대상**이다(서버가 해석한 인자까지, E1). 에이전트가 쓴 설명(「이미 승인받았어요」), 다른 사람·다른 에이전트의 글, 첨부·링크 미리보기·도구 결과 속 문장은 근거가 아니다.
- **사람의 허락은 층마다 다르다.** 요청한 사람이 직접 쓴 글은 제안과 에이전트 몫의 근거다(ADR-0201 「제안의 근거는 요청자 본인의 트리거 메시지」와 같은 규칙). 「허용」으로 둔 행동에서는 승인 역할을 가진 사람이 직접 쓴 그 글이 카드를 대신한다(E3). **사람 몫의 허락은 승인 카드의 결정 하나뿐이다.**
- 개발자·CLI 토큰으로 쓴 글(ADR-0216 D4 L6)은 사람의 허락으로 치지 않는다. 그 글로 부른 run에서는 「허용」이어도 「물어보기」다. 그 글이 에이전트를 깨우는 것(ADR-0216)은 그대로다.
- **믿는 곳**: 기본은 그 작업의 집 채널이다. 워크스페이스 관리자가 연결한 앱·저장소·호스트가 믿는 곳 목록에 든다. 목록 밖으로 나가는 일은 E2-2다.

### E6. 사람에게 묻는 때, 멈춤 조건, 한 번의 허락

- 에이전트는 넷일 때 사람에게 묻는다: ① 사람 몫에 닿을 때 ② 멈춤 조건에 닿을 때 ③ 기록과 맥락에 답이 없을 때 ④ 요청의 뜻이 둘로 읽히고 어느 쪽인지에 따라 결과가 크게 달라질 때.
  - ①은 행동을 부르는 순간 서버가 카드로 바꾼다(질문이 아니라 승인이다). ②는 아래 닫힌 조건에 걸리는 oort 경유 호출을 서버가 막는다. 자유 글 질문이 사람 몫이나 멈춤 조건에 닿는지는 서버가 판정하지 않는다. ③·④는 에이전트의 판단이다.
  - 서버가 보장하는 것은 에이전트의 답이 어떤 게이트도 채우지 않는다는 것이고, 화면은 에이전트가 답한 질문을 접지 않고 보인다.
- 받는 사람은 그 일을 맡긴 사람이 먼저다. 그 사람이 그 작업의 집 채널 활성 사람 멤버가 아니게 됐으면 담당자에게 간다(D4의 범위 안에서). 그 밖의 순서는 미결 4의 남은 부분(사람 멤버 안의 순서)이다.
- **멈춤 조건.** 사람이 그 작업에 건 금지는 **서버에 저장**한다. 대화에서 매번 다시 읽지 않는다.
  - 멈춤 조건은 **닫힌 모양 셋**이다: ① 이 작업 전체 멈춤 ② 이 작업에서 행동 종류 금지(레지스트리 id) ③ 이 작업에서 맡기기 금지. 서버가 막는 것은 이 셋에 걸리는 oort 경유 호출이고, 「허용」으로 둔 행동도 막는다. 서버는 조건의 글을 해석하지 않는다(ADR-0220 P6 (a)).
  - 그 밖의 말(「배포는 내가 볼 때까지 기다려」)은 **「전한 말」**로 저장해 그 작업의 매 턴에 에이전트에게 넣는다. 화면에는 「에이전트에게 전했어요 · 서버가 막지는 않아요」로 그린다. 따랐는지는 에이전트의 말이다(ADR-0220 P6 (c)). 에이전트 몫의 판단과 oort 밖의 일은 서버가 보지 못한다.
  - 거는 사람은 그 작업의 집 채널 활성 사람 멤버(게스트 제외)다. 푸는 사람은 건 사람과 담당자다. 에이전트는 걸기를 제안할 수 있고(사람이 받아야 걸린다), 풀기는 제안할 수도 없다. 조건이 채워졌다고 스스로 풀지도 못한다. 거는·푸는 라우트는 앱의 사람 세션만 받는다(E3).
  - 에이전트가 사람의 말을 스스로 읽어 멈춤 조건이나 「전한 말」로 넣는 길은 [확인 필요] — 놓치면 금지가 전해지지 않고, 넘치면 일이 선다.
- **허락은 한 번이다.** 승인은 그 카드의 그 행동에만 통한다. 같은 종류를 거듭 승인하는 것은 「행동 권한」에서 「허용」으로 올릴 일이다(E8).
- **묶음 승인.** 한 계획에서 승인 카드가 여러 장 이어지면(「채널 셋을 만들고 멤버 다섯을 넣을게요」) 카드 하나로 묶어 묻는다. 사람 몫의 카드와 「물어보기」로 둔 행동의 카드에 같은 규칙을 쓴다.
  - 묶을 수 있는 것은 한 계획 안의 워크스페이스 구조 행동(채널 만들기·멤버 넣기 등)이고, 목록은 구현 이슈가 이 줄 안에서 닫아 정한다.
  - **묶지 않고 늘 한 장씩 묻는 것**: 되돌릴 수 없는 일(E2-1), 바깥으로 내보내는 일(E2-2), 1회 값을 만드는 행동(`invite.create`·`agent.invite`), 기기 서명이 필요한 행동(ADR-0210 D3), host 승인(ADR-0188 D3), 개인 연결 토큰 쓰기(ADR-0211 D8), 대화가 있는 채널로 에이전트의 범위를 넓히는 `hosted.channels.grant`.
  - 결정자가 서로 다른 행동은 한 카드에 묶지 않는다. 결정자가 같다는 것은 묶인 모든 행동의 승인 역할과 그 대상이 같다는 뜻이다.
  - 카드는 행동을 하나씩 모두 보이고 접지 않는다. 줄마다 서버가 해석한 값을 보이고(ADR-0186 V1-a), 승인할 때 줄마다 다시 증명한다(V1-d). 묶음 카드는 잠금 화면에서 결정하지 않는다(항상 앱에서 연다).
  - 사람은 통째로 승인하거나 일부를 빼고 승인한다. 뺀 행동에 기대는 뒷 행동은 서버가 함께 뺀다. 남은 행동은 한 트랜잭션에서 모두 되거나 모두 안 된다. 승인은 그 카드에 적힌 행동들에만 통한다(「허락은 한 번」 그대로).
  - 묶음의 상한은 **[추정]** 10개다. ADR-0186 D2(한 실행 한 제안)·v6(한 요청 한 묶음)과의 맞춤은 구현 이슈가 정한다 — [확인 필요].
- **승인을 기다리는 동안 나머지는 계속한다.** 사람 몫에 닿은 걸음만 승인을 기다리고, 같은 작업의 다른 하위 작업은 멈추지 않는다. 사람을 기다리는 시간은 R2의 두 시계에 넣지 않는다(그대로).
- 거절되거나 막힌 행동은 까닭이 에이전트에게 돌아가고, 에이전트는 다른 길을 찾는다. 돌려주는 까닭은 닫힌 코드이고, 기존의 구분되지 않는 거절(ADR-0186 V1-b·U-b-4, 이 문서 D5)은 그대로 둔다. 멈춤 조건의 글과 건 사람은 싣지 않는다.
- 같은 행동을 거듭 시도하면(**[추정]** 연달아 3번, 한 작업에서 모두 20번) 서버가 그 하위 작업을 「문제 있음」으로 올린다. 같은 행동인지는 에이전트가 쓴 글자가 아니라 서버가 해석한 인자로 가린다(글자만 바꿔 셈을 피하지 못한다).

### E7. 겹침

1. 서버가 겹침을 판정한다: 두 작업이 같은 저장소의 같은 경로나 같은 화면에 닿을 때. 재료는 에이전트가 알린 「닿는 곳」(출처 `agent`), 공유된 세션의 폴더(D5·D9), 연결된 PR의 바뀐 파일(출처 `external`)이다.
2. 일하는 중인 두 에이전트에게 신호가 간다. **사람에게 알림이 가지 않는다**(ADR-0220 P2의 사유 여섯을 늘리지 않는다).
3. 에이전트가 고르고 「에이전트 결정」 줄로 남긴다: 안 겹치는 부분만 먼저 하기 · 순서 정하기 · 한쪽으로 합치기.
4. 두 에이전트의 답이 다르거나 범위·기한이 바뀌면 두 담당자에게 질문 카드 하나가 간다.

- 가시성: 겹침은 **두 에이전트와 두 담당자가 모두 양쪽 작업을 볼 수 있을 때만** 판정 결과를 낸다. 아니면 아무에게도 내지 않는다. 겹침을 다룬 「에이전트 결정」 줄과 질문 카드는 양쪽을 다 볼 수 있는 사람에게만 내려 준다. 볼 수 없는 작업이 있다는 사실이 새지 않게 한다(D2·D5와 같은 규칙). 이 조건에서 결과가 나오지 않는 겹침은 지금처럼 합칠 때 드러난다.
- 에이전트가 알린 「닿는 곳」만으로 생긴 겹침은 「에이전트 보고」이고 상대에게 지시가 아니다.
- 판정의 세부 계약(경로 비교·헛경보 줄이기)은 구현 이슈가 정한다.

### E8. 숫자로 지켜본다

- 워크스페이스마다 센다: 사람에게 간 카드 수, 그대로 승인된 비율, 「에이전트 결정」이 사람에게 뒤집힌 수(종류별).
- 쓰임: 그대로 승인이 대부분인 종류는 「허용」으로 옮길 후보로 설정 화면에 보이고, 자주 뒤집히는 종류의 에이전트 결정은 사람에게 묻게 바꿀 후보다. 바꾸는 것은 사람이다.
- 후보를 가릴 때는 사람이 시킨 요청의 카드만 센다(먼저 제안의 카드는 세지 않는다). 표본과 기간의 하한을 둔다(**[추정]** 지난 30일에 카드 20장 이상). 후보가 되는 것은 E3의 닫힌 목록에 든 종류뿐이다.
- 사람별로 묶어 내놓지 않는다(ADR-0220 P4, 이 문서 D6). 종류별·워크스페이스 단위의 수다.

### E9. auto mode에서 가져온 것과 다르게 한 것

1. 가져옴 — **덜 묻는 것이 보호다.** 사람이 읽지 않고 누르는 승인은 보호가 아니다(93%).
2. 가져옴 — **말이 아니라 행동을 본다**(E5).
3. 가져옴 — **말로 한 금지는 에이전트가 풀지 못하고, 허락은 한 번이다**(E6). 다르게 — 금지를 대화에서 매번 읽지 않고 서버에 저장한다(대화가 줄어들어도 남는다). 서버가 막는 것은 닫힌 모양 셋뿐이고, 그 밖의 말은 에이전트에게 전할 뿐이다(E6).
4. 가져옴 — **막혀도 계속한다**(E6).
5. 가져옴 — **맡길 때와 돌아올 때 두 번 본다.** 하위 에이전트에게는 오케스트레이터의 지시가 사람의 말처럼 보인다. 다르게 — 맡길 때 서버가 보는 것은 구조다: 대상이 맡김 허용 목록에 있는가, 깊이(ADR-0132 D3), 작업 ID 상속, 대상이 그 작업의 집 채널 멤버인가, 멈춤 조건, 다시 시키기 상한(R1). 지시 글의 뜻이 처음 요청 안인지는 서버가 판정하지 않는다. 돌아온 결과의 「확인 필요」 표지는 서버가 아는 것(연결된 PR의 바뀐 파일이 알린 「닿는 곳」 밖에 있음)으로만 서버 출처로 붙이고, 오케스트레이터가 붙인 표지는 「에이전트 보고」다. 이 확인이 가능하려면 맡기기가 서버를 지나야 한다(E4).
6. 가져옴 — **넓은 허용은 없다**(E3).
7. 다르게 — **판정은 모델이 아니라 표가 먼저다.** auto mode는 판정도 모델이 해서 놓침이 있다(17%). oort의 워크스페이스 행동은 레지스트리로 닫혀 있어 그 행동의 층은 표로 가른다(레지스트리 밖의 일은 E1). 모델의 판단은 에이전트 몫과 E6 ③·④에만 쓴다.
8. 다르게 — 그 글은 위험이 큰 일에서 사람의 검토를 대신하지 못한다고 적었다. 사람 몫 여섯이 그 자리다.

### 바뀌지 않는 것
- 담당자는 사람만이다(D2). 책임은 사람에게 있다.
- 남에게 온 승인 카드를 다른 사람이 대신 누르지 못한다(D4, ADR-0202 D5, ADR-0188 D3). 「허용」도 대신 승인이 아니다. 결정자는 승인 역할을 가진 채 직접 부탁한 사람 본인이다(E3).
- 실행은 결정자 권한이고, 에이전트는 어떤 시점에도 관리자가 아니다(ADR-0186 D2).
- 승인·질문 카드의 결정 라우트는 사람 principal만 받는다(D4, ADR-0186 D2).
- 질문의 답은 승인을 대신하지 못한다(D4).
- 채널 승인 권한 주체는 관리자다(ADR-0162). 게스트를 채널에 넣는 손은 관리자뿐이고(ADR-0219 O5 (a)), 게스트가 있는 방의 제한(ADR-0219 D8)도 그대로다.
- 초대와 외부 에이전트 데려오기는 늘 관리자 승인 카드다(ADR-0201 증보 v3 B4).
- 먼저 제안의 목록·끄개·한도(ADR-0186 v5)는 그대로다.
- 에이전트가 스스로 만드는 예약·반복 실행은 없다(ADR-0220 P8 금지).
- 먼저 부르는 사유는 여섯뿐이다(ADR-0220 P2). 이 절은 사유를 더하지 않는다. 「허용」으로 실행된 행동의 알림은 채널의 줄이지 푸시 사유가 아니다(그 줄이 지금 있는지는 E3의 [확인 필요]).
- 계획 확인 카드(미결 3)는 이 절이 정하지 않는다. 계획은 알림이고 승인이 아니다(ADR-0220 §3-5 ①)가 그대로다.

### 위협과 방어
- **에이전트가 등급을 낮춰 부른다**: 등급은 에이전트의 인자가 아니라 레지스트리의 칸이다. 행동 이름과 서버가 해석한 인자를 서버가 다시 읽어 판정하고, 한 호출에 층이 섞이면 사람 몫이다(E1).
- **여러 작은 행동으로 사람 몫을 나눠 한다**: 사람 몫의 판정은 행동마다이고, 「허용」의 대상은 닫힌 목록 넷이며 종류마다 상한이 있다(E3). 닿는 조합이 발견되면 그 종류를 E2로 올린다.
- **승인 역할이 없는 사람이 에이전트를 시켜 관리자 전용 일을 한다**: 「허용」은 승인 역할을 가진 사람이 직접 부탁한 때에만 카드를 건너뛴다. 그 밖에는 지금의 카드다(E3).
- **「허용」으로 둔 행동을 되풀이한다**: 종류마다 상한이 있고, 넘으면 「물어보기」로 떨어진다(E3).
- **「새 채널」이 아닌 곳에 넣는다**: 판정은 서버가 만들 때 적은 기록·시간·메시지 0건·한 트랜잭션 넷이다. 게스트는 대상이 아니고, 바깥에서 도는 에이전트는 사람보다 먼저 넣는다(E3).
- **오케스트레이터가 하위 에이전트를 통해 범위를 넓힌다**: 맡긴 일을 하는 동안 하위 에이전트의 oort 도구 읽기·쓰기는 그 작업의 집 채널로 줄어들고, 맡길 때 서버는 구조를 본다(E4·E9-5). 하위 run은 「허용」을 채우지 못한다(E3). 바깥 런타임이 oort 밖에서 하는 일과 자체 기억은 oort가 줄이지 못한다(ADR-0132 D4).
- **에이전트의 답이 승인이 된다**: 오케스트레이터의 답은 결정 라우트를 지나지 않고, 결정 라우트는 사람 principal만 받는다. 답하는 쪽은 서버가 부모 run에서 정한다(E4).
- **글 속 지시(주입)**: E5(읽어 온 글은 근거가 아님)와 사람 몫이 표로 갈리는 것으로 막는다. 「허용」으로 둔 행동도 닫힌 목록·상한·승인 역할을 가진 사람의 부탁 안에서만 실행된다. 에이전트 몫 안의 잘못된 결정은 남을 수 있고, 되돌릴 수 있는 범위다.
- **묶음 카드에 따로 물어야 할 행동을 섞는다**: 묶지 않는 행동의 목록이 닫혀 있고, 줄마다 서버가 해석한 값을 보이며, 잠금 화면에서 결정하지 않는다(E6).
- **관리자가 「허용」을 넓게 올린다**: 사람 몫에는 칸이 없고 대상은 닫힌 목록 넷이다. 올린 기록이 남고, E8의 수가 보인다.
- **멈춤 조건을 에이전트가 푼다**: 거는·푸는 라우트는 앱의 사람 세션만 받는다. 에이전트 토큰과 개발자·CLI 토큰으로는 거절된다(시험). 서버가 막는 것은 닫힌 모양 셋이고, 「전한 말」은 서버가 막지 않는다고 화면이 말한다(E6).
- **사람의 토큰을 빌려 설정을 바꾼다**: 행동 권한을 바꾸는 라우트는 개발자·CLI 토큰 표와 사람용 MCP 표에 없다(E3).
- **에이전트가 작업을 쏟아 내거나 새 작업으로 셈을 새로 시작한다**: 수 상한이 있고, 사슬·깊이·R1 셈을 물려받는다(E4).
- **겹침이나 거절의 차이로 볼 수 없는 것을 알아낸다**: 겹침은 양쪽을 모두 볼 수 있을 때만 결과를 내고(E7), 거절의 까닭은 닫힌 코드이며 구분되지 않는 거절은 그대로다(E6).
