## 배경

DM은 지금 두 사람이다(`POST /v1/workspaces/{ws}/dms {memberId}`). 3명 이상 DM은 ADR-0217로 에이전트가 합류할 때만 생기고, 채널은 관리자만 만들 수 있다(ADR-0128). 그래서 멤버가 즉석에서 몇 명과 이야기할 방이 없다. 이 ADR은 **사람 여럿(과 에이전트)을 골라 새 대화를 만드는** 그룹 DM을 정한다. 이 ADR은 문서만이고 코드·migration은 아래 이슈에서 만든다.

## 선택지와 기각 사유

| 물음 | 채택 | 기각 |
|---|---|---|
| 종류 | `kind='dm'` 유지 | 새 종류 `group_dm`: 기억 적격 검사 `mem_channel_eligible`이 `kind <> 'dm'`에서 통과시켜 **사람 여럿의 사적 대화가 기억 요약 대상으로 조용히 열린다.** `kind='dm'` 분기(2026-11-05 grep: Rust 11파일·TS 43파일·SQL 12파일)를 전수 고쳐야 하고 빠뜨려도 컴파일이 못 잡는다. 구 서버는 모르는 값에서 Decode 오류를 낸다 |

## 결정

### D1. 종류와 표식 — `kind='dm'`을 그대로 쓴다

- 새 ENUM 값·새 테넌트 표·RLS 정책 변경은 없다. 그룹 DM은 `dm_key`가 `group:`(D2)·`admitted:`(ADR-0217)로 시작하거나 활성 참여자가 3명 이상인 DM이다. SQL 함수 `dm_is_group(channel)`이 판정하고 채널 DTO에 가산 필드 `isGroup`으로 싣는다. 클라이언트가 인원 수로 추측하지 않는다(에이전트 허락을 기다리는 2사람 방이나 2명으로 줄어든 방이 1:1처럼 보이면 개인 상태 점·자동 답장 안내가 잘못 붙는다). `dm_is_group`과 D4의 트리거는 SECURITY INVOKER로 두고 안에서 `workspace_id`를 명시 조건으로 건다.
- 기억 적격 검사 `mem_channel_eligible`(102)과 답장 채널의 `count = 2` 검사(100)는 `dm_is_group`이면 거짓이다. 인원이 「사람 1 + 에이전트 1」로 줄어든 그룹도 계속 제외한다.
- 수용: ① 1:1 열기 API·`dm_key` 바이트 불변(골든). ② `dm_is_group` 진리표(두 접두사, 활성 2·3명, 2명으로 줄어든 그룹 = 참). ③ `isGroup`이 `GET …/dms`·만들기·채널 조회 응답에 실린다. ④ 그룹 DM 글의 기억 후보 0건, **나가서 「사람 1 + 에이전트 1」이 된 그룹도 0건** — 그룹 조건을 빼면 RED. 워커 쪽 「후보 0건」만 재지 않고 **기억을 쓰는 DB 함수(102의 `mem_apply_digest`와 104~109의 항목·제안·통합 함수)를 직접 불러 그룹 채널에서 거절되는 것까지** 잰다. `mem_channel_eligible`은 SECURITY DEFINER라 `CREATE OR REPLACE`로만 고치고, 102의 소유자·권한 목록과 `mem_schema_conformance_pg` 시험을 통과해야 한다(`dm_is_group`이 그 안에서 불리므로 소유자 권한으로 `membership`·`channel`을 읽는지도 같은 시험이 잰다).

### D2. 만들기 — 받는 사람 2~9명, 만들 때마다 새 방

- 새 라우트 `POST /v1/workspaces/{ws}/dms/groups` `{memberIds, name?, clientRequestId}`. `memberIds`는 만든 사람을 뺀 받는 사람이며 사람과 에이전트를 섞는다. 응답은 채널 DTO(+`isGroup`)·`created`·에이전트 사전 요청 목록(D6)이다. 경로·필드 이름은 openapi가 확정하되 뜻은 이 ADR을 따르고, 새 라우트는 ADR-0219 T2 분류표(착륙 뒤)에 한 줄 더한다.
- **사람 전용 라우트다(만들기와 D3의 이름 바꾸기 둘 다).** 에이전트 베어러의 닫힌 허용 목록(`momo-auth`의 `agent_scope`)에 올리지 않고 핸들러도 `PrincipalKind::Human`을 확인한다(이중). 현행 `/dms` 핸들러는 주체 종류를 보지 않고 허용 목록 하나에 기대고 있다. 에이전트가 만들기를 부를 수 있으면 만든 사람 membership, 곧 다른 사람의 동의 없는 착석이 서기 때문이다.
- 규칙: 받는 사람 2~9명(방 전체 3~10명), **그중 사람이 1명 이상**. 받는 사람이 1명이면(사람이든 에이전트든) 만들기가 아니라 기존 1:1 열기다(400). 사람 없이 에이전트만 2명 이상 고르면 400이다(혼자 여러 에이전트와 쓰는 방은 이 ADR 밖). 본인·중복·비활성·정지·삭제·없는 id는 어느 id 때문인지 알리지 않고 1:1과 같은 404 「active workspace member not found」다.
- **서버-2 전 단계**: 서버-2의 사전 입장 요청이 서기 전에는 `memberIds`에 에이전트 id가 하나라도 있으면 균일 400으로 거절하고 방·membership·요청을 0으로 둔다(무시하지도, 사람처럼 membership에 넣지도 않는다). 이 거절을 푸는 변경은 서버-2 PR에서만 하고 D6 ⑦ 사보타주와 같은 PR이다. 웹·폰은 서버-2 착륙 전 에이전트 행을 선택 불가로 둔다.
- **그룹은 만들 때마다 새 방이다**(카카오톡 그룹 채팅처럼). 같은 사람들로 또 만들어도 새 방이 생기고, 같은 모음을 한 방으로 합치는 모음 키는 **1:1 DM에만** 남는다(1:1은 같은 두 사람이면 같은 방이고 키는 접두사 없는 해시 그대로다). 그룹 방의 `dm_key`는 만들 때부터 `group:<channel.id>`다. 그룹은 방 id로만 찾으므로 모음으로 방을 다시 찾는 길도, 나간 사람이 되살아나는 업서트(1:1 열기의 `ON CONFLICT (channel_id, member_id) DO UPDATE SET left_at = NULL`)도 없다. 에이전트가 앉으면 키는 ADR-0217대로 `admitted:<channel.id>`로 바뀐다(둘 다 그룹 표식이다).
- **재시도 안전은 요청 단위다.** `clientRequestId`는 1~128자 `[A-Za-z0-9_-]`다. 같은 만든 사람이 같은 `clientRequestId`로 다시 보내면(응답을 못 받은 재시도) 같은 방을 돌려준다(`created=false`, 재생은 속도 제한을 더 쓰지 않는다). ADR-0208의 재시도 멱등을 따르되, 같은 id에 받는 사람·이름이 다른 본문이 오면 옛 방을 돌려주지 않고 409다(0208은 옛 행을 돌려주지만 구성이 다른 방을 돌려주면 안 된다). **본문 비교는 저장한 요청 지문으로 한다**: `channel`의 nullable 열 둘(`clientRequestId`와, 받는 사람·에이전트 id를 정렬하고 이름을 D3로 정규화해 이은 값의 SHA-256 지문)과 부분 유일 인덱스(`workspace_id` + 만든 사람 + `clientRequestId`)를 둔다. 현재 membership과 비교하지 않는다(누가 나간 뒤의 정상 재시도가 409가 되면 안 되고, 대기 중 에이전트는 membership이 아니다). **재생 응답 전에** 만든 사람이 지금도 그 방의 활성 참여자(`left_at IS NULL`)이고 방이 보관되지 않았는지 확인하며, 아니면 방 정보 없는 409다(나간 뒤 방 이름·참여자를 돌려주지 않는다). 새 테넌트 표는 없고, 같은 사람들로 **새** `clientRequestId`를 보내면 새 방이다.
- **속도 제한(남용 방지)**: 방마다 허락 카드가 사람 전원에게 가고(최대 20장) 입장 요청은 에이전트 보류 행동 한도에서 제외돼 있어(ADR-0217) 아래 제한이 유일한 제어다. 현행 프로세스 메모리 제한기(`rate_limit.rs`)는 재시작하면 리셋되고 복제본마다 따로 세며, 모든 제한기가 `RATE_LIMIT_WINDOW_SECONDS` 하나를 공유하고, 멤버별 쓰기 예산(#4234, ADR-0208 D10 증보)은 지정한 라우트에만 달려 있어 새 라우트가 자동으로 걸리지 않는다. 그래서 방식을 정한다. ① 만든 사람당 시간 창과 하루 창([추정] 시간당 20·하루 60). ② 같은 받는 사람이 든 새 그룹 만들기 상한(만든 사람 + 한 사람 쌍 기준, 24시간, [추정] 5개). ③ 만든 사람당 허락 대기 중인 요청이 있는 방 수 상한([추정] 3개). ④ **DB 조회 기반 하드 캡**: 만든 사람의 최근 1시간 `channel.created_by`·`created_at` 개수를 멤버별 advisory lock 아래에서 세어(ADR-0208의 대기 상한과 같은 방식) 상한을 넘으면 거절한다. 재시작·복제본에 흔들리지 않는 백스톱이고 프로세스 메모리 제한기는 앞단이다. ⑤ 만들기와 D3의 이름 바꾸기를 멤버별 쓰기 예산 목록에 더한다. ⑥ 429에는 감사 행을 남긴다(멤버별 제한의 기존 `rate_limit.exceeded` 관례). 숫자는 [추정]이고 서버-1b가 확정한다.
- 방·`channel_seq`·사람 membership·에이전트 사전 요청·「○○님이 이 대화를 만들었어요」 시스템 줄은 **한 트랜잭션**이다.
- 수용: ① 받는 사람 1명·10명·사람 0명은 400, 2명·9명은 성공(10명 방 생성). ② 같은 모음으로 두 번 만들면(새 `clientRequestId`) 방 id가 다른 새 방 둘이고 처음 방의 membership·글은 그대로다. ③ 같은 `clientRequestId` 재시도(동시 포함) → 방 1개, `created=false`, 새 요청·카드 0, 제한 추가 소모 0. 같은 id에 다른 본문 → 409(지문 비교를 빼면 RED). **다른 참여자가 나간 뒤의 정상 재시도 → 200.** **만든 사람이 나간 뒤(또는 방이 보관된 뒤)의 재생 → 방 정보 없는 409.** 형식을 어긴 id → 400. ④ 모든 그룹 방의 `dm_key`는 만든 직후부터 `group:<channel.id>`이고, 1:1 열기는 같은 두 사람이면 같은 방·같은 키다(골든). ⑤ 트랜잭션 중간 실패(강제) → 방·membership 0. ⑥ **속도 제한**: 초과 → 429이고 감사 행이 서며 방·카드가 늘지 않는다. 제한기 상태를 초기화(재시작 모의)한 뒤에도 DB 하드 캡이 같은 429를 낸다(메모리 제한기만 켠 시험은 재시작 뒤 통과하므로 DB 캡 시험이 따로 필요하다). 쌍 상한과 동시 대기 방 상한도 각각 429이고, 각 제한을 빼면 해당 시험이 RED다. ⑦ 서버-2 전 단계: 에이전트 id가 든 요청 → 400, 방·membership·요청 0. ⑧ 사람 전용: 에이전트·work-host 베어러 → 거절(허용 목록), 그리고 허용 목록을 우회해 핸들러를 직접 부른 시험에서도 에이전트 주체 → 거절(핸들러 검사를 빼면 RED).

### D3. 이름 — 선택, 비우면 참여자 이름, 참여자 누구나 바꾼다

- `channel.name`(nullable)에 저장한다. 앞뒤 공백을 지우고 NFC로 정규화한 뒤 1~60자이며, 유니코드 제어(Cc)·서식(Cf) 문자는 금지한다(방향 전환·제로폭 문자로 푸시 제목과 시스템 줄에서 다른 사람을 흉내 내지 못하게). `channel_name_required_ck`·`channel_name_uniq`가 이미 dm을 빼서 제약 변경은 없고 같은 이름의 방이 여럿이어도 된다. 만들 때 `name`은 선택이다. 1:1의 이름은 NULL이고 바꿀 수 없다.
- **비우면 화면이 참여자 이름으로 짠다**(카카오톡처럼): 나를 뺀 3명까지 이름을 쉼표로 잇고 더 있으면 「외 N명」(9명 방에서 제목줄이 넘치지 않게). 참여자가 나가면 라벨도 따라 바뀐다. 코어 `channelLabelParts`를 이 규칙으로 바꾼다.
- **누가 바꾸나**: 그 방의 활성 **사람** 참여자 누구나(방장 없음). 에이전트·참여자가 아닌 관리자·나간 사람은 못 바꾼다. 이름은 **모든 참여자에게 같다**(카카오톡 일반 방의 이름 적용 범위는 공식 문장을 확인 못 했고, oort는 방장이 없어 공유 이름 하나로 정한다). 바꾸기는 `PATCH /v1/workspaces/{ws}/dms/{ch}` `{name}`이고(사람 전용, D2) 감사 + 시스템 줄(「○○님이 이름을 …로 바꿨어요」)이다. 비우면 이름이 지워져 위 라벨로 돌아간다. 바꾸기는 멤버별 쓰기 예산을 쓴다(D2).
- 수용: 61자·공백뿐·제어/서식 문자 → 400. **판정 순서는 참여자 확인(404)이 먼저, 1:1 거절(400)은 그다음이다**(비참여자가 그 id가 1:1 방임을 알지 못하게). 비참여자·나간 사람의 바꾸기 → 404. 에이전트 principal의 바꾸기 → 403. 참여자의 1:1 이름 바꾸기 → 400. 바꾸기 뒤 감사 행 1·시스템 줄 1. 이름을 비우면 라벨이 참여자 이름 규칙(3명 + 외 N명)으로 돌아온다.

### D4. 최대 10명 — 방 전체(만든 사람·에이전트 포함), DB 트리거가 백스톱

- 활성 참여자(`membership.left_at IS NULL`, 사람+에이전트)는 10명을 넘지 못한다. **세는 방식은 하나**다: 같은 SQL 함수로 `left_at IS NULL` 행 수를 세어 API·착석·트리거가 같은 값을 본다(정의가 갈리면 마지막 허락 투표가 15분 동안 매번 롤백된다). 정지된 사람은 복권하면 돌아오는 자리라 센다(영향은 에이전트 착석 한 자리에 한정된다). 삭제(추방)는 membership을 지운다(ADR-0128 D3). 세 겹으로 막는다. ① 만들기 API: 받는 사람(사람+고른 에이전트) ≤ 9. 허락을 기다리는 에이전트도 이 9에 센다(착석해도 11이 되지 않게). ② 에이전트 착석의 마지막 허락 트랜잭션(만들 때의 요청과 ADR-0217 `@` 경로 모두): 활성 수 + 1 > 10이면 착석하지 않고 요청을 종결하며 「대화가 가득 찼어요」 줄을 남긴다. ③ **DB 백스톱**: `kind='dm'` 채널의 `membership` INSERT와 `left_at`을 NULL로 되돌리는 UPDATE(착석 업서트가 이 길로 재진입한다)에서 **BEFORE ROW 트리거**가 `channel_seq` 행을 `FOR UPDATE`로 먼저 잠근 뒤 활성 수를 세어 10을 넘으면 거절한다(잠금 순서가 보내기·착석의 `channel_seq` → membership과 같다). 트리거가 스스로 잠그므로 호출 코드가 잠금을 빠뜨려도 병행에서 새지 않는다.
- **통과 조건은 좁게 둔다.** 잠글 `channel_seq` 행이 membership보다 먼저 있어야 하므로 그룹 만들기는 방과 `channel_seq`를 먼저 만들고 그 뒤 membership을 넣는다. 한 문장 CTE의 실행 순서는 정해져 있지 않으므로 트리거는 `channel_seq`가 보이는지에 기대지 않는다: 보이면 잠그고 세고, 안 보이면(방을 만드는 같은 문장) 잠금 없이 센다. 같은 명령에서 앞서 처리된 행도 센다(PostgreSQL은 BEFORE ROW 트리거의 질의가 같은 명령의 앞선 행 변경을 본다고 문서화한다. 이 가정은 아래 11행 시험으로 못 박는다). 그래서 현행 1:1 열기(방당 2행)는 막히지 않고, 새 방에 한 문장으로 11행을 넣는 길도 11번째 행에서 막힌다.
- 기존 방은 소급하지 않는다. 10명을 넘는 기존 DM이 있으면 더 늘지 못할 뿐이다(migration PR이 그 수를 조회해 본문에 적는다. 기대값 0).
- 수용: ① 10명 방은 만들어지고 11번째 membership은 API 경로와 직접 SQL(비우회 역할) 둘 다에서 거절된다. ② 에이전트 착석이 11번째가 되면 착석 0·카드 종결(앱 검사). ③ **병행(직접 SQL)**: 비우회 역할 연결 둘이 같은 9명 방에 `INSERT INTO membership`을 동시에 실행하면 정확히 한 건만 성공한다. API 경로의 병행은 `lock_room`과 앱 검사가 이미 직렬화해서 트리거를 빼도 GREEN이므로, 트리거의 RED는 이 직접 SQL 시험이 맡는다. ④ **11행 한 문장**: 새 `kind='dm'` 방을 만들면서 membership 11행을 한 문장으로 넣는 직접 SQL → 거절. ⑤ 트리거를 빼면 ①의 직접 SQL·③·④가 RED. ⑥ 1:1: 새로 열기와 이미 있는 1:1 다시 열기가 트리거가 있어도 같은 응답으로 통과하고(골든), 동시 「보내기 + 열기」를 반복해도 교착(40P01) 0건이다. ⑦ 정지된 멤버가 낀 방의 마지막 허락: 앱 검사와 트리거가 같은 값을 봐서 롤백이 반복되지 않는다.

### D5. 대화 중에는 사람을 더하지 않는다 — 「사람 더하기」는 새 그룹 만들기

- 방의 사람 참여자 집합은 늘지 않는다. 1:1이든 그룹이든 사람을 더하는 API·화면은 없다. 사람을 바꾸려면 **새 그룹 만들기 화면**을 현재 사람 멤버로 미리 채워 연다. 새 방이 생기고(D2) 기존 방과 기록은 그대로다. 앉은 에이전트와 그 동의·기록은 새 방으로 따라가지 않는다(에이전트는 새 방에서 다시 고르고 D6의 동의를 새로 받는다). 방 안 직접 더하기를 다시 열려면 읽기 하한(ADR-0219 `history_from_seq`)과 좌석 폐기 규칙을 갖춘 새 결정이 필요하다.
- 이미 있는 막음을 사실로 인용한다. 관리자용 채널 멤버 추가·제거(`add_channel_member_in_tx`·`remove_channel_member_in_tx`)는 `kind IN ('public','private')`로 DM을 이미 제외한다.
- 수용: ① 관리자의 채널 멤버 추가·제거 라우트가 1:1·그룹 DM에 404(회귀 시험, 코드 변경 없음). ② 같은 모음으로 다시 만들면 새 방이고 기존 방의 membership은 늘지도 줄지도 않는다. ③ 「사람 더하기」 진입은 새 그룹 만들기이며 사람만 미리 채운다(에이전트는 채우지 않는다).

### D6. 만들 때 고른 에이전트 — 사전 입장 요청, 전원이 허락해야 앉는다 (ADR-0217 증보)

- 받는 사람에 에이전트가 있으면 방은 **사람만 활성**으로 만들어지고, 에이전트마다 ADR-0217 결정 2~3의 입장 요청이 같은 트랜잭션에서 선다(서버-2가 서기 전에는 D2의 거절이 이 절을 대신한다). 만든 사람을 뺀 활성 사람 모두에게 각각 15분짜리 `dm.agent.admit` 카드가 가고(본인만 결정한다. 관리자·에이전트 소유자·만든 사람이 대신 못 한다), 전원이 허락한 마지막 트랜잭션에서 호출 권한과 연결의 생존을 다시 증명한 뒤에야 에이전트 membership이 생긴다. 한 명의 거절·만료·취소면 착석 0이고 방은 사람만 남는다. 같은 방에서 다시 부르려면 `@`(ADR-0217)다.
- **허락 전 에이전트는 membership이 아니다.** 읽기·쓰기·푸시·실시간·받은함이 0이다. 착석 뒤 읽기는 착석 이후 글뿐이다(ADR-0217 결정 5의 시각 + seq 하한).
- **화면에서 보이는 대기.** 만들기 화면에서는 고른 에이전트에 `허락 후 입장` 꼬리표가 붙고 「다른 분이 모두 허락하면 들어와요. 허락 전에는 대화를 보지 못해요」 한 줄이 선다. 초대받은 사람의 화면에서는 새 대화에 「△△을 이 대화에 부르고 싶어 해요」 허락 카드(허락·거절, 15분)가 서고, 허락하기 전에는 그 에이전트가 멤버 목록이 아니라 「허락 기다리는 중」 줄로만 보인다(대기 표시는 서버가 쓴 카드의 상태에서 그린다).
- **카드 문구.** 사전 요청 카드의 「읽는 범위」 행은 「들어온 뒤의 글만 봐요. 이전 대화는 보지 않아요」다(요청 줄은 내용이 없으므로 `@` 요청 카드의 「부른 메시지 하나」를 쓰지 않는다). 에이전트가 외부(hosted) 런타임이면 「이 대화의 글이 외부 런타임으로 전달돼요」 행을 더한다. 최대 8명이 한꺼번에 동의하는 자리라 무엇을 허락하는지가 카드에 그대로 보여야 한다.
- **요청 메시지는 서버가 쓰는 내용 없는 시스템 줄**(「○○님이 △△을 이 대화에 부르고 싶어 해요」)이다. 에이전트가 착석 뒤 읽는 예외 한 건이 이 줄이다. 만든 사람의 첫 글이나 클라이언트가 가리킨 메시지는 요청 메시지가 될 수 없다(다른 사람 글이 예외로 새는 길을 만들지 않는다).
- 입장 전용이다. 착석 뒤 작업(run) 전달이 없고(`vote_in_tx` 끝의 요청 글 작업 전달을 사전 요청에서는 건너뛴다) 답장은 ADR-0217 결정 7(명시적 멘션·기존 스레드 깨움)을 따른다. 허락을 기다리는 동안 그 에이전트를 `@`로 부른 글은 같은 대기 요청에 합쳐질 뿐 작업으로 전달되지 않는다(착석 뒤 다시 부른다). 에이전트마다 요청·카드가 따로이고 카드 수는 인원 상한이 묶는다(만든 사람을 뺀 사람 수 × 에이전트 수, 최대 20장, 사람당 최대 8장).
- `created=false`(같은 `clientRequestId`의 재시도)로 답할 때는 새 요청을 만들지 않는다. **방마다 동의를 새로 받는다.** 거절·만료된 뒤 같은 사람들과 같은 에이전트로 다시 만들면 새 방이고 새 요청·새 카드다(이전 방의 거절은 이어지지 않으며 반복은 D2의 속도 제한이 막는다). 허락을 기다리는 동안 사람이 나가면 요청은 무효가 되고 나가기 트랜잭션이 정리한다(D9).
- 수용: ① 에이전트 포함 만들기 → 에이전트 membership 0, 요청 = 에이전트 수, 카드 = 요청 × (만든 사람을 뺀 사람 수). ② 허락 전 에이전트의 읽기 0·쓰기 INSERT 거절. ③ 전원 허락 → 착석, 이후 글만 읽고 예외는 시스템 줄 1건이며 만든 사람의 첫 글은 읽지 못한다. ④ 한 명 거절·만료 → 착석 0·형제 카드 취소. ⑤ 본인 외 결정 거절. ⑥ 착석 뒤 작업 전달 0, 대기 중 `@` 멘션도 새 요청 0·작업 전달 0. ⑦ 전원 동의 검사를 빼면 RED(사보타주). ⑧ 같은 `clientRequestId` 재시도 → 새 요청 0. ⑨ 거절·만료 뒤 같은 모음으로 다시 만들면 방 id가 다른 새 방이고 새 요청·카드가 선다(이전 방은 그대로 사람만 남는다). ⑩ **소유자 전용 에이전트가 앉은 그룹에서 소유자가 아닌 사람의 스레드 답글 → 작업 전달 0**(스레드 깨움도 `delivery_gate`를 보낸 사람 기준으로 부른다: `agent_mentions.rs`의 깨움 경로가 같은 함수를 `send`로 호출한다). ⑪ 사전 요청 카드의 문구 행(읽는 범위·hosted 전달)이 위 규칙대로 선다.

### D7. 누가 어떤 에이전트를 넣을 수 있나

**넣는 권한 = 만든 사람이 그 에이전트를 지금 `@`로 부를 수 있는 권한**이다(ADR-0217 결정 1의 호출 판정, 만든 사람 기준). 요청을 세울 때와 마지막 허락 때 두 번 증명한다. 착석은 호출 권한을 넓히지 않는다. 소유자만 부를 수 있는 에이전트가 앉아도 다른 사람의 호출은 기존 gate가 거절한다. 관리자도 에이전트 소유자도 대신 고르거나 대신 허락하지 못한다.

| 에이전트 | 만들 때 고를 수 있나 | 근거 |
|---|---|---|
| 모두가 부를 수 있는 에이전트(팀 AI 등) | 활성 사람 누구나 | 호출 판정 통과 |
| 소유자만 부를 수 있는 에이전트(구독·커넥터 소유) | 그 소유자만. 다른 사람에게는 후보로 안 보이고 서버도 거절 | 기존 owner-only 규칙 |
| 개인 에이전트 | 아무도 못 고른다 | ADR-0217: 개인 에이전트는 동의 좌석 대상이 아니다 |
| 멈춤·은퇴·삭제·두뇌 불가·연결 끊김·시험 조건 미충족 | 못 고른다 | 기존 호출 제한 |
| 외부(hosted) 에이전트 | 활성 연결이 있을 때만. 동의한 연결 id를 요청에 고정하고 바뀌면 재동의 | ADR-0217 위협 「런타임 바꿔치기」 |
| 게스트가 만드는 그룹 | D11 | ADR-0219 D-4 |

- 후보 목록은 코어의 호출 가능 판정(`dmCallableAgent`, 개인 에이전트 제외)으로 거르지만 **표시는 권한이 아니다.** 서버가 증명한다. 고른 에이전트 중 하나라도 증명에 실패하면 만들기 전체가 거절되고 방은 만들어지지 않는다(일부만 만드는 길 없음). **거절은 균일하다**: 개인 에이전트·소유자 전용·멈춤·끊김을 서로 다른 코드나 문구로 답하지 않는다(다른 사람의 개인 에이전트 id를 가려내는 오라클이 되지 않게).
- 수용: ① 소유자만 부를 수 있는 에이전트를 소유자가 아닌 사람이 고름 → 거절·방 0. ② 개인 에이전트·멈춘 에이전트·연결 끊긴 에이전트 → 거절·방 0. ③ 위 거절들의 응답 본문·상태가 서로 같다(바이트 동일). ④ 소유자는 같은 에이전트로 성공. ⑤ 마지막 허락 때 에이전트가 멈췄거나 연결이 바뀌었으면 착석 0, 허락은 소비되지 않는다(ADR-0217). ⑥ 관리자의 대리 결정 거절.

### D8. 첫 글 전에는 남에게 보이지 않는다

- 화면은 **초안 대화**로 두었다가 첫 보내기에서 방을 만든다(방 id는 그때 생긴다). 그래도 보내기 실패·앱 종료로 빈 방이 남을 수 있어서, 서버는 `channel_seq.last_readable_seq = 0`(읽을 글 없음. 시스템 줄은 세지 않는다. 146·126과 같은 정의)인 그룹 방을 **만든 사람 외의 목록·푸시·받은함에 내지 않는다.** 에이전트 입장 요청 카드는 읽을 글이라 그 방은 만들 때부터 사람 전원에게 보인다.
- 같은 사람들의 방이 이미 있어도 새로 만들면 새 방이므로 「이미 있던 대화」 안내는 없다. 읽을 글 없이 남은 빈 방은 만든 사람이 나가면 보관된다(D9 ⑤).
- 수용: 시스템 줄만 있는 방 → 만든 사람 외의 `GET …/dms`·푸시·받은함 0건, 첫 읽을 글 뒤 각 1건. 에이전트 요청이 있는 방은 만든 직후 사람 전원에게 카드 푸시(`approval` 종류).

### D9. 나가기 — 그룹에서만, 참여자 누구나 (ADR-0128 D4 증보)

- `DELETE …/channels/{ch}/members/me`는 `dm_is_group`일 때 허용한다(`leave_channel_in_tx`의 dm 거절을 그룹에 한해 푼다). 1:1은 계속 거절하고 「닫기」만 있다. **나가기는 `channel_seq` 행 잠금(`lock_room`)을 가장 먼저 잡고 membership·channel 행은 그 뒤에 잡는다**(보내기·착석과 같은 순서). 현행 `leave_channel_in_tx`는 membership·channel 행만 `FOR UPDATE`로 잡고 `channel_seq`를 잠그지 않으므로 그룹 분기가 이를 바꾼다. 거꾸로 잡으면 hosted 에이전트가 앉은 방에서 보내기와 교착(40P01)이 난다. 마지막 사람 판정도 이 잠금 아래에서 센다(READ COMMITTED에서 마지막 두 사람이 동시에 나가면 서로의 미커밋 변경을 못 봐서 둘 다 「남았다」고 볼 수 있다).
- 같은 트랜잭션에서 한다. ① `left_at` 설정. ② 이 방의 **대기 중 입장 요청을 취소**한다(admission `revoked_at`, 형제 카드 `cancelled`, 보류 run 종료). 청중이 바뀐 요청의 마지막 허락이 오류가 아니라 거절로 끝나게 하려는 것이다. ③ 시스템 줄 「○○님이 나갔어요」. ④ 내 `dm_closure` 행 삭제. ⑤ 마지막 활성 사람이면 방을 보관하고 앉은 에이전트 좌석을 끝낸다(ADR-0128 private 규칙, ADR-0217 내보내기 함수). **키는 바꾸지 않는다.** 그룹 방은 만들 때부터 `group:<channel.id>`이고 에이전트가 앉으면 `admitted:<channel.id>`이며 둘 다 그룹 표식이다. 코어 `removableDmAgents`는 `admitted:` 접두사로 앉은 에이전트를 알아본다.
- 나간 뒤 그 방의 **읽기·쓰기·검색·푸시·받은함·스레드·첨부는 0이고 과거 글도 못 본다.** 새로 구독하는 길도 구독 프록시가 라이브 membership을 확인해 막는다. 다시 들어오는 길은 없다(새 그룹으로 초대받는다). 이력 GET은 `is_channel_member`(`left_at IS NULL`)가 이미 막는다. 스레드·첨부·검색 길이 같은 함수를 쓰는지는 라우트별로 점검한다.
- 나가기는 앉은 에이전트를 내보내지 않는다(동의한 사람이 줄 뿐 새 읽기 주체가 없다). ADR-0217 결정 3의 「사람이 추가되거나 나가면 기존 동의를 재사용하지 않는다」는 **대기 중인 요청에만** 적용한다.
- **남는 위험(수용)과 후속.** 나간 사람이 **이미 열어 둔 실시간 연결**은 이 서버에 구독 해제 호출이 없어서(`ephemeral_grant`의 주석: 구독은 다시 구독할 때만 다시 인가된다) 재연결·재구독 때까지 새 글을 받을 수 있다. 허용 지연의 상한은 없다. 추방(ADR-0128 D3)과 private 채널 나가기에 이미 있는 한계와 같다. 닫는 길은 후속 서버-4(Centrifugo 구독 해제 호출 + 나가기와 같은 트랜잭션에서 그 채널의 outbox 파티션에 넣는 해제 행으로 이후 글보다 먼저 처리되게 순서 보장 + 실패 재시도와 알림 + 모의 기록과 실 Centrifugo 스모크 1회)다. 서버-4가 서기 전에는 이 한계를 승격 PR 본문에 적고 owner가 수용 여부를 정한다.
- 수용: ① 1:1 나가기 거절 유지, 그룹 나가기 성공. ② 나가기 뒤에도 `dm_key`는 그대로(`group:`·`admitted:`)이고 `admitted:` 방에서 사람이 나가도 에이전트 내보내기가 계속 된다. ③ 대기 중 요청이 있는 방에서 나가면 카드 `cancelled`, 남은 사람의 뒤늦은 결정은 오류(500)가 아닌 거절. ④ 나간 뒤 이력·스레드·첨부·검색 GET은 거절 또는 0건, 푸시·받은함 0, **새 구독 요청은 프록시가 거절**. ⑤ 마지막 사람이 나가면 보관·좌석 종료(읽을 글 없는 빈 방도 같다). ⑥ `group:` 방에 에이전트가 합류한 뒤 내보내면 그 에이전트의 새 글 INSERT가 막힌다(156 가드). ⑦ 나간 사람이 있는 모음으로 다시 만들면 이전 방과 무관한 새 방이고 나간 사람의 이전 방 membership은 `left_at`이 유지된다. ⑧ **경합**: 동시 나가기 2건(마지막 두 사람) → 보관 1회·좌석 종료. 동시 보내기 + 나가기를 반복해도 교착(40P01) 0건. 나가기와 마지막 허락 투표의 경합에서 착석 0 또는 거절이며 500 없음. 잠금 순서를 거꾸로 하면 ⑧이 RED.

### D10. 권한 — 방장이 없다

- 이름 바꾸기(D3)·나가기·에이전트 내보내기(ADR-0217 결정 6)는 참여자 누구나 한다. 사람이 다른 사람을 내보내는 길은 없다(세 레퍼런스의 일반 방에도 없다). 워크스페이스 추방(ADR-0128 D3)은 전 채널 membership을 빼므로 그룹에서도 빠진다. 정지된 사람의 membership은 남아 자리를 차지하고 복권하면 돌아온다(D4). 워크스페이스 관리자는 그룹 DM 내용을 읽지 못하는 현행 그대로다.
- 수용: 비참여 관리자의 이름 바꾸기·나가기·에이전트 내보내기 → 404. 추방된 사람의 membership은 모든 그룹에서 없어지고(ADR-0128 D3의 `DELETE FROM membership` 그대로) 그 뒤 활성 수·푸시 대상·받은함 수신자에 세지 않는다.

### D11. 게스트

- 만들기는 모든 참가자 쌍에 `visible_person`을 요구한다(ADR-0219 감사 D-3이 미리 정한 규칙). 어느 쌍이 안 맞는지 알리지 않고 1:1과 같은 404를 쓴다. **ADR-0219 구현이 착륙하기 전에는** 만든 사람과 받는 사람 전원이 비게스트일 때만 허용한다. 여기서 게스트의 기준은 **워크스페이스 역할**(`workspace_membership.role = 'guest'`, ADR-0219 D1이 정본으로 정한 값이며 `active_workspace_role`이 읽는다)이고 채널 `membership.role`은 보지 않는다. 게스트 초대는 지금 멈춰 있어도 기존 게스트 행은 있을 수 있어서 이 검사가 필요하다. 착륙 뒤 에이전트 후보는 ADR-0219 D-4를 따른다(`visible_person` ∩ 게스트 호출을 허용한 에이전트).
- 수용: 워크스페이스 역할이 게스트인 사람이 만들거나 받는 사람에 들면 착륙 전 거절. 착륙 뒤 T3 진리표에 그룹 만들기 행(모든 쌍)을 더한다. 보이지 않는 사람이 응답·카드 문구에 나타나지 않는다.

### D12. 알림·받은함·검색·읽음 — 1:1과 같다

- 알림은 작성자 외 활성 사람 전원에게 모든 새 글이다(`dm` 알림 종류, 방별 음소거 그대로). 푸시 제목은 이름 또는 「A, B 외 N명」, 본문은 「보낸 사람: 미리보기」다(ADR-0204 표시에 셋째 행). 받은함 `dm` 항목은 다른 참여자 전원이고 나간 사람은 즉시 수신자에서 빠진다(ADR-0199 D2). 검색은 현재 membership으로 좁힌다. 읽음은 멤버별 seq 커서이고 에이전트의 읽기를 다른 사람의 읽음으로 보지 않는다. 「멘션만」 단계는 이 ADR 밖이다(ADR-0206 D7의 저장 방식을 따라 후속).
- **결과를 알리는 시스템 줄은 푸시·받은함 0이다.** 푸시 후보는 모든 메시지 종류에서 생기고 현행 판정 SQL의 `dm` 분기는 메시지 종류를 보지 않으며, 받은함 투영은 text·artifact만이라 받은함은 이미 0이다. 이 ADR의 시스템 줄 네 종류(`group_created`·`member_left`·`renamed`·`agent_invited`)가 참여자 최대 9명 전원에게 푸시가 되지 않게 `dm` 분기에서 `message_type = 'system'`만 거른다. ADR-0217의 합류·내보내기 결과 줄(`dm_agent_membership`의 `joined`·`removed`)도 같은 필터를 받는다(사실 기록이지 알림이 아니다).
- **동의 요청은 지금처럼 알린다.** ADR-0217에서 상대에게 「에이전트를 들여도 될까요?」를 묻는 것은 시스템 줄이 아니라 `approval_request` 카드다(`dm_agents.rs`의 `propose_in_tx`가 사람마다 `MessageType::ApprovalRequest`로 쓰고, `System`으로 쓰는 것은 합류·내보내기 결과 줄 둘뿐이다). 푸시는 판정 SQL에서 `dm` 분기보다 앞서는 `approval` 분기가 카드의 대상자에게 보내고(ADR-0217의 pinned target 판정), 받은함은 승인 항목을 저장하지 않고 첫 페이지의 `approvalsPending` 라이브 조회로 합친다(ADR-0199 D2, `inbox.rs`). 그래서 필터는 `message_type = 'system'`에만 걸고 `approval_request`는 건드리지 않는다. 이 ADR의 만들 때 사전 요청도 같다: 요청 줄(`agent_invited`)은 푸시 0이고 알림은 카드가 맡는다.
- 수용: 푸시 대상 수 = 활성 사람 − 작성자(에이전트 제외). 나간 사람의 받은함 0. **판정 SQL 단독 시험**: 그룹 DM의 시스템 줄 네 종류와 ADR-0217의 결과 줄 → 푸시 판정 0행, 사람 글은 1행 이상(종류 필터를 빼면 RED). **동의 요청 카드(`approval_request`, 사전 요청과 `@` 요청 둘 다)는 현행 그대로 대상자에게 `approval` 푸시 판정이 서고 받은함 `approvalsPending`에 보인다**(필터를 `approval_request`까지 넓히면 RED).

### D13. 이 ADR이 하지 않는 것

방 안 사람 더하기 · 사람이 사람을 내보내기 · 같은 모음을 한 방으로 합치기(그룹) · 지난 대화 공개 선택(Slack) · 조용히 나가기(카카오) · 「멘션만」 알림 단계 · **채널로 바꾸기**(채널은 관리자만 만든다는 규칙과, DM 시절 글이 새 멤버에게 보이는 사생활 등급 변화 때문에 읽기 하한과 관리자 규칙을 갖춘 뒤 별도 증보) · 사람 없이 에이전트 여럿과 쓰는 방 · 열린 실시간 구독 해제(후속 서버-4). 10명을 넘는 모임은 채널이 맞고 안내는 「더 많은 사람이 필요하면 관리자에게 채널을 요청하세요」다.

### D14. 롤링 배포 호환

새 ENUM 값이 없고 `isGroup`은 가산 필드라 구 서버·구 클라이언트가 깨지지 않는다. 구 클라이언트는 에이전트 허락을 기다리는 방이나 2명으로 줄어든 그룹을 1:1처럼 그릴 수 있다(수용. 3명 이상은 이미 「· N명」으로 그려진다).

## 위협과 방어

- **나간 사람 복귀**: 그룹은 모음으로 다시 찾지 않고 되살리는 업서트가 없다(방 id로만 접근). 나가면 새 그룹으로 초대받아야 한다.
- **동의 없는 에이전트 읽기**: 사전 요청도 전원 허락 전에는 membership 0. 요청 메시지는 서버가 쓴 내용 없는 줄. 호출 권한을 두 번 증명하고 개인 에이전트는 제외한다. 새 방에는 앉았던 에이전트·동의·기록이 따라오지 않는다. 만들기·이름 바꾸기가 사람 전용이라 에이전트가 동의 없이 착석하는 입구도 없다(허용 목록 + 핸들러 이중).
- **카드 반복·남용**: 방마다 허락 카드가 가므로 메모리 제한기만으로는 재시작과 복제본에 뚫린다. 만든 사람당 창, 받는 사람 쌍 상한, 동시 대기 방 상한, DB 하드 캡, 쓰기 예산, 429 감사 행(D2)이 막고 한 방의 카드는 20장으로 묶인다.
- **재생 응답**: 요청 지문으로 다른 본문을 막고, 만든 사람이 나간 뒤에는 방 정보를 돌려주지 않는다(D2).
- **상한 레이스**: 트리거가 스스로 `channel_seq`를 잠그고 API·착석에서도 같은 함수로 센다(D4). 나가기도 같은 잠금을 먼저 잡는다(D9).
- **빈 방·존재 노출**: 읽을 글 0인 방은 만든 사람에게만. 없는 사람·보이지 않는 사람·비활성은 같은 404이고 어느 id인지 알리지 않으며, 에이전트 선택 실패도 균일 거절이다. 이름 바꾸기는 참여자 확인이 먼저다.
- **기억 유출**: D1의 `dm_is_group` 조건. 줄어든 그룹도 제외한다.
- **알림 폭주**: 결과를 알리는 시스템 줄은 푸시 0이고 동의 요청 카드는 지금처럼 알린다(D12).
- **나간 뒤 잔존**: 이력·스레드·첨부·검색은 라우트별 점검. **이미 열린 구독은 남는 위험**이고 후속 서버-4가 닫는다(D9).
- **관리자 우회**: 관리자 멤버 추가·제거 라우트는 DM을 이미 제외한다(D5). 관리자는 그룹 DM 내용을 읽지 못한다.

## 검증과 전달

실 PG(비우회 역할·두 테넌트)에서 위 수용 항목을 잰다. 각 보안 gate를 하나씩 뺀 사보타주(상한 트리거, 요청 지문 비교, 재생 전 참여자 확인, 사람 전용 핸들러 검사, 에이전트 id 거절, 전원 동의 검사, 호출 권한 증명, 읽을 글 0 숨김 술어, `dm_is_group` 기억 조건, 대기 요청 취소, `channel_seq` 잠금 순서, 속도 제한 각 항목과 DB 하드 캡, 시스템 줄 푸시 필터와 동의 요청 카드 유지)에서 해당 시험이 실패해야 한다. 게이트는 AGENTS.md 검증 표를 따른다(Rust 워크스페이스 fmt·clippy·test, 코어·웹·폰 typecheck·test와 `scripts/verify_merge_tree.sh`, SQL은 격리 PG 적용). UI는 독립 design-review Blocker 0·High 0이고 미실행 캡처·실기기는 미검증으로 적는다. 구현 진척과 사보타주 원문은 각 PR 본문이 정본이다.

## 결과

- (+) 새 표·RLS 정책 변경 없이 소규모 모임 방이 생긴다. 1:1 키와 API는 그대로이고 ADR-0217의 전원 동의 불변식은 만들 때도 깨지지 않는다.
- (+) 그룹은 방 id로만 접근해 키 은퇴·모음 재조회·나간 사람 복귀 갈래가 없다. 사람을 더하는 길이 하나(새 방)라 새 사람이 지난 글을 보는 길과 앉은 에이전트의 재동의 문제도 생기지 않는다.
- (−) 사람을 바꾸면 기록이 새 방으로 따라오지 않는다(의도). 같은 사람들로 또 만들면 새 방이라 방이 늘어난다(카카오톡처럼 이름으로 구분하고, 빈 방은 나가면 보관되며, 반복 생성은 속도 제한이 막는다).
- (−) 에이전트를 같이 고른 그룹은 허락이 모일 때까지 에이전트가 없고, 대기 중 멘션은 착석 뒤 다시 불러야 한다. 거절된 뒤 다시 고르려면 같은 방에서 `@`로 부르거나 새 방을 만든다.
- (−) 나간 사람이 이미 열어 둔 실시간 연결은 서버-4가 서기 전까지 새 글을 받을 수 있다(D9의 남는 위험, 추방·private 나가기와 같은 한계).
