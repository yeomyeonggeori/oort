# 트랙 구조 진단 — 2트랙(engine/UXUI)이 충분한가, 3~4트랙(infra/QA 등) 세분화가 필요한가 (2026-07-21, Fable · PLN-20260721-01)

> 발단: 성재 질문(2026-07-21) — "engine·UXUI 2트랙이 개발속도·작업 정밀성에서 충분한지, infra·qa 같은 영역으로 3~4개 세분화하면 좋을지 진단하고 설계에 포함."
> 정본 관계: `docs/TRACKS.md`가 트랙 운영 정본. 본 문서는 진단·권고이며, TRACKS.md 반영은 오케스트레이터(momo-main) 통합으로 수행.

## 1. 실측 근거 (JOURNAL 2026-07-18~21 관찰)

| 관찰 | 사례 | 시사점 |
|---|---|---|
| 트랙 분할이 파일군 충돌을 실제로 0으로 유지 | 이중트랙 main 머지에서 "충돌은 docs만(STATUS union), 코드 충돌 0" 반복 | **surface 기준 분할(클라 vs 서버)이 작동 중** — 원리는 "기능 영역"이 아니라 "파일군 비충돌" |
| 검수·게이트 결함은 오케스트레이터 1인이 흡수 | verifier 결함 수정 다수(bash 3.2 배열, 컨테이너 curl 부재, 포트 충돌 28023, psql -q, jsonb nil ::캐스트, uuid 소문자), 서버 500 2계열 중앙 unwrap 승격 | 병목은 트랙 수가 아니라 **검수 용량**. 다만 결함 유형이 반복 패턴 — 사람(트랙)이 아니라 **규율(패킷 함정 체크리스트)**로 해소 가능 |
| 게이트 flake·QA 부채가 트랙 무소속으로 적체 | MOMO-472(스냅샷 flake 2건, full-suite 3회 통과 증명 대기), QA_FOLLOWUP Q1~Q9, docker 자원 누적(momo-docker-reclaim) | "정비 작업"이 배치 사이에서 주인 없이 밀림 |
| 오픈소스 공개 갭도 트랙 무소속 | LICENSE+법무, ghcr 릴리스 파이프라인, install.sh 자동화(S 배치) | 공개 직전 일괄 항목이 feature 트랙 큐와 경합 |
| 성재 승인이 유일한 직렬화 지점 | 모든 track→main 머지가 성재 명시 승인 대기(main+N 상태 반복) | 트랙을 늘리면 **승인 대기열도 비례 증가** — 속도 개선이 아니라 대기 상태 증가로 전화할 위험 |
| worker 동시 상한 5 공유 | codex-fleet 규율 | 트랙을 늘려도 실행 용량은 불변 |

## 2. 옵션 비교

- **A. 현행 2트랙 유지 + 규율 보강 (권고)** — 아래 §3.
- **B. infra/QA 상시 트랙 신설(3~4트랙)**: infra·QA는 크로스컷(서버 verifier·클라 스냅샷·compose 전부 접촉)이라 **파일군 비충돌 원리를 깨뜨림** → 머지 순서 복잡성·rebase 부담 증가, 성재 승인 대기열 3~4배, worker 5 상한은 그대로. 현재 인력 구조(성재 1 + Fable 오케스트레이터 1 + 동생 UXUI + worker 풀)에서 트랙별 상주 오너를 채울 수 없음. **기각.**
- **C. 웹을 3번째 surface 트랙으로 즉시 분리**: 웹 클라(clients/web)는 파일군 기준으로 분리 가능하나, 현재 웹 배치는 UXUI 트랙이 순차 소화 중이고 규모가 아직 작음. **지금은 기각, 트리거 조건부 예약**(§4).

## 3. 권고 — "2트랙 + 2규율 + 1한시트랙"

1. **2트랙(engine/UXUI) 유지** — 분할 원리(파일군 비충돌)가 실측으로 검증됨. PLN-20260721-01 배치도 이 구조로 설계(엔진 Wave M/A, UXUI Wave U).
2. **규율 ① 함정 체크리스트의 패킷 템플릿 승격**: JOURNAL에 축적된 반복 함정(nil 바인딩 ::캐스트·트랜잭션 HTTPError·bash 3.2·컨테이너 curl·포트 대역·uuid 케이스·LibreSSL·Centrifugo config drift)을 `HANDOFF_TEMPLATE.md`의 고정 섹션으로 — worker가 만들기 전에 읽게. 검수 결함의 재발 계열을 구조적으로 차단(= "정밀성"의 실질 개선 수단).
3. **규율 ② 정비 배치(QA/infra)의 정례화**: 매 3~4 배치마다 1회 "정비 배치" 슬롯 — QA_FOLLOWUP 트리아지, flake 안정화(MOMO-472류), docker 리클레임, verifier 부채. 트랙이 아니라 **기존 트랙이 번갈아 소화하는 배치 유형**으로(파일군은 그때그때의 소유 트랙 기준 배정).
4. **한시 트랙 ③ track/release (오픈소스 공개 배치 한정)**: LICENSE·법무 패킷·ghcr CI·install.sh 승격·공개판 README/docs는 feature 파일군과 거의 비충돌(루트 문서·.github·infra/release). 공개 배치 개시 시 개설, 공개 완료 시 폐쇄. 상시 3트랙이 아니라 **기간 한정**이라 승인 대기열 부담이 일시적.

## 4. 상설 3트랙 전환 트리거 (이 조건이 실측되면 재진단)

- 성재 승인 처리량이 병목으로 실측(main+N 대기가 상시 2자리)
- worker 동시 5가 상시 포화
- 웹 클라가 배치 3개 이상을 연속 점유(→ track/web 분리가 파일군 기준으로 정당화)
- 검수 결함 중 "함정 체크리스트로 못 막는 신규 계열"이 배치당 2건 이상 지속(→ QA 전담 검수자/트랙 재검토)

## 5. 결론 1줄

**속도의 병목은 트랙 수가 아니라 검수 용량·승인 직렬화·게이트 flake이므로, 트랙 증설(B) 대신 함정 규율 승격+정비 배치 정례화+한시 release 트랙으로 푼다.** 정밀성은 이미 2트랙 파일군 분할이 지키고 있다(코드 충돌 0 실적).
