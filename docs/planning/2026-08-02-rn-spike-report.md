## 게이트 1 — 한글 IME · **PASS (실기기 판정 완료, 설계 제약 1건)**

### 실기기 판정 (2026-08-02 저녁 · 성재 iPhone 17 / iOS 26.5.1 · 표준 쿼티 + 10키 천지인)

| 케이스 | 하네스 1차 표시 | **최종 판정** | 최종값 |
|---|---|---|---|
| A 비제어(기준선) | FAIL | **PASS** | `안녕하세요` ✅ |
| B 제어 — **oort 컴포저와 동일 조건** | FAIL | **PASS** | `안녕하세요` ✅ |
| C 제어 + 조합 중 리렌더(멘션 60건) | FAIL | **PASS** | `안녕하세요` ✅ |
| D 제어 + **비동기 setState(한 틱 지연)** | FAIL | **FAIL — 진짜** | 표준 `ㅇㅏㄴㄴㅕㅇㅎㅏㅅㅔㅇㅛ` / 10키 `ㅇ\|·ㄴㄴ··\|ㅇㅎ\|·ㅅ·` |
| E 조합 중 백스페이스 | PASS | **PASS** | (빈 칸) ✅ |

타수: 표준 12타 / 10키 21타(다단 조합이라 배 가까이 든다 — 의도한 스트레스가 실제로 걸렸다).

### 1차 FAIL 은 하네스의 오탐이었다 — 정정 기록

A·B·C 는 **최종값이 셋 다 `안녕하세요` 로 정확히 일치**했는데 FAIL 로 찍혔다.
원인은 RN 이 아니라 `composition.ts` 의 불변식이 **한글을 몰랐다**는 것이다:

```
9.  안녕하 → 안녕핫       (−1/+1)
10. 안녕핫 → 안녕하세     (−1/+2)  ⚠ 위반   ← 오탐
12. 안녕하셍 → 안녕하세요 (−1/+2)  ⚠ 위반   ← 오탐
```

`안녕핫` 에서 ㅔ 를 누르면 **받침 ㅅ 이 다음 음절 초성으로 옮겨간다**(받침 이동).
한 keystroke 가 두 글자를 만드는 것이 한글에서는 정상인데, 옛 정의는 `added >= 2` 를
위반으로 셌다. 10키는 한술 더 떠 조합 꼬리가 `ㅅ·` 처럼 **2글자**로 벌어졌다가 접히므로
`dropped >= 2` 도 정상적으로 발생한다.

**정정한 불변식**: `suspicious = dropped > 2` — 확정된 앞부분이 되돌아갈 때만 파손으로
센다. 그리고 이 신호는 **보조**이며 **주 판정은 언제나 `finalMatches`** 다.
실측 전이를 그대로 담은 회귀 테스트를 붙였다: `__tests__/gate1_composition.test.ts` (12케이스).

### 「조합 중 밑줄」 항목은 폐기한다

RN #55257 의 확증 증상이 조합 밑줄 소실이라 사람 판정 항목으로 뒀으나, **한국어에는
판정력이 없다**: 성재가 iOS **메모 앱**에서 확인한 결과 네이티브에서도 밑줄이 없다.
**iOS 한국어 입력기는 원래 조합 밑줄을 그리지 않는다**(밑줄은 일본어·중국어의 marked text
관례다). #55257 의 제목 자체가 `[Japanese Market Blocker]` 인 것과 일치한다.
→ 한국어 대상 게이트에서 이 항목은 **비신호**이므로 판정에서 뺀다.

### 얻은 설계 제약 (이 스파이크의 실질 소득)

> **RN 컴포저의 `value` 를 비동기로 반영하면 한글이 깨진다.**

D 만 파손됐고, D 는 `setTimeout(() => setValue(next), 0)` 로 한 틱 늦게 반영하는
케이스다. 그 사이 iOS IME 의 조합 상태가 끊어져 **자모가 아예 합쳐지지 않는다**.
주목할 점: **D 는 위반 0건이었다** — 되돌아갈 것이 없었기 때문이다. "위반 0건"이
"정상"을 뜻하지 않는다는 것을 실측이 보여줬고, 그래서 주 판정을 `finalMatches` 로 둔다.

oort 컴포저는 controlled 이되 **동기** setState 이고 그것이 B 이며 B 는 통과했다.
따라서 **`packages/momo-core` 추출 시 규율로 못박는다**: 입력 value 가 네트워크·스토어·
큐를 거쳐 되돌아오는 구조를 만들지 말 것. 낙관적 로컬 상태를 동기로 유지하고,
서버 왕복은 별도 경로로 둔다.

### 하네스 자체에서 잡은 결함 (기기가 아니었으면 못 봤다)

`ImeGate.tsx` 의 `onKeyPress` 가 이벤트를 **setState 업데이터 안에서** 읽고 있었다.
그 함수는 이벤트 시점이 아니라 나중에 렌더 중 호출되는데, 그때 RN 은 이미 합성 이벤트를
회수해 `nativeEvent` 가 null 이다 → 기기에서 `Cannot read property 'key' of null` 로
앱이 죽었다. 조합 단계가 많은 입력기일수록 더 잘 터진다. 값을 **동기적으로** 읽도록 수정.

또 키보드 전환 버튼이 **라벨만 바꾸고 케이스를 초기화하지 않아** 앞 키보드의 타수·위반이
다음 판정에 섞이는 구멍이 있었다 → 전환 시 전 케이스 remount 로 수정.

### 키보드 라벨 정정

옛 라벨 `['2벌식', '천지인', 'iOS 기본 한글']` 은 틀렸다. **iOS 의 한국어 키보드는
하나**이고 그 안에 레이아웃이 둘이다(설정 → 일반 → 키보드 → 키보드 → 「한국어」 탭 →
**표준 / 10키**). 즉 `2벌식` 과 `iOS 기본 한글` 은 같은 것이었고, `천지인` 은 Apple 이
쓰는 이름이 아니라 **「10키」** 다. → `['표준(쿼티)', '10키(천지인)', '서드파티']` 로 교체.

### (이하 1차 작성 시점 기록 — 하네스 설계 근거)

**최우선 게이트이고, 이 배치에서 판정할 수 없다.** 시뮬레이터는 맥 하드웨어 키보드로
입력을 받으므로 iOS 한글 IME 의 조합(composition) 경로를 아예 타지 않는다.
시뮬레이터에서 낸 어떤 수치도 PASS 근거가 못 된다 — 그래서 재지 않았다.

### 하네스가 기계로 답하는 것 (사람 판단 불필요)

`src/gate1_ime/composition.ts` 의 **조합 불변식**:
한글 IME 가 정상이면 조합 중인 음절은 항상 문자열의 **마지막 한 글자**다.
따라서 keystroke 하나가 바꿀 수 있는 것은 마지막 글자 1개 + 새로 붙는 1글자뿐.
`dropped >= 2 || added >= 2` 인 전이는 조합이 깨진 것이고, 화면에 **빨간 ⚠ 위반**으로 찍힌다.

기계 판정 = **최종 값이 목표와 정확히 일치** AND **위반 0건**. 둘 중 하나라도 어긋나면 FAIL.

### 사람이 답하는 것 (딱 하나)

**조합 중 밑줄이 보였는가.** RN #55257 의 확증 증상이 정확히 이것이고,
**RN iOS 는 composition/markedText 이벤트를 JS 로 노출하지 않으므로 관측할 방법이 없다.**
화면의 `밑줄 보임 / 안 보임` 버튼으로 답한다.

같은 이유로 `onKeyPress` 는 조합 중 키를 주지 않을 것으로 보이며, 화면이 그 사실을
그대로 표기한다(수신되면 그것도 데이터다).

### 5개 케이스 — 원인을 가르도록 설계

| | 케이스 | 무엇을 가르나 |

| A | 비제어 입력 | 여기서도 깨지면 RN/iOS 자체 문제, 여기만 멀쩡하면 controlled 가 원인 |

### 성재가 실기기에서 할 조작

1. 설정 → 일반 → 키보드에 **2벌식**과 **천지인** 추가.
2. `1 · IME` 탭 → 상단에서 지금 쓰는 키보드 버튼 선택.
3. A~D 각 칸에 **"안녕하세요"** 를 **한 글자씩 손으로** 입력(붙여넣기·예측변환 탭 금지).

7. **키보드 3종(2벌식/천지인/iOS 기본 한글) 각각 반복 → 총 3장.**

### 정직한 사전 판단

패킷의 구분을 유지한다: 확증된 증상은 **조합 밑줄 소실**이고,
"한글 입력 불가"는 집계 이슈의 서술이며 RN 팀이 재현하지 못했다.

→ 밑줄만 FAIL 이고 입력 자체는 멀쩡할 가능성이 높다고 **예상**하지만,
이 예상을 PASS 로 적지 않는다. 기기가 답할 때까지 **기기대기**다.

## 게이트 2 — URL 폴리필 + `oort://join` · **PASS** (어댑터 1파일)

### 측정 방법 — 복사본이 아니라 진짜 파일

`__tests__/gate2_deeplink.test.ts` 는 **웹의 실제 소스를 그대로 import** 한다:
`clients/web/src/features/auth/deepLink.ts` · `clients/web/src/lib/serverBase.ts`.
jest `moduleNameMapper` 와 metro `resolveRequest` 가 `@/…` 를 웹 트리로 이어 준다.
케이스는 웹 `model.test.ts` 의 딥링크 3개 describe(총 19건)를 **문자 그대로** 옮겼다.

### 결과 — URL 구현 3종 비교 (`npx jest`)

| # | URL 구현 | 통과 |
|---|---|---|
| 1 | Node 내장 URL (= 브라우저/웹 기준선) | **19/19** |
| 2 | **RN 0.86 코어 URL (폴리필 없음)** | **12/19 — 7건 실패** |
| 3 | **`react-native-url-polyfill@4.0.0`** | **19/19** |

기준선이 19/19 라는 것이 "케이스 전사가 정확하다"는 증거이고,
2번이 깨진다는 것이 "폴리필은 선택이 아니다"를 **주장이 아니라 측정**으로 만든다.

**RN 코어에서 깨진 7건 (전부 커스텀 스킴 계열)**

- `oort://join?server=…&code=…` → `null`
- 파라미터 순서 무관 + 미지 파라미터 무시 → `null`
- authority 없는 `oort:join?code=abc` → `null`
- server 불량 시 code 보존 → `null`
- **`momo://` 구 스킴 회귀 가드 → `null`** (B13 하위호환이 통째로 깨진다)
- `?join=` 로 감싼 링크 언랩 → `null`
- `urlWithoutJoinParams` → `"…/?stress=40#"` (해시 쿼리를 통째로 날림, 기대는 `#/inbox?tab=all`)

**근본 원인(코드 확인)**: RN 0.86 의 `Libraries/Blob/URL.js` 는 WHATWG 구현이 아니라
정규식 래퍼다. `validateBaseUrl` 이 `https?|ftp` 만 허용하고 `host` getter 도
`/^https?:\/\//` 로 매칭한다 → **커스텀 스킴은 구조적으로 파싱 불가**다.

### Hermes 실행 확인 (시뮬레이터 — 이 항목은 시뮬레이터가 거짓말하지 않는다)

`URL.canParse` 존재 `true`, 라이브 파싱 정상.

### 어댑터 비용 — 실측

| `features/auth/deepLink.ts` (161줄) | **0줄. 무수정 통과.** |

Metro/Hermes 는 `import.meta` 자체를 지원하지 않는다.** serverBase 가 실제로 쓰는

### 패킷 정정 2건

1. **URL 사용 파일은 15개가 아니라 19개**다(`new URL` / `URLSearchParams` 기준).
   비테스트 15 + 테스트 4. 비테스트 15에는 `.ts` 가 아닌 `features/pwa/sw.js` 가 포함된다.
2. **`URL.canParse` 는 `clients/web/src` 에 0건** 사용된다.

### 부수 발견 — ADR-0137 D3 분류 확인

`serverBase.ts` 는 `localStorage` 와 `window` 를 직접 만진다(tsc 가 RN lib 에서 잡아냈다).
즉 **순수 로직이 아니다.** ADR-0137 D3 이 `deepLink.ts` 를 A군(그대로 이식),
`serverBase.ts` 를 B군(얇은 어댑터)에 넣은 것이 **맞았다**는 확인이다.

### 막힌 지점 (숨기지 않는다)

**OS 레벨 딥링크 왕복은 검증하지 못했다.** `Info.plist` 에 `oort`/`momo` URL 스킴을
등록하지 않았다 — 그건 스파이크가 아니라 프로젝트 설정 작업이고, 이 배치의 판정
기준(`deepLink.ts` 가 무수정 통과하는가)에 필요하지 않았다.
**검증된 것은 파서이고, 검증되지 않은 것은 "Safari 에서 링크를 누르면 앱이 뜨는가"다.**

## 게이트 3 — centrifuge-js 실왕복 + 리플레이 · **PASS**, 단 **서버 설정 변경 필수**

### 차단 발견 — RN 의 WebSocket 은 `Origin` 헤더를 보낸다

**이것이 이 배치에서 가장 중요한 발견이다.**

레포의 `infra/centrifugo.json` `ch` 네임스페이스 설정과 `client.allowed_origins` 를
**그대로 복사**해 로컬 Centrifugo v6 을 띄우고 RN 에서 붙였더니:

```
{"level":"info","origin":"http://127.0.0.1:18901",
 "allowed_origins":["https://app.oor7.com","https://app.localhost",
 "http://localhost:5173","http://127.0.0.1:5173","tauri://localhost","http://tauri.localhost"],
 "message":"request Origin is not authorized"}
```

앱 화면에는 `client error: {"code":2,"message":"transport closed"}` 가 무한 반복되고
**WS 는 한 번도 연결되지 않았다**(WS 복구 0건, `ctx.recovered=null`).

- RN 의 WebSocket 은 **Origin 을 보낸다** — 값은 **ws URL 자신의 origin**(측정: `http://127.0.0.1:18901`).
- 사전 조사에서 "RN WebSocket 은 Origin 헤더를 보내지 않는다(보통 문제없다)"는 가정이 있었는데
  **그 가정은 틀렸다.** 측정으로 반증됐다.

**프로덕션 영향 분석**

| 접속 형태 | RN 이 보내는 Origin | 현재 목록 통과? |
|---|---|---|
| `wss://app.oor7.com/...` | `https://app.oor7.com` | **통과** (목록에 있음) |
| 셀프호스팅 LAN `ws://macbook.local:28001/...` | `http://macbook.local:28001` | **거절** |
| 로컬 개발 `ws://127.0.0.1:<port>/...` | `http://127.0.0.1:<port>` | **거절** |

**셀프호스팅이 oort 의 제품 특성이므로 이건 실제 문제다.** 조치는 서버 쪽이며
게이트 3 자체가 아니라 **설정/정책 결정**이다 → 별도 티켓 대상.
(선택지: 네이티브 클라이언트 origin 을 목록에 추가 / 네이티브 경로에 origin 검사 완화 /
`allowed_origins` 를 배포 환경별로 생성. **보안 판단이 필요하므로 여기서 정하지 않는다.**)

### 하네스가 한 번 거짓말했다 — 기록해 둔다

`allowed_origins` 로 막혀 WS 가 완전히 죽은 상태에서도 화면에 **PASS 가 찍혔다.**
원인은 내가 웹 `gate-resume.mjs` 의 판정식(**Centrifugo 복구 ∪ REST `?after` 백필**)을
그대로 옮긴 것이다. 웹에서는 "WS 가 살아 있다"가 전제였는데, **이 게이트가 묻는 것이
정확히 그 전제**이므로 union 은 여기서 틀린 판정식이다. REST 백필이 25건을 전부
메워 `missing=0` 이 되어 버렸다.

→ `wsRailOk` 를 추가해 고쳤다: **끊기 전 라이브 수신 > 0 AND `ctx.recovered===true`
AND WS 복구 건수 == 주입 건수.** 이제 `pass = missing===0 && wsRailOk` 다.
REST 만으로 메워진 것은 이 게이트의 PASS 가 아니다.

### 설정을 열고 재측정 → PASS

`./run.sh up open`(= `allowed_origins="*"`)으로 같은 코드를 다시 돌린 결과:

| 항목 | 값 |
|---|---|
| 끊기 전 라이브 수신 | **3건** |
| 끊긴 동안 주입 | 25건 |
| **WS 복구 수신** | **25건** |
| `ctx.recovered` | **true** |
| `hasRecoveredPublications` | **true** |
| REST 백필 | 25건 |
| WS 레일 생존 | **예** |
| **missing** | **0건** |
| 판정 | **PASS** |

동시에 확인된 것들:

- **`websocket` 구현 주입 불필요.** 웹과 동일하게 아무것도 넘기지 않고 붙었다
  (화면 표기 `websocket 주입: 안 함`). RN 전역 `WebSocket` 으로 충분하다.
- **`createReplayGate` 가 의존하는 성질이 RN 에서도 성립한다** —
  `hasRecoveredPublications=true` 가 `subscribed` 와 함께 온다.
- `centrifuge@5.7.0` 이 `protobufjs` 를 의존하지만 JSON 프로토콜 경로에서는
  Hermes 에서 문제를 일으키지 않았다.

**Node 기준선**(`tools/centrifugo-spike/resume-node.mjs`)도 동일 시나리오 PASS:
`recoveredViaWs 25 · ctx.recovered true · missing 0`. 앱과 Node 가 같은 답을 냈으므로
**하네스가 틀린 게 아니다**가 확인된다.

> 이 게이트에서 시뮬레이터를 쓴 것은 의도적이다. 패킷의 시뮬레이터 금지선은
> **IME·푸시·스크롤 보존**이고, 네트워크/WS 는 시뮬레이터가 거짓말하는 항목이 아니다
> (같은 Hermes, 같은 NSURLSession 경로). 남는 기기 고유 위험은 셀룰러 전환·백그라운드
> 유예 정도이며 그건 v0 배선 티켓에서 다룬다.

### 측정 장치 (자격증명 0)

`tools/centrifugo-spike/` — Centrifugo v6 컨테이너(레포 `ch` 네임스페이스 회복 설정 복사)
+ 의존성 0 브로커(토큰 발급 / 메시지 주입 / seq 백필).
시크릿은 **매 기동마다 `openssl rand` 로 생성**하고 파일에 쓰지 않는다.
`.env` 도 실서버 자격증명도 읽지 않았다.

**의도적 차이 2가지**: `subscribe_proxy_enabled` 대신 `allow_subscribe_for_client`,
`channel_regex` 제거. 이 게이트가 재는 것은 **oort 의 채널 인가가 아니라
centrifuge-js 의 positioned recovery 상태기계가 Hermes 에서 도는가**이기 때문이다.
채널 인가(subscribe proxy)는 API 서버가 필요하고 그건 자격증명 영역이다.

### 미검증으로 남긴 것

- **실서버(app.oor7.com) 왕복 — 시도하지 않았다.** 자격증명이 필요하고 지시로 금지됐다.
  → **오케스트레이터 몫.**
- 레포 API 서버 경유의 진짜 연결 토큰(`POST /v1/auth/realtime-token`) 경로 — 동일 이유.
- **Android cleartext**(`ws://*.local` 이 Android 9+ 기본 정책에 막힘) — 게이트 6 소관.
  여기서는 문서로만: network security config 를 열어야 하고 보안·심사와 얽힌다(ADR-0137 D4).

## 게이트 5 — 타임라인 리스트 3자 · **기기대기**

### 측정 방법 — 왜 `contentOffset` 이 아니라 `measureInWindow` 인가

리스트가 보정을 안 하면 `contentOffset` 은 **그대로인 채 내용만 밀린다.**
offset 만 보면 "안 움직였다"는 잘못된 결론이 나온다. 사람이 실제로 겪는 것은
**읽던 줄이 화면에서 튀는 것**이므로 **앵커 행의 절대 화면 좌표**를 재야 한다.
이 값은 세 라이브러리에서 같은 의미를 가진다(내부 구현과 무관).

조건: 1,000행 · 한국어 **가변 높이**(2~5줄 섞임) · `inverted` · 앵커 index 40 을 화면 중앙에 고정.
프레임률은 FlashList 의 `JSFPSMonitor` + `autoScroll` 로 재서 **손가락 대신 스크립트가
같은 거리를 같은 속도로** 민다(3자 비교 가능).

### 시뮬레이터 참고 수치 — **PASS 근거 아님**

| 구현 | 새 메시지 도착 | 과거 프리펜드 | JS FPS(평균) |
|---|---|---|---|
| `Animated.FlatList` (mVCP 켬) | **67.3px 이동** | **0px** | 60.2 |
| `FlashList v2` | **67.3px 이동** | **0px** | 60.1 |
| `@legendapp/list` | **92.3px 이동** | **0px** | 60.4 |

읽는 법:
- **과거 프리펜드는 3자 모두 0px** — 위로 로드는 세 구현 다 위치를 지켰다.
- **새 메시지 도착(하단 삽입)은 3자 모두 튀었다.** 이것이 Mattermost 가 RN 코어
  `RCTScrollViewComponentView.mm` 을 패치한 바로 그 지점과 같은 증상이다.
- **다만 `Animated.FlatList` 와 `FlashList v2` 가 67.3px 로 똑같이 나왔다.**
  구현이 전혀 다른 둘이 소수점까지 같은 값을 낸다는 것은 **하네스 아티팩트일
  가능성을 배제하지 못한다**는 뜻이다(삽입된 행 높이만큼 밀린 것으로 보인다).
  `@legendapp/list` 만 92.3px 로 갈린 것을 보면 측정이 구현을 구분하기는 한다.
  **이 수치로 라이브러리를 고르지 마라. 기기에서 다시 재야 한다.**

**JS FPS 는 3자 모두 60 부근이고 차이가 없다.** 그리고 이건 **JS 스레드** 값이다 —
인버티드 리스트의 끊김은 UI 스레드에서 생기는 경우가 많아 이 수치로는 판정할 수 없다.
UI 스레드는 기기에서 개발자 메뉴 → **Perf Monitor** 로 따로 읽어야 한다.

### 기기 없이도 확정된 사실

- **3자 모두 RN 0.86 / New Arch 에서 마운트·렌더된다**(1k행, 크래시 없음). 확인함.
- **`@shopify/flash-list@2.3.2` 와 `@legendapp/list@3.3.3` 은 podspec 이 없다 = 순수 JS.**
  네이티브 링크·pod 추가가 필요 없다(FlashList v1 은 네이티브가 있었다). 이식 비용 항목에서 뺄 수 있다.
- `@legendapp/list` 는 **루트 export 가 없다** — `@legendapp/list/react-native` 로 import 해야 한다.
- `FlashList v2` 는 `maintainVisibleContentPosition` 을 **기본 활성화**하므로 별도 설정이 없다.

### 성재가 실기기에서 할 조작

`5 · 리스트` 탭에서 구현 3개 각각:
1. 구현 버튼 선택 → **`▶ 전체 자동 측정`** 한 번(①FPS ②새 메시지 ③프리펜드를 순서대로 수행).
2. `Animated.FlatList` 는 **`mVCP: 켬/끔` 을 토글해 양쪽 다** 측정(차이 자체가 데이터).
3. 세 구현 결과가 한 카드에 누적되므로 **마지막에 스크린샷 1장**.
4. 추가로 개발자 메뉴 → **Perf Monitor** 로 **UI 스레드** FPS 를 읽어 기록.

판정 기준: **앵커 이동 ≤ 2px 이면 보존, 그보다 크면 튄 것.**

| `@legendapp/list` | **0px PASS** | 25px |

**시뮬레이터를 판정에 쓴 근거**: 이 항목만큼은 시뮬레이터가 실기기와 일치한다. 인버티드
수치를 양쪽에서 재 보면 FlashList **67.3 = 67.3**, Legend **92.3 ≈ 91.3** 로 사실상 같다.
(IME·푸시와 달리 스크롤 위치 보존은 시뮬레이터가 거짓말하지 않았다 — 1차에 이 항목을
"시뮬레이터는 못 믿는다"로 분류한 것은 과했다.)

### 판정

**게이트 5 = PASS. 단 전제가 바뀐다: `inverted` 를 쓰지 않는다.**

- 46~91px 이동은 **RN 의 결함이 아니라 인버티드 리스트의 성질**이다. 같은 라이브러리·같은
  하네스에서 방향만 바꾸면 **0px** 이 된다.
- 인버티드는 **우리 설계가 아니었다.** 티켓이 Mattermost 전제를 그대로 승계했을 뿐이고,
  `clients/web/src/features/timeline/Timeline.tsx` 는 **정방향 + 명시적 앵커 보존**
  (react-virtuoso `firstItemIndex` 를 삽입 개수만큼 감소)으로 이미 돌아간다.
- 따라서 **Mattermost 처럼 RN 코어(Fabric ObjC++)를 패치할 이유가 없다.** 이것이 이
  게이트에서 가장 값진 결론이다 — 유지보수 부담이 큰 결정을 피했다.

### 이식 규율 (`packages/momo-core` 추출 시)

1. **`inverted` 금지.** 정방향으로 렌더하고 최신을 아래에 둔다.
2. **프리펜드(위로 로드)에는 명시적 위치 보존이 필요하다.** 정방향에서도 Legend 가
   25px 움직였다 — 웹이 `firstItemIndex` 로 푼 그 문제이며, RN 에서도 같은 종류의
   보정이 필요하다. 구현 선택 시 이 항목을 1급 기준으로 본다.
3. 새 메시지 하단 삽입은 정방향에서 **구조적으로 0px** 이다(내용이 아래로만 자란다).

### 하네스 한계 (정직하게)

정방향에서 `Animated.FlatList` 는 앵커를 못 잡아 측정이 실패했다(`-1px`).
`getItemLayout` 없이 `scrollToIndex` 를 쓰는 문제로, `onScrollToIndexFailed` 처방을
넣었으나 이 하네스에서는 끝내 안정적으로 도달하지 못했다. **결론을 바꾸지는 않는다** —
독립된 두 구현(FlashList v2 · Legend)이 같은 조건에서 0px 을 냈고, 인버티드 대비가
명확하기 때문이다. FlatList 를 실제로 채택한다면 `getItemLayout` 을 주고 다시 재야 한다.

### 측정 과정에서 고친 하네스 결함 3건

1. **모드 전환을 사람 조작에 맡겨 잘못된 모드의 수치가 표에 남았다** → 자동 매트릭스
   (앱이 뜨면 세 구현을 스스로 다 잰다)로 조작을 제거. 게이트 1의 키보드 전환과 같은 구멍.
2. **측정 실패를 조용히 건너뛰어 `?px` 로 남겼다** → 실패를 `-1` 로 명시 기록.
   "측정 안 됨"과 "0px"이 표에서 구별되지 않는 것이 더 위험하다.
3. **결과가 화면 밖으로 못 나갔다** → 시뮬레이터 시스템 알림이 결과 카드를 덮어
   스크린샷 판독이 막힌 뒤, 로컬 수집기로 직접 쏘는 경로를 추가.
