# buzz 기준 oort 진단 — 우로보로스 인터뷰 산출물

> 발제(성재, 2026-08-09): "전체 oort 리뷰 후에 오픈소스화, 프로덕션화, 단일 이미지 베이스로 셀프 호스팅 및 실제 buzz급 작업이 가능한지 진단해줘. 기준을 buzz로 두고 버즈급 런칭을 할 수 있을 수준의 상태인지 진단해줘."
>
> **인터뷰 세션 ID: `interview_20260809_145721`** (3라운드, ambiguity 0.09로 수렴 — Seed 생성 가능 상태이나 이번 임무는 인터뷰까지)
>
> 기준의 정본: buzz = `github.com/block/buzz` (Apache 2.0, ~180k LOC Rust). ADR-0145에 따라 buzz는 **fork가 아니라 레퍼런스**이고 하드 불변식 3개가 정면 충돌한다. 따라서 "buzz급"은 **아키텍처 모방이 아니라 오픈소스 프로젝트로서의 성숙도·런칭 가능 상태** 벤치마크로 읽는다. 이 재해석이 이 인터뷰의 첫 고정점이다.

## 0. 보고서 형식 (인터뷰 라운드 1~3 합의)

**두 층으로 낸다.**

| 층 | 내용 | 수명 |
|---|---|---|
| **1층 — 차단 항목 판정(go/no-go)** | "지금 퍼블릭 전환 버튼을 누르면 무엇이 즉시 깨지거나 부끄러워지는가" | 시점 무관 유효 |
| **2층 — 격차 베이스라인** | buzz 대비 축별 거리 | 시점이 밀려도 안 죽음 |

근거: 발제 문언이 판정형("~할 수 있을 수준인지")이고, 라이브가 이미 실도메인에서 서빙 중이며 데스크톱·폰이 검수 대기까지 와 있다 — 제품은 런칭 직전인데 **배포·공개 성숙도가 크게 어긋나 있다.** 공개 시점 자체는 성재 몫(§3).

**본체는 축별 독립 체크리스트, 그 위에 기계적 간선만 그린 얇은 DAG 한 장을 얹는다.**
- 간선은 **기계적으로 참인 것만** 그린다. "먼저 하는 게 낫다"는 선호는 안 그린다(성재 몫).
- 간선마다 "왜 기계적인가"를 한 줄로 붙여 성재가 반박 가능하게 한다 — 간선이 틀렸다면 그게 가장 중요한 정정이다.
- **DAG를 통째로 기각해도 축별 체크리스트는 그대로 살아남는다.** 반대로 축별 독립만 내면 "라이선스는 세 곳에서 세 번 고치나"라는 오독이 생긴다.

**감사 순서 ≠ 수리 순서 (인터뷰 최대 구조적 소득).** 감사는 *측정*이지 *수리*가 아니다. 라이선스 사각지대는 Swift가 지워졌든 말든 지금 그대로 잴 수 있다. 따라서 **워커 편성은 완전 병렬**이고, DAG는 워커 배치가 아니라 **보고서 안의 산출물**이다. 이걸 섞으면 감사가 자기가 재려는 대상의 수리를 기다리는 교착이 된다.

## 2. 인터뷰가 드러낸 것

### A. 최대 발견 — 라이선스 고지·copyleft 게이트가 **현행 스택을 하나도 안 본다**

발제에도 내 초기 4축 정의에도 없던 축이다. 실측:

- `legal/THIRD_PARTY_NOTICES.md`의 생성 구간은 **SwiftPM 10 그래프**만 덮는다.
- `scripts/check_spm_licenses.sh`에 `cargo`/`crate` 문자열이 **0회** 등장 → `server-rust/Cargo.lock`의 **309 crate가 고지·copyleft 차단에 단 하나도 안 걸린다.**
- npm 섹션은 `clients/web-legacy`(폐기 트리) 기준. 정본 `clients/web`(477) · `clients/mobile`(1076) · desktop(Tauri) **전부 미커버**.
- `NOTICE` 본문에 `TODO(Codex): regenerate from Package.resolved` 가 미해결로 남아 있고, 나열된 주요 컴포넌트가 삭제 예정 Swift 스택 중심이다.

**왜 이게 단순 위생이 아니라 결함인가:**
1. `CONTRIBUTING.md`가 기여자에게 "의존성 바꾸면 `check_spm_licenses.sh --write`로 재생성하라, GPL/AGPL/LGPL/MPL/SSPL/BUSL은 fail-closed로 거부된다"고 **약속**한다. 그 게이트가 실제로 검사하는 그래프는 삭제 예정 Swift뿐 — **약속과 집행이 어긋나 있다.**
2. `CLAUDE.md` 하드 룰이 "permissive 스택, AGPL 백본 금지"인데, 그걸 강제하는 **유일한 기계 장치가 현행 스택을 안 본다.**
3. Apache-2.0 §4(d) 고지 의무는 **"공개"가 아니라 "재배포"에 발효**한다. `publish-images.yml`은 이미 GHCR로 푸시하고 README는 그 이미지를 pull하라고 적어 두었다 — **이 의무는 공개 전환을 기다리지 않고 이미 발효 조건에 걸쳐 있다.**

### B. 축 ③은 지금 **판정 자체가 불가능**하다 (기계적 간선 #1)

"이미지 하나로 올릴 수 있는가"를 재려면 *어느* 이미지인지가 먼저 정해져야 한다.

| | 문서가 가리키는 것 | 실제 운영되는 것 |
|---|---|---|
| 이미지 | `ghcr.io/dawn-kim-official/momo` | `momo-rust:6bfc9b82` |
| 빌드 정의 | `infra/prod/docker/momo.Dockerfile` — **전부 Swift**(MomoServer·OutboxRelay·AgentWorker·LinkShort) + `clients/web-legacy` | `server-rust/Dockerfile` — Rust 5커맨드, **웹 SPA·LinkShort·workd·T3 의도적 제외** |
| 배포 정의 | `infra/prod/install.sh` + `docker-compose.prod.yml` | 서버 위 `/opt/momo/infra/rust/` compose 5 + env 2 **수작업** |
| CI 게시 | `publish-images.yml`이 이 쪽을 빌드 | **게시 워크플로 없음** |

즉 **단일 이미지가 두 개**이고, 어느 쪽도 "제품 전체"가 아니다. 감사 워커는 이 축을 "판정 불가 + 그 사실 자체가 결함"으로 답하게 된다. 선호가 아니라 **측정 불능**이다.

### C. 외부 기여를 받는 순간 로컬 게이트 모델이 붕괴한다 (기계적 간선 #2, 조건부)

- 워크플로 5개 전부 `workflow_dispatch`. 헤더 주석: *"2026-06-26: GitHub Actions는 조직 과금/결제 이슈가 해소될 때까지 수동 전용. 기본 merge gate는 `docs/LOCAL_PR_GATE.md`의 local evidence."*
- 즉 merge gate = **성재 기계에서 Fable이 돌리는 로컬 스크립트 146개**(`verify_merge_tree.sh` 8레인). 외부인 PR에는 붙일 방법이 **없다.**
- `ci-build.yml`이 빌드하는 것은 **Swift 5패키지**뿐 — **CI가 Rust 워크스페이스를 한 번도 빌드한 적이 없다.**
- 우회 선택지가 존재한다: "공개하되 기여는 안 받는다"(source-available 운영). 그래서 이 간선은 **조건부**로 그리고 우회 선택을 성재 질문으로 올린다.

### D. §4(d) 의무는 이미 발효 조건에 걸쳐 있다 (기계적 간선 #3)
→ §2-A 3번. 라이선스 결함은 세 축에 나타나지만 **원인은 하나, 수리도 한 곳**이다.

### E. 초기 4축 밖에서 드러난 빠진 축

| 빠진 축 | 상태 |
|---|---|
| **부하·성능 근거** | 스크립트 0 · 문서 0. README가 "부하테스트 결과 아님"을 정직하게 자인 — 정직하지만 **buzz급 주장의 근거는 0** |
| **관측 가능성** | prometheus가 라이브 Rust 스택에서 부재 |
| **업그레이드·마이그레이션 경로** | `upgrade.sh`가 Swift 경로용. 마이그레이션 forward-only(63개) — 외부 운영자의 스키마 롤백 경로 없음 |
| **운영 인력/온콜** | 1인. 공개 후 이슈 유입(현재 열린 이슈 125·PR 13)에 대한 응답 능력이 축으로 미정의 |
| **보안 감사** | `docs/security/README.ko.md` 1건 + 최근 헤더 랜딩. 외부 감사·위협 모델 문서 미확인 |
| **브랜드/도메인** | oort/oor7.com 확정, 저장소·이미지·코드는 `momo` |

### F. 알아 둘 것 — 실측이 초기 가정 하나를 뒤집었다

내 사전 가정 "셀프호스트 compose가 아직 Swift 이미지 → 감사 4단계 미집행"은 **절반만 맞았다.** `infra/rust/docker-compose.rust.yml`은 레포에 **존재한다**. 문제는 부재가 아니라 **그 파일이 스스로 "prod-shaped smoke"라 선언하고 caddy·redis·prometheus·notifier·web·linkshort·T3·workd를 의도적으로 뺐다**는 점이다. 즉 결함의 성격이 "빠졌다"가 아니라 **"운영은 이 파일이 덮지 않는 영역에서 수작업으로 돌고 있다"**이다. 감사 워커는 이 구분을 놓치면 안 된다.

**편성 근거**

- **C는 사람이 아니라 워커가 실제로 밟아야 한다** — 문서 리뷰로 대체하면 이 축은 측정되지 않는다. 인터뷰가 가장 강하게 요구한 항목.
- **B는 라이브 서버 접근이 필요**하다. NCP ssh/scp/docker 원격 조작은 분류기 차단 대상이므로 **성재 `!` 대행(한 줄 스크립트 묶음)** 전제 — 발주 전 이 제약을 패킷에 명시해야 한다.
- **A는 도구가 없어서 못 하는 게 아니라 도구가 잘못된 그래프를 본다**는 것이 이미 확인됐다. 워커의 일은 "게이트를 고치는 것"이 아니라 **"사각지대 안에 실제로 무엇이 있는지 전수 조사"**다.
- 5 워커는 병렬 상한과 정확히 같다. 줄인다면 **D를 E에 합치는 것**이 가장 손실이 적다(둘 다 2층 기여). **A·B·C는 줄이면 1층이 안 나온다.**
