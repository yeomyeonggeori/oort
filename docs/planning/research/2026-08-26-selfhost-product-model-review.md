# 셀프호스팅 제품 모델 검수 — 성재 확정안 vs 오늘의 코드 (Fable, 2026-08-26)

> 검수 대상: 성재가 확정한 셀프호스팅 제품 모델(원문은 발주문에 — "그록봇 VM 셀프호스팅에 허들·데이터 보관·그록봇 연동·클라우드 연동, 클라우드=그록봇 VM 유휴 자원, 로컬=사용자 랩탑, 세팅은 사용자가 하되 그록봇이 대행").
> 사실 기반: [전수 감사](2026-08-26-selfhost-external-dependency-audit.md) · [NCP 정리 판정](2026-08-26-ncp-teardown-judgment.md) · [RA-7](2026-08-26-ra7-tunnel-identity-feasibility.md) — **재작성하지 않고 참조하며, 이 문서는 그 위에 제품 모델 판정만 얹는다.**
> 표기: `코드 확인` = 이 검수에서 파일을 직접 읽음 · `감사 승계` = 어제 감사의 실측을 신뢰 · `미실측` = 실행/재현 없이 추정. 이 검수 중 코드·정본은 일절 수정하지 않았고, 산출물은 이 파일 하나다.

## 2. 급소 7개

### 급소 1 — 허들이 그록봇 VM에서 안 된다 (모델 정중앙)

**감사 판정 재확인 (코드 확인):** 시그널링 7880·RTC TCP 7881 모두 `127.0.0.1` 바인드(`docker-compose.rust.yml:133-134`), 미디어 UDP 50000-50100(`:135`). quick tunnel은 HTTP(S)/WS만 나른다(감사 ⑤ 승계). TURN 블록은 "공개 도메인+TLS 인증서가 생길 때까지 유보" 주석(`infra/livekit.yaml:15-19`). **⇒ 오늘 코드로 모델 2b는 성립하지 않는다 — 감사 판정 유지.**

후보별 판정. 순위는 (d-1) > (c, 한정 용도) > (b) > (a).

**(d-1) 외부 SFU 연동 — 모델 3번("추천만")을 허들에 적용한다. [권고]**
- **왜 되나 (코드 확인):** 서버는 `MOMO_LIVEKIT_URL`에 임의 호스트의 ws/wss/http/https를 수용하고(`bins/momo-server/src/config.rs:137-154` — 루프백 제한 없음), join 응답이 그 URL을 그대로 클라에 광고하며(`routes/huddles.rs:38,133`), compose api에 세 키가 `${VAR:-}` 보간으로 이미 배선돼 있다(`docker-compose.rust.yml:271-273`). **미디어는 클라↔외부 SFU 직결이라 그록봇 VM inbound가 필요 없다** — quick tunnel은 REST/WS만 나르면 된다.
- **바꿀 파일:** 서버 코드 0줄. ① 가이드 문서 신설(SELF_HOST.md 연동 절 — "사용자가 LiveKit Cloud 무료 계정 또는 자기 VPS SFU를 만들고 URL/KEY/SECRET을 자기 env에 넣는다") ② **CSP 한 줄**: 셀프호스트 엣지 CSP의 `connect-src`가 `'self' + ws://localhost:* + googleapis`뿐이라(`infra/rust/Caddyfile.local:57`, 코드 확인) 외부 SFU의 `wss://`가 브라우저에서 막힌다. Caddy env 보간(`{$VAR}`)으로 SFU 오리진을 주입하는 형태가 후보(운영 `infra/rust/Caddyfile`의 대응 줄은 라인 미확인). 데스크톱(tauri) CSP는 별도 확인 필요(미실측).
- **red proof:** env에 외부 SFU 3키 주입 → `scripts/verify_huddle_livekit.sh`(존재 확인) 통과 → 서로 다른 네트워크의 브라우저 2클라 오디오 왕복. 지금은 CSP 때문에 웹 클라가 wss 연결에서 죽는 것이 예상 red다.
- **대가:** ① 허들이 "아웃오브박스"가 아니라 "연동 항목"이 된다(성재 모델 3번과는 오히려 정합) ② 미디어가 제3자 클라우드를 경유한다 — E2EE 아님, 가이드에 신뢰 고지 필수 ③ 사용자 SFU 키가 운영자 env에 들어간다 — 셀프호스트에서 운영자=사용자이므로 ADR-0004 비유입과 무충돌(급소 5) ④ CSP 주입 메커니즘 신규.

**(c) 허들만 사용자 랩탑(로컬) — 모델 5번과 정합하는가? 표면만 정합한다.**
- SFU는 **모든 참가자의 공통 도달점**이어야 하는 서버다. 랩탑은 그록봇 VM보다 더 inbound가 없다(NAT 뒤·유동 IP·터널 페르소나 없음). 같은 랩탑에서 브라우저 2개, 또는 같은 LAN까지만 성립 — NCP 판정 §3이 실측 근거로 삼은 바로 그 형태다(승계). 원격 참가자가 한 명이라도 붙는 순간 (a)/(b)와 같은 문제로 회귀한다. **판정: 데모·QA용으로는 이미 성립, 제품 경로로는 불성립.** 모델 5번("로컬=랩탑 자원")은 PTY/작업 세션에는 맞는 문장이지만 허들에 이식되지 않는다.

**(a) 7881 TCP 0.0.0.0 바인드 + 두 번째 터널 — 미실측, 성립 의심.**
- 바꿀 자리 자체는 한 줄이다(`docker-compose.rust.yml:134`의 바인드 접두를 env로). 그러나 **quick tunnel(cloudflared 무인증)은 원시 TCP 모드가 없고**(감사 M5 승계), Tailscale Funnel의 TCP 프록시는 443/8443/10000 한정에 클라이언트 TLS(SNI)를 요구하는 구조로 알려져 있다(**미실측** — 브라우저 ICE-TCP는 TLS가 아니므로 통과 여부 의심). 추가로 LiveKit이 광고할 외부 주소 설정(`livekit.yaml`의 external advertise 계열 — 키 이름 미확인)이 딸려온다. **red proof를 설계할 수는 있으나(원격 클라 ICE-TCP 연결 성공/실패), 선행 미지수가 둘이라 권고하지 않는다.**

**(b) LiveKit TURN 블록 활성 — 주석의 전제(공개 도메인+TLS)가 그록봇 VM에 없다.**
- `infra/livekit.yaml:15-19` 주석 해제 + TURN TLS 인증서 필요. quick tunnel 도메인은 L7 HTTP 프록시라 TURN/TLS 종단에 못 쓴다. Funnel이면 노드 인증서가 state dir에 실존하므로(RA-7 RQ-1 승계) `turns:443` 통과가 **이론상** 가능하나, Funnel TCP 모드 실측·인증서 파일 배선·LiveKit turn 설정 3단이 전부 미실측이다. **RA-7 B트랙(성재 결정 대기)이 선행돼야 검토 가치가 생기는 경로.**

**(d-2) 허들을 셀프호스트 v1 범위에서 제외** — 코드 변경 0. 대가는 모델 2번 문장 자체의 수정(성재만 결정 가능 → §3 G1).

### 급소 2 — "그록봇 VM 유휴 자원 = 클라우드"가 무엇을 대체하는가

**판정: CubeSandbox(T3)의 대체가 아니다. 성재 문장은 두 축으로 갈라 읽어야 하며, 어느 쪽도 T3 어댑터 추가로 구현되지 않는다.**

- **데이터 축(디스크):** 이미 그렇게 돼 있다. pgdata가 `/workspace` bind(`SELF_HOST_AGENT.md:122-123`), 첨부 보관소가 로컬 볼륨 기본(ADR-0169 Decision 3). 이 축에서 모델 4번은 신규 작업이 아니라 **현상 확인**이다.
- **컴퓨트 축(작업 세션):** 어댑터 경계를 읽으면(`server-rust/crates/momo-t3/src/provider/mod.rs:73-83`, 코드 확인) wire adapter는 **cubesandbox 하나**이고, T3 provider의 계약은 "인스턴스를 만들고 부수는 substrate의 API"다(`MOMO_T3_PROVIDER_CUBESANDBOX_API_BASE_URL` 필수 — 감사 승계; T3 표면 자체가 `MOMO_T3_ENABLED=1`+운영자 allowlist 뒤, `infra/rust/t3.override.yml:52-59` 코드 확인). 그록봇 VM은 ① 그런 provisioning API가 없고 ② microVM을 만들려면 중첩 가상화(KVM)가 필요한데 존재 미실측이며 ③ display/attach의 공인 inbound가 없다(감사 승계). **"어댑터 하나 추가"가 아니라 계약 자체가 안 맞는다.**
- **맞는 그림은 T2다:** `work_host.type`에 `workd`가 이미 있다(`server/Migrations/021_work_host.sql:23` CHECK `app|workd|cloud`, 코드 확인 — ADR-0125 D1). 그록봇 VM을 **인스턴스 수명주기 없는 상시 work host(workd)**로 등록하는 것이 "유휴 메모리·디스크를 세션에 쓴다"의 코드상 정확한 번역이다. 정직한 비용: ⑴ **linux workd 실행체가 없다** — `server-rust/bins/`는 5종(server/relay/agent-worker/notifier/migrate)뿐이고 WorkHostDaemon은 Swift 은퇴 트리·맥 전제(linux 빌드 미실측) ⑵ attach 광고 주소가 터널 뒤에서 #1788과 같은 계열의 same-origin 문제를 만난다(미실측 — 설계 필요).
- **TC-2와 같은 그림인가: 다른 그림이다.** TC-2의 "클라우드"는 CubeSandbox T3이고, display 평면은 `type='cloud' AND provider='cubesandbox'` 한정이라 T1을 못 덮는다는 것이 TC-2 자신의 실측이다(`2026-08-26-tc2-work-console-remote-control.md:21`(㉮)·`:489`(D5-B)·`:523`(⑦)). 이번 모델의 "클라우드"(그록봇 VM 유휴 자원)는 그 display 평면의 전제(cubesandbox provisioning·oort TURN)를 하나도 갖지 않는다. **⇒ TC-2는 관리형(oort 운영) 표면의 그림, 이번 모델은 셀프호스트의 그림 — 직교한다.** TC-2 ADR을 기안할 때 이 구분을 전제에 명기해야 하고, 셀프호스트에서 같은 UX를 원하면 유일 경로는 PTY 평면(T1/T2 — #1777 계열)이다. 테스트 로드맵이 D5-B를 이미 기각한 판정(로드맵 판정 ①)과도 정합한다.

### 급소 3 — 데이터 보관이 터널에서 깨진다 (#1788)

**결함 재확인 (코드 확인):** upload URL이 부팅 시 읽은 `base_url`로 조립되고(`momo-drive/src/local.rs:229`), 그 값은 env `MOMO_DRIVE_ARCHIVE_LOCAL_BASE_URL`(부재 시 루프백 기본 — `bins/momo-server/src/config.rs:266-270`)이다. 터널 원격 클라는 `http://localhost:8088/...`에 PUT하라는 URL을 받는다.

**정정 노트 — 감사 M6·#1788 본문이 부분적으로 낡았다 (코드 확인):** `--public-origin`은 이 키를 갱신**한다** — `ensure_local_drive_public_base()`(`scripts/self_host_env.sh:436-446`, 기존 env 경로 `:879`에서 호출)가 #1696(`b76a709e`)부터 존재한다. 그러나 두 조건에서 결함이 그대로 살아 있다:
1. **claim env에서는 생성기 자체가 거절된다 (이 검수의 신규 발견, 코드 확인):** 기존-env 경로는 공개 오리진 처리(`:878-879`)에 도달하기 **전에** `validate_owner_password`(`:872`)를 통과해야 하는데, 이 함수는 12–128자 literal을 요구한다(`:225-233`). ADR-0166 claim 수술 env에는 `MOMO_INITIAL_OWNER_PASSWORD`가 없으므로(§1.4 awk가 제거 — `SELF_HOST_AGENT.md:141-148`) **여기서 fail한다.** 즉 플레이북 §2.3(`:300-302`)이 시키는 `--public-origin`·`--compose`가 §1.4가 만든 바로 그 env에서 실행 불가다 — **플레이북 내부 모순**(§1.4 `:151-153`이 스스로 "생성기를 다시 돌리지 않는다"고 적어 놓고 §2.3이 돌리라고 한다). 그록봇 경로에서는 #1788이 원문 그대로 유효하고, 공개 오리진의 Centrifugo 등록도 같은 벽에 막힌다.
2. **quick tunnel URL은 재기동마다 바뀐다**(`SELF_HOST_AGENT.md:290-292`) — env 고정 방식은 회전마다 "생성기 재실행+재기동"을 요구하는 구조라 근본적으로 못 따라간다.

**수리 방향 판정: same-origin 파생이 정답이고, `--public-origin` 편입은 이미 있으나 위 두 조건 때문에 보완책 이상이 못 된다.** 결정적 근거: **same-origin은 이미 이 경로의 문서화된 의도다** — 셀프호스트 엣지가 `/__momo_stub/*`를 api로 프록시하며 주석에 "ADR-0169 — local archive PUT is **same-origin**. The capability URL the client is handed is `$origin/__momo_stub/...`"라고 적어 뒀다(`infra/rust/Caddyfile.local:36-42`, 코드 확인; 라우트 실존 `bins/momo-server/src/lib.rs:1180`·`routes/attachments.rs:391`). 구현만 부팅 고정 env로 어긋나 있는 것이다.

**ADR이 필요한가: 신규 ADR 불요, 증보 1건 필요.** Host 스푸핑 신뢰 경계는 ADR-0167이 이미 Accepted로 정리했다 — 파생은 신뢰 프록시(Caddy)가 정규화한 `X-Forwarded-Proto/Host` 기준이고, 악의 Host로 오염된 광고는 **그 요청자 자신의 응답에만** 실린다(0167 판정 승계). capability URL도 정확히 같은 모양이다(요청자 자신의 업로드 목적지 — 자해 외 피해자 없음). 따라서 **ADR-0169에 증보**를 달아 "capability URL 조립을 0167의 same-origin 파생 규칙에 준용한다"(예: `MOMO_DRIVE_ARCHIVE_LOCAL_BASE_URL=same-origin` 센티널 — 0167과 대칭)로 정하면 된다. 절대 URL 명시값은 verbatim 유지(0167과 동일). → §4 ADR-2, §5 델타 D-a·D-b.

### 급소 4 — "그록봇이 알아서 진행"의 현재 좌표 (가장 두껍게)

`docs/SELF_HOST_AGENT.md`는 "이 문서가 제품이다. 그록봇이 이것만 읽고, **사람 개입 없이**"를 표방한다(`:3`). 실측하면 무인 구간과 사람 개입 지점이 이렇게 갈린다.

**무인으로 서 있는 구간 (문서·코드 게이트 확인):** 이미지 pull(GHCR 공개 — 감사 승계) → pgdata `/workspace` 볼륨(`:122-123`) → env 생성+claim awk 수술(`:127-148` — 그록봇이 스스로 실행) → compose 직접 기동 → claim URL 캡처 → quick tunnel 기동(`:285-288`) → 외부 도달성 자가검증(`:312-319`) → 백업 생성 → 사용자 핸드오프 회신 → 도어벨 루틴 자기 생성(§4). 2026-08-24 도어벨 E2E가 이 경로의 실기동 증거다(수동 우회 2건 — #1747이 닫으면 사라짐, 로드맵 판정 ⑥ 승계). **서버 생애주기에 관한 한 "그록봇이 알아서 진행"은 이미 사실이다.**

### 급소 5 — "추천만 하고 가이드는 친절하게"의 제품적 의미

ADR-0004의 금지는 정확히 "**자격증명 바이트가 우리(또는 에이전트 대화)를 통과·체류하는 것**"이다(본문 Rules: 토큰 비저장·비프록시·비로깅, 증보 1: GUI는 base URL+opaque bearer만, 증보 2: 운영자 소유 키=서버 시크릿). 셀프호스트에서는 운영자=사용자이므로 "사용자가 자기 서버에 자기 키를 넣는 것"은 애초에 0004가 금지한 적이 없는 형태다.

- **연동 대상 목록·비교표를 앱 안에:** **된다.** 자격 흐름이 없다. 제품 표면이므로 디자인 게이트(momo-design-taste) 대상일 뿐.
- **원클릭 연동 마법사:** **조건부로 된다.** 허용 상한은 "키 입력 칸까지 데려다주는 원클릭"이다 — provider 콘솔 딥링크, 엔드포인트 URL 프리필, 붙여넣기 칸, 연결 테스트 버튼(0004 증보 1 D5의 검증 콜과 동형)까지. **안 되는 순간:** ① OAuth 리다이렉트를 우리 도메인이 받는 것(0004 Rules — 토큰이 우리를 통과) ② 그록봇 대화에 키를 붙여넣게 하는 것(provider 로그 유입 — 0166 Context가 기각한 그 형태) ③ 우리가 관리하는 어디든 사용자 키를 보관(0004 증보 2가 금지한 관리형 BYO-key).
- **경계 문장 (요청대로 한 줄):** **"추천·비교·프리필·딥링크·연결 테스트까지는 전부 친절해도 된다. 자격증명 바이트가 '사용자 → 자기 서버 GUI' 한 홉이 아닌 경로 — 우리 도메인, 그록봇 대화창, 우리 보관소 — 를 한 번이라도 지나는 순간, 그것은 추천이 아니라 커스터디이고 ADR-0004 위반이다."**
- 급소 1의 (d-1) 외부 SFU 키, 백업 오프사이트(S3 등), CubeSandbox 대신 사용자 자기 클라우드 — 전부 이 경계 안쪽에서 "친절한 가이드" 문서로 소화 가능하다(감사 ⑧의 "연동 매트릭스" 제안과 동일 방향).

### 급소 6 — 우리가 제공하는 웹서버/서브도메인의 정체

"만들어는 줄 수 있는데"의 기술적 후보 4개와 각각의 판정:

| 후보 | 실체 | 판정 |
|---|---|---|
| (i) 랜딩·문서·다운로드 사이트 | 정적 웹(oor7.com 루트는 현재 무응답 — NCP §1 실측 승계). Vercel/Pages류로 신설 | **무충돌·즉시 가능.** NCP 정리와도 독립. "우리 제공분"의 안전한 최소 해석 |
| (ii) DNS 레코드 발급 — `<이름>.oor7.com` → 사용자 공인 IP | 우리는 이름만 팔고 트래픽 비경유. TLS는 사용자 측 ACME | **약관 무충돌.** 그러나 **그록봇 VM 모델과 비정합** — VM에 공인 inbound가 없어 가리킬 IP가 없다(감사 ⑤). 숙련자(자기 VPS) 전용 편의로만 의미 |

| (iv) 인증서 대행(우리 도메인 와일드카드) | 우리가 사용자 오리진의 TLS 신원을 쥔다 | **비권고.** (iii)의 MITM 능력 문제를 인증서 층에서 반복. 사용자별 DNS-01 위임은 가능하나 운영 복잡도만 사고 (ii) 이상의 가치가 없다 |

**판정:** 즉시 성립하는 것은 (i)뿐이다. (ii)는 무해하나 이 모델의 기본 배치(그록봇 VM)에는 대상이 없다. (iii)이 성재 문장의 진의라면 그것은 부가 기능이 아니라 **릴레이 사업 진입 결정**이고, RA-7이 이미 "무계정 사용자의 유일한 구현"이라는 정확한 대가표(인터뷰 `:14` A트랙 개정)와 함께 성재 결재석에 올려 둔 사안이다 — 이 검수는 **v1에서 열지 않기**를 권고한다(§3 G4).

### 급소 7 — ADR-0165 D3의 운명

**현상 (코드 확인):** D3 문면 "TURN은 oort 운영分만·제3자 금지"(`0165:27-28`), 증보 2가 `ice.turn: required, operator: oort(momo-turn)`로 강화(`0165:88-89`). 한편 코드는 운영자 지정 TURN을 받고(`config.rs:1513-1515`의 세 키 → `:1532-1535`에서 수용), allow-list 부재가 **의도**임을 주석이 명시하며(`:1521-1525` — "강제 주체는 운영자 env + verify_display_attach.sh conformance"라고 문면으로 적혀 있다), 라이브 오버레이도 세 키를 빈 기본값으로 둬 가역성을 설계해 뒀다(`t3.override.yml:65-74`). NCP 정리는 momo-turn 정지를 권고한다.

**판정: 증보(주어 재정의)다.** 한정(셀프호스트 예외 조항 삽입)은 "oort 운영分"이라는 잘못된 주어를 남긴 채 예외를 덧대는 누더기이고, 잠금(문면 유지)은 NCP 정리와 양립 불가 + 셀프호스터에게 무의미한 조항을 강요한다. D3의 보호 대상은 "oort가 운영한다"가 아니라 **"미디어가 신뢰 경계 밖 제3자를 경유하지 않는다"**였다 — 주어를 정확히 하면 불변식은 그대로 산다.

**증보 문안 초안 (ADR-0165에 붙일 것 — 성재 결재 대상):**

> ## 증보 3 (Proposed) — D3 주어 재정의: "oort 운영分"에서 "해당 배포 운영자 소유分"으로
>
> - 발단: ① NCP 정리 판정(2026-08-26)이 momo-turn 정지를 권고 — 증보 2 D3-turn(`required·operator: oort`)이 상시 만족 불가능해진다. ② 셀프호스팅 제품 모델 확정 — 셀프호스터의 인스턴스에 "oort 운영分"은 정의상 존재하지 않는다. ③ 코드는 이미 운영자 지정 TURN을 수용하며(`config.rs:1513-1515`) allow-list 부재가 의도임을 명시한다(`:1521-1525`). 감사 M7이 이 괴리의 판정을 요구했다.
>
> ### D3-재정의. TURN 신뢰 경계의 주어는 "그 배포의 운영자"다
> 본문 D3·증보 1 D3-2·증보 2 D3-turn의 "oort 운영分만"을 다음으로 대체한다: **"display 평면의 TURN relay는 해당 oort 인스턴스의 운영자가 소유·통제하는 호스트여야 한다. 운영자가 통제하지 않는 제3자 TURN(공용 SaaS TURN, 타인의 coturn)은 금지한다."**
> Dawn 운영 배포에서 운영자=oort이므로 기존 문면과 동치다 — 약화가 아니라 주어의 정확화. 셀프호스트 배포에서 운영자=셀프호스터이므로 자기 coturn을 `MOMO_TURN_URLS`로 지정하는 현행 코드 동작이 문면과 정합해진다. 금지의 실질(egress·관측 경계)은 불변.
>
> ### D3-강제. allow-list 부재는 의도이며 유지한다
> `config.rs:1521-1525`의 판정을 결정으로 승격: 프로세스는 TURN 호스트 신원을 검증하지 않는다. 강제 주체는 ① 운영자 env(static-auth-secret 소유가 곧 통제 증명) ② Dawn 배포 한정 `verify_display_attach.sh` conformance. 셀프호스트 문서에는 "제3자 TURN 금지"를 운영자 의무로 명기한다.
>
> ### D3-부재. TURN 미구성 = display 평면 fail-closed
> TurnCredentialPolicy 부재 시 `ice_servers`는 빈 배열이고(`t3.override.yml:66-71`의 가역성 설계가 전제하는 동작) display 도달성은 성립하지 않는다 — 이를 결함이 아니라 **정상 상태**로 성문화한다. momo-turn 정지 후 Dawn 배포의 display 평면은 "미구성"이며, TC-2/display 검증 창에만 재기동한다(NCP 판정 §2 묶음 A와 정합).
