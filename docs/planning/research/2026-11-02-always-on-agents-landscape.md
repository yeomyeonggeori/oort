- 성격: 리서치(결정 아님). 뒤에 올 **제품 방향 ADR-0220**의 바깥 근거다. 기능 선정은 그 뒤에 한다.
- 확인일: 2026-11-02. 출처마다 자료의 발표·갱신 날짜를 적었다.
- 짝 문서: oort가 지금 가진 기능은 `2026-11-02-always-on-agents-oort-inventory.md`가 다룬다(다른 워커 몫, 이 문서는 건드리지 않는다).
- 표기: **[레포]** 저장소 기록(바깥 재확인 전) · **[공식]** 제품·저자 공식 자료 · **[2차]** 언론·제3자 · **확인 못 함** 근거를 찾지 못한 것.

## 요약

1. owner의 문제의식(메신저는 상주 에이전트가 머물고 사람이 점검·방향 전환하는 곳)은 이번에 본 제품 대부분이 같은 쪽으로 간다는 점에서 **뒷받침된다.** Grok Bot·Muse·dots·Hermes·Claude Tag·Slack.
2. 영상은 「Stanford CS146S: How always-on agents work」(leerob)이고 Grok Bot의 상주 구조를 다룬 강의로 보인다. **본문은 미확인**이고 2차 요약 둘이 서로 일치한다.
3. **pstack은 메신저에 사는 에이전트가 아니라 Cursor의 개발 기술 묶음(MIT)**이다. owner가 뜻한 것이 맞는지 확인이 필요하다.
4. Muse는 Meta 공식 발표로 레포 기록 넷(백그라운드·승인 때 복귀·전체 감사 기록·민감 행동 확인)을 모두 확인했다.
5. Grok Bot은 공식 문서로 점검(사이드바 세 상태)·방향 전환(승인 카드·넘겨받기)·알림(봇별)을 확인했다. **정지 방법과 감사 기록은 문서에서 못 찾았다.**
6. Hermes는 「새 메시지가 기본 방향 전환」이고 `/stop`·`/approve`·`/usage`·예약 작업 제어가 메신저 안에 있다. oort는 이를 멤버로 붙이고 승인·감사·예산은 oort 서버가 소유한다(레포).
7. Slack은 정지 버튼과 계획·작업 카드를 기본 제공하고 승인은 앱 몫으로 둔다. 완료 알림과 비용 표시는 문서에서 못 찾았다.
8. Buzz는 가장 닮은 참조다. 활동 피드의 목적을 「위임을 얻어내는 것」으로 둔다. 비전 문서의 구현 여부는 확인 못 함.
9. 종합: 정지와 진행 표시는 거의 기본 제공, 승인은 제품 몫, **되돌리기와 비용 귀속은 비어 있다.**
10. 일치하는 설계 셋: 기본은 조용히 있고 부를 이유를 걸러 정한다 / 비밀은 모델 밖 / 들어온 글은 지시가 아니다.
11. 연구 5편은 승인자↔관찰자 손잡이, 개입 지점 두 종류, 방해 비용의 저울, 정지·정정·이유 체크, 알림의 비용을 뒷받침한다.
12. 작업 지시서가 전한 dots의 연결처(Slack·문자)와 다른 곳: 공식 요약은 문자를 「곧」으로 적는다. 레포 문서에서는 이 기록을 찾지 못했다.
13. 확인 못 한 것: 영상 본문, Muse·Grok Bot의 정지, Buzz 구현, dots 공식 페이지(403), 연구 원문 수치(7절).

### 2.1 Slack

팀 메신저가 에이전트를 맞이하는 방식의 기준선이다. 2026년 들어 에이전트 표면이 **세 겹**으로 정리됐다. 공식 개발자 문서·변경 기록·블로그로 확인했다(확인 2026-11-02). †표는 검색 결과 요약으로만 확인하고 원문은 열지 않은 것이다.

| 겹 | 내용 | 날짜·출처 |
|---|---|---|
| ① Slackbot | Slack의 개인 AI 에이전트. 요청을 전문 에이전트로 보내고 여러 단계 작업을 관리하고 결과를 돌려주는 「단일 인터페이스」를 표방한다. Business+·Enterprise+ 고객에게 일반 제공(GA)이다. | 2026-01-13 [S5]†, 2026-03-31 [S3] |
| ② 에이전트 앱 표면 | 분할 화면(split view)·DM·채널 멘션으로 에이전트와 대화한다. 2026-08에 **「에이전트 세션」 API**로 갈아타는 중이다(기존 `assistant_view`는 2027-02 폐기 예정, 새 `agent_view`로 이전 권장). | 2026-08-20 [S1][S2]†[S6] |
| ③ Slack Code | 더 큰 작업을 위한 **에이전트 전용 채널**. 기존 대화에서 시작해 맥락을 가져가고, 에이전트가 필요할 때 채널을 만들며, 코드 diff·Block Kit 화면·HTML 미리보기·캔버스 같은 **산출물**을 올리고 일이 끝나면 세션을 닫는다. 동료가 들어와 검토하고 맥락을 보탠다. | 2026-08-20 [S4] |

| 항목 | 확인한 내용 | 출처 |
|---|---|---|
| 어디서 얼마나 도나 | **Slack은 에이전트를 돌리는 곳이 아니라 대화·상태 표면**이다. 런타임은 앱을 만든 쪽이 가진다. 표면이 정한 시간 제한이 있다. `processing` 상태는 1시간 뒤 만료되고, 스트림을 10분 안에 끝내지 않으면 Slack이 마무리하며 안 끝난 작업을 `error`로 표시한다. | [S6] |
| 메신저 안 점검 | 새 **에이전트 세션 사이드바**(고정·보관·안 읽음 표시·실시간 갱신), 스레드의 개정된 생각 중(thinking) 화면, 여러 에이전트 쌓기, 스레드 이름. 긴 작업은 **계획(plan) 블록 안에 작업 카드**를 두고 `chat.update`로 단계마다 바꾼다(작업 카드 상태: 대기·진행 중·완료·오류, 계획 하나에 최대 50개). 에이전트는 `agents.sessions.setStatus`로 「처리 중」을 알린다. 응답에 피드백 버튼(좋아요·싫어요)을 붙일 수 있다. | [S1][S6][S7] |
| 방향 전환 | 스레드의 **기본 제공 정지 버튼**. 사용자가 누르면 앱이 `agent_session_stopped` 이벤트를 받는다. 정지 뒤 앱이 무엇을 해야 하는지는 문서에 없다. 그 밖의 방향 전환은 스레드에 말하는 것이다. **승인 카드는 플랫폼이 정하지 않았고** 각 앱이 만들어야 한다(Slack Code 문서도 승인 방식은 적지 않았다, 확인 못 함). | [S1][S6][S4] |
| 권한 | 에이전트가 Slack 데이터를 읽는 길은 **실시간 검색(RTS) API와 Slack MCP 서버**이고, 사용자 권한 범위의 검색을 한다고 소개된다. MCP는 현재 Slack 마켓플레이스에 게시된 앱과 내부 앱만 쓸 수 있고, 에이전트·AI 앱 기능(`assistant:write`)의 마켓플레이스 제출은 선별된 파트너에 한정된다고 문서가 적는다†. Slackbot 접근은 관리자가 정한다. | [S3][S8]†[S9]† |
| 비용 표시 | Slackbot은 요금제별 **메시지 한도와 크레딧 사용** 도움말이 있다(Enterprise+는 한도 없음, Business+는 한도가 있고 추가 크레딧 구매 가능). 2026-06 이후 나온 고급 기능은 사용량 기반 요금으로 갈 수 있고 30일 전에 알린다고 한다†. **작업별 비용을 대화 안에서 보여 주는지는 확인 못 함.** | [S10]† |
| 밖(폰·알림) | 모바일 제공 여부는 블로그에 없다(확인 못 함). 완료 알림은 문서에 따로 없고 「상태를 active로 두면 Slack이 응답을 적절한 때 보여 준다」는 서술뿐이다. 알림은 Slack의 일반 알림 체계를 따른다고 보는 것이 자연스럽지만 **확인 못 함**. | [S6] |
| 서드파티 연동 방식 | Slack 블로그가 Claude·Cursor·Linear·Vercel(v0) 등을 Slack 안 에이전트로 소개한다(Cursor는 Slack에서 코딩 에이전트 시작, Linear는 스레드를 티켓으로). 코딩 에이전트별 방식은 3절 사례에서 본다. | [S3] |

- 주목: Slack은 **정지는 기본 제공, 승인은 앱 몫**으로 갈랐다. 「멈춤」은 모든 에이전트에 같은 모양이 필요하고 「승인」은 에이전트·행동마다 다르다는 판단으로 읽힌다(해석).

### 2.3 pstack

**결론: pstack은 메신저에 사는 상주 에이전트 제품이 아니라, 코딩 에이전트에게 주는 기술(skills)·원칙 묶음이다.** 레포에는 기록이 없었고, 공식 저장소와 Hermes 공식 문서에서 아래를 확인했다. owner가 「pstack」으로 뜻한 것이 이것인지는 확인이 필요하다(7절).

| 항목 | 확인한 내용 | 출처 |
|---|---|---|
| 무엇인가 | AI가 쓴 군더더기 코드(slop)를 줄이고 엄밀하게 개발하기 위한 기술과 원칙의 묶음. Cursor의 공식 플러그인 저장소 `cursor/plugins` 안 `pstack` 폴더. README 작성자는 poteto(Lauren Tan)이고, 라이선스는 MIT. 진입 명령 `/poteto-mode`가 요청을 읽고 플레이북(작업 순서표)을 골라 나머지 기술을 부른다. README 기준 플레이북 23·원칙 기술 24·하위 에이전트 2개이고 버전은 표기가 없다. | [P1] |
| 어디서 얼마나 도나 | **자체 상주 프로세스는 없다.** 실행 환경(Cursor·Claude Code·Hermes)이 돌린다. 같은 저장소의 `automations/benny`는 Slack의 이슈 신고를 분류하고, 확인된 버그를 재현해 작은 초안 수정을 만들 수 있는 Cursor 자동화(automation) 둘이며 휴면 상태로 있다가 설정 때 켠다. | [P1][P3] |
| 메신저 안 점검 | benny는 결과를 신고가 올라온 **원래 스레드**에 남기도록 적혀 있다. 그 밖의 점검 UI는 없다. | [P3] |
| 방향 전환 | 사람이 자동화 초안을 검토한 뒤에 켠다. 개별 초안 수정의 승인 방식은 적혀 있지 않다(확인 못 함). | [P3] |

[P4] SourceForge에도 같은 이름의 오래된 프로젝트가 검색에 섞여 나오지만 이 맥락과의 관련은 확인하지 않았다.
- 영상이 pstack을 언급하는지는 본문 미확인이다. 검색 결과 요약에 「Grok Bot을 pstack으로 유지한다」는 취지의 제3자 서술이 있었으나 원문을 열지 않았고 공식 자료로 확인하지 못했다([P5], 저신뢰, 확인 못 함).

| 메신저 안 점검 | 봇과의 대화방이 곧 점검 화면이다. 사이드바가 봇을 **「주의 필요(질문·승인·넘겨받기 요청)」 / 「안 읽은 활동」 / 「작업 중」**으로 가른다. 대화를 열면 읽음 처리된다. 그룹 채팅에서 봇끼리 조율하고 판단이 필요할 때만 사람을 부른다(보도). 폰에서 스레드 답장·멘션·반응이 되고, 이메일·Slack 메시지 초안은 보내기 전에 보고 보내거나 버린다. | [G2][G5][G4] |
| 방향 전환 | 채팅으로 수정 요청. **승인 카드**(허용 한 번 / 항상 허용=규칙 저장 / 거부). 컴퓨터를 직접 **넘겨받아** 비밀번호·2단계 인증·캡차를 처리하고 「I'm done」으로 돌려준다. 루틴은 폰에서 일시정지·재개, 수정은 봇에게 말로 시킨다. 승인은 **이미 끝난 일을 되돌리지 않는다**고 문서가 못 박는다. 작업 자체를 멈추는 방법은 문서에 없다(확인 못 함). | [G1][G3][G4] |
| 권한 | **Auto Review**(모델이 행동 전에 검토, 기본 켜짐). 사용자 규칙은 「자동 허용」「먼저 묻기」 두 종류이고 충돌하면 **묻기가 이긴다**(종류별 20개, 규칙당 1,000자). 관리자가 팀 규칙을 강제할 수 있고, 사용자 규칙은 더 엄격하게만 만들 수 있다. 데스크탑 명령 실행은 명령마다 승인이 기본. 로컬 컴퓨터 접근은 따로 「매번 묻기」가 기본. 자격증명은 금고→비밀번호 관리자→보안 입력 순서로, 모델에 값이 보이지 않는다. **내 메시지만 요청으로 인정**하고 이메일·웹 글은 지시로 보지 않는다. 같은 컴퓨터를 쓰는 봇들 사이는 보안 경계가 아니다. 문서에 별도 감사 기록은 없다(문서가 직접 행동 기록을 남기라고 권한다). | [G3][G2] |
| 비용 표시 | 설정의 사용량·결제 화면에 **주간 포함 사용량과 추가(온디맨드) 사용량**, 계정 메뉴에 주간 사용량. **작업별 비용 표시는 문서에 없다.** 접근 자격은 출시 때 고가 요금제 세 종류로 한정됐다가(MacRumors) 지금 문서는 유료 Cursor 개인·팀 요금제 등으로 넓게 적는다. | [G2][G1][G5] |
| 밖(폰·알림) | iPhone(iOS 18+)·iPad·Android 9+ 앱. 폰에서 채팅·승인·컴퓨터 보기와 넘겨받기·루틴 보기와 일시정지가 된다. 알림은 **봇별 설정**(「끝났을 때 또는 나를 기다릴 때」)이고 그룹 채팅에는 같은 스위치가 없다. 데스크탑 앱을 쓰는 동안 내 봇의 알림은 폰이 아니라 데스크탑으로 간다. 앱이 열려 있으면 알림이 억제되고 배지만 남는다. iPhone 푸시는 **점진 배포 중**이라고 문서가 적는다. 폰에서 못 하는 것은 루틴 시험·컴퓨터 갱신·가르치기. | [G2][G4] |
| oort와의 관계 | **외부 에이전트 멤버로 붙는 쪽**이다. 레포의 Agent Port가 벤더 VM의 루틴(webhook)과 MCP 커넥터로 연결한다. 동시에 Grok Bot 앱 자체가 「에이전트와 대화·점검·승인」 메신저 구실을 하므로 **oort가 겨루는 경험의 기준선**이기도 하다. 다른 점은 Grok Bot이 개인 한 사람의 컴퓨터 중심이고, 팀 안에서 사람과 에이전트가 같은 대화방을 쓰는 구조는 Cursor 팀 공유 정도로만 적혀 있다는 것이다. | [레포 ADR-0186·ADR-0162][G1] |

- 확인 못 함: 앱이 Slack·iMessage 같은 **서드파티 메신저를 대화 입구로 쓰는지**는 공식 문서(get-started)에 없다. 연결된 앱은 봇이 쓰는 도구이지 대화 채널이 아니라고 적혀 있다. 출시 보도에서 Slack은 Cursor 커넥터가 이어받는다는 서술로만 나온다.
- 위험 신호: Cursor 포럼에 「iOS 1.0에서 알림이 켜져 있어도 푸시가 안 온다」는 제목의 글이 있다(내용은 열지 않았다). 밖에서 점검하는 경험은 **푸시 신뢰도**가 좌우한다는 점만 시사한다. [G6]

### 2.6 Hermes

Nous Research의 오픈소스(MIT) 에이전트 `hermes-agent`. 공식 README와 공식 문서 세 쪽(메시징, 예약 작업, 보안)으로 확인했다(확인 2026-11-02, 문서는 갱신되는 문서이고 쪽마다 날짜 표기가 없다). [H1][H2][H3][H4]

| 항목 | 확인한 내용 | 출처 |
|---|---|---|
| 무엇인가 | 스스로 개선하는 에이전트라고 소개한다. 여러 모델 제공자를 지원하고, 에이전트가 가꾸는 기억, 복잡한 작업 뒤 스스로 만드는 기술(skills), 세션 검색을 갖는다. | [H1] |
| 어디서 얼마나 도나 | 5달러짜리 VPS, GPU 클러스터, 서버리스 어디서든 돈다고 한다. **게이트웨이는 백그라운드 프로세스 하나**로 모든 메신저를 잇고 세션을 관리하며 예약 작업을 60초마다 확인한다. 서비스(systemd·launchd·작업 스케줄러)로 설치할 수 있고 재시작·감시 동작이 있다. 서버리스 환경은 놀 때 잠들었다 깨어난다. 「얼마나 오래」를 못 박은 문장은 없다(확인 못 함). | [H1][H2] |
| 메신저 안 점검 | 지원 메신저는 Telegram·Discord·Slack·WhatsApp·Signal·SMS·이메일·Microsoft Teams·BlueBubbles(iMessage) 등 20여 곳이고, 비교표에는 **Buzz**도 있다. 대화마다 세션이 따로 있다. `/status`로 세션 정보, `/usage`로 토큰 사용량을 본다. 진행 표시는 `display.tool_progress`(끄기·새 것만·전부·상세·로그)로 고르고, 로그 모드는 대화방에 아무것도 보내지 않고 감사 파일에 쓴다. 예약 작업 결과는 **시작한 대화방(origin)이나 홈 채널**로 가고, 실패는 항상 전달된다. | [H2][H3] |
| 방향 전환 | 에이전트가 일하는 중에 **새 메시지를 보내면 기본이 현재 턴을 바꾼다**(실행 중인 터미널 명령은 죽이지 않고 백그라운드로 보낸다). 대안으로 `queue`(다음 턴으로 줄 세움)와 `steer`(다음 도구 호출 뒤 현재 실행에 끼워 넣음)가 있다. `/stop`은 강제 정지. `/retry`·`/undo`·`/rollback`도 있다. 예약 작업은 일시정지·재개·수정·삭제·즉시 실행·현재 실행만 취소가 되고, `hermes pause`는 전체 예약 작업을 막는 전역 정지다. | [H2][H3] |
| 권한 | 위험한 명령은 패턴 목록으로 걸러 사람이 승인한다(한 번·세션·항상·거부, 기본은 거부). 모드는 `smart`(보조 모델이 위험 평가)·`manual`·`off`. 메신저에서는 명령 내용을 대화방에 올리고 `/approve`·`/deny`로 답하며 **제한 시간(기본 300초)이 지나면 거부**(fail-closed)한다. 어떤 모드에서도 못 푸는 하드라인 차단 목록이 있다. 예약 작업은 위험 명령을 **기본 거부**(`cron_mode: deny`)한다. 누가 말을 걸 수 있는지는 허용 목록과 **DM 페어링 코드**(1시간 만료)로 정하고, 목록이 없으면 전부 거부한다. 관리자·일반 사용자 두 등급이 슬래시 명령 범위를 가른다. 컨테이너 백엔드는 권한을 줄인다. | [H4][H2] |
| 감사 기록 | 게이트웨이 로그와 승인 결정을 모아 제안하는 명령이 있고, **승인 결정만의 전용 감사 기록은 문서에 없다.** | [H4] |
| 비용 표시 | `/usage`가 CLI와 메신저에서 모두 된다. 예산 상한은 문서에 없다(확인 못 함). 예약 작업은 작업별 모델 고정, 에이전트를 아예 깨우지 않는 사전 스크립트 문, 도구 허용 목록으로 비용을 줄인다. 조용한 응답(`[SILENT]`)은 알림만 막고 **실행 비용은 막지 못한다**고 적었다. | [H1][H3] |
| 밖(폰·알림) | 전용 앱이 아니라 **사용자가 이미 쓰는 메신저 앱이 곧 폰 표면**이다. 알림은 그 메신저의 푸시이고, 재시작·장애 알림은 홈 채널(`/sethome`)로 간다. | [H2] |
| oort와의 관계 | **oort가 에이전트 멤버로 붙이는 런타임.** [레포] oort는 두 길을 둔다(oort가 돌리는 관리형 / 사용자가 가져오는 BYOA 게이트웨이). 어느 쪽이든 실행 상태 기계·승인·예산 장부·감사·메시지 순서는 **oort 서버가 소유**하고 런타임은 진행·제안·결과만 보고한다. 같은 호스트에 붙인 Hermes는 터미널·코드 실행·브라우저를 끄고(허용 표면은 할 일 목록·웹 검색·이미지 생성), 세션 검색·기억 도구도 껐다. 그래서 oort 안의 승인은 Hermes 자체의 `/approve`가 아니라 **oort의 승인 카드**다. | [레포 research/11 Hermes 계약, ADR-0203] |

- Hermes 문서가 **「메시지 하나로 방향을 바꾸는 것」을 기본 동작**으로 둔 점이 핵심이다. 대안으로 줄 세우기·끼워 넣기를 고를 수 있게 했고, 강제 정지는 따로 둔다. 메신저에서의 「고침」이 곧 다음 메시지라는 사실을 제품이 그대로 받아들인 설계다.
- 예약 작업은 **매번 새 세션**에서 돌고 이전 맥락은 붙인 기술·연속성 설정으로만 이어진다. 상주와 기억이 별개라는 점을 보여 준다.

### 3.1 Cursor 클라우드 에이전트 in Slack — 스레드 하나가 작업 하나이고 상태를 이모지로 보여 주는 가장 가벼운 모양 [C1]

| 항목 | 내용 |
|---|---|
| 시작 | `@Cursor`와 요청. 저장소·모델·브랜치는 메시지에서 알아내거나 `repo=` 같은 옵션으로 지정. 같은 스레드의 `@Cursor [요청]`이 **후속 지시**이고 `@Cursor agent`는 별도 에이전트. |
| 점검 | 코드를 바꾸기 전 짧은 계획을 올릴 수 있고, 스레드 아래에 「코드를 읽는 중」 같은 짧은 상태가 뜬다. 반응 이모지로 실행 중·완료·실패를 표시. 끝나면 알림과 PR 링크. |
| 방향 전환 | 후속 지시. 저장소를 바꾸면 **새 에이전트**가 시작되고 첫 에이전트의 브랜치·PR은 그대로. 멈추기는 컨텍스트 메뉴의 「삭제(정지하고 보관)」뿐이고 전용 정지 버튼은 문서에 없다. 후속 지시를 줄 수 있는 사람은 팀 설정으로 제한한다. |
| 권한·비용 | Slack 스코프 목록이 문서에 있다. 사용량 기반 요금을 켜야 하고, 레거시 개인정보 모드는 임시 코드 저장이 필요해 지원하지 않는다. 채널 기본 저장소는 누구나 바꿀 수 있고 바꾼 사람이 스레드에 표시된다. |

### 3.2 OpenAI Codex(@ChatGPT in Slack) — 승인 카드는 요청자만 보고 결과는 채널이 보는 혼합 가시성 [C2]

| 항목 | 내용 |
|---|---|
| 시작 | 공개·비공개 채널에서 `@ChatGPT` 멘션. 저장소와 스레드 맥락을 포함. Slack Connect 채널은 미지원. 계정 연결·승인 안내가 먼저. |
| 점검 | 시작 때 원래 스레드에 메시지, 결과(답·변경·보고된 검사)를 스레드로 반환. 「Follow along」으로 작업을 열어 본다. 진행 중 갱신은 문서에 없다(확인 못 함). |
| 방향 전환 | 같은 스레드에서 다시 멘션하면 같은 계정의 작업과 환경이 이어진다. 환경을 바꾸려면 새 대화. 「Cancel」은 배포 설정이 제공할 때만 요청자에게 있다. |
| 권한·비용 | 워크스페이스 관리자가 배포하고 게시된 환경을 공유해야 한다. 승인이 필요하면 **요청자에게만 보이는 허용·거부 카드**가 뜬다. 그러나 채널 답변은 채널 접근자 누구나 읽을 수 있고 승인 카드가 답변을 비공개로 만들지는 않는다고 문서가 경고한다. 비용은 문서에 없다. |

### 3.3 GitHub Copilot 클라우드 에이전트 — 「PR이 진행 지표」이고 조종·정지의 규칙이 가장 또렷한 사례 [C3][C3b]

| 항목 | 내용 |
|---|---|
| 시작 | 이슈, 에이전트 패널, Copilot Chat, IDE, CLI, Jira·**Slack·Teams**·Linear·Raycast 등 입구가 많다. 일정이나 이슈 생성 같은 이벤트로 자동 시작도 된다. |
| 점검 | 어느 GitHub 페이지에서든 열리는 에이전트 패널, 저장소의 Agents 탭, GitHub Mobile에 세션 목록. 세션 화면은 로그와 개요로 **진행·토큰 사용량·세션 길이**를 보인다. 클라우드 에이전트 세션은 기본으로 저장소 접근자에게 공유된다. |
| 방향 전환 | 로그 아래 입력창에 쓰면 **세션을 멈추지 않고** 현재 도구 호출이 끝난 뒤 반영된다(조종 메시지는 AI 크레딧을 쓰고 서드파티 코딩 에이전트에는 안 된다). 「Stop session」은 실행을 끝내고 **이미 푸시한 커밋은 남긴다.** 멈춘 세션은 보관만 되고 삭제는 안 된다. |
| 권한·비용 | 사용량과 크레딧 소모를 화면에서 알려 준다. 쓰기 권한자만 지시할 수 있다는 서술은 검색 요약으로만 확인했다(†). 알림은 문서에 없다(확인 못 함). |

### 3.4 Linear 에이전트 — 제품마다 다른 UI를 하나의 약속(에이전트 세션·상호작용 지침)으로 묶으려는 시도 [C4][C4b]

| 항목 | 내용 |
|---|---|
| 시작 | 이슈를 에이전트에게 **위임(delegate)**하거나 멘션하면 **에이전트 세션**이 만들어진다. 위임이 가장 흔한 입구. 개발자 문서에 위임·멘션 스코프가 있다. |
| 점검 | 세션 상태가 이슈 안에서 사용자에게 보이고 에이전트가 내보낸 활동에 따라 자동 갱신된다. 문서는 세션이 시작되면 10초 안에 첫 「생각」 활동을 내보내 시작을 알리는 것으로 설명한다. |
| 방향 전환 | 지침 여섯 원칙(에이전트임을 밝히기, 플랫폼 안에서 자연스럽게, 즉각 피드백, 내부 상태 투명하게, **중단 요청 존중**, 사람이 책임)이 공개돼 있다. 에이전트는 물러나라는 요청에 **즉시 물러나고 분명한 신호가 있어야만 다시 관여**한다. 세션 상태값과 정지 신호의 개발자 문서는 확인 못 함. |
| 권한·비용 | 위임받은 담당자(사람)가 결과에 책임을 진다. 에이전트는 사용자 목록에서 배지로 구분한다. 비용은 확인 못 함. |

### 3.5 Claude Tag (Slack) — 에이전트가 팀 공유 신원으로 채널에 앉고 관리자가 채널별로 접근과 비용 상한을 정하는 사례 [C5][C5b][C5c][C5d]

공개 베타이고 Team·Enterprise 요금제용이다. 예전 Claude in Slack 봇은 Claude Tag에 연결된 조직에서 2026-10-05부터 응답하지 않는다고 문서가 적고, 개인 계정(Pro·Max·Ultra) 방식의 Claude Code in Slack은 Claude Tag에 연결되지 않은 워크스페이스에서만 계속 쓰인다. [C5e]

| 항목 | 내용 |
|---|---|
| 시작·상주 | 채널·그룹 DM·1:1 DM에서 `@Claude`. 스레드마다 **격리된 샌드박스**가 생기고 스레드가 조용해지면 해제되며, 답장하면 새로 만들어진다(스레드·푸시한 브랜치·올린 결과는 남고 샌드박스 안 파일은 사라진다). 작업은 클라우드에서 돌아 Slack을 닫아도 계속된다. 일정 작업·채널 지켜보기·PR 구독을 **루틴**으로 맡기고, 「바뀐 때만 게시」 같은 침묵 규칙을 지시문에 넣는다. |
| 점검 | 스레드 아래 작업 중 표시, 여러 단계 작업은 **체크리스트**를 갱신. 답글 푸터에 모델 이름과 「Configure」 링크(그 채널의 연결 확인). 「이 채널에서 무엇에 접근하나」를 말로 물으면 답한다. 작업 전체가 채널에 보인다. |
| 방향 전환 | 스레드에 답장하면 방향이 바뀐다(다시 멘션하지 않아도 읽음). 채널 스레드에 **Stop 버튼**이 있고 DM에는 없다. 루틴은 말로 일시정지·수정·중지하고 `!scheduled`로 목록을 본다. 개인 연결로 한 작업은 소유자가 스레드에서 멈추라 하면 멈추도록 설계됐고, Enterprise는 게시 전에 사용자가 결과를 검토하게 강제할 수 있다. 행동마다 뜨는 승인 카드는 문서에서 못 찾았다(확인 못 함). |
| 권한 | 채널에서는 **요청자 계정이 아니라 에이전트 자기 서비스 계정**으로 행동한다. 기본은 채널 읽기·쓰기와 공개 채널 키워드 검색뿐이고 외부 시스템 접근은 0에서 시작해 관리자가 전체·워크스페이스·채널 단위로 부여한다. 자격증명은 샌드박스에 없고 프록시가 요청 시점에 넣으며, 외부 접속은 기본 차단이다. **채널 멤버 모두가 같은 접근을 쓴다는 점을 문서가 경고**하고 서비스마다 전용 계정을 권한다. 스레드의 남의 글은 지시가 아니라 정보로 본다. |
| 비용 | **좌석당 과금 없이 사용 잔액에서 사용량 과금**이고 소유자가 월 지출 상한을 정한다. 관리자 화면에 **채널별 사용량 분해**가 있다. |
| 밖(폰·알림) | Slack 앱이 곧 폰 표면이다. 루틴을 만든 사람에게는 완료·실패 알림이 간다(Slack 계정 연결 시). |
| oort와의 관계 | 모델이 가장 가깝다. 에이전트가 자기 신원을 갖고 채널별로 접근이 정해지며 감사가 따라붙는다. 다른 점: Claude Tag는 Slack 안에서만 돌고 Anthropic 에이전트 하나다. oort는 에이전트를 멤버로 받는 **자체 호스팅 메신저**다. |

## 4. 핵심 연구

다섯 편 모두 제목으로 검색해 실재와 링크를 확인했다. 초록·목록·서지는 직접 열었고, 원문 PDF를 텍스트로 읽지 못한 곳은 그렇게 적었다. 「oort 시사점」은 해석이다.

### 4.1 에이전트의 자율성 단계 (2025) [R1]
Feng, McDonald, Zhang, 「Levels of Autonomy for AI Agents」, arXiv 2506.12469(v1 2025-06-14, v2 2025-07-28).
- **핵심 주장**: 에이전트의 자율성 수준은 능력·환경과 **따로 정하는 설계 선택**이다. 사용자가 맡는 역할로 다섯 단계를 나눈다. 운영자(operator)·협력자(collaborator)·자문가(consultant)·승인자(approver)·관찰자(observer). 자율성 인증서(autonomy certificate)로 에이전트 행동을 다스리자는 아이디어와 자율성을 재는 초기 아이디어도 낸다.
- **근거**: 개념 틀이다. 초록에는 실험·수치가 없다. 각 단계의 역할 설명은 초록에 없고 본문을 확인하지 못했다.
- **oort 시사점**: 「승인자」와 「관찰자」 사이를 사람이 고르는 손잡이로 볼 수 있다. 행동마다 승인(승인자)과 알림만 받기(관찰자)를 에이전트·행동별로 고르게 하는 설계 후보의 이론적 근거다.

### 4.2 사람이 계획·실행에 끼어드는 에이전트 UI (2025) [R2]
Mozannar 외, 「Magentic-UI: Towards Human-in-the-loop Agentic Systems」, arXiv 2507.22358(2025-07-30), Microsoft Research.
- **핵심 주장**: 오픈소스 웹 인터페이스로 사람-에이전트 상호작용을 연구한다. 초록이 드는 장치는 **공동 계획(co-planning)·공동 작업(co-tasking)·병렬 작업(multi-tasking)·행동 보호막(action guards)·장기 기억**이다(초록은 여섯 가지라 하면서 다섯 가지만 적는다). 한 2차 요약은 행동 보호막을 고위험 행동을 사람이 명시적으로 승인할 때까지 붙잡는 장치로 소개한다.
- **근거**: 에이전트 벤치마크 자율 완수, 모의 사용자 시험, 실제 사용자 질적 연구, 안전 평가의 네 가지로 평가했다고 적는다. 초록에는 수치가 없다. 집계 사이트가 인용한 수치는 원문으로 확인하지 못해 옮기지 않는다.
- **oort 시사점**: 「실행 전에 계획을 사람이 고친다」와 「위험한 행동은 붙잡아 둔다」가 **개입 지점의 두 종류**라는 점이다. 메신저에서는 계획 카드(Slack의 plan 블록)와 승인 카드가 각각에 대응한다.

### 4.3 혼합 주도 인터페이스의 원칙 (1999, 오래된 기본 문헌) [R3]
Horvitz, 「Principles of Mixed-Initiative User Interfaces」, CHI '99, pp. 159–166, DOI 10.1145/302979.303030.
- **핵심 주장**: 자동화 서비스와 직접 조작을 **우아하게 결합**하자고 한다. 에이전트가 사용자의 목표를 잘못 짐작하는 일이 핵심 문제이고, 불확실하면 사용자와 짧게 대화하되 **쓸데없이 방해하는 비용**을 따져야 한다고 논한다. 일정·회의 관리 시스템 Lookout이 예시다.
- **근거**: 사용자 모델링과 의사결정 이론에 기댄 설계 논문이다. 한 조사 논문은 이를 12개 원칙으로 정리했다고 적는다. **12개 원칙의 전체 목록은 원문 PDF를 텍스트로 읽지 못해 확인 못 함.**
- **oort 시사점**: 「에이전트가 먼저 알릴까」는 정답이 아니라 **방해 비용과 이득의 저울**이다. 사람이 직접 하는 길(직접 조작)을 에이전트 길과 항상 같이 둔다는 원칙이 oort 메신저에서는 「채팅으로 시키되 화면에서도 같은 일을 할 수 있다」로 읽힌다.

### 4.4 사람-AI 상호작용 지침 18개 (2019) [R4]
Amershi 외, 「Guidelines for Human-AI Interaction」, CHI 2019(Glasgow, 우수 논문 언급상), Microsoft Research.
- **핵심 주장**: 지침 18개를 네 시점(처음, 상호작용 중, 틀렸을 때, 시간이 지나며)으로 정리했다. 학술·블로그·사내 문서의 150여 개 권고에서 출발했다.
- **근거**: 여러 차례 평가를 거쳤고, 디자인 실무자 49명이 인기 있는 AI 제품 20개를 이 지침으로 시험했다.
- **oort 시사점**: 지침 제목 중 이 문서의 질문과 직접 겹치는 것은 **G3 맥락에 맞춰 서비스하기, G8 효율적 닫기, G9 효율적 정정, G11 왜 그랬는지 밝히기, G16 사용자 행동의 결과 알리기, G17 전역 통제, G18 변경 알림**이다(제목은 HAX 라이브러리 확인). 정지·정정·이유·되돌릴 수 없음의 고지를 점검 화면의 체크 목록으로 쓸 수 있다.

### 4.5 업무 중단의 비용 (2008, 오래된 자료) [R5]
Mark, Gudith, Klocke, 「The cost of interrupted work: more speed and stress」, CHI 2008, pp. 107–110, DOI 10.1145/1357054.1357072.
- **핵심 주장**: 중단된 사람은 일을 **더 빨리 끝내지만**(품질은 비슷) 스트레스·좌절·노력·시간 압박을 더 느낀다. 저자들은 사람이 중단을 빠르게 일해서 만회하고 그 값을 치른다고 해석한다. 이상은 2차 요약 기준이다.
- **근거**: 중단 없음·같은 맥락 중단·다른 맥락 중단의 3×2 요인 실험이다. 원문 PDF를 텍스트로 읽지 못해 **참가자 수와 수치는 확인 못 함**이다. 중단의 맥락이 결과를 바꿨는지도 확인하지 못했다.
- **oort 시사점**: 알림은 공짜가 아니다. 상주 에이전트가 사람을 부르는 이유를 **닫힌 목록**(질문·승인·막힘·실패·끝남)으로 좁히는 것의 근거다. 15년 넘은 연구라 에이전트 알림에 그대로 옮길 수 있는지는 확인하지 못했다.

## 5. 패턴 종합

위 자료에서 반복해서 나온 것만 묶었다. 한 행에 판단 하나이고, 근거는 절 번호나 출처 ID로 붙였다. 「해석」은 이 문서의 판단이다.

### 5.1 점검 신호의 종류

| 신호 | 근거 사례 | 판단 |
|---|---|---|
| **「나를 기다리는 것」을 따로 가른다**(질문·승인·넘겨받기 요청 / 안 읽은 결과 / 작업 중) | Grok Bot 사이드바 [G2], Buzz 활동 피드의 「통제」 질문 [B3] | **잘 됨.** 사람이 움직여야 할 것만 먼저 눈에 띈다. |
| 스레드 안의 한 줄 상태, 체크리스트, 계획·작업 카드 | Slack plan 블록(대기·진행·완료·오류) [S6][S7], Claude Tag 체크리스트 [C5d], Cursor 상태 한 줄과 이모지 [C1] | **잘 됨.** 메신저의 문법 안에서 끝난다. |
| 살아 있다는 신호(경과 시간, 만료) | Buzz 사이드바 경과 시간 [레포 UX 서베이 §4-A], Slack `processing` 1시간·스트림 10분 마감 [S6] | **잘 됨.** 조용한 정체를 숨기지 않는다(Buzz 활동 피드의 원칙 [B3]). |

| 예약·상주 작업의 일시정지·재개·수정·목록 | Hermes cron [H3], Grok Bot 루틴(폰에서 일시정지) [G4], Claude Tag 루틴 [C5c] | **필수에 가깝다.** 상주 에이전트는 예약이 쌓이면 사람이 모르는 일이 돈다. |

### 5.3 알림 빈도와 중단 비용

| 관찰 | 근거 | 판단 |
|---|---|---|
| 기본은 **조용히 있기**이고 부를 이유는 걸러서 정한다. 하루 한 번 상태 보고가 맞는 작업이 있다. | 강연 요약 [V4][V5](본문 미확인), Muse가 「바뀌었거나 승인이 필요할 때」 돌아온다 [M1] | 방향 근거. 수치는 옮기지 않는다. |
| 중단은 사람을 빠르게 만들지만 스트레스를 올린다. 방해의 비용과 이득을 저울질해야 한다. | [R5][R3] | 오래된 연구라 에이전트 알림에 그대로 맞는지는 확인 못 함. |
| 알림을 **봇별로 끄고 켠다.** 그룹 채팅에는 같은 스위치가 없다. | Grok Bot [G2] | **피할 것**: 여러 봇이 모인 대화방에 스위치가 없는 것. |
| 「바뀐 때만 게시」「조용한 날은 건너뛰기」를 지시문에 쓴다. | Claude Tag 루틴 [C5c], Hermes `[SILENT]` [H3] | **잘 됨.** 단 Hermes는 조용한 응답이 **알림만 막고 실행 비용은 못 막는다**고 적는다. |
| **실패는 항상 전달**하고 반복 실패는 한 번만 알린 뒤 일정 시간 쉰다. | Hermes 예약 작업 [H3] | **잘 됨.** |
| 푸시는 신뢰도가 좌우한다. 점진 배포 중이고 Cursor 포럼에 푸시 불도착 글이 있다. | Grok Bot [G2][G6] | **피할 것**: 푸시를 믿고 앱 안 상태를 비워 두는 것. Grok Bot은 푸시가 꺼져도 앱 안 주의 상태가 남는다. |

### 5.4 권한 모델

| 모델 | 근거 사례 | 판단 |
|---|---|---|
| 요청한 사람의 계정으로 실행 | 예전 Claude Code in Slack(개인 계정) [C5e], Muse(개인 비서) [M1] | 단순하지만 **팀에서는 책임이 흐려진다.** |

| 행동마다 사람 승인 | Grok Bot [G3], Hermes [H4], Codex [C2], Muse [M1] | 가장 안전하다. 승인 피로를 **모델 검토**로 보완하는 곳이 많다(Grok Bot Auto Review [G3], Hermes `smart` [H4], 강연 요약 [V4]). |
| **규칙 두 종류(자동 허용 / 먼저 묻기)와 충돌 시 묻기 우선** | Grok Bot [G3], dots 사용자 규칙† [D1] | **잘 됨.** 관리자 규칙은 사용자가 풀 수 없게 한다(Grok Bot [G2]). |
| **비밀은 모델 밖** | Grok Bot 금고·보안 입력 [G3], Muse [M1], Claude Tag 프록시 주입 [C5b], Hermes 자식 프로세스 환경 정리 [H4] | 이번 자료에서 **가장 일치하는 결론.** |
| **들어온 글은 지시가 아니다** | Grok Bot 「내 메시지만 요청」 [G3], Claude Tag [C5b], 강연 요약 [V4] | 일치. 프롬프트 주입 방어의 최소선. |
| 봇들이 컴퓨터를 같이 쓴다 | Grok Bot(봇 사이는 보안 경계가 아님) [G3] | **피할 것**: 에이전트 간 경계가 없는 구조. 문서가 스스로 경계가 아니라고 못 박는다. |
| 설치 한 번 동의로 넓은 스코프 | 레포 ADR-0186의 기각 사유(Slack·Discord 봇 모델) | 이번 조사에서 새로 확인한 것은 없다. |

### 5.5 비용 표시

| 사례 | 표시 방식 | 판단 |
|---|---|---|
| Claude Tag | **채널별 사용량 분해**와 월 지출 상한, 좌석당 과금 없음 [C5] | 팀 메신저에 맞는 귀속. |
| Copilot | 세션 개요에 토큰·길이, **조종 메시지가 크레딧을 쓴다**고 문서가 밝힌다 [C3] | 조종이 비용이라는 사실을 숨기지 않는다. 화면에서 어떻게 보이는지는 확인 못 함. |
| Grok Bot | 주간 포함 사용량과 추가 사용량. **작업별 표시 없음** [G2] | 개인 단위. |
| Hermes | `/usage`, 에이전트를 아예 깨우지 않는 사전 스크립트 문, 도구 허용 목록 [H3] | 비용을 **줄이는 수단**이 많다. 조용한 응답은 비용을 못 막는다. |

### 5.6 밖(폰·알림)에서 점검

| 모양 | 근거 사례 | 판단 |
|---|---|---|
| 전용 앱과 푸시 | Grok Bot(iPhone·iPad·Android), Muse(앱·WhatsApp) [G4][M1] | 폰에서 **승인·넘겨받기·루틴 일시정지**까지 되는 것이 기준선. 못 하는 것은 데스크탑으로 남긴다(루틴 시험·컴퓨터 갱신·가르치기 [G4]). |
| 이미 쓰는 메신저가 곧 폰 | Hermes, Claude Tag, Cursor·Codex in Slack, dots† [H2][C5][C1][C2][D1] | 개발 비용이 낮다. 단 **카드가 그 메신저 표현력에 묶인다**(Codex는 승인 카드를 요청자 비공개로 [C2]). |
| 폰 표면이 아직 비어 있음 | Buzz 모바일 「배선 중」 [B1] | 에이전트 점검의 폰 기능은 문서에 없다. |
| 폰 승인 카드의 선택지 | Grok Bot 폰 카드는 「허용 한 번」·「거부」만 [G4] | 폰에서는 위험한 선택(항상 허용)을 줄이는 것이 한 방법. |
| 알림 라우팅 | 데스크탑 앱 사용 중에는 폰이 아니라 데스크탑으로, 앱이 열려 있으면 억제 [G2][G4] | 중복 알림을 막는 규칙이 제품에 있다. |

### 5.7 한 줄 결론

- 이번에 본 제품은 **정지와 진행 표시는 거의 기본 제공**이고, **승인은 제품 몫**이며, **되돌리기와 비용 귀속은 비어 있다**. (해석)
- 일치하는 설계 셋: ①기본은 조용히 있고 부를 이유를 걸러서 정한다 ②비밀은 모델 밖에 둔다 ③들어온 글은 지시가 아니다.

## 6. oort 시사점 후보 (결정 아님)

owner가 인터뷰에서 정한 네 질문에 맞춰 적는다. 전부 **후보**이고, 고르는 것은 ADR-0220의 일이다. 바깥에서 확인한 사실과 레포 기록을 구분해 근거를 붙였다.

### 6.1 질문 ① 점검·방향 전환의 원칙

| # | 후보 | 근거 |
|---|---|---|
| A1 | **에이전트가 먼저 알리는 이유를 닫힌 목록으로 둔다**: 질문·승인·막힘·실패·끝남(그리고 사람이 정한 정기 보고). 그 밖에는 조용히 있는다. | [V4][V5][M1][R3][R5] |

### 6.2 질문 ② 경쟁 제품과 다르게 가는 점

| # | 후보 | 근거 |
|---|---|---|
| B1 | **Slack이 비워 둔 칸(승인·되돌리기·비용)을 차별로 삼을 수 있다.** Slack은 정지와 진행 표시를 기본 제공하고 승인은 앱 몫으로 둔다. oort는 승인 카드·서버 감사·예산 장부를 서버가 소유한다는 **레포 사실**이 있다. | [S1][S6][레포 research/11 Hermes 계약 §2] |
| B2 | **개인 한 사람의 컴퓨터가 아니라 팀 대화방이다.** Grok Bot·Muse·dots는 개인 비서 중심이다. 팀 대화방에서는 사람과 에이전트가 같은 기록과 같은 감사를 본다. | [G3][M1][D1]† |

| B4 | **가장 닮은 제품은 Claude Tag와 Buzz다.** Claude Tag는 에이전트 자기 신원과 채널별 접근을 갖지만 Slack 안에서 Anthropic 에이전트 하나로 돈다. Buzz는 에이전트=멤버 철학이 같고 점검 화면 철학이 앞서 있다. **「에이전트가 멤버」만으로는 차별이 안 된다**(해석). | [C5b][B1][B3] |
| B5 | 자체 호스팅·벤더 중립은 Claude Tag(Slack 종속)·Grok Bot(Cursor 요금제 묶임)과 갈리는 점이다. | [C5][G1][레포] |
