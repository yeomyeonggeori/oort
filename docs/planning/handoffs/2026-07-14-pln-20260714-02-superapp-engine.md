## 2. 핵심 판단

- Work 카드와 server run/approval ledger는 구현되어 있다.
- codex-workbench adapter는 repo-local mock 8개가 green이지만 실제 Codex/momo end-to-end는 미검증이다.
- 현재 workspace-write 승인은 Codex native approval relay가 아니라 “read-only plan → momo coarse approval → workspace-write resume” 합성 경로다.
- 실제 interactive Work에는 user-owned host의 local `codex app-server` stdio bridge를 ADR 후보로 권고한다. `codex exec`는 read-only batch/fallback로 유지할 수 있다.
- Context Broker는 partial, Memory Plane/Capability Cache는 spec-only, inbound MCP는 runtime stub, plugin은 spec-only, webhook은 placeholder, GWS는 research spec-only다.
- critical path는 ADR-S1 → Context Packet → Memory/Capability runtime → Plugin/Webhook reference runtime → GWS read sync/citation → real approval/resume gate다.
- GWS write는 첫 slice에서 제외하고 common approval-bound executor가 증명된 뒤 연다.

## 3. 절대 보안 경계

- momo가 upstream Codex/OpenAI OAuth token, refresh token, API key를 보관·proxy·log하는 설계 금지.

- Hermes-facing bearer는 별도 runtime secret이며 packet/manifest/message/audit에 넣지 않는다.
