# Sol 인수인계 패킷 — 외부 에이전트 수용 축 (2026-08-12)

> 발신: Fable(momo-main 오케스트레이션 세션, 2026-08-12). 수신: **sol**(GPT 5.6, Codex — 기획·리뷰 주도, 2026-08-11 인수인계의 연장).
> 미션: **ADR-0162·0163 초안 검수 → 로드맵 편성 검증 → Accepted 후 실작업(티켓 분해·발사 준비)까지.** 추적 이슈 **#1343**.

## 0. 발단 (한 문단)

SpaceXAI+Cursor의 **Grok Bot**(2026-08-11 베타 — 상시 가동 호스팅 AI 팀메이트, 외부 호출 API 없음)이 출시됐고, 성재가 "사용자의 Grok Bot을 oort 팀메이트로 쓰는 hermes형(oort 일감을 봇이 감지→자기 방식으로 처리) 연동, 배포 허들 0이라 실마리를 뚫으면 파급력이 크다"는 방향을 냈다. Fable이 웹 리서치 6기(2배치)로 실측한 결론: **인바운드(봇 호출/반입)는 불가능**(API 전무+AUP 저촉), **역방향(봇이 oort MCC 서버로 다이얼인해 일감을 당겨감)은 조건부 성립**(커스텀 MCP 커넥터+루틴 웨이크업 — Slack 트리거는 실동작 검증됨). 이 과정에서 성재가 구조 원칙을 확정했다: **"oort는 에이전트를 소유하지 않는다 — 주=연동형(외부 에이전트 연동), 부=관리형 동봉 호스팅(+개별 업데이트 버튼)"**. 설계 감사 결과 ADR-0102가 이미 이 철학이나, ACP 체인(ADR-0130)은 Swift 퇴역으로 부분 좌초, 동봉·업데이트는 설계 공백이었다.

## 2. 검수 포인트 (Fable이 자신 없는 순)

1. **ADR-0163 D3 업데이트 실행 주체** — v0=C(안내 카드)→v1=A(호스트 헬퍼), B(서버 Docker 소켓) 기각을 권고했다. 셀프호스팅 운영 현실(#1227~#1229 트랙)과 보안 경계에서 이 단계 승격이 맞는지, C의 "어댑터 heartbeat로 버전 감지"가 현행 어댑터 계약에 실재하는지(없으면 신설 비용 추가) 검증.
2. **ADR-0162 D2 도구 집합** — inbox/task 6종이 기존 gateway 계약(pending/events/complete/lease)과 **의미 중복**된다. 별도 표면이 맞는지, gateway 계약의 MCP 바인딩으로 흡수하는 게 맞는지 — Fable은 별도 표면(대화 중심 vs 잡 중심, 인증 위계 상이)으로 기안했으나 반론 여지 있음.
3. **ADR-0162 D3 인증 v0** — 정적 bearer로 시작하는 판단이 MCP 2026-07-28 인증 의무(RFC 9728 MUST)와 충돌하는지(스파이크 실측 전 과설계 금지와의 균형).
4. **좌초 감사(§8)의 전수 재검증** — work_tool_profile server-rust 부재·X-11 정지 등은 grep 수준 실측이다. #1345에서 코드 레벨로 재확인하고 낡은 판정은 교정하라.
5. **로드맵 충돌** — Wave 3의 #1228 선행 권고, Wave 1·2 병렬 판단이 기존 큐(셀프호스팅 트랙·데스크탑 검수 후속·S10 engine→main)와 자원 경합하는지.
6. 리서치 사실관계는 출처가 전부 각주화돼 있다 — 의심 항목은 재실측 환영(특히 출시 1일차 정보라 유동적).

## 3. 규율 (요약 — 정본 CLAUDE.md·2026-08-11 패킷 §2)

- 하드 불변식 6(PG=SoT·Centrifugo 전송전용·단일 쓰기경로·seq·에이전트=member·RLS FORCE·ADR-0004) — Agent Port는 전부 이 파사드여야 한다.
- **경계 변경 구현은 Accepted ADR 없이 착수 금지**(ADR-0100). 두 ADR 모두 Proposed — 검수→성재 승인이 선행.
- 공용 정본(ROADMAP·BUILD_TICKETS)·GitHub Issue 추가 발급·main 머지는 성재 승인 뒤 momo-main 통합. sol은 이 축의 ADR/research/plan 문서 수정까지.
- 워커 발사=성재 명시 신호. 티켓은 핸드오프 패킷 없이 워커에 넘기지 않는다.

## 4. 성재 결정 큐 (이 축 — 재촉 금지)

## 5. 검수 후 작업 순서 (Accepted 도달 시)

1. Wave 1 티켓 분해(Agent Port v0 — 서버 표면·토큰 발급 UI·약관 문구·가이드 문서, 1 Issue=1 goal) + 핸드오프 패킷 작성.
2. #1345 감사 실행 → Wave 2 분해 → 성재 편성 승인 요청.
3. #1344 스파이크는 성재 게이트 해제 시 즉시 실행 가능하게 절차서(테스트 MCP 서버·터널·측정 항목)를 미리 준비.
4. 각 단계 종료 시 JOURNAL 항목 추가, 이 패킷·plan 문서 현행화.
