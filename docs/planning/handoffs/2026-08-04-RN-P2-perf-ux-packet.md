**진단 없이 최적화 금지.** Release 번들에서 재현된 체감이므로 원인 후보를 계측·정적 분석으로 좁혀라:
1. 유력 후보(코드에서 검증): ①`useNow`/`useTickingNow` 1Hz가 화면 전체 리렌더를 유발하는 자리(ConversationScreen — 턴 진행 중 매초 메시지 리스트까지 다시 그리는지) ②realtime 이벤트(신호 스토어 emit·목 갱신)가 FlatList 전체 재렌더로 번지는 경로(memo 경계·keyExtractor·row 등가성) ③화면 전환 애니메이션 중 JS 스레드 블로킹(전환 시점의 쿼리 폭주 — roster/프로필/원장 동시 발사).
2. 각 후보에 대해 "재현 경로 + 근거(계측 수치나 리렌더 카운트) + 수리"를 PR에 표로. 추측 수리는 이탈이다.
3. 수리 후 회귀 잠금: 리렌더 카운트 단정(예: 신호 1회 갱신에 메시지 row 리렌더 0회)류의 테스트.

- 증상: 입력 중 마지막 메시지(특히 자기 직전 발신)가 컴포저 뒤에 가려짐. 키보드 인셋/스크롤 앵커 문제.

## Goal 3 — "에이전트가 일하는 중"이 사람에게 안 보인다

- 배경: 신호 배선(#994)은 실재하지만 **짧은 턴(수 초)에서는 활동 줄·배지·중단 버튼이 인지 전에 사라진다**. 성재는 요청 후 그 UI를 한 번도 인지하지 못했다.
- 방향(설계 판단은 네 몫, 근거를 PR에):
  1. **메시지 자리에서 보이게** — 멘션 직후 타임라인에 "루나가 답하는 중…" 자리표시(응답 도착 시 그 자리가 메시지로 바뀜)가 가장 인지 확률 높은 자리다(활동 줄은 시선 밖). 신호 스토어를 소비하면 된다.
  2. 활동 줄 최소 표시 시간(깜빡임 방지) 또는 등장 애니메이션.
  3. 중단 버튼은 turn이 서버 cancel 라우트를 아는 환경(재배포 후)에서 실기 확인 — 접근성·발견성(라벨/대비) 점검 포함.
- 어휘 경계 유지: 작업 중=열린 턴 · awaiting_approval은 절대 「작업 중」 금지(core 규칙 소비).
